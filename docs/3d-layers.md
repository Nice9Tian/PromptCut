# 三维图层：Three.js 与控件的空间编排

**状态：设计稿。四条待验证项还没做，代码一行没写。**

目标是两件事：让 Agent 能做 3D 模型和动画（B 层），以及让现有的 30 张卡能摆进三维空间（A 层）。
最后由 C 层把它们按显式层序合成一张图。

这份文档记的是**决定和理由**。理由比决定重要 —— 下面每一条"为什么不那么做"，
都是有人真的会那么做、而且看不出问题在哪的岔路。

## 先说这套设计的边界

**A 和 B 之间是画家算法，不做穿插。** 一块牌子一半插进模型里、一半露在外面 —— 这个做不到。
CSS 的三维和 WebGL 的三维各有各的深度缓冲，跨不过去，和相机统不统一无关，是浏览器的边界。

分层烘焙**没有解决**穿插，它是让穿插变得不可能。接受这条边界是整套设计成立的前提；
不接受的话要走完全不同的路（A 带深度进 B 的场景），那是另一份文档。

## 坐标与相机

开了 3D 模式全部换算成三维坐标，**不混用**。屏幕平面就是 `z = 0`。

```
world.x = stageX - W/2
world.y = -(stageY - H/2)        ← y 轴要翻:屏幕向下增长,three.js 向上
world.z = translateZ             ← + 是朝观众来
1 world unit = 1 stage px
camera.position = (0, 0, d)      ← +z,不是 -z
camera.lookAt(0, 0, 0), up = +y
```

### d 不是自由参数

一旦定死「1 世界单位 = 1 舞台像素」（必须定死，否则开 3D 模式整个画面会突然缩放），
相机距离和视场角就锁在一起：

```
d = H / (2 · tan(fov/2))
```

| fov | d(H=1080) |
|---|---|
| 30° | 2015 px |
| 40° | 1484 px |
| 50° | 1158 px |
| 60° | 935 px |

**用 fov 当旋钮，d 由它推**，不要反过来。因为竖屏项目 H 是 1920，同一个 d 的透视强度会变，
而 fov 是「透视有多强」的直接表达，跨画幅稳定。默认 40°。

顺带记一个数：`d = 100` 对应 **fov 159°**，是鱼眼。这个数看着"合理"（像是个距离），
实际完全不能用 —— 直觉在这里会骗人，所以永远从 fov 推 d。

### A 和 B 白拿同一个相机

CSS 的 `perspective: N px` 在数学上**就是**「观察者距 z=0 平面 N 像素」，和上面那个 d
是同一个量、同一个单位。所以这两处天然对齐，不需要任何标定：

```css
/* 挂在卡片的**直接父元素**上 —— perspective 只作用于直接子元素,隔一层就静悄悄失效 */
.pc-pv-stage { perspective: <d>px; perspective-origin: 50% 50%; }
```

**不要加 `transform-style: preserve-3d`。** 这条是实现时实测推翻的:它对透视投影
一点贡献都没有(加与不加,卡片投影宽都是 201.96),唯一的作用是把兄弟卡片从「按 DOM 顺序叠」
改成「按 z 深度排序」—— 那和下面「层序」这一节、以及「穿插本来就不做」直接冲突。
它还会改掉没碰过三维的卡的像素(截图 sha256 变了),等于开个三维把别的卡全换了光栅路径。

```js
camera = new THREE.PerspectiveCamera(fov, W / H, 1, d * 10);
camera.position.set(0, 0, d);
```

这不是巧合，three.js 自己的 `CSS3DRenderer` 就是这么干的（把相机焦距写进 DOM 的 perspective）。

**这也是「A 默认不烘焙」的依据**：既然透视本来就一致，A 留在 DOM 里、B 是一个 canvas，
两者按层序叠起来就是对的。

### 为什么相机在 +z 而不是 -z

three.js 默认相机朝 **−z** 看，放在 `(0,0,+d)` 看向原点才是自然朝向。
更要紧的是这样才和 CSS 对齐：CSS 里观察者在 +z，`translateZ(+)` 是朝观众来。
写成 -d 的话，要么相机背对屏幕，要么 z 的正负和 CSS 相反 ——
两种都是「看着不对但说不清哪不对」的那类 bug。

### 映射要有单测

`layout.ts` 那边算 CSS transform、three 那边算相机，两边算的是同一件事。
**做成一个模块 + 往返测试**（给一组舞台坐标和 fov，断言算出来的 world 坐标和相机参数），
不要散在两处各写一遍 —— 只要有一处改了没同步，画面就悄悄错位，而且不报错。

## 层序

每个 A/B 对象带一个**遮蔽标识**，`0` 在最前面。

```
z-index = -遮蔽标识
```

**方向要写死在这里**，因为 CSS 是数字越大越靠前，和这个约定相反。不写下来必然有人搞反。

## 什么时候烘焙

**只有一种情况：A 要贴到 B 的物体表面上当纹理。** WebGL 采样不了 DOM，绕不过去。

不是「产生空间遮挡就烘焙」—— 遮挡由层序解决，不需要烘焙。
也不是「进了 3D 模式就烘焙」—— A 留在 DOM 里做 CSS 3D，文字保持矢量清晰。

### 为什么默认不烘焙

四条理由，任何一条单独都够：

1. **`backdrop-filter` 会坏掉。** `hud.css` 的毛玻璃按定义采样它背后的东西，
   单独烘焙时背后什么都没有，出来的和合成后该有的样子完全不是一回事。
2. **代价是数量级的。** 60fps × 10 秒 × 5 层 = 3000 次截图，对比不烘焙的 600 次。
3. **预览和导出会分叉。** 预览走 DOM、导出走烘焙，毛玻璃一边对一边错，而且不报错。
   `server/vite-plugin-vision.ts` 里写过为什么这类分叉「比没有视觉更糟」。
4. **不需要。** 层序已经解决了遮挡，而穿插本来就不做。

### 烘焙时怎么处理特效

**不烘死，把属性传给 B 层重新实现。**

`box-shadow` 本来就是 2D 对真实阴影的伪造。烘死进纹理再放进 3D 场景，会得到两个互相矛盾的
阴影 —— 画上去的假的，加上灯光真投出来的。丢掉假的、让 B 打真光，是修正不是妥协。
`backdrop-filter` 同理，它是对折射的伪造，而 `MeshPhysicalMaterial` 的 transmission 是真的。

顺带解决一个问题：烘焙时把 `box-shadow: none` 一起关掉，**截图矩形就正好是元素盒子** ——
否则投影画在盒子外面（`0 24px 48px`），按矩形截会切掉一圈，合成回去看着发飘。

| CSS | → B 层 | 备注 |
|---|---|---|
| `background-color` | 材质 color + opacity | 直译 |
| `backdrop-filter: blur(N)` | `transmission` + `roughness` | **N → roughness 没有物理换算**，是审美常数，试出来写死 |
| `border` | 留在纹理里 | 想要发光边缘再走 emissive |
| `border-radius` | 纹理的 alpha 裁切 | 除非要侧面厚度，否则别做成几何 |
| `box-shadow: 0 Y B` | 光源方向 + 阴影 | 那个 Y 下偏移**就是光的方向**，可以反解 |

**这张表是封闭的。** 其余一律烘死进纹理。一旦开了「把 CSS 效果翻译成材质」这个口子，
`filter`、`mix-blend-mode`、`mask`、`text-shadow` 每一条都想进来，最后就是在重新实现一个浏览器。

属性从哪儿取：`src/editor/left/contentBox.ts` 已经在 `stage.querySelectorAll("*")` 上逐个
`getComputedStyle`，里面 `paintsItself()` 判的正是有没有底色/描边 —— 要抓的属性和它已经在看的
是同一批。而且 `getComputedStyle` 返回解析后的最终值，`--pc-glass-bg` 那些变量自动落成具体颜色，
**卡片不需要声明任何东西，30 张卡一张都不用改**。

### 单位

`blur(24px)`、`0 24px 48px`、`radius: 32px` 全是**舞台像素**，B 层是世界坐标。
按上面「1 world unit = 1 stage px」这条，两者数值相同 —— 但要在实现里显式写出来，
不要因为"数值一样"就省掉换算函数。将来任何人想改比例尺，得有一个地方可改。

## 实体模式（浏览用的低保真预览）

浏览时把每个控件画成一个色块，不渲真内容。暂停时再渲真的。

### 硬规矩：绝不进 Agent 的眼睛

`see_preview` 走 `scripts/export-frames.mjs` 另起一个 Chrome、加载 `?export=1`，
**根本不经过编辑台那个窗口**。所以只要实体模式活在 `?stage=1` 这条路上，vision 那边读都读不到。

参数必须是**显式打开**：

```
?stage=1            → 真渲（默认）
?stage=1&proxy=1    → 实体模式（只有编辑台预览会加）
```

反过来设计（默认开、导出时关）的话，一个漏掉的判断就能让导出悄悄输出彩色方块，
而那种错不会报，只会被当成渲染 bug 查半天。**退化方向必须是「慢但正确」。**

`src/StageView.tsx` 开头写着「预览所见 = 导出所得」。实体模式是这句话的例外，
破得**自明**（彩色方块没人会当成成品），而且只破在人这一侧。那句话要跟着补一句例外说明，
否则下一个读到的人会以为实体模式是 bug。

### 换挡不能靠卸载重挂

`src/render/pinAnimations.ts` 的锚点是「**头一次出现时**的舞台时间」。
卡片卸载再挂回来会拿到新锚点，进场动画在升级那一刻从头播一遍 ——
用户看到的是「每次暂停，字都重新飞进来一次」。

**用 `display: none` 把真卡藏起来，代理平面画在同一个位置。**

- `display:none` 跳过布局和绘制 → `backdrop-filter` / `blur` 的开销归零，这正是要省的
- 元素还在 DOM 里 → 锚点不丢
- 而动画本来就被 `pinAnimations` 钉住并暂停了 → 藏着几乎不花钱

### 颜色按真实纹理取，不按 ID 哈希

哈希色只告诉你「这是哪张卡」；纹理色让实体模式变成**能判断构图的低保真预览** ——
色块压在视频上是不是打架、明暗关系对不对，哈希色看不出来。

**取色要按 alpha 加权**：标题卡的包围盒里九成是透明的，直接对整盒求平均会被透明稀释，
所有文字卡都变成同一坨灰。要两个数：

- **RGB 按 alpha 加权平均**（只统计真画了东西的像素）→ 这张卡的墨色
- **alpha 对整盒平均** → 这张卡有多"实"

代理平面用 `rgba(墨色, 平均alpha)` 画。这样满底的面板卡和只有几个字的标题卡在实体模式下
**长得不一样** —— 构图判断要的正是这个区别。

两级挂载：

| 层级 | 键 | 来源 | 什么时候有 |
|---|---|---|---|
| 基线 | `cardId` | 离线那趟，默认参数 | 随包发，永远有 |
| 实例 | `clipId` | 真渲过一次之后采样 | 浏览过就有 |

基线是白捡的：`scripts/preview-boxes.mjs` **已经在浏览器里把每张卡真渲出来了**，
只是量完盒子就把像素扔了。`src/editor/left/prewarmBoxes.tsx` 挂的那个 `dump()` 就在渲染现场，
加一句取色即可，和 `boxes` 一起写进 `src/cards/preview-boxes.json`，`rev` 那套失效机制照旧复用。

实例那层也是白捡的：按「暂停 = 真渲」，卡片每次真渲都是一次采样机会。
**用得越久，实体模式越准** —— 用户改了 accent、换了文案，方块跟着变。

canvas 类的卡（粒子、以后的 three.js）必须走真取色，静态表里默认参数的颜色对它们没意义。
`contentBox.ts` 里已有「canvas 扫像素」的先例，扫的时候顺手把 RGBA 累加出来，一次遍历两个结果。

### 渐进式的调度

最省事的版本是「**拖动/播放 = 实体，暂停 = 真渲**」。不需要 `requestIdleCallback`，
不需要优先级队列，而且符合剪辑软件的直觉。先做这个，很可能就够了；
真要更细，再按「离播放头的距离」分批升级。

### 顺带兜住了 3D 的性能风险

有实体模式在，即使 B 层在预览里很重，浏览体验也有保障：**浏览看方块，暂停看真的，导出无所谓慢**。
这把「three.js 会不会把预览拖死」从「能不能做」降级成「暂停后要等几帧」。

## 分层实施

| 层 | 内容 | 依赖 |
|---|---|---|
| A | `ClipFrame` 加 `rotateX/rotateY/translateZ`，舞台加 perspective | **零新依赖**，30 张卡立刻能进三维 |
| B | three.js 作为一类新卡，自带 canvas | 动态 import（主包已 2.0 MB / gzip 590 KB，three 核心还要 ~150 KB gzip） |
| C | 按遮蔽标识合成 | 复用 `server/vision-compose.mjs`，它现在合的就是「素材层 + 卡片层」的透明底 PNG |

**A 层可能就够八成需求**，做完再评估 B 的优先级。

## 最大的风险不是 three.js 本身

**是确定性导出。** 项目有一整套虚拟时钟（`src/kernel/exportClock.ts`、`src/render/pinAnimations.ts`、
`__pcFrameReady`、`__pcRafCount`），导出时逐帧钉住动画。three.js 的 `requestAnimationFrame`
**必须接进那套时钟**，否则导出的帧会抖、不可复现 —— 而这正是这个项目花了大力气保证的东西。

次要风险：`transmission` 需要额外一遍渲染（先把场景渲到 transmission render target 再采样），
几个毛玻璃面板同屏就是几遍，逐帧导出时这个开销直接乘进时长。

## 待验证（四条，都还没做）

任何一条结果不对，上面的设计都要改：

1. **headless 截图能不能稳定拿到 WebGL 内容。** B 层的地基。
   现有那张 tsParticles 卡是 canvas 2D，**不能代表 WebGL**。
2. **一张现成卡加 `perspective` 导出看效果。** 决定「A 不烘焙」这条路够不够用。
   如果够，B 的优先级大幅下降。
3. **关掉 `box-shadow`/`backdrop-filter` 在透明底上截一张**，看纯内容纹理干不干净。
4. **`transmission` 能不能替代毛玻璃观感**，以及 `blur(24px)` 大概对应多少 `roughness`。
   如果观感撑不起来，翻译这条路就不如直接烘死一张半透明 —— 这条会反过来推翻上面那张映射表。

# AGENT-quota-send-refuse

分支 claude/quota-send-refuse(从 main 1c11557e 切出)。任务:main 上全量 UX 探针(默认步骤)38/40,E2 里"这一轮收尾 last:null"与"找不到发送按钮"。协调方假说:用量流水记账有滞后,`quota set --tokens used+1` 的 used 比真实用量小,E2 第一条消息被发送前预检(`account-master-assembly.mjs` 的 `send`,429 quota-exceeded)当场拒掉。

## 一、产品侧:发送被额度拒绝后页面是什么样(没有复现出"没有发送按钮")
把 E2 的上限故意设成"已用 - 1"(第一条一定被拒),在探针副本里逐步转储页面状态(副本是临时文件,已删,未入库),并等了 70 秒再发第二条:
- 被拒后 500 毫秒、3 秒、30 秒、40 秒、发第二条前,**一直**是:输入框可用(未禁用)、按钮是 `ai-send`(没有 stop/enqueue)、`view.streaming=false`、队列为空、提示栏 `cloud-notice` 显示"这个项目的云端 Agent 额度已用完(已用 603 / 上限 602)。请联系托管方。"、用户气泡标"没有发出去:…已用 603 / 上限 602…"(`sendState: failed`)、草稿留在输入框里。没有助手消息(这一轮根本没开始)。
- 再发一条:旧的失败气泡撤掉,只剩新的;能正常发出;额度恢复后能跑。
- 所以按现有代码,被拒的发送**不会**让用户卡住:拒绝有明确说明(提示栏 + 气泡两处,都带"已用 N / 上限 M"),乐观气泡被标成失败而不是假装已发,输入框回到空闲、有发送按钮。没有需要修的页面缺陷;为钉住这个行为,加了测试(见下),没有改 src/ 行为。
- 最终 final7 里那次"找不到发送按钮"在我这里没复现出由"被拒"引起;我复现并解释过的那个"找不到发送按钮"是另一个原因:探针的"再发"之后清额度竞态(上一轮 model-error-surface 已记录,main 上的探针已改成等新增的助手消息或 cloud-notice)。final7 的具体现场(日志里没有页面状态转储)无法回放;若还出现,请用 `--keep` 保留现场或把页面状态转储加进探针。

## 二、探针侧:E2 的额度起点
- 全量默认步骤跑下来,我这边的 E2 第一条消息始终被放行(usedBefore=114160,上限 114161,那一轮只做了一次模型调用,用量记到 114316,再发被拒),没有复现"流水滞后";即协调方的假说**未能证实也未能证伪**,但它与观察到的症状(第一轮没有助手消息 + 之后一系列后果)一致,而且被拒的现场我已经按它整套演练过(上一节),后果与 final7 日志的第一条失败("等到:这一轮收尾 last:null",因为被拒的发送没有助手消息)吻合。
- 改探针(只改 E2 的准备,断言一条没动、没放宽):`scripts/probes/cloud-agent-ux-ui-probe.mjs` 的 E2 起始处,`used` 改成"连着读两次相同(隔 2 秒,最多 10 次)才算稳定",设上限后再读一次核对,变了就按新值重设;上限仍是 used+1(余量 1 个 token:第一次模型调用放行,记账后用完,所以仍测"一轮中途额度用完、已落地的写入保留")。

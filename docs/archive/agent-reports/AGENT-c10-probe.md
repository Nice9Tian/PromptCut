分支 `claude/c10-probe`，worktree `.worktrees/c10-probe`，从 main `1dad2b7` 开出。端口段 5420～5429。

状态：四项都已跑完（P1 90 例、P2 有头无头各 3 轮、P3 有头无头各 3 轮加一次真实配额、P4 有头无头各一遍），报告写完。

## 环境

- Windows 11 Pro，28 逻辑处理器，RTX 3080 / 180 Hz 显示器。puppeteer 25.10.0 自带的 **Chrome/152.0.7977.75**，有头、无头各跑。
- 启动时去掉 puppeteer 缺省的 `--disable-background-timer-throttling`、`--disable-backgrounding-occluded-windows`、`--disable-renderer-backgrounding` 和它那串 `--disable-features`（其中有 `ProcessPerSiteUpToMainFrameThreshold`），让节流与进程模型接近用户的 Chrome。
- **本机 GPU 路径的 rAF 异常**：带 GPU 时，连一个空白 data: 页的 rAF 都只有 11 次 / 秒（有头、无头都是；`--disable-gpu-vsync` 也一样，再加 `--disable-frame-rate-limit` 才到 59）。加 `--disable-gpu` 走软件合成器后，有头 181 次 / 秒（显示器 180 Hz）、无头 61 次 / 秒。探针缺省加 `--disable-gpu`（`--gpu on` 可关）。推测是机器上其他子 Agent 在用 GPU 或显示器休眠，没深究；结论只比较同一时段的相对值，不受影响。
- **有头 Chrome 刚起来的几秒 rAF 只有 2～3 次 / 秒**，之后跳到 180。探针在测量前等父页 rAF 超过 30 次 / 秒（`waitFps`）。
- 同时有别的子 Agent 在跑测试。每轮开头记 Win32_Processor LoadPercentage，每个用例记测量窗口内 os.cpus() 的系统占用（表里「CPU%」）。

- 实验数据在主会话 scratchpad 的 `c10p/` 下（`p1-*.json`、`p2-*.json`、`p3-*.json`、`p4-*.json` 与控制台输出），不入库。

## 旁证：createSnapshot 的代价

`calibrate`：粒子场景每个元素内联样式后约 4 KB HTML。**不带 id** 时 50 / 100 / 200 / 300 / 400 / 600 个元素单帧 17 / 32 / 63 / 91 / 121 / 309 ms。P1 的后台重活取 500 个元素（约 130～300 ms、控件 HTML 约 2.0 MB），P2 的轻场景取 50 个（约 17 ms）。

另见：**每个元素都带 id** 时代价是平方级的：200 / 600 / 1000 / 1400 个元素 130 / 1353 / 3174 / 6541 ms。原因是 `serializeScene` 对每个 id 在整段 HTML 上各跑三遍正则改名（`src/render/createSnapshot.ts` 的 `serializeScene`）。真实卡片 id 不多时不成问题；带大量 id 的卡（例如逐元素带 id 的 SVG）要当心。不在本任务范围，只记下。

## P1 进程隔离与主文档长任务（D1）

### 做法

父页（640×360 的可见舞台 iframe + 同位置 `opacity:0; pointer-events:none` 的后台舞台 iframe，照 `src/editor/Preview.tsx` 的藏法；父页自己跑一条时间轴播放头动画）。可见舞台每个 rAF 推一帧 120 个元素的粒子场景（模拟播放）。每个用例新起浏览器：先量 3 s 基线（后台空闲），再让后台舞台干活、量 6 s。父页与可见舞台各自用 `PerformanceObserver('longtask')` 数长任务、用 rAF 间隔量掉帧。

后台负载三种：
- `busy`：150～300 ms 的忙循环，段间 `setTimeout(0)`；
- `snap`：500 个元素、有状态（每帧由上一帧推出）的场景，每帧 `createSnapshot`（130～300 ms，控件 HTML 约 2.0 MB）；
- `snapidb`：同 `snap`，并把控件 HTML `postMessage` 给父页，父页 `CompressionStream('deflate')` 后写 IndexedDB（L2 的写法）。

布置五种：
- `a-same`：两个舞台与父页同源（`127.0.0.1:5420`）；
- `b-port`：可见舞台、后台舞台各用一个端口（5421、5422），同站跨源，不加 OAC；
- `c-port-oac`：同 b，三个文档都加 OAC；
- `d-sub`：`editor.pc.test` / `s1.pc.test` / `s2.pc.test` 同一个端口，同站跨源（模拟线上子域），不加 OAC；
- `e-sub-oac`：同 d，都加 OAC。

顺序是「轮 → 有头 / 无头 → 负载 → 五种布置」，五种布置在同一时段交替跑，共 3 轮 × 2 × 3 × 5 = 90 例，全部跑完、无报错。

补充读数（同一 JSON）：
- **OOPIF**：只有 c、e 两种布置里两个舞台各成一个 `type: iframe` 的独立 target，渲染进程 7 个；a、b、d 没有 OOPIF，渲染进程 5 个。
- **长任务的归属**：a 的父页长任务记为 `same-origin-descendant`，b、d 记为 `cross-origin-descendant`，即后台舞台的任务就在父页的事件循环里跑。
- **加载窗口里父页 rAF 最大间隔**：a / b / d 为 150～360 ms（与单个后台单元等长）；c / e 为有头 7.0～7.5 ms、无头 17.7～31.5 ms。唯一例外：有头 `snapidb` + c 的第 2 轮有一次 66 ms 间隔（没有长任务），见下。
- **后台吞吐**：c / e 下单帧 `createSnapshot` 有头 130～166 ms、无头 255～278 ms；与 a / b / d 相当，没有因隔离变慢。

- `window.originAgentCluster` 在五种布置、三个文档里**全是 true**，没加头的也是：Chrome 152 缺省按源分 agent cluster，但**不因此分进程**。所以这个属性不能用来判断是否隔离，要看 OOPIF。
- 系统 CPU 占用：各用例测量窗口 8～59 %，Win32 负载每轮开头 1～15 %。隔离布置 c / e 的加载窗口 CPU 往往高几个百分点：多出的两个渲染进程与父页真正并行。

### 结论

- **(c) 同站跨源 + OAC 满足判据**：两种负载、有头无头、各 3 轮，父页和可见舞台的长任务都是 0；父页 rAF p95 与基线相同（有头 6.2～6.6 → 6.2～6.6 ms；`snapidb` 时 8.4～9.4 ms，多出的是父页自己 deflate 加写库）；可见舞台 rAF p95 不变。
- **(b) 同站跨源不加 OAC、(d) 子域不加 OAC 与 (a) 同源一样**：后台的每一段重活都成为父页与可见舞台的长任务，一帧 150～300 ms，播放明显卡顿。
- **子域与换端口的效果一样**：e 与 c 数字一致。线上用 `s1.<主机>`、`s2.<主机>` 加 OAC，在 Chrome 152 里就能得到独立进程。没加 OAC 的子域和同源一样卡。
- **可见舞台不受后台舞台拖累**：c / e 下可见舞台的长任务 0、rAF p95 与基线相同。本次测的是两个舞台都跨源的布置；「可见舞台与父页同源、只有后台舞台跨源加 OAC」没单独测，按进程模型推断同样成立（后台在自己的进程里），实施时若采用要补一轮。
- **父页写 L2 的代价在预算内但要留意**：一次性 `postMessage` 2 MB 字符串到父页，父页反序列化再 deflate，有头 9 例里出现过一次 66 ms 的 rAF 间隔（没有记成长任务）。建议舞台里先 deflate（`CompressionStream` 在舞台自己的进程里），再以可转移的 `ArrayBuffer` 交给父页，父页只写库。

## P4 跨源舞台读素材

### 做法

起托管组合 `server/hosted/main.mjs`（文档服务 5428、素材服务 5429，只绑 127.0.0.1，数据目录用系统临时目录，跑完删掉），用 `server/asset-store/client.mjs` 传一段 2 s 的 320×180 H.264 mp4（ffmpeg testsrc，10815 B）和一张 128×128 png。舞台页放在父页（5420）的 iframe 里，URL 都带 `?t=probe-ticket`（形状同 C10a 的只读票据；这一轮素材服务信任本机回环，票据不核对，所以只测 CORS 这一层）。三种路：

- **A** 舞台在 5424，直连素材服务 `127.0.0.1:5429/api/asset/media/<hash>`（素材服务自带 `Access-Control-Allow-Origin: *`，见 `server/asset-service.ts` 文件头「跨源」）；
- **B** 舞台在 5424，经一个**去掉全部 `access-control-*` 头**的代理（5425）读，模拟「反代没配 CORS」；
- **C** 舞台在 5426，同一个进程既发舞台页，又把 `/media/<hash>` 反代到素材服务的 `/api/asset/media/<hash>`，也去掉 CORS 头，模拟「子域也反代 /media、对舞台同源」。

每条路测：`fetch` 带 `Range: bytes=0-1023`；`fetch` 带 `Authorization: Bearer`（会触发预检）；`<video>` 与 `<img>` 不带和带 `crossorigin="anonymous"`，加载后 `drawImage` 到 canvas 再 `toDataURL()`（快照的 canvas 换 `<img>` 就是这么做的）。另起一次 `PROMPTCUT_TEST_NO_LOOPBACK_TRUST=1`，用假票据看 401 能否被跨源读到。有头、无头结果完全相同。

### 结果

| 路 | fetch + Range | fetch + Bearer（预检） | `<video>` 无 crossorigin | `<video crossorigin>` | `<img>` 无 crossorigin | `<img crossorigin>` |
|---|---|---|---|---|---|---|
| A 跨源直连（有 ACAO:*） | 206，`bytes 0-1023/10815` | 206 | 能播，canvas **被污染**（`SecurityError`） | 能播，canvas 可读 | 能显示，canvas **被污染** | 能显示，canvas 可读 |
| B 跨源、去掉 CORS 头 | `TypeError: Failed to fetch` | 失败 | 能播，canvas 被污染 | **加载失败**（media error 4） | 能显示，canvas 被污染 | **加载失败** |
| C 同源前缀反代 /media（无 CORS 头） | 206 | 206，**没有预检** | 能播，canvas 可读 | 能播，canvas 可读 | canvas 可读 | canvas 可读 |
| A，不信任回环 + 假票据 | 能读到 **401**（35 B 回包） | 能读到 401 | 失败（media error 4） | 失败 | — | — |

代理计数：B 共 6 个请求（3 个带 Range，1 个 OPTIONS 预检）；C 共 6 个请求（4 个带 Range，0 个 OPTIONS）。

### 结论

- **舞台跨源直连素材服务要 CORS**：`fetch`（含 Range、含 Bearer 预检）靠素材服务现有的 `Access-Control-Allow-Origin: *` 才读得到；反代若把这组头吃掉就全断。401 也带着 ACAO，所以票据过期时页面能读到状态码去换票。
- **CORS 之外还有一层画布污染**：跨源素材在元素上不带 `crossorigin` 时能显示、能播，但一画进 canvas 就被污染，`toDataURL()`、WebGL 取纹理都会抛 `SecurityError`。现在 `src/` 里的素材元素都不设 `crossOrigin`（在 `src` 里搜不到），桌面版舞台读的是同源 `/@media`，所以没暴露。在线若让舞台跨源直连素材服务，就得给所有素材元素加 `crossOrigin = "anonymous"`（且素材服务必须回 ACAO），否则画素材的 canvas 卡生成不了快照。
- **子域也反代 /media（对舞台同源）时，CORS 与画布污染两件事都不用管**：C 路去掉了全部 CORS 头，Range、Bearer、元素、canvas 全部正常，而且 Bearer 不再有预检（少一个往返）。推荐线上这样部署：`s1.<主机>`、`s2.<主机>` 的 nginx 都把 `/media/`（或原路径 `/api/asset/media/`）反代到素材服务，舞台用相对地址。
- 没测到：真实票据的签发与过期（本轮票据不核对，只证了 401 可读）；HTTPS 下的混合内容；nginx 本身（用 Node 代理模拟）。

## P2 后台舞台的节拍（D7）

### 做法

父页 + 一个跨源带 OAC 的后台舞台（即 P1 的布置 c），后台舞台放在六种位置：

| 位置 | 样式 |
|---|---|
| `onscreen-opacity1` | 原位、不透明（对照） |
| `overlay-opacity0` | 原位 `opacity:0`（桌面版现在的藏法） |
| `translate-offscreen` | `opacity:0; transform: translate(-5000px,0)` |
| `left-10000` | `left:-10000px`，不透明 |
| `tiny-1px` | 原位 `opacity:0`，1×1 px |
| `visibility-hidden` | 原位 `visibility:hidden` |

每种位置在三种页面状态下各测一遍：页面可见；切到另一个标签（`bringToFront` 一个 about:blank）；窗口最小化（仅有头，CDP `Browser.setWindowBounds`）。不可见的两种状态只对 `overlay-opacity0`、`translate-offscreen` 测，冒烟时各位置在不可见状态下数字相同。

每个节拍单独开一个窗口计数（可见 2.5～5 s，不可见至少 6 s），单位都是「次 / 秒」：
- `raf`、`timeout0`（setTimeout 0 链）、`timeout16`、`ric`（无超时）、`ric1000`（超时 1000 ms）；
- 三种 L1 推帧调度，每次推一帧并对它 `createSnapshot`，轻场景 50 个元素（14～45 ms）、重场景 500 个元素（126～350 ms）：
  - `bake`：`requestIdleCallback(…, { timeout: 1000 })` 里推一帧，即前置核对里 D7 的建议；
  - `bakeT`：每帧之间只让一次 `setTimeout(0)`，表示空闲时能推的上限；
  - `bakeRT`：用 rIC（无超时）当门闸，门闸过了再 `setTimeout(0)` 推一帧。

### 结论

- **后台舞台要留在视口里，原位 `opacity:0` 可以**：`overlay-opacity0` 与 `tiny-1px` 的 rAF、定时器、空闲时的 rIC 都和不透明的对照一样（有头 180 / 210 / 180 次 / 秒，无头 60 / 220 / 60）。
- **移出视口或 `visibility:hidden` 都会被 Chrome 节流**：`translate-offscreen`、`left-10000` 的 rAF 0.4 次 / 秒、`setTimeout(0)` 链只剩 3.6～4 次 / 秒、`bakeT` 只能推 2～2.5 帧 / 秒；`visibility-hidden` 的定时器不受影响，但 rAF 0.4、rIC 为 0。桌面版避开 `display:none` / `visibility:hidden` 的理由（`src/editor/Preview.tsx` K5 (4) 那段注释）在线同样成立，而且屏外也不行。
- **在 `opacity:0` 的舞台里，rIC 当不了推帧的节拍器**：页面可见且空闲时，`bake`（rIC + 1000 ms 超时）在不透明对照里能推 65 帧 / 秒（轻，有头）、7.4 帧 / 秒（重，有头），在 `opacity:0` 里只剩 1～4.7 帧 / 秒（轻）和 1 帧 / 秒（重），几乎全靠 1000 ms 超时触发。`bakeRT` 也一样。原因推测是每推一帧都弄脏了 DOM，而 `opacity:0` 的帧一直有待出的画面，渲染器不进入空闲期；单独数 rIC（不改 DOM）则一直是满速。**`bakeT`（每帧之间 `setTimeout(0)`）不受影响**：`opacity:0` 下轻场景有头 52～55、无头 31～32 帧 / 秒；重场景有头 7.3～7.7、无头 3.8～3.9 帧 / 秒，约等于 1000 / 单帧耗时。
- **可见且空闲时每秒能推多少帧**：约 1000 ms ÷ 单帧 `createSnapshot` 耗时。本机轻卡（15～30 ms）30～55 帧 / 秒，重卡（130～260 ms）4～8 帧 / 秒。
- **不可见时不会自己停，只会变慢**：无头切到别的标签后（`hidden`），`setTimeout(0)` 链 2.16 次 / 秒、rAF 0.17、rIC 0（带超时的 0.5）；`bakeT` 仍有 1.2～2 帧 / 秒。有头最小化时定时器降到 66 次 / 秒，`bakeT` 还有 24～27 帧 / 秒（轻）。所以「不可见就停」必须由代码按 `visibilitychange` 主动停，不能指望浏览器节流替它停。
- Chrome 88 起的「隐藏 5 分钟后每分钟唤醒一次」没测（每个窗口最长约 10 s）。

## P3 IndexedDB（D6）

### 做法

父页 `http://127.0.0.1:5420`（安全上下文），库 `c10probe-p3`，键形同 L2 的复合键 `['snap', 'cardN', i]`，值是随机字节的 `Uint8Array`（deflate 后的快照接近不可压缩，所以用随机字节；Chrome 会压缩 IndexedDB 的值，冒烟时 100 条 1 MiB 的「大部分为零」值只记了 6.6 MiB 用量）。

1. 每条 20～200 KB 随机大小，**每条一个事务**（L1 每帧写一次）写到 256 MiB；随机顺序逐条 `get` 读回；再以 20 条一个事务写 64 MiB 对照。写读期间在父页数长任务。
2. `estimate()` 前后、`persisted()` 与 `persist()` 的回应。
3. 配额：先用 CDP `Storage.overrideQuotaForOrigin` 压到「当前用量 + 32 MiB」再写 150 KB 的条目到报错，然后删最早的约 16 MiB、立刻重试一次。
4. 分区：父页建库 `c10probe-part` 写一条，跨源舞台（5422，OAC）打开同名库数条目；再把舞台换成同源（5420）对照。
5. 隐身上下文（puppeteer `createBrowserContext`）里的 `estimate()` 与 `persist()`。

有头、无头各 3 轮。另加 `p3q`：因为第 3 步压配额不生效（见下），改用真实配额写到报错，按 8 MiB 一条、每 64 条从 Node 驱动一次；磁盘剩余少于 40 GiB 时由探针自己停。

### 结论

- **吞吐足够**：每帧一个事务写 20～200 KB，写入 136～143 MiB/s、单事务 p50 0.5 ms、p95 0.8～0.9 ms（最大 70～95 ms，偶发）；随机读 338～360 MiB/s、单次 get p95 0.4～0.5 ms、最大约 11 ms。写读期间父页**没有长任务**。所以 L2 在父页里读写不会碍播放；播放时按拍 `get` 一个快照远低于一帧的预算。批量事务（20 条）只快到 104～163 MiB/s，没必要为吞吐合批。
- **`estimate()` 不是上限**：这台机器上 Chrome 给的 `quota` 恒为「当前用量 + 10 GiB」（10 GiB 约为磁盘剩余 102 GiB 的 10 %），实际写到 32 GiB 也没报错。所以「按 `estimate()` 剩余的 10 % 收紧上限」在 Chrome 上等于 1 GiB 左右，不会比 256 MiB 更紧；这条规则对 Chrome 几乎不起作用，保留也无害（在 Safari 上才有意义，没测）。
- **`persist()` 在未交互、未安装的页面上回 false**（有头、无头、隐身都是）。L2 不能依赖它，与 codex 的建议一致。
- **「回收一批再试一次」的机制可行**：删一个事务完成后，用量立刻下降（16 MiB 与 64 MiB 两个量级都是），紧接着的写入成功。但**本机没能撞出真正的 `QuotaExceededError`**：CDP 压配额不生效，真实配额要把磁盘写满才会到。错误分支的实际表现（错误名、事务是 `error` 还是 `abort`）没实测，写代码时两个事件都要接。
- **分区如预期**：跨源舞台看不到父页的库，自己另有一份配额。L2 由父页写、舞台经 `postMessage` 交结果的设计成立；若舞台自己写库，会与父页各成一个库，互不可见。

## 对 D1、D6、D7 的建议

### D1 后台舞台从哪来

- **用同站跨源的两个舞台，并且都加 `Origin-Agent-Cluster: ?1`**，编辑器页面也加。子域（`s1.<主机>`、`s2.<主机>`）与同主机换端口在 Chrome 152 里效果完全一样（P1 的 e 与 c），按部署方便选：
  - 子域要 DNS 记录和覆盖子域的证书（通配符或多域名证书），可能是待用户项；
  - 换端口要在轻量服务器控制台放行端口（前置核对已提到 `docs/local.md` 那条），也可能是待用户项。
- **不加 OAC 的跨源（b、d）与同源（a）一样卡**，不能当折中方案；同源后台舞台（前置核对里的选项 (c)）在后台重活时每段都成为主文档长任务，「播放时主文档 Long Task 为 0」做不到。
- 两个舞台的服务都**把 `/media/` 反代到素材服务**，舞台用相对地址读素材：这样既不需要 CORS，canvas 也不会被跨源素材污染（P4 的 C 路）。若舞台要直连素材服务，必须给所有素材元素加 `crossOrigin = "anonymous"`，否则画素材的 canvas 卡生成不了快照。
- 舞台交给父页的快照：**在舞台里先 deflate，再用可转移的 `ArrayBuffer` 交给父页**，父页只写库。直接传 2 MB 字符串时父页有过一次 66 ms 的掉帧。
- 判断是否隔离看 OOPIF（CDP 的 `type: iframe` target），不要看 `window.originAgentCluster`（Chrome 152 缺省就是 true）。

### D7 后台舞台放哪、节拍规则

- **放在原位 `opacity:0; pointer-events:none`，留在视口内**（同桌面版）。不要 `translate` 到屏外、不要 `left:-10000px`、不要 `visibility:hidden` / `display:none`：前两种 rAF 0.4 次 / 秒、定时器 3.6～4 次 / 秒，后一种 rAF 0.4、rIC 为 0。
- **后台舞台里不要用 `requestIdleCallback` 当推帧节拍**：`opacity:0` 的舞台一边推帧一边改 DOM，rIC 就只靠超时触发，重卡轻卡都只剩约 1 帧 / 秒。建议：
  - 「空闲」由父页判：可见、没在播放或拖动、探针队列空、最近一次操作过了冷却期。父页自己不透明，rIC 正常（180 / 60 次 / 秒），需要的话用父页的 rIC 当门闸。
  - 父页用 `postMessage` 给后台舞台发开始、停止；舞台每推一帧就让一次 `setTimeout(0)`（或 MessageChannel），每帧之间检查停止标志与角色代数。一批 = 一帧；用户一操作，最多等当前这一帧做完。
- **页面可见且空闲时每秒能推的帧数约为 1000 ÷ 单帧 `createSnapshot` 耗时**：本机轻卡（15～30 ms）30～55 帧 / 秒，重卡（130～260 ms）4～8 帧 / 秒。按重卡 4 帧 / 秒算，30 秒能推约 120 帧，「10 秒时间轴的锚帧」够用；最终按真实卡片再量。
- **不可见时必须由代码主动停**：浏览器节流不会让它停，无头切标签后仍有 1.2～2 帧 / 秒，有头最小化时还有 24～27 帧 / 秒（轻卡）。按 `visibilitychange` 停、回到可见再续。因为 puppeteer 控制的有头 Chrome 在切标签、最小化后 `visibilityState` 仍报 `visible`，建议再加一道保险：父页 rAF 间隔连续超过约 500 ms 时也当作不可见、暂停（这时 rAF 已降到每秒 1 次）。
- 「30 秒内推完锚帧」的验收按前置核对的建议改为「前台可见且空闲时判」，与实测一致。

### D6 L2 的配额与淘汰

- **保留 256 MiB 的软上限（普通档），自己按压缩字节做 LRU**。Chrome 的 `estimate().quota` 在本机恒为「用量 + 10 GiB」（约为磁盘剩余的 10 %），写到 32 GiB 也不报错，它不会比 256 MiB 更紧。「按 `estimate()` 剩余额度的 10 % 收紧」在 Chrome 上等于不起作用，可以保留给 Safari。
- **不依赖 `persist()`**：六次都回 false，隐身也回 false。
- **淘汰一批 16～64 MiB、在一个事务里删**：16 MiB（约 150 条）115～146 ms，64 MiB（8 条大条目）572 ms。删完 `usage` 立刻下降，紧接着重试写入成功。`QuotaExceededError` 分支只重试一次，事务的 `error` 与 `abort` 两个事件都要接（错误的真实形状没能实测）。
- **每帧一个事务就够**：写 p95 0.8～0.9 ms、读 p95 0.4～0.5 ms，都没有长任务；无需合批。一帧 2 MB 的控件 HTML deflate 后约 61 KB，正落在「20～200 KB 一条」的假设里；256 MiB 大约能存 4000 帧这样的重卡快照。
- **L2 由父页写**：跨源舞台看不到父页的库，自己另有一份配额。

## 没测到的

- **Safari、Firefox 没测**（本机没有），Edge 与手机浏览器也没测。OAC 在 Safari / Firefox 是否分进程、跨源 iframe 的节流、IndexedDB 配额，都只有资料（`c10-research.md` 的 Q1、Q4），没有实测。
- 真实用户 Chrome 里切标签、最小化时 `visibilitychange` 是否触发：puppeteer 有头下没触发（见 P2），无头切标签能触发。
- Chrome「隐藏 5 分钟后每分钟唤醒一次」的强节流：每个测量窗口最长约 10 s，没测。
- 真正的 `QuotaExceededError`：CDP 压配额不生效，真实配额要写满磁盘。
- 「可见舞台与父页同源、只有后台舞台跨源加 OAC」这种布置没单独测。
- 仓库里真实的重卡：用的是合成的有状态粒子场景 + 真实的 `createSnapshot`，没有起 dev server 跑真实卡片。
- 真实票据的签发与过期、HTTPS、真实 nginx：P4 用本机托管组合和 Node 代理模拟，票据不核对。
- GPU 合成路径：本机 GPU 路径的 rAF 只有 11 次 / 秒（原因没查），全部用 `--disable-gpu` 的软件合成器测。进程隔离与长任务的结论不依赖合成路径，节拍的绝对数字会随显示器刷新率变化。

## 对任务书与语义的更正建议

- `docs/plan/cloud-task.md` 目标 L 的 L1：「页面可见时用 `requestIdleCallback` 的窗口」改为「父页判空闲、舞台用 `setTimeout(0)` 每帧推一帧」（P2：`opacity:0` 舞台里 rIC 约 1 次 / 秒）；「不可见时按 E4 每 8 帧让出」改为「不可见就停」（与 D7 建议相同，P2 证明浏览器不会替它停）。
- `c10-research.md` Q1 第 5 条「L1 iframe 尽量与编辑页同源」与 P1 冲突：同源后台舞台做不到「主文档 Long Task 为 0」。应改为跨源加 OAC，L2 由父页写。
- 语义层面没有发现冲突。`product/platforms.md`「在线浏览器模式」只说后台舞台在闲时兼做渲染节点，没规定放法与节拍，以上都属三级（机制）或计划层面的取舍。
- 旁记（不在本任务范围）：`createSnapshot` 对 id 多的场景是平方级（1400 个带 id 的元素 6.5 s），原因在 `serializeScene` 的逐 id 正则改名。

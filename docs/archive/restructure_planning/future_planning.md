## 1. 桌面版给「只有原片」的云端素材补转小版

**记录日期**：2026-09-22
**来源**：讨论 `user_pinned_goal.md` 架构 1（素材云端的上传 / 拉取规则）时定的。

**现状与缺口**：小分辨率版本（800×600 的 H264）由上传方在自己机器上用 ffmpeg 转出，云端不转码。在线浏览器模式没有本机 ffmpeg，所以**在浏览器里导入的素材上传到云端时只有原片一档**。别人拉这份素材时云端没有小版，只能按 pinned 的「还没有小分辨率版本就直接拉原素材」走，要等原片下完才看得到画面。

**现在的决定**：先不管。小规模运行期间浏览器导入是少数情况，多等一会儿可以接受。

**以后要做的事**：任何一个桌面版用户打开项目、把这类素材的原片拉到本地内容库之后，如果发现云端缺小版，就在后台低优先级补转一份 800×600 的 H264 传上去。之后所有人再拉这份素材都能先拿到小版。

**为什么这条路便宜**：
- 不需要云端有转码能力，也不改 pinned 已定的上传 / 拉取规则，只多一个「缺小版就补」的后台任务。
- 转码命令和分片上传都复用上传方原有的那一套（任务书第 5 步 A1）。
- 小版有自己的内容哈希，几个桌面版同时补转，云端按哈希去重，谁先传完用谁的。

**动手时要定的细节**：
- 怎么知道云端缺小版：素材记录里没有小版的哈希，或者云端查询回「没有」。
- 补转完成后由谁把小版的哈希写回项目：走文档服务的一次普通操作，和别的写入一样排序、记版本。
- 多人同时补转时避免重复劳动：开转之前先问一次云端，已经有人传完就跳过。
- 只在机器空闲、且原片已经完整落盘时做，不和用户自己的导入、上传抢带宽。

**不走的路**：在页面里用 WebCodecs 解码原片、缩小、重新编码成 H264。能做，但工作量不小，平板和手机上又慢又耗电，各浏览器的编码器支持也不齐。

## 2. 导出页 / 预渲染页装虚拟定时器

**记录日期**：2026-09-22
**来源**：R3 只在舞台里接管了 `setTimeout` / `setInterval` / `Date.now`（E4b），导出页和预渲染页没装；独立复核 R3-18 提出，用户 2026-09-22 定「先接受，开一条待办」。

**现状与缺口**：靠定时器计时的卡（打字机、倒计时）在舞台里按虚拟时间走，在导出页和预渲染页按真实时间走，两边可能对不上。今天的卡库里没有这类卡（只有 `src/cards/_probe/timers.tsx` 两张探针卡），所以没有实际受害者。

**现在的决定**：不装。执行者说导出页自己的三处墙钟定时器（`snapshotSettle` / `frameMedia` / `prerender`）装了会死锁，这一点没实际验过。

**以后要做的事**：有真实的定时器计时卡进卡库时，先验死锁是不是真的（把那三处改用 `__pcRealSetTimeout`），再给导出页装同一份 `virtualTimers`；导出逐字节基线会变一次，要重立。

**另一条已定的**：舞台里 `Date.now` 固定成纪元（`pinEntropy`），不取舞台打开时的真实时间——确定性优先，用户 2026-09-22 定。

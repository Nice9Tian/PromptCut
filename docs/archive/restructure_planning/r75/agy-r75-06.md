# 第 75 轮 · 第 6 份：第 4b 步：M1～M6 共享 WebGL 渲染器
## 1. 结论
**不能直接动工。阻塞 8 条、非阻塞 1 条（另有 manager 在 4.2 表里补的 3 条「给了但形状不符」的前置接口，建议与阻塞同等对待）。**

不能动工。执行者走查发现多处阻塞性逻辑缺失（如 Worker 加载卡片函数的机制、可见舞台等待 `done` 的异步机制、路线 2 丢失抗锯齿等），且要求迁移的三张运行期用户卡源码不在本仓库内，无法在本仓库完成迁移和验收。

## 2. 阻塞项
### 2.1 Worker 加载卡片代码的机制缺失
任务书行号与原句摘录：L285「three 的 build(THREE, params)... 2d 的 draw... gl 的 uniforms」
证据：Worker 是独立的 JS 运行环境，无法通过 `postMessage` 传递函数对象。M1/M2 均未说明 Worker 侧从哪个模块或以何种机制导入并执行这些卡片的渲染函数，尤其在 L365 规定「在线浏览器模式不加载用户卡」的情况下，`import.meta.glob` 方案如何适用于 Worker 未予交代。
建议改法：在 M2 中明确写明 Worker 侧如何获取各卡片的渲染函数（如提供专门供 Worker import 的注册表模块），并说明运行时加载方案。

### 2.2 three/2d 契约未定义如何声明和复用纹理
任务书行号与原句摘录：L285「textures: Array<{ name, mediaId \| url }>, uniforms(t: params)...」；L286「素材纹理只上传一次：按 mediaId + tier 缓存 WebGLTexture」
证据：M1 仅为 `gl` 契约定义了 `textures` 数组，`three` 和 `2d` 契约缺乏对应的素材纹理声明机制。执行者无法实现让这两种卡享受 M2 承诺的「素材纹理只上传一次」优化。
建议改法：在 M1 中为 `three` 和 `2d` 契约补充纹理声明的签名，并说明在它们的 `build` 或 `draw` 中如何获取 Worker 缓存好的纹理。

### 2.3 图集 FBO 缺少多重采样（导致丢失抗锯齿）
任务书行号与原句摘录：L287「先 bindFramebuffer(READ_FRAMEBUFFER, fbo) + blitFramebuffer 到默认帧缓冲」；L289「同一上下文属性 { alpha: true, antialias: true }」
证据：WebGL2 中只有默认帧缓冲受初始化时的 `antialias` 属性影响。如果在路线 2 自建的 framebuffer (fbo) 上没有显式开启多重采样（如 `renderbufferStorageMultisample`），`blitFramebuffer` 的结果将没有抗锯齿，这直接导致无法通过 M5 要求的「逐像素相同（允许抗锯齿末位差异）」验收。
建议改法：在 M3 描述路线 2 建立图集 framebuffer 时，写明需使用多重采样的 Renderbuffer，并在裁切前解析到普通颜色附件。

### 2.4 可见舞台（StageView）缺乏对 done 消息的等待机制
任务书行号与原句摘录：L287「然后才走 K4 的等真实一帧 -> post frame」；pinned 渲染 10（材料文件第 119 行，非任务书行号）「画完回 done 主线程才推进一拍」
证据：K4 的 `__pcRealRaf` 循环在 `StageView.tsx` 中是同步发起的，它自身并没有去 await `waitForFrameWork()`（该机制仅在 `ExportView` 和 `bakeFrames` 中被消费，见 `export-frames.mjs:610`）。如果没有写明 `StageView` 如何在 K4 循环内等待 `done` 信号，主线程会直接进入下一帧，违背「画完回 done 才推进」。
建议改法：在 M3 中补充 `StageView` 侧的具体等待实现（如在 `__pcRealRaf` 触发前插入检查 `frameWorkStatus()` 或专门的 Promise 等待逻辑，并与 `settle` 的微任务排好顺序）。
> **manager 核对（证据更正）**：原文「K4 的 `__pcRealRaf` 循环在 `StageView.tsx` 中是同步发起的」与仓库不符——`src/StageView.tsx:73` 是 `const realRaf = () => new Promise<void>((r) => (window.__pcRealRaf ?? window.requestAnimationFrame)(() => r()));`，`:377` 处写的是 `          await realRaf();`，本身就是可 await 的；而 K4 的播放循环在 b5c65dc 里根本还没落地（第 4 步才做）。本条的**实质缺口成立、保留**：M3 没写 `beat` 发在 `clock.advanceTo` 之前还是之后、`await done` 卡在 K4 一拍的哪两步之间、`settle` 的 `queueMicrotask`（`StageView.tsx:180`）和这个 await 谁先、`done` 迟到时「慢帧就等」等在哪个 await 上。

### 2.5 ExportView 侧的 beat 触发点缺失
任务书行号与原句摘录：L287「导出页 / 预渲染页每一帧（落点：glHost 每发一次 beat 就用 beginFrameWork...）」
证据：导出页的帧推进由 `window.__pcSetT` 驱动（直接修改 `__pcExportMs` 引发 React 重新渲染），而 M 未指明 `ExportView` 在重渲染循环的哪个生命周期（如特定的 `useEffect`）中调用 `glHost` 发送 `beat` 消息，执行者照写会无从下手。
建议改法：在 M3 中写明 `ExportView` 发送 `beat` 的具体落点（如补充在依赖 `__pcExportMs` 的 `useEffect` 中派发）。

### 2.6 要求迁移和验收本仓库中不存在的用户卡
任务书行号与原句摘录：L289「scene-3d 和三张 three.js 用户卡改成 canvas.kind: 'three' 契约」；L291「5 张卡迁移后 verify-unified-frames.mjs 逐像素通过」
证据：`src/cards/user/` 目录下仅有 `index.ts` 和 `mu-animated-shiny-text.tsx`，L283 提到的三张运行期用户卡（`logo-3d-9tian` 等）不在本仓库中（仅在测试文件中有引用），执行者无法拿到源码进行迁移，也无法独立在本仓库运行 `verify-unified-frames.mjs` 覆盖它们。估时和迁移无法进行。
建议改法：在 M5 写明这三张运行期用户卡在何处获取、由谁负责迁移（如提供外部测试替身 fixture），并在验收中明确外部卡加载方式；或者将 M5 及验收要求涉及的卡片缩小为本仓内的 2 张。

### 2.7 dom2d 契约签名定义缺失
任务书行号与原句摘录：L285「三种契约的共同点：只收 t...」；L289「M1 加第四种契约 kind: 'dom2d'——仍在主线程用真画布画」
证据：M1 在类型中给出了 `dom2d` 联合类型，但正文仅描述了前三种契约的函数签名，对于 `dom2d` 需要暴露什么接口（如 `draw`）并未给出说明，执行者无法实现 `dom2d` 卡片在主线程同拍落定的逻辑。
建议改法：在 M1 中补全 `dom2d` 的具体对象结构与函数签名。

### 2.9 M 验收条件中关于上下文实例数量的断言与路线 2 矛盾
任务书行号与原句摘录：L291「舞台文档里 WebGLRenderingContext / WebGL2RenderingContext 实例只有 Worker 里那一个」
证据：在路线 2 下，舞台 iframe 内部一个 WebGL 上下文都不开（不创建 Worker，仅接收 MessageChannel 端口），唯一的一个上下文位于父页面。该验收条件与路线 2 的设计冲突。另关于「20 张 three.js 卡同时活跃」，本仓内置仅一张，20 张卡来源未在 fixture 明确。
建议改法：在验收条目中针对路线 2 补充说明（如：路线 2 下舞台文档内为 0 个，父页面为 1 个）。明确 20 张卡是在 fixture 中复用同一内置卡或由脚本动态生成。

## 5. 对 user_pinned_goal.md 的建议
建议修改「渲染 10」中与路线 2 设计自我矛盾的首句：
原句：「每个舞台文档只开一个 WebGL 上下文...在交互界面的舞台 iframe 里开的一个 Web Worker」

# 文档服务

展开 `../architecture.md` 的「文档服务」角色。从属于 `architecture.md`，与它冲突时以它为准。

## 职责

- 文档服务是项目文档的唯一修改入口。编辑界面和 Agent 都只向它提交操作，由它排序、记版本、通知各方、管理锁。各方手里的项目都是它的副本。
- 它管理：项目信息、每一次操作的接收与分发、锁、覆盖通知、卡片源码。
- 它和各方之间是一条长连接，传小消息、要求快速响应。素材字节和预渲染结果不走这条连接，走素材服务。

## 部署组合

- 文档服务和素材服务各自独立选位置，部署不设限：
  - **本地文档服务**：作为本地守护进程跑在本机。**远程文档服务**：部署在局域网里的另一台机器或公网云端。
  - **本地素材服务**、**远程素材服务**同理，见 `asset-storage.md`。
- 两套服务可以任意组合，例如文档服务在公网云端、素材服务在局域网 NAS 或本机。只要遵守标准的接口契约，用户可以自由部署。
- 无论怎么组合，协议不变：操作和通知只走文档服务，素材字节和预渲染结果都经素材服务读写。
- 切换所连接的服务是用户的显式操作，不自动发生；切换前后版本号连续，不归零。

## 连接发现（预留）

- 为上面的混合部署预留连接发现 / 信令接口：将来由文档服务交换本地端与移动端（或其它设备）之间的地址映射，帮它们建立直连（局域网或点对点），之后字节在两端之间直接走。
- 文档服务只做地址交换，绝不承担素材传输流量。
- 现在只留接口，不实现。

## 版本与身份

- 项目每次被修改，项目版本号加一；卡片源码每次被修改，卡片版本号加一。
- 每次写入都带写入者的身份：是哪个用户的哪个页面，或哪个 Agent 的哪个对话。

## 冲突

- **最后写的赢**，不做合并。
- **发生覆盖时，覆盖方和被覆盖方都要知道。** 被覆盖的一方在换成最新版本之前，先把自己那份存成本地备份。
- 某张卡最近的写入者在新版本落地时收到通知；Agent 和用户都可以对某张卡退出跟踪。
- Agent 的写操作带期望版本，和当前版本不符就拒绝，并告诉它期间落地了哪些改动，由它重读后再改。用户在页面上的操作不带期望版本，按到达顺序落地。
- 两个 Agent 在短时间内反复交替改同一张卡时，锁住先写的那一方对这张卡源码的写权限，并通知双方和用户；由用户解锁，或空闲一段时间后自动解锁。

## 离线

- 连不上文档服务时照常编辑，操作攒在本地；恢复后按顺序提交。
- 只有第一条用离线时记下的期望版本做冲突检测。第一条被拒说明离线期间别人改过，整批停下，由用户决定重放还是丢弃。

## 项目文件

- 项目保存成文件（`.proc`）由页面完成，文档服务不写项目文件。页面只在拿到文档服务对最新操作的确认之后才写。

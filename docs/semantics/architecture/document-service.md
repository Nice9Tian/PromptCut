# 文档服务

展开 `../architecture.md` 的「文档服务」角色。从属于 `architecture.md`，与它冲突时以它为准。

## 职责

- 文档服务是项目文档的唯一修改入口。编辑界面和 Agent 都只向它提交操作，由它排序、记版本、通知各方、管理锁。各方手里的项目都是它的副本。
- 它管理：项目信息、每一次操作的接收与分发、锁、覆盖通知、卡片源码、渲染任务队列。
- 它和各方之间是一条长连接，传小消息、要求快速响应。素材字节和预渲染结果不走这条连接，走素材服务。
- 它是通用的轻量文本 / JSON 调度分发中心：路由层不绑定具体业务，渲染任务队列只是挂在它上面的模块之一；以后与渲染无关的文本消息模块也可以挂上来。无论挂什么模块，都只传小的文本消息，不传字节。

## 部署组合

- 文档服务有两种部署：**本地文档服务**跑在本机，**云端文档服务**跑在云端。素材服务同理：**本地素材服务**、**云端素材服务**，见 `asset-storage.md`。
- 无论怎么部署，协议不变：操作和通知只走文档服务，素材字节和预渲染结果都经素材服务读写。
- **多用户协作项目放在哪**：只有两种，谁都能选。
  - **本机**：文档服务和素材服务都在创建者本机。创建者本机不在线时，其他成员打不开这个项目。勾上「多用户协作」时默认放本机。
  - **云端**：文档服务和素材服务都在云端，项目内容、任务队列、内容库、素材和预渲染产物都在那里，成员直接连过去。
  - 两种之间可以随时搬（见 `../workflow/project.md` 的「多用户协作」）。
- **连接路径**：成员连本机项目的主机时按顺序找路，用第一条通的：
  1. 局域网直连：在本网段发现主机，直接连上；
  2. 公网直连：按云端托管服务牵线给的地址直接连；
  3. 云端托管服务中继：往来全部经它转发（见 `../product/hosting.md`）。

  三条都是常规路径，依次更慢，中继最慢、受限速。
- **公网可达性只用来告知**：勾上「多用户协作」时，云端托管服务验证创建者机器能否从公网直连。不可达时提示「局域网外的成员将经中继加入，会受限速」，仍可放本机，不锁任何选项。
- **本机项目不依赖云端**：本机项目的创建、局域网发现与接入都不依赖云端，断网照常工作。可达性验证尽力而为，离线时提示「当前离线，局域网外成员暂时无法加入」，项目照建。向云端托管服务的登记在有网时做，离线就跳过，恢复后自动补。
- 待定（机制）：补登记时遇到项目名重名，怎么处理。
- 切换所连接的服务是用户的显式操作，不自动发生；切换前后版本号连续，不归零。

## 连接发现

- **服务地址下发（已引入）**：素材服务 URL 的动态下发作为基础设施发现功能提前引入。素材服务所在的一方把它的地址上报给文档服务，文档服务再下发给需要它的渲染节点和客户端；上报方断开后，这个地址随之撤回。
- **设备间直连（预留）**：公网直连所需的地址交换归云端托管服务的牵线（见 `../product/hosting.md`），机制在 `docs/plan/direct-connect-plan.md`，现在只留接口，不实现。
- 文档服务只下发地址，不承担素材传输流量；成员直连不到主机时的转发属于云端托管服务的中继，不属于文档服务。
- **局域网发现（已引入）**：本机项目的主机在本网段广播项目名和地址，成员据此走局域网直连，连上它的文档服务和素材服务。这一步不经云端，也不承担任何传输。

## 版本与身份

- 项目每次被修改，项目版本号加一；卡片源码每次被修改，卡片版本号加一。
- 每次写入都带写入者的身份：是哪个用户的哪个页面，或哪个 Agent 的哪个对话。
- 身份来自凭证，不由消息自报。共享项目里，用户由进入时的凭证确定；Agent 沿用它所属用户的凭证，另记它是第几个对话。

## 共享项目与权限

- 共享项目是权限的隔离单位：文档服务按共享项目隔离项目内容、任务和通知，成员看不到别的项目的任何东西。
- 进入方式在创建时二选一：自由进入，知道项目名和项目密码就能进，进入时自报用户名；限定进入，只有创建者名单里的用户名加密码能进。
- 创建者特权只有三项：改项目密码或名单、删项目、踢人，每次都要出示创建者用户名和创建者密码。其余操作所有成员一样。
- 凭证由文档服务核对；素材服务凭文档服务签发的票据放行（见 `asset-storage.md`）。
- 一期不做第三方登录和密码找回。

## 冲突

- **最后写的赢**，不做合并。
- **发生覆盖时，覆盖方和被覆盖方都要知道。** 被覆盖的一方在换成最新版本之前，先把自己那份存成本地备份。
- 某张卡最近的写入者在新版本落地时收到通知；Agent 和用户都可以对某张卡退出跟踪。
- Agent 的写操作带期望版本，和当前版本不符就拒绝，并告诉它期间落地了哪些改动，由它重读后再改。用户在页面上的操作不带期望版本，按到达顺序落地。
- 两个 Agent 在短时间内反复交替改同一张卡时，锁住先写的那一方对这张卡源码的写权限，并通知双方和用户；由用户解锁，或空闲一段时间后自动解锁。

## 离线

- 连不上文档服务时照常编辑，操作攒在本地；恢复后按顺序提交。
- 只有第一条用离线时记下的期望版本做冲突检测。第一条被拒说明离线期间别人改过，整批停下，由用户决定重放还是丢弃。

## 渲染任务队列

预渲染不绑在某一台设备上：本机、局域网或远程的独立渲染主机、在线浏览器模式的页面都可以做**渲染节点**，从文档服务托管的任务队列里取活。

- **只记账，不分配**：文档服务只记每个任务的状态和认领者，不测算节点的算力，不主动把任务派给谁，也不替节点判断它做不做得了。唯一的例外是下文的「指纹前置过滤」。
- **拉取式**：节点在闲时向文档服务认领任务。认领是「比对状态再加锁」一步完成：只有还没被认领的任务能认领成功，两个节点同时认领同一个任务时只有一个成功，另一个换下一个。
- **节点自己挑**：每个任务标明它有多重、要求什么能力（例如要不要本机转码、有没有用户卡或图卡）和渲染环境；节点按自身能力和环境过滤，只认领自己做得了、环境相符的。
- **只把权限关**：文档服务不替节点判断能力，但要按凭证把权限关。节点只能看到、只能认领自己所在共享项目的任务。纯浏览器节点更窄：只能看到、只能认领当前登录用户自己产生的任务，同一共享项目里其他成员的任务也不行；这两条都由文档服务保证，不靠节点自己过滤。
- **指纹前置过滤（特例）**：为防止指纹锁引发并发风暴，允许特定队列（如预渲染队列）基于节点环境指纹进行前置拦截过滤，作为不干涉节点原则的特例：环境指纹与任务要求不符、或这张卡已被别的环境锁定的任务，不发给该节点，也不让它认领。能力过滤仍由节点自己做。
- **谁发布**：需要预渲染结果的一方（编辑界面、Agent）只发布粗粒度的计划任务「给这一版项目做预渲染」。第一个认领它的渲染节点算出要预渲染哪些卡，把细粒度的任务切分后发布回队列。任务按预渲染结果的键标识，同一个结果只有一个任务，重复发布不产生第二份。
- **完成**：节点先把产物推送到素材服务，再向文档服务报完成；文档服务把完成通知发给关心这个项目的各方，它们从素材服务取字节。
- **断开与超时**：认领者的连接断开，或在约定时间内既没报进度也没报完成，它认领的任务回到未认领状态，别的节点可以重新认领。晚到的完成报告按最新的认领为准，旧认领者的报告不作数。
- **队列只在内存里**：队列是可以重建的记账，不持久化。文档服务重启后队列为空，各发布方重连后把自己仍需要的任务重新发布一遍；已经在素材服务里的结果不用重做。
- **任务不带字节**：任务只写要渲染什么（项目版本、片段、帧范围、预渲染结果的内容键），不带项目文件以外的字节。节点按项目版本从文档服务取项目，按哈希从素材服务取素材。
- **离线**：连不上文档服务时，本机的预渲染进程照常为本机的项目做预渲染，不经过队列；恢复连接后照「队列只在内存里」那一条重新发布。
- **查询渲染不进队列**：Agent 的查询渲染和用户交互需要的查询仍在各自所在的位置直接做（见 `rendering.md` 的「查询渲染与预渲染进程」）；队列只管预渲染。

## 项目文件

- 项目保存成文件（`.proc`）由页面完成，文档服务不写项目文件。页面只在拿到文档服务对最新操作的确认之后才写。

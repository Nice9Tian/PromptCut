# 提交与发版

展开 `../04-agent-guide.md`。从属于 04，与它冲突时以 04 为准。写 main 的操作须按 04 原则 4 先得到用户授权。

## 提交

- 提交信息用中文，开头写类别，冒号后写做了什么。常用类别：文档、探针、重构、修、测试、合并。
- 子分支合并进 main 用 `--no-ff`，合并提交写成「合并 <分支或步骤名>:摘要」。

## 构建

- 先提交，再构建。构建产物必须对应一个已提交的版本，不能对应工作区状态。
- 网页构建：`npm run build`（先类型检查，再 `vite build`）。
- 桌面发版：在 `desktop/` 下运行 `npm run release -- --from-head`，源码取自 HEAD。

## 版本号

版本号只在发版时改，不是每次合并都改。

两个版本号分开：

- **应用版本**：根目录 `package.json`，对应 Node 那一半，更新补丁负责更新它。
- **外壳版本**：`desktop/src-tauri/tauri.conf.json`，对应 Rust 外壳、Chrome、ffmpeg、内置 Python，只随完整安装包更新。

格式都是 `0.<内核代次>.<修订>`。改完先问：Node 这一半放到老外壳上，还能不能照常跑？判断时不看改的是不是 Rust，看缺了新外壳会不会出事：加一个菜单项、多一个可选入口，都属于下表第二行。

| 情况 | 怎么进位 | 用户怎么升级 |
|---|---|---|
| 只动了 Node 那一半 | 应用版本末位 +1 | 更新补丁 |
| 动了 Rust，但老外壳上能降级运行 | 应用版本末位 +1，外壳版本末位 +1 | 更新补丁 |
| 动了 Rust 且 Node 硬依赖它；换了 Chrome、ffmpeg、内置 Python；运行时目录布局变了 | 两个版本号的中间位一起 +1 | 完整安装包 |

补丁清单用两个字段拦住装不上的用户：

- `shellGeneration`（外壳版本的前两段，如 `0.2`）：代次不同直接拒绝。
- `minShellVersion`（`desktop/scripts/make-patch.mjs` 顶部手写的常量）：代次相同但外壳比它旧，也拒绝。它只在第三种情况下抬高，回答的是「Node 这一半最低需要什么外壳」，不是「这次顺手编了什么外壳」。外壳换代时要把它挪到新代次的起点。

## 0. 要解决的两个症状

| 症状 | 用户原话 |
|---|---|
| A. Agent 一调渲染（see_frames 之类），界面就卡住，CPU 却不到 5% | 「Agent 调用渲染，直接卡用户的界面，而实际 CPU 占用不足 5%」 |
| B. 项目里一加视频素材就很卡，而且不在导出的时候 | 「只要加入视频素材就会很卡」 |

## 1. 查出来的原因

### 1.1 症状 A：界面和渲染挤在同一个服务、同一条队列上

1. **浏览器连接池被占满。这是主因，已实测复现。**
   - dev server 走 HTTP/1.1：`vite.config.ts` 里没有配 https / http2。Chrome 对同一个源大约只开 6 条连接，代码里自己也写过：「浏览器对同一个源只给约 6 条 HTTP/1.1 连接」（`src/editor/preview/useBakePrefetch.ts:362`）。
   - 编辑器平时一直占着的长连接有 5 条：
     - MCP 事件流 1 条（`src/ai/mcpExecutor.ts:306`）；
     - AI 对话流 1 条（`src/ai/useAiChat.ts:620`）；
     - 3D 视图预烘 2 条（`useBakePrefetch.ts:367` `const INFLIGHT = 2`）；
     - 3D 前台烘焙 1 条（`Scene3DView.tsx:789`）。
   - Agent 再调一个 see_frames，页面就要发 `/api/vision/snapshot`（`src/editor/right/index.tsx`），正好凑满 6 条。
   - **实测**：在一次性的 5231 端口上，先挂 1 条 SSE 和 5 个慢请求，一个轻请求要等 **7702 ms**；只挂到 5 条时是 2 ms。满了之后，界面要加载的一切（模块、素材、接口）都在浏览器里排队，CPU 为零。
   - 雪上加霜的是，页面发出的渲染请求都没有超时（`index.tsx` 的 `/api/cards/dom`、`/api/vision/snapshot`、`/api/vision/bake`，`mcpExecutor.ts` 的 `/api/ai/visual`）。Agent 那边早放弃了，连接却要一直占到服务端渲完。
2. **同步处理 PNG，堵住给界面供模块的 Vite 进程。**
   - 代码：`vite-plugin-vision.ts:996-998`、`:1042-1044` 和 see_frames 的 `shrink`。其中 `:998` 在没有素材层时，会把刚解码的图原样再编码一遍，这一步完全多余。
   - **实测**（pngjs，一张有内容的 1080p 帧）：解码 54 ms、编码 94 ms。see_frames 每帧先后解两次、编两次，事件循环每帧被卡约 300 ms。
3. **Agent 和用户前台排在同一档队列。**
   - see_frames、bake_card、get_gif 都是 priority 1，和 3D 前台烘焙同级（`Scene3DView.tsx:801`），同级按先来后到（`vite-plugin-vision.ts:263`）。
   - 已经在跑的任务不能插队（`:179`「插队只插**还没开始**的」）。
   - 客户端断开时，服务端不撤掉还在排队的任务：`vite-plugin-vision.ts` 里没有监听请求的 close / aborted 事件。
4. **已经隔离好的部分**（证据见审查记录）：
   - Chrome 在独立的 worker 进程里跑（`vite-plugin-vision.ts` fork `render-worker.mjs`）；
   - ffmpeg 一律异步 spawn；
   - MCP 桥没有全局锁（`vite-plugin-ai.ts` 的 `pendingCalls` 按调用 id 分开存）。

### 1.2 症状 B：编辑器预览切换视频的方式太笨

**实测**：采样真实软件（0.4.0，打开了《九箭旅行社》项目）10 秒：

- 服务端 vite 占 0.9% 个核，渲染 Chrome 为 0；
- 编辑器页面（WebView2 渲染进程）占 20.8% 个核、1 GB 内存，GPU 进程占 11.9%。

所以卡在编辑器页面，不在渲染管线。原因按影响排：

1. **每切一个视频片段，就新建一个播放器，再从文件中段 seek。**
   - 代码：`MediaLayers.tsx:134` `key={l.clip.id}`，只挂播放头下的片段，下一段不提前准备；`:99` 的 `preload="auto"` 是在切换的那一刻才开始加载。
   - 素材每 5 秒才有一个关键帧（`mediaSync.ts:11-12` 的注释，引自当时的实测），所以一次中段 seek 最多要解 150 帧才能出画。
   - **实测**（这个项目）：26 个视频片段来自 9 个文件，共 25 次切换：
     - 16 次是同一个文件内部切，但**没有一次在原片里是连续的**；
     - 9 次是换文件；
     - 片段平均 2.95 秒，最短 1.8 秒。
   - 结论：88.7 秒里每 3 秒左右就要付一次中段 seek。只"按素材复用播放器"救不了，因为同一个文件内部切也要跳位置。
2. **拖动播放头时，鼠标每动一下就 seek 一次。**
   - `useScrub.ts:105` 在每个 pointermove 都会 `actions.seek`。
   - 暂停时，只要偏差超过 0.03 秒就立刻 seek，没有冷却（`mediaSync.ts:41`、`:87-91`）。
   - 每次 seek 又是"从关键帧解到目标"，解码器一直在推翻重来。
   - 附带一个 bug：seek 进行中收到的新位置会被丢掉（`mediaSync.ts:85`）。如果最后一次移动恰好落在 seek 期间，最终位置就再也不会补上，画面停在旧的一帧。
3. **播放时整条时间轴每帧重渲**，开销随视频时长增加。
   - store 每写一次就通知所有订阅者（`store/project.ts:90-95`）；时间轴订阅了 `t`（`timeline/index.tsx:34`），子组件都没做 memo。
   - 这不是视频独有的问题，但视频把项目时长撑长了。本计划不展开，列在第 5 节。
4. **导入时整个文件先读进 Vite 进程内存再写盘**（`vite-plugin-media.ts:37-40`）。只在导入那一刻有影响。

**已排除**：导入后不会自动跑镜头识别、听写或主体检测；时间轴不生成缩略图和波形；3D 视图不贴视频；加视频不会让卡片烘焙的缓存失效。

**还没查清**：用户没在播放时，编辑器页面也持续占 21% 个核。播放循环只在播放时跑（`Preview.tsx:121`），所以另有来源，需要在编辑器里做一次性能采样。

## 2. 视频预览：两个修法

### 2.1 修法 1：双缓冲播放器，下一段提前挂好、提前 seek 到位

**做法**

- 每一层画面固定两个 `<video>` 槽位：A 放当前片段，B 放下一个片段。
- 播放头离下一段起点还剩约 1 秒（估计值，按实测再调）时，B 装上下一段的素材，seek 到它的 `mediaOffset` 并暂停。
- 用 `requestVideoFrameCallback` 确认"那一帧已经画出来了"。已实测：Chrome 152 支持这个接口，不支持 `fastSeek`。
- 到了交界处只切显示（B 显示、A 隐藏）并让 B 开始播放，然后 A 退下去准备再下一段。
- 下一段和当前段是同一个文件时，不必重新加载文件：同一个素材的解码器和缓冲可以复用，只多一次 seek。但它仍然要走"提前 seek"这一步，因为这个项目里同文件切换全都不连续。
- 暂停时拖到任意位置，照旧只用 A，行为不变。

**改动范围**

- `src/editor/preview/MediaLayers.tsx`：`VideoLayer` 从"按片段 id 挂"改成"按层挂两个槽位"。
- 新增一个纯函数 `nextVideoLayerAfter(project, t)`，放在 `src/kernel/project.ts` 的 `videoLayersAt` 旁边，配单测。
- `mediaSync.ts` 基本不动，只增加"预备槽位：暂停并 seek 到起点"这种状态。

**验收**

- 在隔离端口上打开这个项目的副本（见第 4 节"怎么测"），从头播到尾，逐个记录每次交界的出画延迟：从片段起点到 `requestVideoFrameCallback` 回调的间隔。
- 目标：25 个交界里，至少 23 个延迟 ≤ 1 帧（33 ms）。
- 对照：改前同样测一遍，记下基线。

**风险**

- 两个 `<video>` 各占一套解码器。1080p H.264 在 WebView2 里走硬件解码，两路没有压力；叠了交叉溶解的地方最多四路。估计可接受，要实测。
- 片段短于"提前量"时（最短 1.8 秒），B 可能还没 seek 完就轮到它。这时退回"切换时 seek"，不比现在差。

### 2.2 修法 2：拖动节流，松手补一次精确位置

**做法**

1. **seek 按帧合并。** pointermove 只更新"想去哪"，每个 animation frame 最多下发一次。前一次 seek 还没完成（`el.seeking`）就不发新的，只记下最新目标。
2. **seek 完成后补一次。** 监听 `seeked` 事件：如果"想去的位置"和当前位置差超过一帧，立刻再 seek 一次。这同时修掉第 1.2 节第 2 条那个"最后位置被丢掉"的 bug。
3. **松手时一定落到精确位置。** 在 pointerup 里强制做一次同步，保证停下来的画面就是播放头所在的那一帧。
4. 拖动期间视频画面允许比播放头晚一两帧（估计值），换来手感跟手。卡片层照旧实时渲染，不受影响。

**改动范围**

- `src/editor/timeline/useScrub.ts`：合并 seek，pointerup 时补一次。
- `src/editor/preview/mediaSync.ts`：暂停状态下加最小间隔；`seeked` 之后重新判一次。
- `src/editor/preview/MediaLayers.tsx`：挂上 `seeked` 监听。

**验收**

- 在这个项目上，用脚本匀速拖动 3 秒（每 16 ms 一个 pointermove）：
  - 统计实际下发的 seek 次数：目标 ≤ 60 次，现在大约 190 次（估计，改前实测记下基线）；
  - 页面长任务：目标没有超过 100 ms 的。
- 松手后，画面在 300 ms 内和播放头对齐。
- 专门测"最后一次移动落在 seek 中间"这种情况：停下后画面必须是最终位置。

**以后可选的根治办法**（这次不做）：导入时生成一份关键帧密集的代理文件（例如每 0.5 秒一个关键帧），预览播代理，导出用原片。那样修法 1、2 里 seek 的成本都几乎为零。代价是导入要转码，还要多占磁盘。

## 3. 三端分离：数据管理 / 交互界面 / 预渲染

### 3.1 讨论里定下来的规则（用户原话）

- 「把数据管理，用户交互界面（附带一个及时交互离屏渲染），预渲染。拆成三个部分解耦开」
- 「Agent 从数据管理中拉取信息，走预渲染通道。用户界面需要及时响应的走自己的离屏渲染」
- 「卡片交给数据管理」
- 「烘焙全都借预渲染的 chrome。但是 Agent 请求优先级排高」
- 「用户的前台烘培是在交互界面里面的常驻离屏渲染，这个优先级最高，Agent 等没有用户体验，但是用户一毫秒都不应该多等」

最后一条修正了前一条：**用户前台烘焙不进预渲染池**，由界面自己常驻的离屏渲染器专门处理。预渲染池里排的是 Agent 请求和空闲预烘，Agent 优先。

### 3.2 三部分各管什么

```
                 ┌──────────────── 数据管理 ────────────────┐
                 │ 项目(带版本号) · 卡片源码 · 卡片模块(按哈希)  │
                 │ 渲染缓存索引 · 编辑校验与备份 · 用户改动层      │
                 └──────┬──────────────────────────┬────────┘
             订阅变更 / 写入                    读项目+卡片 / 写入
                        │                          │
   ┌──────── 交互界面 ───────┐              ┌──── Agent ────┐
   │ 2D 预览:实时 DOM        │              └──────┬────────┘
   │ 常驻离屏渲染器(专用)    │                     │ 渲染请求(带版本号)
   │  · 最高优先级 · 只保留最新 │              ┌──────▼──── 预渲染 ─────────┐
   │  · 页面常驻,原地换数据    │  缓存命中 ◀── │ 独立进程 + 独立端口          │
   └─────────────────────────┘              │ Chrome 池:Agent > 空闲预烘   │
                                            │ 断开即撤单 · 低于正常优先级    │
                                            │ 导出:卡片透明层 + ffmpeg 合素材│
                                            └────────────────────────────┘
```

**数据管理**

- **项目**：带单调递增的版本号。
  - 第一步做**只读镜像**：页面每次改动，把项目连同版本号推一份过来。Agent 的读取和渲染（get_project、see_frames、get_gif、bake_card、inspect_card_dom）直接找数据管理和预渲染，不再经过编辑器页面。
  - Agent 的写操作仍经过页面，撤销/重做保持不变。
  - 现在的出处："时间轴的真身在浏览器 store 里"（`src/editor/right/index.tsx:1744`）。Agent 的一切都要经过页面中转，这正是它能卡住界面的结构原因。
- **卡片**：
  - 源码归数据管理，包括内置卡、Magic UI 适配卡、用户卡，以及卡片用到的 `src/parts` 文件。现有的编辑校验（`checkSourceEdit`、备份）搬过来。
  - 编译：按依赖闭包（`vite-plugin-cards.ts` 的 `importClosure`）用 esbuild 打包，文件名用内容哈希 `/cards/<hash>.js`，带 source map。
  - React、motion、three 等依赖不打进每张卡。界面和预渲染都先加载同一个运行时包，再用 import map 指过去，避免页面里出现两份 React。
  - 改动通知：卡片一改，就推送"X 卡的哈希变成了什么"。界面换掉这一个模块；预渲染按哈希让缓存精确失效，不再像现在这样一有文件变化就全清。
  - **内置卡作为只读底版随包发布**，Agent 和用户的改动存到数据管理的用户数据目录里。这样打补丁就不会覆盖掉这些改动（[after-0.4-plan.md](after-0.4-plan.md) 第 1 条）。
- **渲染缓存索引**：键是「项目版本 + 卡片哈希 + 时刻 + 画面参数」。

**交互界面**

- 订阅数据管理的变更。2D 预览照旧实时渲染 DOM。
- **常驻离屏渲染器：两台 Chrome 热备轮换（A / B）**。专给用户的前台烘焙用（3D 视图的贴图、拖动播放头时要的那一帧），**不和任何人共用、从不排队**。
  - 用户原话：「交互端需要留两个 chrome 渲染，永远保持一个是热状态……如果 A 正在渲染，这时候接到了新的任务，立刻交给热状态的 B，同时清空 A，之后 B 在渲染，A 热状态待机」。
  - **为什么要两台**：一台 Chrome 被打断之后，页面状态已经不可信，必须换一张新页面才能再用（`render-worker.mjs:128`「这个页面已经不可信了」）。只有一台的话，新请求就得等它换完。**实测**（[hybrid-sampling-plan.md](hybrid-sampling-plan.md) E0）：换一张新页面约 310 ms，冷启动整个 Chrome 5.6 s；往已经就绪的空页面里灌项目只要 3~4 ms。两台轮换，新请求永远落在已经就绪的那台上，只付这 3~4 ms，换页的 310 ms 放到后台去付。
  - **"清空"具体做什么**：默认是换页，即关掉旧页面、打开提前开好的全新空页面。现成的零件是 `export-frames.mjs:339-355` 的 `preload` / `resetWith`，以及 `render-worker.mjs:114-116` 的 `preloadNext`。只有页面卡死、超时或崩溃时，才整个重启这台 Chrome，这时另一台照常顶着。两台用两个独立进程而不是同一个 Chrome 里的两张页面，就是为了这一点：一台崩了不连累另一台。
  - **调度规则**（下面的毫秒数都是估计，按实测再定）：
    1. 新请求到达、另一台是热的：交给热的那台。正在渲的那台如果只做了一小段（例如已渲不到 150 ms），就打断并清空；否则让它渲完，结果照样显示，渲完再去清空。
    2. 新请求到达、两台都不是热的（一台在渲，一台正在换页）：新请求放进"待办"，只保留最新一个，后来的覆盖先来的。哪台先变热就接哪个。
    3. 第 1 条里"做了一小段才打断"必不可少。拖动播放头时每秒会来几十个请求，如果每来一个都打断正在渲的那台，两台会一直在"打断、换页"之间来回，一张图都出不来。这样安排后，拖动时屏幕上是"不断刷新、只晚一点点"的画面，停手时落在最终位置。
  - 先查缓存，命中就直接显示；没命中才渲，渲的过程中显示上一张贴图。
  - 两台进程都用正常优先级。
- 渲染本身的耗时（推起跑段加截一张，零点几秒，估计值）省不掉。能保证的是：不排队、不重新加载页面、能命中缓存就不渲。

**预渲染**

- **独立的进程和端口**。Agent 的渲染请求不再从编辑器页面发出，也就不会占用界面那个源的 6 条连接。
- **一个 Chrome 池**：Agent 请求优先，空闲预烘其次。有 Agent 请求在排队时，预烘整个暂停。
- **客户端一断开，就撤掉它还在排队的任务**。
- PNG 的解码、合成、编码都挪进渲染子进程，不再占 Vite 的事件循环；顺手删掉 `:998` / `:1044` 那次多余的编码。
- 进程优先级设为"低于正常"，池子的大小给界面的常驻渲染器留出核。
- **完整导出也走这里**：Chrome 只渲卡片的透明层，素材交给 ffmpeg 合成，照 see_frames 已有的 `cardsOnly` + `composeFrame` 做法（`vision-compose.mjs:16-21`）。
  - 现状是完整导出仍然把视频挂进 Chrome、逐帧 seek（`ExportView.tsx` 的 `visualMedia` 和 `__pcSetT`）。
  - 而且 `/api/export` 不传 `--workers`，命令行默认是 `'auto'`（`scripts/export-frames.mjs:783`），最多会开 4 个分片，每个分片都从第 0 帧开始 seek。

**两种渲染器必须逐像素一致**：同一套 `export-frames.mjs`、同一个 chrome-headless-shell 版本、同样的启动参数。这样预烘出来的缓存和常驻渲染器现场渲出来的可以混用。

### 3.3 优先级总表

| 请求来源 | 走哪里 | 优先级 | 排队 |
|---|---|---|---|
| 用户前台（3D 贴图、拖动时要的那一帧） | 界面的常驻离屏渲染器（A / B 两台热备轮换） | 最高，专用 | 从不排队：交给热的那台；两台都忙时只保留最新一个 |
| Agent（see_frames / get_gif / bake_card / inspect_card_dom） | 预渲染池 | 池内最高 | 排队超时（现在是 25 s）；断开即撤单 |
| 空闲预烘 | 预渲染池 | 最低 | 有 Agent 请求时暂停 |
| 完整导出 | 预渲染池 | **最低**（用户定：「导出优先级最低，不过这时候 Agent 和用户应该也停止工作了」） | 默认单进程，最多占池子的"总数 − 1"个槽位，永远给 Agent 留一个；空闲预烘在导出期间整个暂停 |

导出排最低，但有两处要写死：

1. **导出是一趟长任务，开跑之后打断不了**（同 `vite-plugin-vision.ts:179`「插队只插还没开始的」）。所以"最低"光靠排队顺序不够，还要限制它占的槽位：导出最多用"池子总数 − 1"个。这样导出途中来的 Agent 请求总有空槽，不用等导出跑完。默认单进程导出本来就只占 1 个，这条主要防以后开分片时把池子占满。
2. **导出期间暂停空闲预烘**。预烘是给 3D 视图"猜着先烘"的，导出时用户多半不在看；如果让它和导出按优先级正常排，导出反而要排在这些投机性的活后面。所以导出期间实际的顺序是：Agent → 导出，预烘暂停，导出结束后恢复。平时 Agent 和用户都停着，导出就能用满池子（留出的那一个槽位除外）。

## 5. 风险和没解决的问题

- **共享运行时 + import map**：导出页、离屏渲染页、编辑器页三处都要能跑通。依赖的边界要划清：哪些进运行时包，哪些随卡片一起打包（`src/parts`、`src/kernel` 里的共用代码）。这一条先做雏形验证。
- **界面不再用 Vite 热更新卡片**：换模块会让卡片整个重新挂载。卡片画面只由 `t` 决定，影响应该很小，但正在编辑的那张卡会闪一下。
- **常驻渲染器的内存**：两台热备要多占两个 Chrome，合计约 0.6~1.5 GB（单个的数据：`vite-plugin-vision.ts:194` 的注释写"一个约 300~500MB"，另有实测约 750 MB）。内存紧张的机器上可以退成一台加一张备用页，也就是现在 `render-worker` 的做法。那样仍然不用冷启动，只是新请求要等正在渲的那一趟被打断、换上备用页，多等几毫秒到一趟的时间（估计），而且一台崩了就没有顶班的。
- **两台同时在渲会抢 CPU**：拖动时 A、B 可能同时在跑。它们都是正常优先级，预渲染池是低于正常，所以抢的是预渲染池的 CPU，而不是界面的。
- **位置相关的 3 张卡**（mu-word-rotate、versus-card、lottie-bodymovin，见 `scripts/card-audit.mjs` 的审计）：它们挪到起跑线上渲会和原位置不一样。在"缓存按哈希加时刻"之前要先修掉。
- **时间轴每帧整条重渲**（第 1.2 节第 3 条）：不在本计划内，但视频长的项目上会一直存在，需要单独排期。
- **空闲时 21% CPU 的来源**：还没查清，要在编辑器里做一次性能采样。
- **导出的槽位限制要实测**：导出最多占"池子总数 − 1"个槽位。池子只有 1 个槽位的机器（`maxConcurrentRenders` 按核数和空闲内存算，最少是 1）留不出这一个；这种机器上导出期间来的 Agent 请求只能等导出跑完，或者 Agent 渲染临时借用界面热备里空闲的那台。两条路选哪条，等实测后再定。

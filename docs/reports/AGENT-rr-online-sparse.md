# AGENT 报告：rr-online-sparse（稀疏流三：在线页面打开项目测量时先产稀疏版）

分支 `claude/rr-online-sparse`，工作区 `.worktrees/rr-online-sparse`，从 `main` f3e7d5e7 分出；交活前把 `main` 合进来两次（563cdbec、162a72be），都没有冲突。端口只用了 27020～27059。

文中的词：「稀疏版」是一条轨道流里每个分段（15 帧）只截第一帧的那一版，「满密度版」每帧都截，两版同一个键；「本页产流」指在线页面不经任务队列、自己用后台舞台产单卡流（上一块「甲二」，`src/online/pageStreams.ts`）；「切分方」是认领清单计划、切成细任务的节点（桌面预渲染进程、渲染主机）；「清单计划」是在线页面测量落定后发布的、带自己判重片段清单的计划任务；「遮罩」是打开项目时盖住编辑器的加载遮罩（`ProbeGate`）。

## 1. 做了什么

### 一、测量时就产稀疏版

- `src/editor/probeRunner.ts`：加一个口子 `setCardMeasuredHook`。遮罩挡着的那一轮里，每测完一张卡、记录并进分派表之后调它一次并等它回，带上「身份与这张卡相同的全部片段」和这一轮遮罩的编号 `maskRound`（打开项目是 0，切帧率重走遮罩时加一）。不挡界面的补测不调。没人接（桌面版）时行为一个字不变。
- `src/online/pageStreams.ts`：新增 `measure(req)`。次序：等本页当上节点（拿到指纹、探到编码器，最多 `MEASURE_READY_WAIT_MS` 3 秒）→ 用这一版已确认项目算这张卡的单卡流（`planPageStreams`，键与切分方相同）→ 每一份稀疏流任务：先查（自己的键、层表里别的候选，稀疏或满密度有一版就算有）→ 没有才把本页的那一行并进层表、产（`stride` = 一个分段的帧数，宿主的 `bakeStream` 顺带量位置矩形）→ 写清单 → 叫在线来源认这个结果键。这条路不等清单计划、不问有没有切分方、不看闲时闸（遮罩下用户动不了；页面隐藏照旧中止）。只做稀疏的一趟。
- `src/editor/browserNodeHost.ts`：接上口子（`onCardMeasured`）：判重的片段取 `deps.heavyClips()`（与清单计划的清单同一个函数，`Preview.tsx` 的 `heavyCardClips`），项目取此刻文档服务确认的那一版并按版本号留存。**render 连接在测量落定之前就开**，照常报到拿指纹；测量落定之前节点不认领、本页闲时那条路不动（`settled` 为假时两边的 `isIdle` 都是假）。见〔裁〕一。
- 产的东西与切分方、桌面的逐字段相同：任务用 `pageStreamTasks(spec, { density: 'sparse' })`（上一块已与 `split.mjs` 对拍），清单走同一个 `streamManifest` / `putStreamManifest`（先取已有的合并，不降级、位置矩形带到满密度），块推素材服务 `px`。
- `src/editor/stageBake.ts`：`bakeFrame` 多收一个 `ahead`（这一帧做完后先发给舞台的那一帧）。稀疏的一趟先发的是下一个分段的第一帧，不再白做「本地帧加一」（甲二报告点名的那一处）。

### 二、遮罩等稀疏版，最多 50 秒

- 常量只有一处：`src/online/pageStreams.ts` 的 `MEASURE_SPARSE_MAX_MS = 50_000`。
- 墙上时钟（`Date.now`），从这一轮遮罩下第一次调 `measure()` 起算。到时：在产的做完当前这一帧就停（当前帧 1 秒内做不完照让路的时限中止），`measure()` 当场回 `deadline`，这一轮之后再调一律马上回。已经推完的分段按任务 id 留着。
- 没产完的归闲时那条路：清单计划发出去以后，同一个任务 id 接着做，只补缺的分段。
- 时钟由宿主每 250 毫秒的节拍推（`tick()`），所以精度是一拍。

### 三、之后要补的只在闲时产，稀疏排在满密度前面

- `pageStreams.ts` 的缺省两趟 `PAGE_STREAM_PASSES = [稀疏, 满密度]`。挑下一段时只在「还有没落定任务的最前面那一趟」里挑：稀疏的某一段在退避，满密度的也等着。稀疏的一趟的任务是稀疏流任务（id 末尾 `:sparse`）。
- 先查按这一趟的密度认（`lookupOwn` / `lookupOther` 多一个 `need.dense`）。
- 闲时闸没有动：播放、拖动、离上一次交互不到 500 毫秒、后台舞台有更急的活、页面隐藏时都不产。
- 有切分方接了清单计划时本页照旧不产（稀疏流任务经队列发给本页的节点，名次 30 高于满密度的 10，上一块做的）。

### 四、播放保活

- 发的是 render 连接上的 `node.active { busy: 'play' }`，发给文档服务的任务队列，间隔由队列在 `node.welcome.activeIntervalMs` 里给（10 秒）。机制是现成的（M7 的「报忙」）：队列对一把卡片锁算闲置时，把锁定方节点最后一次 `node.active` 的时刻也算进去；闲置超过 30 秒、锁定方又还有没做完的任务，切分方才接手（接手会把本页那一份作废、另一种环境从头产）。
- 原来播放、拖动而后台没活时不发，所以本页认领着一张卡的流任务、用户连着播放半分钟以上，这张卡就会被接手。现在 `browserNodeHost.ts` 的 `busy()` 在播放或拖动时回 `'play'`。页面隐藏、父页 rAF 断档时照旧不发。
- **等着本页结果的别的页面**：页面与页面之间没有认领，也就没有「被当成掉线而接手」这回事（甲二的〔裁〕6）。别的页面每一段开工前、产的途中每 5 秒都按产物先查；本页在播放而没产完时，另一个闲着的页面会把缺的做出来，本页回来先查到就不重产。所以这一侧没有东西要保活，没有加页面之间的心跳。

### 五、`noteQueueEvent`

`src/render/snapshotSource.ts` 那条正则放宽成 `^(?:snapshot|stream):(.+):\d+-\d+(?::sparse)?$`；`src/render/onlineStreams.test.mjs` 里一处改成用 `:sparse` 结尾的 id 走这条路。

### 六、手机身份不产

没有放开：宿主只在 `online && !lowMem` 时启动，口子由宿主接；不当节点的页面（非 Chromium、退回单舞台、开发构建）进口子就回（`no-node`）。探针里加卡用的那个非 Chromium 页面测量了三张卡、口子被调、一帧没产。

2. `src/editor/Preview.tsx`（道三）：把清单计划里算「判重的片段」的那几行提成模块级函数 `heavyCardClips`，给宿主多传两个依赖。
3. `scripts/probes/page-stream-probe.mjs`：见第 3 节。

`src/render/streamPlayer.ts`、`Stage.tsx`、`StageView.tsx`、`snapshotFeed.ts` 没有动；流的计划与清单格式、本机预渲染进程没有动。

## 2. 〔裁〕

都是三级（用户看不出区别），语义文档没有动。

- **〔裁〕一：render 连接在测量落定之前就开，但不认领。** M7 契约第 2 节写的是「测量落定才当节点」。测量时产流要这台浏览器的环境指纹，指纹只有文档服务在 `node.welcome` 里给。所以改成：别的条件都成立、只差测量没落定时先连上、报到；认领和本页闲时那条路仍等测量落定。测量期间后台舞台不被队列的活占着，这一点没变。副作用：测量期间节点照「报忙」发 `node.active { busy: 'stage' }`。
- **〔裁〕二：50 秒只管遮罩下产稀疏版，不截断测量本身。** 时钟从第一次等稀疏版起算，中间夹着的后面几张卡的测量时间也算在里面；到时以后还没测的卡照常测完才撤遮罩（语义：「太慢」按单帧判，不按整趟的累计时间截断）。所以「到 50 秒就先进编辑」在拖慢的卡排在最后测时成立；排在前面时，遮罩是「50 秒 + 剩下几张卡的测量」。另一种读法是 50 秒到了连测量也不等，那样没测的卡要按声明兜底分派，和「遮罩下测完才进编辑」冲突，没有这样做。请用户过目。
- **〔裁〕三：测量时这一趟不问有没有切分方。** 语义原文「打开项目测量时，对本页能单独产流的重卡先查素材服务，没有才自己产一套稀疏版」没有带「线上没有切分方」这个条件。后果：桌面应用同时在线并且自己能产这条流时，它可能按自己的指纹另产一套（稀疏加满密度），本页测量时产的那一套就白产了；画面不会错。
- **〔裁〕四：测量的第一趟后面原有的「快照趟」没有撤。** 语义说第二趟是产稀疏流；现有的快照趟受一拍预算截断、每张卡 0～1 帧，只记三段耗时，在线页面不转发。撤它会让成本记录里那三个数变成 0，不在这一块的范围里，留着。
- **〔裁〕五：成本记录命中、这一轮没测的重卡不在遮罩下产**，归闲时（照 `html-snapshot-removal-dryrun.md` 第 4.3 节）。成本记录全命中时遮罩不出现，也就没有测量时这一趟。

- 乙（第二个浏览器）后进来：遮罩 3.5 秒，口子 3 次都 `ok`，产 0、查到已有 3；编码器 0、送帧 0、推块 0、往 `px/` 的写请求 0；播放时画的是甲产的流。

**slow（一张快的重卡，一张每帧烧 80 毫秒、20 秒长的重卡，稀疏版一趟约一分半）**

- 遮罩从第一次等稀疏版起 50129 毫秒撤下（暂停前那一遍是 50263 毫秒），编辑界面在。那一次以 `deadline` 收场，`left` 3 份任务；快的那张 `ok`。
- 进编辑时慢的那条流清单里只有 16 个分段（共 40 个）。之后闲时在清单计划的那一份记账下接着产稀疏版；第一次满密度开工在进编辑 121.7 秒以后，那时稀疏 6 份任务都落定（3 份 `have`、3 份 `produced`）、清单里 40 个分段都是稀疏版带位置矩形、此前满密度一段没产。全程节点认领 0。
- 「遮罩下推完的分段不重做」：两遍里到时的那一刻正做着的那份任务都刚好一个分段还没推满，所以这一条在 `slow` 里没有被强制检查（探针写成有才查）；`solo` 里拖动让路之后回来 `resumedSegments: 2` 盖着同一段代码。

**solo / splitter / desk**：改了期望——空项目里加第一张卡时遮罩照样出现一轮，所以稀疏版在测量时产，满密度那一趟才等 5 秒、让路；`splitter` 里稀疏版由本页在测量时产（开工次数 = 测量时产的段数），清单计划发出去以后本页一次不开工、流的满密度经队列产。`solo` 最后一遍：测量时产 2 段、满密度开工时计划发出去 5790 毫秒仍是 `open`、`resumedSegments` 2、像素 0.069%（对照 1.2%）。

探针自己的两处毛病（产品代码没有为此改）：停着时这张卡的流轨道会留着（「暂停和拖动贴流」之后），原来等「轨道撤掉」的参照截图有时等不到，改成看包裹层没被抑制；拖动前等「推完两个分段」现在要从满密度那一趟开工时的数起算。

## 第 1 处：粒子卡往回跳以后停下，画面不是这一刻的

### 根因

粒子引擎（tsParticles 4.4.0）有两样东西是**全局的**，所有容器共用：

1. **随机数源只有一个。** `setRandom` 换的是引擎模块里的那一个函数，谁后调谁生效。
2. **容器按名字互相顶替。** `Engine.load` 发现同名的旧容器就先销毁它。不传名字时取的是 `element.id`，我们的 div 没有 id，于是所有容器都叫空串。（`particles.tsx` 里原来的注释说「load 先拿一个随机数给容器起名」，在这个版本上不成立：`params.id ?? element.id ?? 随机名`，空串不是空值，走不到取随机数那一支。）

而装一个容器是异步的（`load` → `start` → `init`，十几个 await），**销毁不会让它停下**：`Container.init()` 只在入口查一次 `destroyed`，被销毁的容器照样把粒子排完，照样从「此刻的」随机数源里取数。

暂停着在时间轴上往回点时，舞台的 `setTime` 是一个同步块，里面先后做两件事：

1. `flushSync(setT)`：把往回的 t 交给旧组件。粒子没有倒带，旧组件就开始重装（播种、发起第一次 `load`，在飞）。
2. 按片段重挂载这张卡（向后跳的定位配方、钉重卡时追帧的起步）。旧组件卸载时只摘了监听，那次 `load` 掐不掉；新组件播种、发起第二次 `load`。

之后两次装载在微任务里交错：第二次 `load` 把第一次的容器当同名销毁，可第一次的 `init` 还在走，从新组件刚播好种的随机数里取走了前 840 个（120 个粒子，每个 7 个）；新容器拿到的是第 841 个起。粒子排布因此和这一刻的毫不相干，而且每次都稳定地错成同一张。

取证的办法：临时在 `particles.tsx` 里给每次播种的随机数流计数、记下每次 `particlesSetup` 事件（没有提交），探针每到一处把记录打出来。往回跳那一次的记录（第 4 次播种的那份流）：

```
reload → mount#3 → cleanup(reloading: true) → mount#4
setup  容器已销毁、不在文档里  各流已取数 [#3: 0] [#4: 840]      ← 被顶替的那次装载,取的是 #4 的数
setup  新容器                  各流已取数 [#3: 0] [#4: 1680]     ← 新容器拿到的是第 841～1680 个
```

干净的一次装载是 `[#n: 840]`。

「再往前挪一步就对了」也对得上：钉成重卡时每次停下都按片段重挂载、从入点重推；往前挪时第 1 步不会触发旧组件重装，没有那次在飞的装载，重挂载出来的就是干净的。

### 改了什么

`src/cards/native/particles.tsx`（`ParticlesView`，粒子卡、53 张粒子封装卡、粒子部件共用这一份）：

- **装容器全模块排队，一次只装一个。** 前一次排完粒子（或失败）之后才开始下一次，随机数源在一次装载期间只属于它。
- 排上了还没开工就被作废的（卸载、配置换了）直接跳过，一个字都不装；晚一个微任务开工，所以「往回拖紧接着被舞台重挂载」的那一次来得及跳过。已经开工的等它排完粒子再销毁。
- **每个容器一个自己的名字**（`pc-particles-<序号>`），互不顶替。
- **每个容器一份自己的随机数流**：推进（`stepTo`）时换上，推完把源还给正在装的那一次。几张粒子卡同屏时各走各的。
- 装载失败现在会报到 `beginFrameWork` 的 `fail`（以前 `load` 失败只打一行警告，那张卡的「就绪」永远等不到）。

单张卡取随机数的次序和以前逐个相同（播种 → 装载时取 → 推进时取，用的是同一份；起名本来就不取），所以单张粒子卡的画面一个像素都不变，见下面「改前改后」。

`src/render/Stage.tsx`（一行）：卡片包裹层的 key 和传给组件的 `playToken` 由 `remountGen ?? playToken` 改成 `playToken + (remountGen ?? 0)`。查第 1 处时在包裹层节点上留记号量出来两处漏挂：

- 舞台的 `playToken` 从 1 起，按片段重挂载的代数第一次也是 1。新开的可见舞台上，每张卡的第一次按片段重挂载 key 没变，等于没挂。（这反而让 `main` 上粒子卡的第一次往回跳碰巧是对的：没有重挂载，就没有那次交错。）
- 一张卡按片段重挂载过之后，它的 key 只认 `remountGen`，整舞台的 `playToken` 再涨也不动它。这个舞台转到后台做整场景补跑（`render(jump)`）、探针复位时，这张卡不再跟着整台重挂载。

两个代数都只增不减，相加之后每次重挂载都严格变大；没有按片段的代数时就是 `playToken`，导出页和 legacy 一个字不变。这一处我没有找到别的卡因此画错的实例（抽查的卡里 `vtOk` 为真的只有粒子卡、`scene-3d`、打字机，它们不靠重挂载也对），改它是因为它明摆着和「重挂载定位配方一步都不许省」的写法不符，而且探针量得出来。

### 两张粒子卡同屏（顺带修好的）

名字都叫空串的后果不只是往回跳：**同一时刻挂着两张粒子卡时，后装的那张会把先装的那张的容器销毁掉。** 在 `main` 上：

- 预览里其中一张卡没有画布（探针取不到活画布，`shot: "no-canvas"`）；
- **导出直接失败**：`scripts/export-e2e.mjs` 导一个两张粒子卡重叠的项目，报「控件、字体或图片在 20 秒内未就绪，已停止截图」，0 帧。

`scripts/probes/stream-probe-project.mjs` 文件头记过这件事（「没有用两张粒子卡」），当时归因于「容器 id 取自引擎的共享随机数」，实际是空串。修后两张各画各的，导出 90 帧、两趟逐像素相同。

按 `src/render/cardSourceVersion.mjs` 的算法实算（卡片源码表是 `src/cards`、`src/parts`、`src/render`、`src/kernel` 四个目录，按 `id: "<卡号>"` 找入口文件，再跟相对导入）：

## 第 2 处：手按着标尺不动时快照贴不上

### 根因

和任务书写的一致，在代码里核对过：`pickForSetTime` 把节流的起点记在发 `setTime` 的那一刻（`base.lastSentAt`）；这一帧的字节手里没有就当场去取，取到之后经 `onArrive` 叫宿主重投；`deliverSnapshots` 里 `now - lastSentAt < 33` 直接 `return 0`。手按着不动时再没有别的事件来投。

量的时候另外看到一件事：预渲染还在干活时（就绪索引的 SSE 每来一条消息父页都会重投一次），被挡掉的那一次会在几百到一千多毫秒后被**顺带救回来**。所以这个毛病在预渲染安静之后才稳定地露出来，探针为此先等轨道流满帧、再等就绪索引安静。

### 改了什么

`src/editor/snapshotFeed.ts`，集中在 `deliverSnapshots` 一处，加一个小函数 `retryAfterThrottle`：

- 不在播放、被节流挡掉、而且真有东西要换（手里有字节的新帧，或要摘的层）时，约一个到点的重投：过了节流窗口叫一次 `onArrive`（和字节到货走同一个口子，由宿主按那时的播放头重算）。每个 iframe 至多挂一个；到点时窗口又被新的 `setTime` 推后了，那一次投递会再约一次。
- 播放中不约（下一拍自己会投）；没有东西要换也不约（不多花一次重算）。
- 同一类的另一处一并补上：一包 2 MB 装不下、留到「下一拍」的那几张，停着的时候没有下一拍，同样约一次补投。
- `stopSnapshotFeed` 时撤掉挂着的定时器。

`src/editor/Preview.tsx` 没有动。缺省行为（节流 33 毫秒、一次一包 2 MB）没有变。

单测 `src/editor/snapshotFeed.test.mjs` 加 4 条：窗口里到货过了窗口会重投；到点时窗口被推后会再约；播放中、没有东西要换时不约；2 MB 装不下的靠补投投完。

### `seek-back-exact-probe.mjs`（第 1 处）

    node scripts/probes/seek-back-exact-probe.mjs [--port 7484] [--cards a,b] [--modes natural,heavy,swap] [--survey]

五个用例：`particles`、`particles-snow`、`particles-life`、`scene-3d`、`particles-pair`（两张粒子卡同屏）。每个用例单独一个项目，不播放，在时间轴上点 13 次（往前跳、往回跳、挪一帧、回到第 0 帧），每次等回到精确活渲、画面稳住再取活画布的像素（1920×1080，不是截图）。每个用例走三种分派：照页面自己测的记录（`natural`）、钉成重卡（`heavy`，可见舞台里按片段追帧）、钉成重卡并改成只认全局时钟（`swap`，后台舞台整场景补跑再互换）。

断言：

- 往回到达的画面与往前到达的同一帧**逐像素相同**（7 对：`back37`、`back37b`、`back59`、`step38`、`back0`、同一帧两次往前到达 2 对）；
- **对照**：第 37 帧与第 59 帧不同的像素不少于 1000 个。主断言是「一个像素都不差」，对照证明这把尺子在两个不同的帧之间量得出差别（实测 17797～296163 个像素不同，按有内容的像素算平均差 13.6～142.6）；
- 每次取像素时这张卡是活渲，第 0 帧之外画布不空（两张卡的用例两张各自不空）；
- 舞台说重挂载了（按片段的代数涨了，或后台整场景补跑后互换），包裹层就是新挂的 DOM 节点。

### `scrub-hold-snapshot-probe.mjs`（第 2 处）

    node scripts/probes/scrub-hold-snapshot-probe.mjs [--port 7487] [--hold 2000]

一张钉成重卡的粒子卡，等 180 帧快照就绪、轨道流满帧、就绪索引安静。在标尺上按住鼠标（真的指针事件），挪到 24 处、每处按住 2 秒：

- 照实际速度 12 处；
- 控制到货时刻 12 处：用 `snapshotFeed.ts` 给测试留的口子（`setSnapshotSource`）包一层快照来源，让字节正好在开始取之后 1、5、9、13、17、21、25、28 毫秒（节流窗口里）和 45、60、100、200 毫秒（窗口外，作对照）到货。

每处都是之前没取过字节的帧。断言：落点是目标帧、`setTime` 不带 settle、拖动标志在；按住的这段时间里贴上的是**这一帧**的快照（舞台快照平面里那张图的签名与父页取到的这一帧的字节一致，挂着上一处的旧快照不算）；贴上之后没有掉下来；控制到货的 8 处确实落在窗口里。

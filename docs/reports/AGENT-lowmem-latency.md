# AGENT-lowmem-latency 报告

分支 `claude/lowmem-latency`，worktree `.worktrees/lowmem-latency`，基于 main c718be6，收尾前合了 main 211695d。任务：M8 遗留 L22（C10a 验收第 3 步「改一处后，低内存档手机拿到新的预渲染小尺寸」本机 157～304 s、外网 330.8 s，没细查）。给 `c10a-demo-probe` 第 3 步加时刻分解，本机替身跑轮次，查慢在哪，改法小就修。端口只用 5800～5805，预渲染进程自选空端口。

**负载**：全程同机有十来个子智能体在跑，CPU 很忙；同一张卡 60 帧一段的渲染耗时在 23～141 s 之间摆动。下面的时间只作相对比较。

## 结论

1. **「157～304 s / 330.8 s」量错了对象。** 旧判据是「手机请求了第 3 步之前没见过的 `px/` 哈希」。但第 3 步改的是重卡的 `probeSalt`，卡片代码不读它，新键下的小位图与旧键**逐字节相同、哈希相同**（第 1 轮：新键 39 个不同哈希里 22 个第 3 步前手机已取过），手机缓存命中、根本不再请求。旧判据量到的第一张「新 px」其实来自同一步里新放的那张轻卡的**补渲**产物——补渲按语义排在全部普通任务之后，所以旧数≈整段重渲 + 补渲，和「整段重渲」只差几秒（外网 330.8 对 333.8 就是这个样子）。第 1 轮旧判据 546.9 s，那一刻正是补渲细任务 `…:0-59` 完成（545.8 s）。
2. **新键的小尺寸真实到手机只要 8～32 s**：改动 → 创建者发布 plan 约 1.3 s → 节点认领 plan 约 1.5 s → 层表换新键、手机看到新键约 4 s → 手机取到新键下带小尺寸的清单、进就绪表 8～32 s（最早那两帧是创建者本机预渲染锚帧那一趟经推送队列写的清单）→ 播放时舞台贴上新键小尺寸 8.5 s。
3. **整段重渲（300 帧）213～465 s 慢在渲染本身**：一个节点 `maxConcurrent: 1`，5 段串行，每段 60 帧渲 23～141 s（忙机上 0.4～2.4 s/帧）；推两档与写清单每段只要 0.07～1.4 s，手机轮询（层表 3 s、清单 2 s）也只是秒级。小尺寸和原尺寸是同一趟产的（`writeSmallSnapshots` 在同一个预渲染间换页前画掉），不存在「小尺寸排在原尺寸之后」。
4. **段的顺序不照优先级走**：锚帧段标 50、其余标 10，但 `pickCandidate` 在排好序的**前 K=4 个里随机挑**，几乎抹平了 50 与 10 的差别（第 5 轮第一个认领的是 10 分的 240-299；第 3 轮手机所在的 0-59 段是 50 分，却最后一个做完，464 s）。另外优先级只看锚帧（片段入点），不看手机的播放头：手机所在段何时有新小尺寸全凭运气。

## 改了什么（只改探针）

- `6d8f44f`、`43911af`：第 3 步「新的小尺寸到手机」改判「层表换了新键、新键下有带小尺寸的清单进了手机就绪表」；就绪后放一小段播放，记舞台贴上新键小尺寸的时刻（`mountedWhilePlayingMs`，只记不判——暂停时低内存档把当前帧活渲出来，不贴小尺寸，合 main 后改完参数也会重新停下追一帧）。旧判据的数留在 `newPxMs`。整段重渲改为与前者并行等，`fullRerenderMs` 取重渲完成那一刻（以前取整步末尾，含补渲等待）。

## 建议（没改，交主会话定）

1. **pickCandidate 只在同一整数优先级里随机**（三级机制，`server/render-node/pick.mjs`，契约 `render-queue-contract.md` B.3 第 2 条要跟着改）：现在前 K 个里混着 50 与 10，锚帧段优先名存实亡。改法十来行，但它是随机取前 K 个防多节点撞车的设计，收窄会让多节点时撞 `taken` 变多，需要主会话定。
2. **按观看者的播放头排段**（二级，改的是「谁先渲」的承诺）：低内存档手机停在哪一段，那一段应先做。可以让页面发补渲 / 查看时带上播放头所在的帧，切分时给那一段更高名次；或节点认领时参考文档服务里成员的播放头。改动跨页面、队列、切分，不属于小改。
3. **渲染吞吐**：单节点串行、忙机上每帧 0.4～2.4 s 是整段 4～8 分钟的主因。放云端在笔记本上复测时看每段 `renderMs`，若笔记本也在 30 s/段以上，再考虑 `maxConcurrent` 或多节点。
4. 验收判据：M8 笔记本复测时看 `newSmallMs`（就绪表）与 `mountedWhilePlayingMs`，不看旧的 `newPxMs`；「整段重渲」看 `fullRerenderMs`。

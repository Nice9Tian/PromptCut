## 做了什么

### 一、补上缺的一环

**先核实了主会话的判断，成立。** 层表的 `streams` 由 `FramePipeline.layerMapStreamOptions` 给，原来只列切分方自己这一版要产的流（`planStreams`，`picked` 是 `streamPicked`，即本机判重的卡），本机没有生产者或 `PROMPTCUT_STREAMS=0` 时整张表都不带。清单计划给浏览器出的流（`listStreamSpecs`）不在其中。端到端里切分方关着流开关时，改之前层表没有 `streams`，乙找不到甲产的流（改之后的第一轮就是验这个）。

**做法**（`server/frame-pipeline.mjs`、`server/artifact-transfer.mjs`，共约 60 行）：

- `layerMapStreamOptions` 交给层表的流分两部分：原来那一部分不变；另加 `issuedStreamSpecs(entry, own)`——切分给别的指纹出过键、而本机自己这一版不产的单卡流。
- 认哪些流「被派过」，用的是现成的切分候选记录（执行器 `afterSplit` 在每次切分完成后按最终发布成功的流任务记，键 `stream:<流的内容键>`，落盘在库根的 `split-candidates.json`）。这一版某张卡的单卡流的内容键在记录里，就列它。
- 算法：对预渲染集合里的卡（清单计划的片段已由 `addBackfill` 并进集合，层表的 `layers` 里有它的快照层）、去掉已经是本机某条流成员的卡，按解码器预算无穷大算单卡流，逐条去对记录。单卡流的内容键只由这张卡的内容、采样窗口、帧率、画幅、代码版本决定，与同一版里还有哪些卡无关，所以不用记住当时清单里是哪些片段。
- 这样列出来的流标 `ownCandidate: false`，`layerStreamsOf` 对它不补切分方自己的指纹：候选只有实际出键的那些。

**为什么这样定，不另记一份「清单计划的流」：**

1. 记录是唯一的事实来源。「这条流有没有派给谁」本来就记在那里，层表的候选也从那里取；再记一份片段清单会有两份要对齐的状态，还得处理两个页面发的清单不一样、进程重启这些情形。
2. 进程重启后照样列得出（记录落盘），和快照层的候选同一个待遇。
3. 以后「甲三」让桌面和渲染主机也替清单计划产流时，它们的指纹会随流任务进记录，这里不用改。
4. 内容换了自动失效：卡改了参数，内容键换了，旧记录对不上，不再列（单测与端到端的 G 项都验了）。

**没有破坏的：** 没有流时层表不带 `streams`，与以前逐字相同；只有本机流计划、没有另列的流时，交给层表的数组就是原来那一个（单测用 `deepEqual` 守着）。记录里一条流都没有时 `issuedStreamSpecs` 直接回空，不算流计划。独立渲染主机写层表的那一处（`vite-plugin-frames.ts`）本来就经 `layerMapStreamOptions`，不用改。

没有改 kernel 下的文件，卡片的源码版本不变。没有碰 `snapshotFeed.ts`、`FrameScene.tsx`、`VideoTrack.tsx`、导出代码、低内存档的分支、`docs/semantics/`。两半改过的页面文件（`snapshotSource.ts`、`browserNode.ts`、`browserNodeHost.ts`）这次一行没动。

### 单测（`server/test/layer-map-streams.test.mjs`，原 8 条，新增 6 条，14 条全过）

- `layerStreamsOf`：标了 `ownCandidate: false` 的流只列切分实际出键的指纹；记录里没有就不列。
- 切分方没有生产者、切分方关着流开关（各一条）：用真的 `FramePipeline`（不开 Chrome）、真的 `splitPlan`（照清单计划那条路，`listStreamSpecs` → `queueStreamOf` → `browserOnly`）、真的执行器 `afterSplit`，层表经假的推送队列收下。切分之前写的层表与不认识流时**逐字相同**；切分之后层表里两张卡各一行，内容键、结果键、分段范围与流任务的逐项相同，候选只有浏览器指纹；重启后的新管线照样列得出；卡改了内容键之后不再列。

- 另列的流不与本机的流重叠（本机并成组流时成员卡不再另列）；预渲染集合之外的卡不列。

## 发现的问题（不是这次改出来的，没有动手）

1. **后进来的页面拿不到快照层的活候选。** 乙是甲产完之后才进来的。层表里这张卡快照层的候选是「切分方的指纹在前、浏览器的指纹在后」（切分时双份出键，切分方那一份先发布）。哪一份活着，页面靠收到的 `task.done` 与 `superseded` 认定（`snapshotSource.ts` 的 `chosen`）；任务做完之后才打开的页面两样都没收到（探针里乙的 `aliveKeys: 0`、`deadKeys: 0`），于是取第一个候选，也就是切分方那一份——切分方只切分、没产，所以乙这张卡的快照层就绪帧数一直是 0。`m7-contract.md` 的 D12 写的是「按 `task.done` 与清单认定」，按清单认定的那一半代码里没有。**流不受影响**（流的候选里浏览器在前）。后果：
   - 流照播，但这一层下面没有海报快照；流缺段时没有快照可退，直接是占位符；
   - 不产流的卡（画布卡、组流成员等只有快照的），后进来的页面播放时一直是占位符，直到它自己发的计划引出新的 `task.done`。
   这是快照那一半原有的行为（改动前的代码同样），线上只要有「切分方的那一份被作废、浏览器那一份活着」的卡就会遇到。建议的补法：选中的候选在播放头附近取不到清单、别的候选取得到时，改认后者（改 `snapshotSource.ts` 的 `loadWindow` 与 `chosen`，约二三十行，加单测）。要不要这次补，请主会话定；我没有动，因为它不属于「流进层表」这一环，而且改的是所有在线页面选快照候选的规矩。
2. **流在画的时候，起播的头 500 毫秒可能盖着「等快照」的沙漏。** 舞台的占位符判据里，「这一帧的快照还没到」（`.pc-awaiting`，`placeholderHost.ts` 的 T2）不看流在不在画；先放播放头再播时，快照没到的那 500 毫秒兜底期里沙漏盖在这一层上，流在下面照画，兜底一过沙漏撤掉。有快照的页面（甲、改参数之后的乙）这段时间里快照到了就没有沙漏（探针里 `placeholderEarly: 0`）；乙第一版因为上一条永远等不到快照，每次起播都有（探针每次采到 4～5 个样本）。照 `mechanism/rendering.md` 的兜底顺序，流在画就不该再显示占位符。探针的 D 项因此判的是「起播 0.7 秒之后没有占位符」，头 0.7 秒里出现几次记在 `placeholderEarly`；截图比像素时等沙漏退下再截。补法在 `placeholderHost.ts`（T2 加上「流不在画」的条件）或 `StageView.tsx`，都不在这次的文件范围里。

## 裁定

没有改语义文档。实现里自己定的，都是用户看不出区别的（三级）：

1. 〔裁〕哪些流算「清单计划给浏览器出的」，按切分候选记录认（键 `stream:<流的内容键>`），不另记片段清单。理由见「做了什么」第一节。
2. 〔裁〕这些流在层表里的候选只列实际出键的指纹，不补切分方自己的（`ownCandidate: false`）。切分方自己不产它，列了只是一个永远取不到清单的候选。
3. 〔裁〕只列在预渲染集合里的卡的流，已经是本机某条流（含组流）成员的卡不再另列单卡流。前者保证流的下面有快照层，后者避免同一张卡同时被一条组流和一条单卡流盖着。
4. 〔裁〕本机自己的流排在前、另列的流排在后（同一张卡在表里列两行时页面只认第一行）。

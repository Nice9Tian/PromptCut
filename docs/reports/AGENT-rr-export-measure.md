# AGENT-rr-export-measure：辛，桌面版导出两条路各量一遍

分支 `claude/rr-export-measure`，工作区 `.worktrees/rr-export-measure`。任务书：`docs/plan/render-refactor-task.md`「辛」一节；`docs/plan/render-standard.md`「还要做的」第 9 条。

只量，不换；没有改 `src/`、`server/`（见下「验证结果」）。「辛」是渲染重构里的一项编号，内容就是本报告：把桌面版导出的两条路（桌面：Chrome 截图加 ffmpeg；在线：浏览器自带编码）在同一台机器、同一个项目上各量几遍，「换不换」留给用户定。

## 做了什么

- `scripts/probes/export-paths-measure.mjs`：一条命令重跑的探针。自起 dev server（缺省端口 7460～7462），每个项目先预热，再交替跑桌面、在线各 `--runs` 遍（缺省 3），输出 JSON 汇总（缺省写在工作目录，`--json` 可指定），失败退出码非 0。参数见文件头。
- `scripts/probes/fixtures/export-paths/projects.mjs`：两个夹具项目的配方（探针在编辑器页面里用 store 的动作搭，再同时交给两条路）。
  - `demo`：像素基线的演示项目。原来的 `make-fixture.mjs` 不在仓库里（`docs/archive/restructure_planning/reports/r7b-report.md` 已指出），这里按 `docs/archive/topics/export-baseline-compare.md` 第 1 节的表重建：1280x720、30 fps、8 秒共 240 帧，文字层、常驻层、图表层、三维层、粒子层各一，加一层 320x180 的 testsrc2 视频。所以它和当年的基线项目是同一配方，不保证逐字节同一份。
  - `heavy`：带重卡和画布卡的项目。同尺寸同时长，视频打底，上面是一张粒子卡（数量 400、带连线，画布卡）、两张 WebGL 卡（scene-3d、terminal-3d），再加 growth-curve、rank-bars、chapter-bar、punch-pill。
- 桌面那条路：直接起 `scripts/export-frames.mjs`，参数和 `/api/export`（`server/vite-plugin-export.ts`）起它时一样（`--workers auto`，不带 `--media`，即素材由 Chrome 截进画面），给输出每行打时间，按行分段。
- 在线那条路：页面里调桌面运行环境已有的 `window.__pcIo.exportVideoBrowser`，没有加开关。各段耗时靠装在页面里的计时垫片量（包住 ExportCompositor、Mp4Muxer、VideoEncoder、VideoFrame、getImageData 的方法），不改产品代码。
- 每遍记：总耗时和各段、成片大小和码率、开跑前一秒整机处理器占用和几类进程个数、跑的过程平均占用；同一条路各遍成片逐帧 sha1 比对；两条路成片逐帧画面差；每项目抽 3 帧存「桌面 | 在线 | 差×8」对比图；拆段单测（只截图落 PNG、PNG 编 ProRes、ProRes 解码、解码加 libx264）。
- 提交：见文末。

## 结论

1. **哪条快、快多少。** 桌面快。被占的机器上：demo 桌面中位 21.1 秒，在线 61.8 秒，约 2.9 倍；heavy 43.7 秒对 150.7 秒，约 3.4 倍。机器没那么忙时的单遍（探针开发中的试跑，没有计入上表）：demo 26.3 秒对 53.7 秒（2.0 倍），heavy 32.9 秒对 79.8 秒（2.4 倍）。所以倍数随机器忙闲在 2 到 3.5 倍之间，方向没有变。
2. **在线慢在哪。** 编码本身不慢：编码调用、等编码队列、flush、封装四项加起来不到 0.1 秒，浏览器编码器（硬件或快的软件编码）一直跟得上。时间全花在「画帧」：生成整场景快照最大（demo 25.3 秒，heavy 50.3 秒，每帧 105～211 毫秒），其次是把快照包成 SVG 画到画布（12.2 / 39.0 秒）、读像素（10.7 / 28.4 秒）、转 YUV、素材帧装好替进快照。只算「画一帧」，在线每帧约 190（demo）到 480（heavy）毫秒，桌面 Chrome 整帧截图每帧约 72（demo）到 156（heavy）毫秒。
3. **桌面慢在哪。** Chrome 截图（软件光栅化，每帧一次 beginFrame），ffmpeg 两段合计占 7%～11%。要让桌面更快，省的是截图，不是编码。
4. **画面差多少。** 平均绝对差 3.1～3.8（满分 255），PSNR 约 31 dB；每帧约 3%～4% 的像素有通道差超过 32，集中在硬边缘；不是错帧，布局一致。所以换了以后导出的像素基线一定要重新定，不可能逐字节相同。
5. **各自稳不稳。**
   - 桌面：同一项目三遍成片逐字节相同；耗时随机器忙闲浮动 20%～35%。启动偶发失败：`export-frames` 起来后预热帧 20 秒内「控件、字体或图片未就绪」被拒（刚起的 dev server 第一次导出必现；demo 正式第 1 遍还又失败 2 次，机器当时 69% 占用，原因没有再查），探针对失败的遍重试。
   - 在线：demo 三遍成片逐字节相同；heavy 两遍之间有 201 帧不同（量级小，见上），粒子、WebGL 一类 stateful 卡跑两遍不保证逐帧相同；项目、素材相同，机器占用高到 94% 以上。另外有一类失败：`Video frame was not presented`（视频帧没送到显示），开发和正式跑过程中共出现 5 次：heavy 4 次（试跑 1 次，正式跑第 3 遍 3 次全败，这一遍没有成片），demo 1 次（被端口更正中断的那趟，重试后过了）；正式跑的 demo 三遍和 heavy 前两遍 0 次。都发生在整机占用很高时，没有在空闲机器上验证是否仍出现。
6. **「换不换」留给用户定。** 从数字看，桌面版用在线那条路会慢 2 到 3.5 倍，画面和现在的逐帧差如上，像素基线要重定。这一步不是探针能替用户定的，已记进待用户项。

## 验证结果

- `node scripts/probes/export-paths-measure.mjs --runs 3 --work out/final1 --assets docs/reports/assets/rr-export-measure`：demo 全部完成；heavy 在线第 3 遍三次重试都失败，退出码 1，其余数字齐全。探针退出码 0 的情形：`--runs 2 --projects demo --frames 0-29` 干净跑完，退出码 0，JSON 里 `failures` 为空，`visibleWindows.newAfter` 为空（实测）。
- 窗口检查：任务要求的 `Get-Process … MainWindowHandle -ne 0` 命令，跑前、跑中、跑后、探针收工后各查过，只有用户自己的一个 Chrome 窗口（启动时间在我开工之前），没有新冒出来的窗口；探针里每个子进程都带 `windowsHide: true`，没有用 detached，Chrome 用无头；收工后查过没有遗留的 node、chrome、ffmpeg 进程。探针从此会在开跑前后各查一次，多出窗口就记进 `failures`（`visibleWindows` 字段）。
- `npx tsc -b --force`：退出码 0，零错误。
- `npm test`（设了 `PROMPTCUT_ACCOUNT_PROVIDER_ROOT`、`PROMPTCUT_PASSWORD_ORDER_MODULE`）：第一次 5498 通过、1 失败（`server/test/agent-live-selection.test.mjs`，等模型工具路由超时 8 秒，当时机器被占满）；`npm test server/test/agent-live-selection.test.mjs` 单独重跑通过（退出码 0）；第二次全量重跑：5499 通过、0 失败、4 跳过，退出码 0。没有改过测试。
- `git diff main...HEAD -- src server`（以分支基点为准）：空，没有改产品代码，导出像素基线不受影响。（`git diff main -- src server` 因为 main 在我分出之后又前进了，会列出 main 上别人的改动，不是我的。）

## 没做成的与原因

- heavy 在线第 3 遍没有数字：三次重试都撞上 `Video frame was not presented`，见上。heavy 在线的中位数只基于两遍。主会话在机器空闲时重跑可补。
- 桌面的「截图」和「ProRes」没有分成 streamed 并行形态来量：默认的 `--workers auto` 路径对这两个项目是先写 PNG、截完再编 ProRes，分得开，已按这条量；只有 `--workers 1` 且整段导出时才边截边编、两段并行分不开，探针没有为它单设一遍（`--workers 1` 可以手动跑）。
- 合成与 libx264 在桌面主流程里是同一趟 ffmpeg，分不开，只能靠拆段单测里的两次相减近似（0.6～0.7 秒）。
- 在线的编码在浏览器另一线程，与画帧重叠，只能看到主线程上「等它」的时间（约 0）；浏览器实际用了硬件还是软件编码器，页面里问不到。
- 没有加音频：两个夹具的素材都没有声音，声音混音和 AAC 编码两条路的耗时没量。
- 没有在空闲机器上量，数字被干扰，见上。

## 发现的问题（不在本项范围内，没动）

1. **同一份项目里放两张粒子卡，桌面导出必现失败。** 两张 `particles` 卡（哪怕 seed、数量、颜色都不同，也不管是否同时出现在画面里，因为预热会把所有卡一起挂上）时，`export-frames` 在预热帧上等不到就绪，20 秒后报「控件、字体或图片在 20 秒内未就绪，已停止截图」，退出码 1，`__pcFrameWorkStatus()` 里一直挂着 `particles`。单张粒子卡、或把两张都改成缺省数量都是同样结果（只改数量没有用），去掉任意一张就正常。第一次写 heavy 夹具时撞上，所以现在夹具里只放一张粒子卡。
2. 在线导出对 `<video>` 素材偶发 `Video frame was not presented (target=… current=… readyState=4 seeking=false rejectedPresentations=[…])`，机器忙时频繁，会让整次导出失败（`src/export/frameCompositor.ts` 的素材装帧）。
3. 两条路的成片容器里都没写颜色标签（`color_range`、`color_space` 等都是空），用 ffmpeg 解出来都按同一个缺省矩阵换算，所以本报告的画面差口径一致；但播放器对 720p 无标签的视频会按 BT.709 解释，而两条路都是按 BT.601 编的。这是产品行为，未验证对观感的影响。

## 对任务书或语义的更正建议

- 任务书「辛」的现状描述说桌面版「先编成带透明的 ProRes 中间文件，再和素材合成」。默认路径（不带 `--media`）下素材是 Chrome 截图时画进画面的，ffmpeg 合成那一趟实际是 0 层素材，只是解 ProRes 加灰底加 libx264；而且 `--workers auto` 时 ProRes 是截完 PNG 再编的，只有单进程整段才边截边编。语义和任务书若要写这条路，建议写清这两点。
- `docs/archive/topics/export-baseline-compare.md` 里像素基线夹具的生成脚本仍不在仓库。现在 `scripts/probes/fixtures/export-paths/projects.mjs` 的 `demo` 配方按那张表重建了项目，但没有和当年的 `project.json` 比过，所以「像素基线 0 不同」这一项要用的基线项目，仍以 `export-baseline-compare.mjs` 当时用的那份为准。

## 一、结论先说

1. **缺陷复现了，修好了。** 新的集成测试真的把 Agent 服务进程硬杀再起：修前退出 30 秒办不完（Agent 一项一直没确认），修后 1 秒左右办完。
2. **修法不是「等不到就放过」。** 旧实例名下的读取只在拿到「那个进程确实不在了」的证据时才收口。证据是 Agent 数据目录上的一把操作系统独占锁：新进程拿到了锁，握过这把锁的旧进程就不可能还在往页面写东西。断线、过了多久、新一代登记了，都不算证据。
3. **顺带去掉了 main 上一条不安全的推断**（见第二节第 2 点）：原来凭「更新一代的只做控制的主服务订阅了」就把旧一代的读取记成已关，活着的旧实例也会被这样「收口」。
4. **回答主会话那句**：改完之后，**没有**任何一条路径能在页面其实还能读到对话内容的情况下报出「已退出」。前提和剩下的假设写在第四节「安全论证」，逐条列了。
5. **安全专审第二轮（2026-10-22）的四处必改都已做完**，见第十二节；第四节「剩余假设」那张表按审查与主会话的节点实测改过。

## 二、根因（自己验证的）

### 1. 卡在哪

- 文档服务账本里，一条读取绑在开它的那个实例上（`agent-read-control.mjs` 的 `handles`，带实例号与代）。退出时点名关它，生成一条控制记录，目标就是那个实例（`fenceInState`）。
- 只有那个实例能关、能确认：`closeReads` 要 `sameInstance(handle, who)`，`acknowledge` 要 `sameInstance(target, who)`。
- Agent 服务进程被结束（部署、重启、崩溃）时，它来不及关、也来不及说一声。新进程是新实例，关不了旧实例的读取（`read-instance-mismatch`）。于是这条控制记录永远等不到回执，`finalizeAccessEvent` 一直抛 `read-close-pending`，Agent 那一项永不确认；文档服务那一项要等其余三样齐了才报，所以也不报；网页一直 `revoking`，45 秒后变失败，不会再变。

修前测试的输出就是这个样子（第五节）：`{"services":{"asset":"confirmed","agent":null,"render":"confirmed"}}`。

### 2. main 上已经有过一次「修」，但它是推断，不是证据

`git log -S supersedePriorControlOnly` 查到 `6841cbd9`（2026-10-18，`docs/reports/AGENT-docservice-eacces-logout.md` 第 5 节第 2 条，用户当时拍板选 A）加了 `supersedePriorControlOnlyInState`：**新一代只做控制的主服务一订阅，就把更早各代主服务记成 `closed`，名下读取全记已关、回执全补上**。注释的理由是「更早代的主服务进程必然已经退出」。

所以：

- 生产配置（主服务都是 `control-only`）下，H07 这个现象从 10-18 起其实已经不出现了。`wait_to_judge_html/source/items/P-H.md` 里 H07 那条写「现状：仍如此」，和代码对不上。
- 但那一条靠的是推断。旧主服务进程没死（例如有人手工再起了一个、或旧进程停在退出途中），它名下开着的读取一样被记成已关，退出就可能报成已办完。这正是这次要防的「设备其实还在读、却报了已退出」。
- 它只认 `control-only`。没开「一条任务一个进程」的配置（集成测试的夹具就是这一档）照样卡住，所以修前测试是红的。

这一条推断这次去掉了，改成凭证据收口（第三节）。

### 3. 同一类的另一个口子（一起修了）

`fenceInState` 把「登记过、却没订阅过读取控制」的实例当成「来历不明、可能开着读取」，给它一个 `unknownInstance` 目标；而 `acknowledge` 一律拒掉 `unknownInstance` 目标，Agent 那一侧收到这种点名也直接报 `read-resource-unknown`。所以**这种目标谁都确认不了**。主服务启动时先登记、后订阅，中间那一会儿要是赶上一次退出（换了锁以后，等旧进程放锁的时间也算在这一会儿里），这次退出就永远办不完。

可是这样的实例名下不可能有读取：开读取要先有本进程里活着的订阅流（`open` 里的 `requireLive`），订阅时就记进了 `t.instances`；对话数据接口也只认经读取控制开的读取（`createConversationInternalHandler` 的 `requireReadControl: true`）。所以这次改成：**这条规矩生效以后登记的、从没订阅过的实例，点名时不等它**；更早登记的（规矩生效以前就在的）照旧按来历不明等。生效的那一代记在账本里（`agentReadsV1.inventorySinceGeneration`），只记一次。

## 三、修法

### Agent 一侧（`server/agent-service/conversation-control-client.mjs`）

1. **数据目录独占锁**（新函数 `acquireDataDirLock`）。在本地回执账本旁边放一份 `<回执账本>.owner`，开一个不提交的 `BEGIN EXCLUSIVE` 一直握着：和文档服务操作历史的 `.owner` 是同一个做法（`server/docservice/modules/operation-history.mjs` 第 52 行），在 Windows、Linux 上都是操作系统的文件锁，进程结束（含被硬杀）时由系统放开。锁文件里存一个锁号；锁号绑在这一份文件上（文件号与所在的卷），目录被整个拷走另起一份时，拷出来的那份换新锁号。拿不到锁就抛 `read-control-owner-busy`，调用方（主服务的 `startReadControl`）隔一会儿再试：**活着的那个不会被顶替，新的一直等它放锁**。
2. **启动顺序**：先拿锁 → 登记实例 → 本地记租约（这个实例在这把锁下跑过）→ 向文档服务报锁（`lease`）→ 替本地记着的、不是自己的那些实例交「已经不在了」（`handover`）→ 订阅。拿锁以前不订阅，订阅以前开不了读取，所以**任何开着读取的实例都握着锁，也都留了租约**。
3. **交证据**：文档服务确认收口了、或明确说这一个永远收不了口（不认识、不是同一身份、没报过锁、旧文档服务不认这个接口），就删掉本地那一笔；它说那个实例还连着、或暂时连不上，就留着，每 2 秒再交一次。
4. **正常收口**：页面上的读取全关完、本地账本关了，最后才放锁。
5. 报给文档服务的「哪台机器」是专用摘要 `sha256('promptcut-agent-lease-machine-v1|' + machineFingerprint())`（`leaseMachineDigest`），**不是** `machineCode()`：后者就是这台节点模型 Key 密文的解开口令（审查必改一，见第十二节）。Windows 上取指纹跑一次 `reg query`，带 `windowsHide`。
6. 锁文件名是 `<回执账本>.agent-instance-lock`，只许拿锁那一条 SQLite 连接碰，有守门测试（第十二节第 4 条）。

### 文档服务一侧（`server/account/agent-read-control.mjs`）

1. 读取控制加两个接口，走原来那套实例签名（证书钉住、TLS 导出值绑定、一次性随机数、整份请求是授权范围）：
   - `lease`：实例报自己的锁号和机器码。一个实例只报一次，报了不能改（`read-lease-mismatch`）。
   - `handover`：后继说「这个实例不在了」。文档服务**逐条核它自己核得了的**，任何一条不符都不收口：
     - 前一个是同一个服务身份（`serviceId`、`serviceKid`）、同一种用途，不是只跑一条任务的进程（`read-handover-forbidden`）；
     - 两个实例**各自**报过锁，是同一把锁、同一台机器摘要（`read-handover-unproven`）。前一个那份是它自己用自己的实例钥匙签的，后继冒充不了；
     - 前一个的锁报得更早（文档服务按报上来的先后给每份记序号 `declaredSeq`），否则 `read-handover-forbidden`。不看代次：主服务先登记、后拿锁，交叠起来时代次低的可能后拿到锁（审查用例 F2）；
     - 前一个此刻没有连着本进程的订阅流（`read-handover-predecessor-live`，409，后继稍后再试）。连着就说明它还活着，和证据矛盾。
   - 核过了才收口：前一个记 `closed`，`closure` 写明 `witnessId: handover:<后继实例>:<代>`、`evidence: agent-data-dir-exclusive-lock`、锁号、后继是谁；名下没关的读取记已关；等它的控制记录补上回执。收口过的实例连订阅、开读取都不行了（`instance-revoked`）。
2. 去掉 `supersedePriorControlOnlyInState`（订阅时、文档服务启动时两处都去掉）。
3. 第二节第 3 点那条「从没订阅过的新实例不等」。

## 四、安全论证

要守的那一条：**报「已退出」的时候，旧登录确实再也读不到对话内容。** Agent 这一项上，等价于：点名关的每一条读取，要么开它的实例自己关了并确认，要么那个实例已经不可能再往页面写任何东西。

### 1. 凭什么判定一个实例「确实没了」

只凭一样：**它的后继握着它握过的那把锁。**

- Agent 一侧的不变式（代码保证）：一个读取控制客户端在拿到锁以后才登记租约、才订阅；页面上的读取只有在订阅流连着、收到 `ready` 以后才写得出东西（`conversation-transports.mjs` 的 `connected` 闸门：每一次 `write`/`end` 前都查）；锁只在两种时候放开：进程结束（操作系统放），或 `close()` 走完（页面读取全关完以后才放）。
- 所以后继拿到了锁 ⇒ 前一个握锁的进程要么已经不存在，要么已经关完了全部页面读取、关掉了自己的客户端（关掉的客户端不能再启动：`start()` 第一行就查 `closed`）。两种情形下它都不可能再往页面写字节。
- 操作系统的锁是这件事的关键，单独验过（`agent-data-dir-lock.test.mjs`）：同进程另一条连接拿不到；别的进程活着握着拿不到；那个进程被硬杀以后拿得到；锁号放开再拿不变；拷出来的那份换新锁号。
- 文档服务另外核的几样（同一身份、同一把锁、同一台机器、更早一代、不连着订阅流）是防「证据交错了对象」：后继只能替**同一把锁下**跑过的实例交证据，而那个实例当初报锁时用的是它自己的钥匙。

### 2. 会不会把活着的实例误判成没了（卡顿、网络抖动、还没来得及心跳）

不会，因为判据里**没有任何一样和时间、连接、心跳有关**：

- **卡顿**（事件循环卡住、GC、虚拟机被挂起）：进程还在，锁还在它手里（数据目录在本机盘上时；网络盘与 Linux 上同进程误关描述符两种例外见下表），后继拿不到锁，起不来读取控制，交不了证据。点名照旧等它，它恢复以后自己关、自己确认。集成测试第三种情形就是这个：活着的实例把关读取压住不做，同一个数据目录上再起一个，起不来（`read-control-owner-busy`）；另一个数据目录上起一个更新的一代，连上了文档服务，但没有证据，退出 4 秒里读了 16 次都没办完；放开以后由它自己确认才办完，它的实例状态始终是 `active`。
- **网络抖动 / 订阅流断了**：断线不放锁，也不是证据。单元测试里专门有一步：旧实例订阅流断了，照旧 `read-close-pending`。
- **还没来得及心跳**：没有心跳这回事。
- **新一代登记了、订阅了**：不是证据（这是本次去掉的那条推断）。单元测试：新一代登记并订阅，照旧 `read-close-pending`。
- **新一代报了同一把锁，但旧实例还连着**：拒（`read-handover-predecessor-live`），单元测试覆盖。

### 3. 判据依赖的假设，以及假设不成立时的后果

| 假设 | 不成立的情形 | 后果 |
|---|---|---|
| 操作系统的文件锁对同一份**本机盘上**的文件有效 | 数据目录放在网络盘（NFS 等）上：锁不可靠，「冻结或断网的进程仍握着锁」这一条在网络盘上**不成立** | 两边都以为自己独占。文档服务的「同一台机器」一条会拦下两台不同的机器；克隆机拦不住（下一行），最后一道是「前一个不连着订阅流」 |
| 持锁进程自己不会用普通文件接口开关锁文件 | **Linux 上一旦发生，锁在进程活着时就丢了**（POSIX fcntl 按进程算，任何一个指向该文件的描述符被关掉，锁整个没了）。主会话 2026-10-22 实测：Windows 本机——SIGKILL 后释放 PASS、自己 open+close 后锁仍在 PASS；**生产节点 Linux 5.15、Node v24.21.0——SIGKILL 后释放 PASS、自己 open+close 后锁仍在 FAIL** | 锁一丢，后继合法拿到锁、交出假证据，活着的前一个被记成已收口——就是要防的假报。现在代码里没有这样的路径；锁文件改了专用名，**守门测试拦住产品代码里任何别处引用它**，拿锁那一段只许用 `mkdirSync`、`statSync`（第十二节第 4 条）。静态扫描拦不住按算出来的路径碰「数据目录里所有文件」的代码，这一条写在拿锁那段注释和守门测试文件头里 |
| 机器摘要能区分机器 | 克隆的虚拟机没重新生成 `/etc/machine-id`；镜像里写死了 machine-id 的容器 | 机器摘要相同，「同一台机器」一条拦不住，只剩「前一个不连着订阅流」这一道 |
| 「前一个不连着订阅流」这一道还在 | 文档服务重启以后，内存里的订阅流表是空的，这一道就没了（审查用例 F4、F5） | 这时只剩锁与机器摘要两道。要误判，得同时有网络盘或同进程误关描述符、克隆机或写死 machine-id，加上两个主服务同时在跑、恰好文档服务重启或断线 |
| 锁文件没被替换成别的东西 | 有人在运行中删掉或换掉锁文件 | 新进程在新文件上拿到锁、生成新锁号；新锁号和旧实例报的不同，交不了证据：往安全方向（照旧等） |
| 同一个 Agent 服务身份（证书与钥匙号）可信 | 主服务的证书和私钥被别人拿到 | 拿到它的人本来就能以主服务身份读对话、回确认，和本次改动无关 |

即使前面几条假设同时不成立、旧实例确实还活着、恰好在那一刻和文档服务断开（或文档服务刚重启）：文档服务把它记 `closed` 以后，它再也认不过（订阅、开读取都 `instance-revoked`），**拿不到任何新的对话内容**；而它的页面读取在订阅流断开的那一刻已经被它自己关掉（`disconnect()` 把 `connected` 置假并撤掉全部页面读取）。剩下的只有一种理论上的窗口：断线这件事它自己还没察觉（半开连接，最长到它那条订阅请求的 5 秒空闲超时），这期间它手里如果有一份在退出之前就取到、还没写出去的数据，可能写出去。要同时满足「网络盘或克隆机器 + 共用数据目录 + 两个主服务同时在跑 + 恰好断线」，部署上不会出现，列在这里供审查判断。

### 4. 误判的后果

误判的方向只有一个：把还活着的实例记成已收口。后果就是上一段：它从此认不过、拿不到新数据；最坏是那个极窄的窗口里写出一份退出之前取到的数据。正常部署（systemd 一个单元、数据目录在本机盘）下不存在这种误判。

反方向（实例确实没了却判成还在）只会让退出继续等，就是修前的样子，不泄露。例如：Agent 数据目录被清空或换了盘，旧实例的租约丢了，那时开着的读取收不了口。

### 5. 明确回答

**改完之后，有没有任何一条路径能让「页面其实还能读到对话内容」的情况下报出「已退出」？**

**没有。** Agent 这一项只有两条路能确认：(1) 开读取的那个实例自己关了、确认了（和原来一样）；(2) 后继握着它握过的那把锁，并且文档服务核过同一身份、同一把锁、同一台机器、它不连着订阅流。第 (2) 条成立时，那个进程要么不存在，要么已经关完全部页面读取并且再也起不来读取控制；文档服务同时把它记成 `closed`，它也再拿不到任何对话内容。原来那条「新一代订阅了就收口旧一代」的推断（会把活着的旧实例记成已关）已经去掉。上一节表里那几条部署假设之外，没有别的路径；那几条假设同时不成立时剩下的极窄窗口，也写在上面了。

## 十二、安全专审第二轮的四处必改

1. **机器码不再明文发出去（审查必改一）。** 原来报的是 `machineCode(machineFingerprint())`，而那串码就是节点模型 Key 密文的解开口令（`runners/machine-id.mjs` 文件头、`service-keys.mjs` 的 `importServiceKey` 缺省 `code`），等于把口令写进文档服务账本。现在报 `leaseMachineDigest()` = `sha256('promptcut-agent-lease-machine-v1|' + machineFingerprint())`，直接从指纹派生、带只给这一处用的前缀，和那串码互相推不出。文档服务只拿它比相等，并且 `lease` 的 `machine` 只收 64 位小写十六进制，别的形状一律 400，账本里进不来可读的识别码。测试：单元测试「报锁时机器只收 64 位十六进制摘要」（`PCM-…` 和大写十六进制都被拒、账本里没留）；集成测试甲把文档服务账本整段读出来，断言里面不含这台机器的 `machineCode()`（带不带横线都查），每份租约的 `machine` 都等于按规格算的摘要。
2. **按「租约报得更早」判前后，不看代次（审查用例 F2）。** 文档服务给每份报上来的锁记序号 `declaredSeq`（同一份再报不另记）；交证据要求前一个的序号小于后继的。去掉了「前一个代次更低」那一条。测试：单元测试「审查 F2」——代次低、后拿到锁的后继能替代次高、先握锁的前一个交；反过来拒（`read-handover-forbidden`）。

# AGENT 报告：rr-online-export（在线浏览器导出分「快速导出」和「完整导出」）

分支 `claude/rr-online-export`，从 main `aa5ee127` 分出，中途并入 main 两次（先到 `21807232`「依赖下层的流贴回舞台」，交活前到 `f952e969`）。端口段 27220～27259。

用到的几个词：

- **导出页**：在线页面导出时在编辑页面里开的一个看不见的子页面（地址带 `?export=1`，和编辑页面同一个源），逐帧推时间、每帧把整个场景转成一份 HTML 再画成位图。
- **本页不执行的卡**：导出页里没有代码、也不许执行的卡，见第 1.2 节。
- **导出位图**：这次新加的一种只给导出用的预渲染产物：渲染节点把一张卡逐帧渲成带透明的 PNG（原尺寸、无损）。不是「每张卡的 HTML 快照」，预览不读它。
- **只为导出的计划**：页面导出时发给任务队列的一个计划任务，认领它的节点只切导出位图任务。

## 1. 现状（动手之前）

### 1.1 在线页面导出时每一类卡的画面各从哪来

查的是 `src/export/browserExport.ts`、`originals.ts`、`frameCompositor.ts`、`onlineExport.ts`、`src/ExportView.tsx`、`src/render/Stage.tsx`、`placeholderHost.ts`（main `aa5ee127`）。

导出前先核对：层表（渲染节点写进内容库的 `layers:<项目 id>`）里每张重卡、每一段清单的 `frames` 是否盖满整段；不满就停在「还有 N 个重卡片段没有预渲染原尺寸」，隔 3 秒再核，不设超时。

| 卡的种类 | 画面从哪来 |
|---|---|
| 轻卡（内置卡，页面判轻、层表里没有它） | 导出页活渲：逐帧推时间，组件在导出页里运行 |
| 本页能跑的重卡（内置卡，层表里有它） | 普通档：不活渲。导出页照常挂着它的组件，但每一帧生成整场景 HTML 之后，把这张卡包裹层里的内容换成素材服务上存好的那一帧 HTML 快照（`snap/<哈希>`）。还没有层表时，页面自己判重的卡一律算缺。低内存档：只有页面判重的卡这样换，层表里别的卡照活渲 |
| 同步来的用户卡（源码在内容库里，在线包里没有它的定义） | 不管判轻判重，一律换成 HTML 快照。导出页不执行它的代码，只挂一个空的包裹层（`exportSyncedMountFor`）。判轻时它不在平时的清单计划里，所以导出开始时把它记进 `exportWanted`，页面发的清单计划并上它，等渲染节点把快照渲出来 |
| 素材效果卡 | 分两种。内置的（定义在在线包里，含转场）和内置卡一样办：判轻由导出页活渲（导出页自己在显卡上执行），判重换 HTML 快照。同步来的（用户写的）和同步来的用户卡一样，一律换 HTML 快照 |
| 依赖下层的卡（毛玻璃这一类） | 内置的：判轻活渲；判重时层表里是它的「本地档」快照层（`kind: 'local'`），同样逐帧换成 HTML 快照 |
| 转场 | 是接了输入的素材效果卡，同上 |
| 素材（视频、图片） | 导出页按原尺寸地址装好这一帧，画成图替进占位（这一块这次没动） |

所以每张卡的 HTML 快照一撤，重卡和同步卡在线导出都会一直停在「缺预渲染原尺寸」。

### 1.2 「本页不执行的卡」现在还剩哪些情形

先说结论：**导出这件事上，剩下的就是「同步来的用户卡与素材效果卡」这一整类，和它在预览里能不能运行无关。**

main 上「卡片源码同步」做的是：在线页面把内容库里的卡片源码转译后，**只在跨源的两个舞台里**执行（声音在舞台起的后台线程里）。编辑页面这个源、同源的单舞台、导出页都不执行（`docs/semantics/mechanism/platforms.md`「在线执行用户卡与素材效果卡」的「在哪里执行」「导出页」两条）。导出页和编辑页面同源，手里有项目凭证和票据，这是隔离设计定的，不是没做完。

逐条：

| 情形 | 预览里 | 导出页里 | 这次怎么出 |
|---|---|---|---|
| 同步来的卡，舞台里载入成功（运行状态 `ready`） | 判轻的活渲 | 不执行 | 按本页不执行办：快速导出先取满密度流，其余请渲染节点逐帧渲 |
| 同步来的卡，本页跑不了：转译失败（`unsupported-syntax`）、引了页面没有的模块（`missing-module`）、载入出错（`load-error`）、图形能力不够（`gpu`）、输入解不了（`media`）、运行中出错（`runtime-error`）、没有隔离环境（`not-isolated`）、低内存档（`low-memory`）、托管方关了在线执行、还在载入（`loading`） | 贴预渲染结果或占位 | 不执行 | 同上 |
| 构建时就在在线包里的卡：内置卡、内置素材效果卡（含转场）、仓库里的用户卡 | 判轻活渲，判重贴流 | **执行** | 完整导出一律由导出页逐帧渲，不管平时判轻判重；快速导出有满密度流的段取流 |
| 被判成只能预渲染的内置卡（声明了 `need_prerendering`、三维、画布卡，或者这台设备上测出来很慢） | 贴流 | 执行（代码在包里） | 同上一行。导出不是实时的，慢也能出 |
| 代码没同步到的卡（内容库里还没有它的源码，或者源码同步还没到本页） | 「未知卡片」，舞台不画 | 不画 | **没有处理**：它不在同步表里，认不出是用户卡，导出时这一层是空的，和桌面版对「未知卡片」的处理一样。源码同步恰好没到就点导出会漏画，这是动手之前就有的缺口，见第 6 节 |

和主会话的预想不同的地方：同步来的卡即使在舞台里能跑（`ready`），导出时也还是要渲染节点。让它「本页逐帧渲」得借跨源的后台舞台来渲（纯浏览器节点产单卡流时就是这么取像素的），只对独立卡成立。这次没做，记在第 6 节。

## 2. 「请渲染节点渲一份」选了哪个办法

要满足的：本页不执行的卡，导出开始时请渲染节点按原尺寸逐帧渲好；只给这一次导出用，不给预览贴；不新建任何「每张卡的 HTML 快照」存放；画质和桌面版一样（所以不能是压缩过的视频）。

| 办法 | 怎么做 | 结论 |
|---|---|---|
| 甲：导出位图，沿用流任务的壳（**选了这个**） | 页面发一个只为导出的清单计划；节点照这张卡的轨道流的计划（同一个隔离工程、同一套推帧和取帧代码）逐帧取图，但不压成视频，每帧存一张 PNG 推到素材服务，清单写进内容库，索引随计划的完成回给页面。任务的种类仍是队列已有的流任务，靠 `input.exportFrames` 认 | 画面无损；取帧代码和轨道流是同一份（依赖下层的卡的差分取层也直接用上），不另写一套；**文档服务和任务队列一个字不用改**（任务形状过得了现有的入站校验，单测核了），已经部署的文档服务不用动；不进层表，预览读不到 |
| 乙：让节点产这张卡的满密度轨道流，标成导出专用 | 复用流任务和流清单 | 没选。流是 H.264，有损；语义写的是完整导出「画质和桌面版一样」，推荐项甲当初的说法也是「画质和现在一样」。而且那样完整导出和快速导出对这类卡就没有区别了 |
| 丙：队列里加一种新的任务种类 | `kind: 'export-frames'` | 没选。要改队列的入站校验、节点的过滤规则、文档服务的路由，托管端要先部署新的文档服务才能用；比甲多动四五个文件，得到的东西一样 |
| 丁：继续用每张卡的 HTML 快照任务 | 现状 | 不许。这正是要撤的东西 |
| 戊：本页的后台舞台逐帧渲同步卡 | 借纯浏览器节点产单卡流时取像素的那条路 | 这次没做。只对独立卡成立（依赖下层的、接了输入的素材效果卡隔离不出来），而且跑不了的那几种状态仍然要渲染节点，所以节点这条路无论如何要有。可以以后加在前面当优化 |

导出位图的几个决定（都是三级，用户看不出区别）：

- 键另算：`导出键 = sha256("export-frames:1\n" + 这张卡的流的内容键)`，结果键 = 导出键 × 节点的环境指纹。它和这张卡的轨道流不是一个键；任务的 `input` 里不带 `contentKey`，所以不占卡片级指纹锁。
- 每张卡一份，不按解码器预算合并成组流；平面的独立卡、源依赖卡、三维外框的卡按单卡流的形状（包裹层坐标），依赖下层的卡按依赖下层的流的形状（舞台坐标、差分取层）。
- 每帧都按这条流的矩形上界取，不量、不收紧、不走画布直取（都截图）。
- 只切给切分方自己，不要求本机转码、不要求能产流（取位图不用 ffmpeg 和编码器）；纯浏览器节点只收带 `input.bake` 的浏览器形状的流任务，这种任务它不收。名次 60，排在别的细任务前面；只为导出的计划本身名次 70（见第 5.3 节量到的等待时间）。
- 节点本机落盘在 `<库根>/export-frames/<结果键>/`，推送成功就删。素材服务和内容库里的那一份留着（内容寻址；同一份内容再导出时直接用，不重渲）。
- 页面等的办法：自己是计划的发布方，会收到 `task.done`；每 3 秒把同一个计划再发布一次，回包里的状态（`open`）就是「还没有节点认领」，已经完成的计划队列会把完成通知再发一遍。索引到了以后每 2 秒取一次清单，全到齐才开始导。

### 5.3 量到的数

| 比的是什么 | 帧数 | 最低 PSNR | 平均绝对误差（0～255） | 最大差 | 一帧里差超过 32 的像素最多 |
|---|---|---|---|---|---|
| 完整导出 对 桌面导出，全部 90 帧 | 90 | 39.55 | 0.11 | 209 | 3282（共 921600） |
| 　其中同步卡不在场的 30 帧 | 30 | 44.44 | 0.06 | 104 | 1123 |
| 　其中同步卡在场的 60 帧（A、B 也多在这一段） | 60 | 39.55 | 0.14 | 209 | 3282 |
| 快速导出 对 完整导出，全部 90 帧（第四步：三张卡取流） | 90 | 40.47 | 0.31 | 155 | 3305 |
| 快速导出 对 完整导出，只看 A 取流的 45 帧（第一步） | 45 | 45.25 | 0.07 | 155 | 813 |

- 完整导出对桌面导出没有一帧逐像素相同。差在字和圆角的边上（差最大那一帧，差超过 32 的像素都落在药丸卡那一条的范围里）：浏览器导出是把整场景的 HTML 放进 SVG 再画成位图，桌面导出是 Chrome 合成器直接截图，两种光栅的抗锯齿不一样。同步卡不在场、全部由导出页活渲的帧同样有这个差，所以它不是这次引入的；这次之前有没有量过同一个数我没找到。
- 快速导出对完整导出的差是压缩视频的画质差，属预期。
- 耗时（只记录，本机，90 帧）：完整导出 10～12 秒（不算等节点）；快速导出 13～17 秒。**这个项目里快速导出并不比完整导出快**：探针卡在导出页里渲得很快，而快速导出每取一帧流要解码、合成、再编成 PNG 贴进去。快的前提是重卡真的重。没有拿真正重的卡（三维、粒子）量过。
- 等渲染节点：四遍分别是 11、13、302、46 秒。302 秒那一遍只为导出的计划名次还是 0，排在节点手里的快照任务后面；之后提到 70，最后一遍 46 秒（一遍，不能说明稳定在这个数）。

## 6. 没做成的及原因

1. **同步来的卡即使本页舞台里能跑，导出时仍要渲染节点**（第 1.2 节）。没有渲染节点在线就导不出带这类卡的项目，和动手之前一样。借后台舞台逐帧渲（第 2 节的戊）没做。
2. **组流和依赖下层的流，快速导出不取。** 在线页面的层表读法（`parseLayerStreams`）现在只认单卡流和组流的行，依赖下层的那种行要等「下层四」；组流一条盖几张卡，这一版没做贴法。这两类卡在快速导出里照没有流办（本页逐帧渲或渲染节点逐帧渲），画面不受影响，只是不快。合成器的贴法（`pasteLayer`）已经按「舞台坐标、层序取这张卡那一层」写了，导出位图的依赖下层那一种走的就是它（探针里的同步卡）。
3. **单卡流只装得下「框外扩 32 像素」以内的画面。** 卡画到框外更远的地方（探针里药丸卡设了小框时遇到），快速导出取流的帧会被裁掉一截，和预览里贴流时一样；完整导出不受影响。这是流本身的规矩，没有动。
4. **卡片源码还没同步到本页时点导出**，那张卡按未知卡片不画（第 1.2 节最后一行）。动手之前就这样，没有加等待。
5. **「没有渲染节点在线」这句话在节点在线但代码版本和页面对不上时也会出现**（计划写着页面的代码版本，版本不同的节点不认领）。页面分不出这两种情形。
6. **低内存档**：原来「只有判重的卡用预渲染原尺寸」那一支去掉了，现在和别的档一样：包里有代码的卡都由导出页逐帧渲。没有在真手机上跑过；重卡在手机的导出页里渲会不会把页面撑崩不知道。
7. **`online-card-exec-probe.mjs` 的 E10 改了没有重跑**（额度紧）。它原来替渲染节点写 HTML 快照、核「导出页贴快照」，那条路已经走不到，照新做法改成核「没有渲染节点时停在等待、不开导出页」。同样的断言在新探针第二步里是过的。
8. **素材效果卡、转场、带视频的项目没有进端到端探针**（探针项目里没有视频素材）。内置的素材效果卡在导出页里照旧活渲，路径没动；同步来的素材效果卡按同步卡办，源依赖的那一种走单卡流的形状，只有单测盖到切分，没有真跑。
9. 导出位图在素材服务和内容库里不清理（内容寻址，同一份内容再导出时直接用）。全屏不透明的卡（套在视频上的素材效果卡）每帧一张原尺寸 PNG，体积会比较大，没有量。

## 7. 裁定

二级（用户看得出区别）：

1. 〔裁〕**在线导出不再因为「重卡没有预渲染结果」而等。** 包里有代码的卡导出时都由导出页逐帧渲；只有本页不执行的卡才等渲染节点。原来普通档的重卡要等节点把每一帧的快照渲齐。依据是语义里「本页能运行的卡由本页逐帧渲」。
2. 〔裁〕**低内存档导出和别的档同一条规矩**（第 6 节第 6 条）。语义里低内存档已经撤销，但代码里那一支原来还在。
3. 〔裁〕**等待的话从提示条挪进了导出进度窗口**，并且分三种说（没有节点、节点接了、节点渲到第几帧）。
4. 〔裁〕**快速导出里，一张卡只有部分分段是满密度时，这张卡照旧在导出页里活渲，有满密度流的帧贴流、其余帧用活渲的画面。** 整段都有满密度流的卡才不活渲。照的是用户确认过的「只取满密度的分段，其余照完整导出的办法出」。
5. 〔裁〕**节点说渲不了、任务失败、等的时候项目被改，导出直接失败并说明**，不无限等。

三级（用户看不出区别）：第 2 节末尾那几条（键另算、不占指纹锁、不进层表、名次、本机不留）；只挂包裹层用占位卡 id 实现；层表按项目自己的 id 取、任务队列按文档服务的项目号发。

## 8. 对任务书或语义的更正建议

- `docs/semantics/mechanism/platforms.md`「在线执行用户卡与素材效果卡」的「导出页」一条现在写的是「同步来的用户卡与素材效果卡一律用预渲染原尺寸，缺的由导出前的核对拦下并等渲染节点补上」，要改成：导出页不执行；它们的画面导出时取现成的，快速导出先取满密度的轨道流，其余由渲染节点为这次导出逐帧渲成位图（导出位图），没到齐时等。
- `docs/semantics/mechanism/` 里要有一处写导出位图：键怎么算、沿用流任务、不进层表、清单的形状、节点本机不留。建议放 `mechanism/rendering.md`「重管线：预渲染」后面，或 `mechanism/asset-service.md`。
- `docs/semantics/product/platforms.md`「渲染节点」表：三种节点「能认领什么」可以补一句导出位图任务由本机 PC 和独立渲染主机做，纯浏览器不做。
- `docs/semantics/product/platforms.md`「导出」一条写的是「本页不执行的同步用户卡、素材效果卡」，和代码一致；但「在线浏览器执行经文档服务同步来的用户卡与素材效果卡」那几条容易让人以为导出时也执行，建议在「导出」里点明「导出页不执行它们，和预览里能不能运行无关」。
- 派活指令说探针用「桌面预渲染进程当渲染节点」。桌面的预渲染进程在没有页面打开项目时不同步内容库里的卡片源码，渲不了同步来的用户卡；探针用的是独立渲染主机（同一份预渲染进程，不带编辑界面，自己同步卡片源码）。
- 派活指令说「先读 `batch3-common.md`」里提到的契约第 1、2、7 节已过时，这一块没有用到它们。

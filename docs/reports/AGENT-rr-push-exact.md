分支 `claude/rr-push-exact`，工作区 `.worktrees/rr-push-exact`，端口段 27580～27599。任务出处：`docs/reports/AGENT-rr-a1-verify.md` 查到的三条根因（渲染重构「甲一」留下的未达成项），加 `docs/plan/prerender-products-contract.md` 第 2.3、4.2 节要在 `bakeFrame` 上做的两处小改。

本文里几个说法的意思（同那份报告）：

- **顺着做**：第 0、1、2…帧连着向后台舞台要，每帧接着上一帧推一步、生成一张快照。
- **从头推**：先让舞台忘掉上一帧，再要第 N 帧：舞台重新挂载这张卡，从挂载帧一步一步推到第 N 帧，只在第 N 帧生成快照。
- **后台舞台**：在线页面里那个看不见的舞台，浏览器节点用它生成快照，接口是 `src/StageView.tsx` 的 `bakeFrame`。
- **舞台时间**：舞台自己管的时间（`src/render/stageClock.ts`）；**真实的帧**是浏览器真的出的那一帧。
- **〔裁〕**：任务没有写明、我自己拿了主意的地方，主会话可以推翻，汇总在「十」。

## 二、改了什么、为什么这样改

### 1. `src/render/pinAnimations.ts`：动画被拨到结尾，结束回调当场交付

- 现象和原因见那份报告「原因一」：`finish()` 调完，浏览器要等这个文档下一次真实出帧才派发结束事件，舞台推帧不等真实的帧，Motion 就一直以为动画没播完。
- 改法：每次 `sync` / `syncIn` 把该钉的动画全部钉完以后，把这一趟里拨到结尾的那些动画的 `onfinish` 当场调掉。
  - **全部钉完再调**，不是拨一条调一条：回调里会撤动画、改样式，夹在中间的话后面的动画被钉的时候状态已经变了。有单测钉住这个顺序。
  - **同步调，不排微任务**：探针里模拟的是排一个微任务。产品里可见舞台有一条同步推几帧的路（`clock.advanceTo`），排微任务的话几帧的结束回调会攒到最后一起来。同步调以后，动画什么时候算结束只由舞台时间决定。
  - **浏览器之后补发的那一次不能再调一遍**。Motion 的回调会把终值再写一次，那时同一个属性上可能已经起了下一条动画。探针里的做法是把 `onfinish` 置空；产品里改成临时换上一个只吞这一次的占位，吞完换回原来的回调。理由：置空以后这条动画再被重播、再结束，就没有回调可调了（手写「播完再播」循环的卡会停住）。占位记着还欠浏览器几次，重播多次也对得上。回调里自己换掉或摘掉 `onfinish` 的（Motion 的 `attachTimeline` 会置空），以它新挂的为准，不换回去。
- 没管的：用 `addEventListener('finish')` 挂的监听、CSS 动画的 `animationend`、过渡的 `transitionend` 仍然等浏览器出帧。当场补发这几种事件的话，浏览器自己那一次没法只对已经收到的监听拦下，会送两遍。查过 `src/cards`、`src/parts`、`src/render`、`src/kernel` 和 Motion 的源码：没有用这三样的（Motion 只用 `onfinish` 属性和 `finished` 这个 Promise，后者在 `finish()` 里就落定，本来不等出帧）。用户卡如果用了，仍然会不稳定，记在「七」。
- 另加一个只读的口子 `endedInLastSync()`：最近一趟拨到结尾了几条。`bakeFrame` 用它决定这一帧要不要再提交一次。没有改 `sync` 的返回值，是因为 `StageView.tsx` 里别处有把 `sync` 直接当回调返回的写法，改了返回类型那几处要跟着改，而那几处不在我的范围里。

### 2. `src/render/stageClock.ts`：每一步的时刻用帧号直接算

- 现象和原因见那份报告「原因二」：逐帧累加 `1000 / 30`，第 60 帧是 1999.9999999999982 而不是 2000。
- 改法：加一个纯函数 `frameGrid(step, fps?)`，`advanceTo` 和 `advanceToAsync` 每一步落在帧格上，第 k 帧的时刻是 `k / fps * 1000`。这和调用方算目标时刻（`帧号 / fps` 得到秒，再乘 1000）、导出页算时刻是同一个式子、同一个运算顺序，逐位相同。
  - 帧率由调用方给（新加的可选项 `fps`，`bakeFrame` 传了）；没给时从步长认：步长正好是整数帧率的一帧就认得出来。别的调用方（节拍循环、`setTime`、测量、互换）都是按 `1000 / fps` 给步长，不用改就走上了帧格。这样做是因为那些调用处不在我的范围里。认不出帧率的步长用 `k * 步长`，同样不累加。
  - 起点不在帧格上（被 `set` 拨过、被 6 秒补跑上限削过）时第一步走到下一个帧格；目标不在帧格上时最后一步走到目标本身；起点或目标只差浮点尾数（百万分之一帧以内）时不为它多跑一拍。
- 新加单测 `src/render/stageClock.test.mjs`（18 条）：24、25、30、60 帧/秒各从头推 20 秒逐帧等于直接算的值；一帧一帧接着推每帧正好一拍；隔几帧取一张；起点、终点不在帧格上；补跑上限；同步和让出两个函数走同一串时刻。

### 3. `src/StageView.tsx` 的 `bakeFrame`：每一帧收尾都把 React 排下的更新提交完

这一处和那份报告的建议不完全一样，说明如下。

- 那份报告的建议是「生成快照之前等 React 提交」，探针里的模拟是推完以后等两轮消息。照这个做，14 张卡里 `mu-word-rotate` 仍有两帧画面不同（第 45、497 帧，换进来的词位移差一帧）。查到两个原因：
  - 改状态的那一下藏在一串 Promise 回调后面（Motion 的「全部退场动画播完」），我发消息的时候 React 还没把这次渲染交给调度器，我的消息排在它前面，等回来时它还没跑。
  - React 提交完以后要先让浏览器画一帧，再在下一个任务里跑副作用（Motion 在副作用里起新动画，并记下「此刻」当起点）。从头推时下一帧的时钟先拨过去了，副作用才跑，起点就晚一帧。
- 所以改成不靠等：新加 `bakeSettle`，一轮两步。先让出一个宏任务（把微任务链排空，那一下 `setState` 才真的发生）；再同步提交一次（`flushSync` 带一次真的状态变化，用的是这个文件里现成的 `bumpPlanes`）。同步提交会把同一棵树上排着的更新一起做掉，副作用也当场跑完，都落在这一帧的时刻上。这一轮里 DOM 变了就再做一轮，最多 4 轮（同导出页 `settleDom` 的上限）。
- **两条路推的每一帧都收尾，不只是生成快照的那一帧**（挂载帧也算）。顺着做和从头推的差别只剩两帧之间隔了多久，而一帧做完时已经没有挂着没提交的东西，隔多久就不影响结果。只在生成快照前等的话，从头推路过的那些帧仍然是「提交落在下一帧」，和顺着做对不上。
- 一帧收尾的顺序是：提交 → 钉动画（拨到结尾的当场交付结束回调）→ 这一帧有动画结束就再提交一次 → 等 GL 位图。和导出页一帧的顺序相同（`server/bakery/bake.mjs` 的 `createStepper`：排空 → 钉动画 → 排空）。原来是先钉动画、提交落在后面；现在提交里新挂的元素的 CSS 动画在这一帧就被钉住，和导出一致。
- 这个做法依赖 React 19 的一条行为：同步提交会连同一棵树上排着的普通优先级更新一起做。React 换了这条行为的话探针会红（退回「等一轮消息」的效果）。用 `startTransition` 排的更新不在其内，内置卡没有用的。

### 4. 两处小改

- **接续条件**（契约第 2.3 节）：从「上一帧正好是目标帧减一」改成「上一帧不晚于目标帧」。隔 15 帧取一张时接着推，中间的帧只推不生成快照；同一帧再要一次不再推。另加一条核对：舞台时钟要正好停在上一帧的时刻上才算接得上，被别人拨过就从头推〔裁〕。`batch4` 另要求两帧在同一批里，保住「每批从头推」（这个模式现在没有调用方用，`BAKE_MODE` 是 `seq`）。
- **remotion 式的卡直接拨**（契约第 4.2 节）：隔离工程里唯一那张卡是 remotion 式时，把时钟拨到目标帧、提交、跑这一帧的一拍、收尾，不重挂载、不逐帧推；回包的 `remounted` 恒为 `false`。判据照主会话中途的要求，和 `server/frame-stream.mjs` 的 `streamNeedsReplay` 相同：取卡的能力表里的写法是 `direct`、并且没有声明要预渲染；认不出来的卡、这台设备跑不了的卡按有状态处理。
  - 证明不改画面：`caption-track`、`av-pulse`、`probe-slow` 三张 remotion 式的卡，改之前（重挂载加逐帧推）和改之后（直接拨）各顺着做 91 帧，逐帧相同。
- 时钟没落在目标帧上（不该发生）时原来是补一次提交照样生成快照，现在改成按可重试交回，不拿别的时刻的画面充数〔裁〕。

## 六、对可见舞台、桌面预渲染、导出各有没有影响（实测）

## 八、没做成的、没验的

1. 用 `addEventListener('finish')`、`animationend`、`transitionend` 等动画结束的卡仍然等浏览器出帧（「二」第 1 条）。内置卡没有；用户卡有的话仍可能不稳定。
2. 可见舞台、测量、互换那几条路没有「每帧提交 React 更新」这一步，只有 `bakeFrame` 有。它们在 `StageView.tsx` 里不归我改。其中**测量的快照趟**现在仍然是「钉完动画立刻生成快照」，原因三在那条路上还在；「稀疏二」要让测量趟顺便产这一套快照，产出来的会和 `bakeFrame` 产的在 `mu-circular-progress`、`terminal-3d` 这类卡上差一帧。见「九」第 3 条。
3. 没有拿导出页的快照和后台舞台的快照逐帧对过。一帧收尾的顺序照导出页排了，但导出页在有动画结束的那一帧会再多跑两拍（`createStepper` 里 `probe.finished` 那一段），后台舞台没有照做。所以 `mu-word-rotate` 换进来的词，后台舞台可能比导出晚一帧开始动。这一句是读代码的推断。
4. `mu-number-ticker`、`chapter-bar` 在可见舞台逐帧走和后台舞台之间的不同（「六」）没有查原因，改前就有。
5. 从没推过帧的新舞台上第一下就从头推，字体还没载完的情形没有单独验（探针里每张卡先顺着做一遍，字体那时已经载完）。
6. 部件 `text-rotate`、`composite`、`lottie`、画布卡没有核对（同那份报告）。
7. 可见舞台按片段追帧的那一处（`StageView.tsx` 里 `stageMs + stepMs` 累加）仍然是累加，不归我改。

## 九、要主会话决定或注意的事

1. **导出像素基线对 `89c15177` 已经在 `main` 上变了**（36 帧，见「四」）。和我的改动无关，但之后每一块照 `89c15177` 比都会报。基准要不要挪、那 36 帧要不要用户过目，由主会话定。
2. **旧快照要不要作废**（「五」）。我的看法是不用单独处理：「庚」落地时全部快照换键一次，那三张卡的旧快照跟着作废；庚如果不在这一版里落地，再考虑给快照的键加一项。
3. **给「稀疏二」的话**：
   - 测量的快照趟要和 `bakeFrame` 产出同一份快照的话，每帧生成快照之前要走同一套收尾。现成的是 `bakeSettle`（提交 React 更新）和 `pinner.endedInLastSync()`，顺序见 `bakeFrame` 里的 `frameEnd`。
   - `src/editor/stageBake.ts` 推完一帧会先发「下一帧」（帧号加一）。隔 15 帧取一张时，节点真要的是加 15 那一帧，先发的那一帧会被作废。作废时它如果还没做完，接续点就丢了，下一帧从头推。结果仍然是对的（两条路现在产出相同），只是白推。先发的那一帧改成「这一套里的下一帧」就没有这个问题。
4. **从头推快了十来倍**（「六」）。`docs/plan/render-standard.md` 里「每推一帧约 4.8 毫秒」「20 秒的卡最深处约 3 秒」那组数字过期了。原来那 4 毫秒不是有意的节流；要是有人指望它限着后台舞台的占用，现在没有了。
5. 合并时 `src/StageView.tsx` 会和「稀疏二」碰。我动的地方：文件头的一行 `import`（加了 `cardCapabilities`）、`bakeGen` / `bakeCursor` 下面新加的 `bakeSettle`、`bakeFrame` 的注释和推帧那一段、回包里 `remounted` 那一处。`render` 的测量那一支没有动。
6. `stageClock.ts` 的 `advanceToAsync` 多了一个可选项 `fps`。别的调用方不传也走帧格（整数帧率认得出来），要逐位精确到非整数帧率就传。

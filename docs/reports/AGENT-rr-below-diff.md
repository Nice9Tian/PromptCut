# 子 Agent 报告：下层二（依赖下层的卡的流：流里的像素怎么取）

分支 `claude/rr-below-diff`，从 `main`（`84f4bb68`）分出，交活前照主会话的通知把 `main`（`80bd5435`，含「甲二」，即在线页面自己产流那一项）合了进来，下面的验证都在合并以后的代码上跑。任务书 `docs/plan/render-refactor-task.md`「戊二」，契约 `docs/plan/prerender-products-contract.md` 第 5.3 节。

「下层二」是「戊二：依赖下层的卡也产轨道流」拆出的四块里的第二块：先用探针量「每帧截两张」的耗时和编码以后的误差，据此定流里放什么，再把定下来的取法接进产流。「下层一」（计划、键、隔离工程，已合入）在它前面；贴回舞台是「下层三」，在线页面怎么读是「下层四」。

几个词：

- **依赖下层的卡**：毛玻璃这一类，画面要采样自己下面的层；审阅表没覆盖到的卡（用户和 Agent 建的）也按这一类处理。
- **差分取层**：每一帧截两张，一张带目标卡、一张把目标卡藏起来，算出「盖在后一张上正好得到前一张」的那一层，流里存这一层。
- **原样盖**：直接把带着下层的画面裁出来存进流，贴回舞台时整块盖上去。
- **上张 / 下张**：带目标卡的那张截图 / 藏起目标卡的那张截图。

## 0. 结论

1. **定为差分取层，做成了。** 两个场景、两种画幅里，差分取层编码以后的误差都明显小于原样盖（甲：1.38 对 3.26、0.88 对 1.43；乙：0.68 对 6.71、0.70 对 5.32；满分 255），多花的时间是每帧几十毫秒，只在预渲染时花。数字在第 1 节。
2. **契约第 5.3 节的算式照字面做不成，改了三处〔裁〕。** 照字面做，甲 960×540 里编码以后的误差比原样盖还大（3.31 对 3.26），流是原样盖的 6 倍大（1920×1080 是 4 倍大）；乙里编码前就有整像素算错（最大差 254）。原因和改法在第 2.2 节。改完以后才是上面那组数。
3. **取两张不扰动页面，实测成立。** 藏目标卡用的是在同一个页面上压一条样式，不重灌、不推时间。四组场景各 90 帧：上张和只截一张时逐字节相同，下张和「只有下层」的工程照导出的办法渲出来的同一帧逐像素相同。产流时每个分段的第一帧还会再实测一次，不过就不交帧。
4. **截图矩形不能跟着收紧。** 把截图矩形收紧到目标卡那一块以后，毛玻璃和带阴影的下层靠边的像素会变（实测最大差 127）。所以两张都截整幅，算完再裁；流仍然只含目标卡改动的那一块。
5. 开关仍然缺省关，合进 `main` 以后产品行为不变。`BELOW_STREAM_VERSION` 加到了 1。**全部轨道流的键会换一次**（新文件进了截图代码的指纹名单），卡片的键、快照的键、卡片声音都不变。
6. **顺带查出 `main` 上原有的一个问题**（不在这一块的范围里，没有改）：带强调（阴影、描边）的卡，改卡片参数以后它自己的单卡流键和共享快照键不变。见第 7 节第 1 条。

## 1. 要报给用户的两组数

机器：这台 PC（i7-14700KF，Windows 11，无头壳 152，软件光栅化，ffmpeg 9.0.1，`libx264`）。量的时候机器上还有别的子 Agent 在跑，耗时的个位数不可信。耗时只记录，不是通过条件。场景「甲」是毛玻璃卡压在一张会动的卡（粒子）和一段视频上面；「乙」是下层半透明（不透明度 0.6、带阴影的药丸，底下是透明的），上面压同一张毛玻璃卡。每个场景 3 秒、90 帧。

| 甲，960×540 | 满密度 | 16.9 | 50.0 | 33.1 | 1.53 |
| 甲，1920×1080 | 稀疏 | 57.5 | 143.2 | 85.7 | 1.00 |
| 甲，1920×1080 | 满密度 | 31.4 | 101.4 | 70.0 | 1.74 |
| 乙，960×540 | 稀疏 | 22.4 | 54.9 | 32.6 | 1.76 |
| 乙，960×540 | 满密度 | 10.6 | 39.7 | 29.1 | 2.97 |
| 乙，1920×1080 | 稀疏 | 67.9 | 147.6 | 79.7 | 1.91 |

### 1.2 误差

把流里的那一层盖回「同一时刻只有下层的导出画面」上，和「同一时刻整幅的导出画面」比。按预乘色，满分 255，只在流的矩形里比，四个通道一起算。「差超过 16 的像素」指四个通道里最大的差超过 16 的像素占矩形的比例。

| 场景，画幅 | 哪一步 | 差分取层 | 原样盖 |
|---|---|---|---|
| 甲，960×540 | 编码前：平均 / 最大 | 0.07 / 1.0 | 0 / 0 |
| | 经 H.264 编码解码后：平均 | **1.38** | **3.26** |
| | 编码后：差超过 16 的像素 | 3.3% | 9.5% |
| 甲，1920×1080 | 编码前：平均 / 最大 | 0.07 / 1.0 | 0 / 0 |
| | 编码后：平均 | **0.88** | **1.43** |
| | 编码后：差超过 16 的像素 | 1.1% | 1.8% |
| 乙，960×540 | 编码前：平均 / 最大 | 0.10 / 1.6 | 6.63 / 63.8 |
| | 编码后：平均 | **0.68** | **6.71** |
| | 编码后：差超过 16 的像素 | 0.4% | 26.5% |
| 乙，1920×1080 | 编码前：平均 / 最大 | 0.12 / 1.6 | 5.26 / 63.8 |
| | 编码后：平均 | **0.70** | **5.32** |
| | 编码后：差超过 16 的像素 | 0.2% | 11.5% |

怎么读这张表：

- **编码前**，下层不透明时（甲）原样盖没有误差，差分取层有不到一级的误差（算式里放宽的那一级，见第 2.2 节）。下层半透明时（乙）原样盖把半透明的下层叠了两遍，平均差 5～7、最大 64；差分取层仍在两级以内。这和契约里那次静态小实验的结论一致。
- **编码后**，甲里差分取层反而比原样盖好一倍。原因：原样盖把矩形里毛玻璃以外的下层（清晰的视频、粒子的细线）也编进了流，这些清晰的彩色边缘过 4:2:0 的编码损失最大；差分取层在那一圈只存一层平滑的阴影，清晰的下层由舞台上活着的那一层出。
- 作参照的「编码本身的误差」（把整幅的导出画面原样过一遍同一个编码器再和自己比）：甲 3.26、1.45，乙 1.05、0.90。差分取层四组都低于它。
- 编码后的最大差两种办法都在 88～244 之间，都落在白字的边缘上（色度减半采样的老问题，现有的单卡流同样有），不是算错。
- **对照**（同一帧盖回去的画面和 7 帧以后的整幅画面比）：平均 7.5～14.2，是同一帧的 9～11 倍。这套比法分得出帧对不对。

另外量了两样，「下层三」贴回舞台时用得上：

| 场景，画幅 | 下层错开一帧时的平均差：差分取层 / 原样盖 | 90 帧的流有多大：差分取层 / 原样盖 |
|---|---|---|
| 甲，960×540 | 3.39 / 6.88 | 99 KB / 355 KB |
| 甲，1920×1080 | 2.81 / 4.30 | 180 KB / 319 KB |
| 乙，960×540 | 2.67 / 8.44 | 101 KB / 130 KB |
| 乙，1920×1080 | 2.73 / 7.12 | 224 KB / 276 KB |

「下层错开一帧」是流取第 f 帧、下层和真画面都取第 f+1 帧：播放时视频和活渲的卡常常和流差这么多。

## 2. 做了什么

### 2.1 怎么取两张（新文件 `server/bakery/capture-below.mjs`）

- **藏目标卡的办法**：不重灌页面、不推时间、不动 React。往 `<head>` 加一条带 `!important` 的样式，把目标卡那一层的不透明度压成 0，截完原样撤掉。照 `server/bakery/chrome.mjs` 里毛玻璃遮罩那一套的做法：只压过渡的时长，撤的时候分两步，不惊动正在跑的动画。藏完读一次算出来的不透明度，不是 0 就报错。
- **为什么不用「不带目标卡的隔离工程」另渲一遍**：那样下层要在另一个页面上重新走一遍，目标卡要是在挂载或动画里用过随机数，下层的随机序列就和带目标卡时不一样了，不能保证是同一帧的状态；还要多付一遍推帧。在同一个页面上藏，下层的 DOM、动画、素材、画布一样都没动。`isolatedBelowProject` 的 `withTarget: false` 只在探针里用来渲对照。
- **顺序固定**：上张（`bakeStream` 原来那一次截图）→ 藏 → 下张 → 撤。藏了以后不管截图成没成都撤。
- **每个分段的第一帧实测两条**（多截两张）：藏着的时候再截一张，要和下张逐字节相同（截到的不是合成器里上一拍的旧图）；撤掉以后再截一张，要和上张逐字节相同（藏和撤没有改动页面，页面在多出来的几拍里自己也没有变）。
  - 前一条不成立：这个分段失败重产，这条流以后每张下张先丢一张再截。
  - 后一条不成立：这条流判死（记诊断），不再产。自动生产每个分段记三次失败以后不再挑它；队列的任务报不可重试。这张卡就和没有这种流时一样。
- **目标卡不在页面上的帧**（入场前、出场后）：不藏、不截第二张，交出一张全透明的。
- **截图矩形恒为整幅**，交给编码器的是裁到这一趟的矩形的那一层（稀疏那一趟是整幅，第二趟是收紧矩形）。原因见第 0 节第 4 条，数字在第 3.2 节。
- **目标卡改到了收紧矩形外面**（稀疏那一趟每 3 帧才量一次，中间的帧可能超出；这种流按舞台坐标产，带着轨迹）：满密度那一趟查得出来，把收紧矩形放大、这个分段按新矩形重来，不算失败。已经按旧矩形产好的分段签名对不上，会自己重产。

### 2.2 算那一层的算式，和契约差在哪〔裁〕

按预乘色，每个像素要满足 `R色 = S色 + L色 × (1 − a)`、`R的不透明度 = a + L的不透明度 × (1 − a)`、`0 ≤ S色 ≤ a ≤ 1`。a 定了 S色 就定了，所以只要定 a。两张相同取 0、下层全透明时 S 就是 R、下层不透明时取能让 S色 不出界的最小值，这三条和契约一样。改的三处：

1. **颜色的下限放宽一级。** 契约的两条下限是拿两张截图的差去除以 `L色`（或 `1 − L色`）。两张截图各自四舍五入到 8 位，差本来就有一级左右的噪声；除数很小时噪声被放大成整张不透明。实测甲里纯色的视频底上有的通道只有 1、2 级（例如下层是 (0, 255, 2)，压上阴影以后是 (0, 238, 1)：照蓝色那个通道算不透明度是 0.5，照绿色算才是该有的 0.07），阴影那一圈的不透明度在该有的值和 1 之间乱跳。960×540 里流是原样盖的 6 倍大（2.07 MB 对 355 KB），编码以后误差 3.31，比原样盖的 3.26 还大；1920×1080 里流是 4 倍大（1.38 MB 对 319 KB），编码以后误差 1.08（产品里用的是 0.88）。改法：每条下限按自己的除数放宽，除数接近 1 的几乎不放，接近 0 的等于不看。代价是盖回去的颜色最多差一级（上表「编码前」那 0.07～0.12）。
2. **下层半透明时，不透明度和颜色的误差两头各让一点。** 契约取「不透明度那条式子」和颜色下限里最大的那个，等于颜色一级都不让、全让不透明度去凑。乙里碰到的像素：下层是不透明度 1/255 的蓝、带目标卡的画面是不透明度 1/255 的黑（预乘以后两个都是 0），照契约算出来是完全不透明，盖回去不透明度差 254 级；全场景平均差 2.06～2.21。改法：颜色要的下限比不透明度那条式子给的大时，取使两种误差相等的那个值。下层完全不透明时它和契约的写法是同一个数（单测 `BD-contract` 钉住了）。
3. **毛玻璃的外框里、下层完全不透明的像素，a 取 1（S 就是 R）。** 这些像素上 a 从最小值到 1 随便取，盖回同一张下层都等于原画面。取最小值时，S 的不透明度是一张跟着下层细节起伏的图：贴回舞台时下层只要和产流时差一点，下层的清晰细节就会从本该模糊的玻璃里透出来（看了图，粒子的连线在玻璃里隐约可见）；编码也更费（甲 960×540：435 KB 对 99 KB，差超过 16 的像素 5.0% 对 3.3%）。外框由页面在藏之前量（目标卡里看得见、真的在滤下层、没有旋转的毛玻璃元素的框和圆角）。量错了也不会算错像素：它只在「怎么取都对」的像素里挑一个。

三处都是用户看不出区别的改法（三级）。和用户原话的关系：第 3 处让毛玻璃那一块在流里是「带着下层」的整块画面，比契约的写法更接近原话；玻璃以外仍然只存目标卡自己的那一层。

## 3. 量出来的别的数

### 3.1 取两张扰不扰动页面

四组（两个场景 × 两种画幅），每组 90 帧：

- 两张那一趟的上张，和只截一张那一趟的同一帧：逐字节相同 90/90。
- 上张和「带目标卡」的工程照导出的办法（`bakeFrames`）渲出来的同一帧：逐像素相同，90 帧 0 个像素不同。
- 下张和「只有下层」的工程照导出的办法渲出来的同一帧：逐像素相同，90 帧 0 个像素不同。
- 每个分段第一帧的两条实测：全过，没有一次打开「下张先丢一张」。

### 3.2 截图矩形收紧以后画面变不变

只截一张，按收紧矩形截，和整幅截的同一帧裁出来比（各 30 帧）：

| 场景，画幅 | 有几帧不同 | 一共多少像素不同 | 最大差 | 落在哪 |
|---|---|---|---|---|
| 甲，960×540 | 24 | 1224 | 3 | 毛玻璃里面 |
| 甲，1920×1080 | 0 | 0 | 0 | |
| 乙，960×540 | 28 | 12974 | 127 | 收紧矩形右边大半：药丸（半透明、带阴影滤镜）所在的那一侧 |
| 乙，1920×1080 | 3 | 563 | 13 | 同上 |

### 3.3 四种放法并排（甲，960×540，90 帧）

## 7. 要主会话决定或注意的

1. **`main` 上原有的问题：带强调（阴影、描边）的卡，改卡片参数以后单卡流键和共享快照键不变。** 探针的乙场景里碰到的：药丸带着阴影，把它的文字从「半透明的下层」改成「半透明的下层(改过)」，它的 `streamMemberKey`、`contentKey`、`snapshotKey` 都没变，只有 `cacheContentKey` 变了；去掉强调以后再改，三个键都变。原因：片段带强调时卡片图的出画节点是强调那个节点（`src/kernel/cardGraph.mjs` 第 174 行），`server/card-cache.mjs` 给它算共享快照键和流的成员键时把上游剥掉了（`inputKeys: {}`），于是键里只有强调自己的参数，没有前面那张卡的参数，连是哪张卡都没有。后果是这种卡改了参数以后，旧的流和旧的快照会被接着贴；两张不同的卡只要强调参数、框、时长相同，还会共用一份。没有去查它从哪一次改动开始。**我没有改**：它改的是单卡流和快照的键，不在这一块的范围里。依赖下层的流的键取的是带整条输入链的缓存内容键，不受它影响（乙里这条流的键照常变了）。
2. **全部轨道流的键换一次**（第 9 节）。以后每改一次 `capture-below.mjs`，单卡流和组流也会跟着作废，虽然它只管依赖下层的流。派活指令点名要把它加进名单，照做了；要是不想让它牵连别的流，可以不进名单、只靠 `BELOW_STREAM_VERSION` 管，代价是改了代码忘了加版本号时没有兜底。
3. **开关打开以后仍然不要拿它开编辑器看画面。** 生产者会把这种流的层发出去（就绪索引里是普通的 `kind: 'stream'`，不带「这是依赖下层的流」的标记，只有流的清单里写着 `kind: 'below'`、`plane: 'stage'`），而舞台还不认。
4. **「下层三」贴的时候**：玻璃以外那一圈（阴影）流里只有一层半透明的黑，要靠舞台上活着的下层才是完整的画面；玻璃里面流是不透明的整块。下层这一拍不是它该有的画面时两处的表现不同，数在第 1.2 节末尾那张表。
5. **编码以后的最大差**在白字边缘上有 88～244（两种办法都有，现有的单卡流也有）。这是编码参数的事，不在这一块里。
6. **毛玻璃掩码管不到的两种情形**：旋转过的毛玻璃、自己或祖先半透明（或带滤镜）的毛玻璃不进掩码，照最小的不透明度算。盖回同一帧的下层仍然等于原画面（误差的数不变），但贴回舞台时下层和流错开的话，下层的清晰细节会从玻璃里透出来一些。淡入淡出期间的毛玻璃卡属于后一种（那时浏览器本来也不模糊下层）。
7. **下层在多出来的几拍里自己会变的页面**（例如下层的卡里有一张动图）：每个分段第一帧的实测会比出来，这张卡就没有这种流，照没有流时那样兜底。内置卡和两个场景里没有碰到。

## 10. 「下层三」接着做时要知道的

- **探针怎么接**：`node scripts/probes/stream-below-probe.mjs --origin <开发服务器> --keep` 会留下每个场景的流库（`<out>/lib-<场景>-<画幅>`）和两幅导出画面，结论里有流键、收紧矩形、每个分段的文件名。播放那一头把「ffmpeg 解出来的帧」换成舞台截图，再用 `below-stream-common.mjs` 里的 `tallyDecoded`、`composeDecoded` 那一套比即可。场景项目是 `scenarioProject(kind, { width, height, mediaUrl, edit })`，`edit` 给 `'below'`、`'above'` 就是改下层、加上层的那两版。
- **流的清单**：`header.kind` 是 `below`，`plane` 是 `stage`，`offset` 是零，每个分段的矩形在它用的那个 `init` 的 `rect` 里（舞台坐标）。稀疏分段的矩形是整幅，满密度的是收紧矩形；收紧矩形中途可能被放大（旧分段会自己重产）。
- **流里是什么**：一层预乘色加不透明度，照普通的叠加盖在目标卡下面那些层上面就是带目标卡的画面。目标卡的包裹层外观（位置、缩放、不透明度、淡入淡出、轨迹、强调）都已经在流里。
- **诊断**：`status().streams[]` 的 `below`。`failed` 有值就是这条流产不出来（下层在多出来的几拍里自己会变的页面），这张卡要照没有流时那样兜底。
- 开关打开的办法没变：环境变量 `PROMPTCUT_TEST_BELOW_STREAMS=1`，或给 `planStreams` 传 `below: true`。

## 两条要先说的结论

- **低内存档的规则没有被动。** `X-c10a-demo-local` 的两条不过在 main（`7a06c392`）上同样不过，是探针断言的问题；播放中「所有卡都抑制着、不活渲」那一条在每一遍里都过。
- **渲染服务不会误杀无关进程。** 结束进程用的 `taskkill /T` 实测不跟「父进程号已被重用」的陈旧父子关系走。但渲染服务自己按父子关系找进程树的两处（`treePids` 与 Windows 内存看护）会把无关进程算进去：前者只影响探针与单测的「没有残留」核对，后者会把无关进程的内存算进工作进程树、可能误判超限后结束**自己的**工作进程。两处都已修（只影响 Windows；生产节点是 Linux，孤儿改挂 1 号进程，没有这个问题）。

## 改过的断言（旧 → 新 → 依据）

1. `c10a-demo-probe`「补渲细任务排在本机判重的任务之后」
   - 旧：所有 `backfill` 认领都排在最后一个 `normal` 认领之后。
   - 新：排在 `normal` 前面的 `backfill` 认领，只有「认领时刻不晚于创建方 `normal` 计划的发布时刻加 1 秒」才放过；`normal` 发布之后、认完之前出现的仍判不过。
   - 依据：`mechanism/document-service.md`「优先级」——节点先认 `normal`，没有了才认 `backfill`。手机的补渲计划先发布约 1 秒，节点那时没有 `normal` 的活。
2. `c10a-demo-probe`「手机播放中判轻的轻卡不活渲、没有产物显示占位」
   - 旧：只认「抑制着、显示占位、没有小尺寸」。
   - 新：按手机层表里这张卡有没有就绪产物分两支——没有产物显示占位；有产物贴小尺寸。另加一条：播放中采到的每一拍它都抑制着。
   - 依据：`mechanism/rendering.md`「低内存档」——播放中一律不活渲，有产物贴小尺寸、没有才占位。创建者那边忙时会把轻卡判重、连它一起预渲染。
3. `desktop-auto-node-probe` A3
   - 旧：在线页面贴出用户卡 U1 的层；U1 那一层写进云端层表。
   - 新：在线页面贴出判重的 H 的层（出自这台桌面的环境）；U1 按在不在在线页面的清单计划里分两路——不在：直接活渲、没有占位与图标徽标、不在清单计划里；在：层贴得出来、云端层表里有。
   - 依据：`product/platforms.md`（决定 C）——在线浏览器能执行仓库用户卡，判轻的在浏览器里跑。
4. `desktop-auto-node-probe` A4
   - 旧：在线页面改用户卡 U2 的文字，新清单计划被桌面节点认领、渲出、贴上。
   - 新：改判重的 H 的 `label`，其余断言不变，另加「新那一层出自这台桌面的环境」。
   - 依据：同上；这一步要验的是桌面节点认领在线页面发布的**判重**任务。
5. `c10-browser-probe --user-card`
   - 旧：不分路，先要求「成员页直接活渲、没有快照与图标」。
   - 新：先等成员页发布清单计划；不在计划里才断言直接活渲，在计划里走原有的「渲染节点渲出、层表里有、舞台上是快照或活画面、没有图标与徽标」。
   - 依据：`pipelinePlan.mjs`（K2 逐位置贪心）——同位置的重卡把轻卡挤出一拍的预算时，它整段进预渲染集合。

# AGENT-busy-mclean-a6cd97：测试文件整份失败（sp-store 那次）的根因与兜底

分支 `claude/busy-mclean-a6cd97`，起点 main `42e691c`。会话「查 sp-store 测试负载下加载失败」（由主会话的任务卡片开出）。

## 结论

- **根因**：Node v24.19.0 在 Windows 上的已知缺陷 [nodejs/node#65756](https://github.com/nodejs/node/issues/65756)。测试运行器以进程隔离方式起的子进程偶发以 0xC0000005（访问违例）原生崩溃，没有任何输出，每次落在不同的文件上。上游抓到的原生转储显示：`ContextifyScript` 析构时经 `CppgcMixin::~CppgcMixin()` 写进了已释放的 Realm（释放后使用）。修复是 [nodejs/node#65778](https://github.com/nodejs/node/pull/65778)（main 上的 `c909c63`），已随 v26.10.0 发布；v24.x 的回移 [#66168](https://github.com/nodejs/node/pull/66168) 还没合，目前没有任何 v24 发布版带这个修复。
- **sp-store 本身没有问题**：它的导入链加载时没有 I/O 和进程级副作用；模块 mock、全局 setup、临时目录、端口都不是原因。它只是那一次被轮到的文件。
- **仓库内的修法是兜底，不是根治**：`npm test` 改由 `scripts/test-suite.mjs` 启动原来的全量命令。测试文件的进程异常终止时，打印退出码与含义，并单独重跑该文件；断言失败与加载错误照常算失败。根治要等换到带 #65778 的 Node。

上游状态是 2026-09-28 用 `gh` 核对的；分支在 2026-10-05 合入了 main `adc3ae2a`，验证是在合入之后做的。

「同源」的把握：本机加压复现抓到的 5 次（全量 1 次、单文件循环 4 次）都是 0xC0000005、都没有输出、都只发生在测试子进程里，与上游一致；而 20 个不经测试运行器的自校验进程各跑 300 秒，零崩溃、零算错。sp-store 那次的退出码当时没有记录（spec 报告不打印），所以它是「同源的最有力解释」，没有逐次取证。和上游不同的一点：上游多是用例全报通过之后才崩，本机抓到的几次在第一条用例报出之前就崩了。

## 现象

- 2026-09-28 09:43:00–09:43:43Z，`.worktrees/merge-test2`（main `f550b02` 加 e6r 合并 `42e691c`）的全量 `npm test`：`server/test/sp-store.test.mjs` 整份失败。spec 只有 `test at …:1:1 / ✖ … (49.9721ms) / 'test failed'`，没有断言、没有 stderr；总条数 3763 → 3755（9 条没报出，多 1 条文件级失败，净减 8）。日志 `%TEMP%\e6r-test.log`。
- 单独跑 9/9 过，重跑全量 3763/3761/0/2。

## 证据链

1. **失败那 43 秒里机器上在干什么**（主会话的任务输出与日志时间戳对出来的）：stall-phases 子 Agent 的几次全量在 09:40:48–09:41:32、09:42:07–09:42:50、09:44:49–09:45:32Z，和出事那次（09:43:00–09:43:43Z）不重叠；跨机探针 w7 在 09:39:45–09:52:13Z 一直在等节点、没有动作。负载主要来自这次全量自己（27 个文件进程跑在 28 个逻辑核上）。
2. **Node 24 运行器怎么报这种失败**：子进程非 0 退出时报 `ERR_TEST_FAILURE('test failed')`，退出码挂在 error 上，但 spec 报告只打印 `cause`，所以日志里看不到退出码；TAP 报告会打印。子进程的 stderr 在 exit 与 stdout 结束后才 `rl.close()`，末尾行理论上可能丢，但本机另外两次文件级失败（开发中真实的加载错误）stderr 都完整。出事那次一行 stderr 都没有，说明子进程没跑到能打错误的地方。
3. **插桩全量**（预加载脚本给每个 node 进程记起止、子进程退出码、每次按 PID 结束进程及目标当时是否已退出）：1 份单跑 + 12 份加压（两个 worktree 同时跑全量 + 16 个忙循环，6 轮）。每份 433 个测试文件进程、6 次按 PID 结束进程，**旧 PID 结束 0 次**；node 起的子进程没有一个以 NTSTATUS 码退出；加压时空闲提交内存始终 ≥ 20 GB。
4. **加压复现**：12 份里 1 份出现同形态失败——`src/kernel/diffProjectEquiv.test.mjs`，TAP 记下 `exitCode: 3221225477`（0xC0000005），约 7 秒，一条用例都没报，没有 stderr；该文件子进程有「起」没有「止」。另外第 1 轮有 2 条是人为压满 CPU 造成的时限失败（c66-integ 60 s 超时、media-hash 100 ms 时延门槛），不是本现象。
5. **单文件循环 + 自校验**（5 分钟重负载）：照运行器的起法（`NODE_TEST_CONTEXT=child-v8`、`--experimental-test-module-mocks <file>`，不经运行器、stdout 丢弃）循环起 diffProjectEquiv 277 次，**2 次 0xC0000005**（2.4 s、2.8 s）；同时 20 个自校验进程（SHA-256、纯 JS 整数哈希、JSON 往返，结果与第一轮逐次比对）各跑 300 秒，**零不一致、零崩溃**。CPU 时间是测试子进程那边的约 7 倍，却一次没出事，所以不像 CPU 随机算错。
6. **崩在哪一段**：`node --test --test-reporter=tap <file>` 8 路循环 + 12 个自校验进程，224 次里 2 次崩溃，都在第一条用例（V8B-1）报出之前（2.4 s、4.6 s）。
7. **上游核对**（用 `gh` 读 issue、PR 与发布说明）：#65756 的报告者在 GitHub 的 Windows 机器上 v24.19.0 / v24.20.0 / v26.8.1 都复现过，`--test-isolation=none` 90 轮 0 次，驱动自己逐文件起 `node --test --test-isolation=none` 约 1.5 万个进程 0 次；另一位贡献者在 v26.8.1 抓到原生转储，把 #65778 的补丁打到 v24.20.0 上 300 轮零崩溃，不打的第 21 轮就崩。#65778 已进 v26.10.0 的发布说明；v24.21.0 不含；v24.x 回移 #66168 仍是 open。
8. **本机环境**：Windows 11 26200，i7-14700KF（20 核 28 线程，微码 0x12F，BIOS 1825 / 2025-10），交互桌面堆 20 MB（SharedSection=1024,20480,768），TCP 动态端口 1024～15000。事件日志在出事时段没有应用崩溃、Defender、WHEA、资源耗尽记录（node 子进程继承了关掉崩溃报告的错误模式，访问违例本来也不会进 WER）。

## 顺带发现（不是本次原因，没改）

几处代码在子进程可能已经退出之后仍按它的 PID `taskkill /T /F`：`server/vision/worker-pool.ts` 在 worker 的 exit 回调里杀（每次都是旧 PID）、`server/vite-plugin-skill.ts` 按 instance.json 里存的 PID 杀、`server/runners/setup.mjs` 与 `server/runners/index.mjs` 的中止路径、几个 vite 插件的取消与超时路径，以及 `scripts/probes/c10-*.mjs` 按裸 PID 杀和按端口找进程杀。实测 `taskkill` 对已退出的根 PID 什么都不杀；PID 一旦被回收，就会误杀别的进程树。本次 13 份插桩全量里没有发生，但属于潜在缺陷。已在会话里立了单独的任务提示「Guard taskkill against stale PIDs」，由用户决定要不要开；可照 `scripts/probes/m8/procs.mjs` 的 `killTree`（先看 `exitCode/signalCode`）改。

## 与任务书不一致的地方

- 任务书假设测试文件是在「加载时」因并发或负载失败，要查 sp-kit、auth-kit、global-setup、模块 mock、临时目录。查下来这些都不是原因，文件本身不用改；原因在 Node。
- 所以「修到这个文件不可能在加载时失败」在仓库内做不到。做到的是：这类崩溃不再把全量判红，并且退出码看得见。

## 需要用户决定的事

1. **合不合**。这个改动改变了「npm test 零失败」的判法：测试进程原生崩溃后单独重跑通过，算通过（首次异常会打印）。`verification.md` 的文字没动；要不要在里面写一句由用户定。
2. **换 Node**。根治是换到带 nodejs/node#65778 的版本：v26.10.0 起已有；v24 要等回移 #66168 发版。仓库没有钉 Node 版本，本机是系统装的 v24.19.0。换好之后这层包装可以拆，文件头里写了。
3. **main 上并发敏感的测试**（`codex-auth-state.test.mjs` 等）要不要另开任务修。
4. 「按旧 PID 杀进程树」的潜在缺陷要不要开那个任务提示。

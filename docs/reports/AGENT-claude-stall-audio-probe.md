# AGENT 报告：claude/stall-audio-probe

任务：给「播放停顿时让声音立刻停」（音频看门狗，`e289b886`，实现在 `src/editor/Preview.tsx` 的 `armStallWatch`）补一支**正向**探针，证明它真的管用，而不只是不误触发。

结论先说：**管用。** 在 front 舞台里真的按住节拍 700 ms / 400 ms，父页的看门狗在「上一拍之后约 80 ms」当场把 `mediaStalled` 置真、声音元素当场 `paused`，比迟到那一拍早约 330～660 ms；拍子回来后 `mediaStalled` 回假、声音从停下的位置接着放。把看门狗关掉（临时改 `Preview.tsx`、跑完已还原）这支探针立刻红。

## 改了什么

只改了 `scripts/probes/playback-probe.mjs`（加用例「停顿声音」、文件头补用法与量法）和本报告。`src/**`、`server/**`、`docs/semantics/**`、`docs/plan/**` 一个字没动。不需要在 `src/` 加任何注入点：舞台页本来就暴露了真时钟 `window.__pcRealNow`，`frame.evaluate` 就能按住它。

## 造停顿的办法，以及为什么可信

- 时间轴上放一段**真的在出声**的音频：页面里合成 16 kHz 单声道 WAV（440 Hz 正弦，3 Hz 幅度起伏，40 秒），做成 blob 地址挂到一条音频素材（`addMedia` + `addMediaClip`），再配一张轻卡 `probe-css` 让舞台逐拍推进。不依赖 ffmpeg 和素材服务。
- 正常起播，等播放头走过 1 秒、声音在出（没暂停、`readyState ≥ 3`、`captureStream → AnalyserNode` 量到能量）之后，用 puppeteer 在 **front 舞台的 iframe** 里 `frame.evaluate` 同步空转 700 ms（再来一次 400 ms）。舞台主线程被占住，它的节拍循环发不出 `frame`，父页收不到——这就是「下一拍迟到」本身。
- 不调 `setMediaStalled`，不拦消息，不改 `src/`：验的是 `Preview.tsx` 自己的看门狗定时器。
- 一个坑：舞台把 `performance.now` 换成了虚拟时钟，拿它空转会转到死（第一次就这样挂了 240 秒）。空转必须用 `window.__pcRealNow`（`src/kernel/clock.ts` 里有声明）。
- 可信性的三道旁证，都写成了断言：
  1. 舞台真的停了：相邻两拍到达间隔 ≥ 按住时长的 80%（实测 721～746 ms / 411～437 ms）。
  2. 父页没被一起拖住：按住期间采样器相邻两行的间隔最大 18～26 ms（若舞台与父页同进程，这里会冲到几百毫秒，测量作废）。本机上两者确实是独立事件循环。
  3. 反向对照：把看门狗关掉后同一套手段下断言变红（见下「反向对照」）。
- 采样器每 5 ms 一行：播放头、`__pcPreviewDiag().mediaStalled / mediaStallCount`、主文档每个 `<audio>` 的 `paused / currentTime / readyState / loadstart 次数 / 实时能量`。时刻统一成 `performance.timeOrigin + 真时钟`，父页与舞台页同一把尺。
- 无头 Chrome 新加两个启动参数 `--autoplay-policy=no-user-gesture-required`、`--mute-audio`（共用的 `puppeteer.launch`）：前者让无手势的 `<audio>` 能起播，后者保证扬声器无输出。

## 四条断言（每次停顿各一组，共两次停顿：700 ms、400 ms）

| 要点 | 实现 | 结果（3 遍均过） |
|---|---|---|
| 1 造出真停顿 | 相邻两拍间隔 ≥ 0.8 × 按住时长；父页采样间隔 < 按住时长一半；停顿前 `mediaStalled` 假、声音在放、量到能量（峰值约 0.35） | 过 |
| 2 不等迟到那一拍就跳闸 | 找按住区间里最长的相邻 `frame` 间隔（上一拍 → 迟到那一拍）；断言存在一行采样 `stalled === true` 且时刻早于迟到那一拍到达；`mediaStallCount` 该行 = 停顿前 + 1 | 过。跳闸距上一拍 79～87 ms（名义 33.3+40 = 73.3 ms），比迟到那一拍早 331～659 ms |
| 3 声音当场停 | 迟到那一拍到达之前，所有声音元素已 `paused`，且此后到迟到一拍之间没有被重新 `play`；迟到那一拍到达前最后 100 ms，实时能量 < 0.003 | 过。元素 `paused` 与首次看到 `stalled` 同一行（5 ms 采样粒度内，0 ms）；实时能量排空 54～85 ms（`captureStream` 管路的缓冲，只记录） |
| 4 恢复 | 迟到那一拍之后 `stalled` 回假（14～24 ms）、元素重新放；位置与 `t − 片段起点` 差 ≤ 0.25 s；位置 ≥ 停下时位置且不在开头；恢复后头 400 ms 位置相邻采样差 < 0.2 s | 过。恢复后位置落后播放头 0.08～0.11 s（正常跟随误差）；停下 0.978 → 恢复后接着走，没有重播、没有跳 |

整段采样的附加断言：声音位置从不倒退、声音元素 `loadstart` 次数不变（没重新加载）、`mediaStallCount ≥ 2`、页面无 JS 报错。通过项和失败项逐条打到 stderr（`PASS …` / `FAIL …`），新用例共 41 条通过。

只记录、不当通过条件的耗时：跳闸距上一拍、比迟到一拍早多少、`paused` 距跳闸、能量排空用时（见上表）。断言里的「先后」是顺序条件不是耗时门槛：按住 700/400 ms 远大于跳闸所需 ≈ 80 ms，机器慢一点也不会颠倒。

## 现有「节拍」用例

我没改它的任何一行；只在共用的 `puppeteer.launch` 里加了上面两个与渲染无关的参数，并让 `check` 把每条结果打到 stderr（`check` 的调用都在每个帧率播完之后，24 fps 那一轮播放之前一次都没调过）。

它本来就对机器负载敏感（到达间隔均值 ±1 ms、主文档长任务 0、24 fps 一次超出名义拍长 >40 ms 就算误判卡顿、30 fps 一次短拍就算短拍），这台机器上另有三个任务并行时会偶发假失败。实测：

- **我的版本** `--only 节拍` 共 14 遍，通过 5 遍。失败的 9 遍：24 fps `mediaStalled` 触发 1 次或长任务 1～2 个（5 遍）、30 fps 一次短拍（1 遍）、四个帧率全 0 拍（2 遍，播放没起来）、开场「两个舞台都注册」等了 180 秒超时（1 遍，发生在我的任何代码之前）。通过的那几遍是全 18 条 PASS、退出码 0（24/25/30/60 fps 各自 `mediaStalled` 触发 0 次、间隔均值 ±1 ms、`sec` 差恒为 1/fps、长任务 0、30 fps 无短拍、页面无 JS 报错）。
- **main 上原版**（`83d5df75`，副本放同目录跑）`--only 节拍` 13 遍，通过 10 遍；失败的 3 遍是 30 fps 一次短拍、25 fps 触发 1 次、24 fps 触发 5 次（同样的负载噪声）。
- 我的版本去掉那两个新参数再跑 4 遍：0 遍通过，同样是 24 fps 触发 1 次、短拍、0 拍——所以不是新参数造成的。
- 把原版和我的版本交替跑（7 对）：我的 3/7 通过、原版 5/7 通过，两边都出现过失败。样本小，没有测出可归因于我的改动的差别；机制上我的改动也碰不到测量窗口。仍要如实说：**我的版本的通过率在这台机器、这个时段低于原版，原因没有查清**，倾向于负载噪声，建议主 Agent 在机器空闲时再跑一次「节拍」。
- 不带 `--only` 的整套一遍：92 条通过，3 条失败（25 fps、30 fps `mediaStalled` 触发 1 次，30 fps 一次短拍，均属「节拍」）；到头、追帧、连点、跳转、时间轴、降级、「停顿声音」全部通过。

- `T3-8` 的原因：`upload-queue.mjs` 的 `atomicWrite` 先写 `.tmp` 再 `rename`，这台机器此刻 `os.tmpdir()`（%TEMP%）里的 `rename` 全部报 `EBUSY`（我用 50 次小实验复现：50/50 失败；同一台机器的 scratchpad 目录里 20/20 正常），于是队列文件没落盘。属于主机环境（多半是实时扫描/索引占着 %TEMP% 里新建的文件），不是本改动：本改动只动了 `scripts/probes/playback-probe.mjs` 和本报告，main 上不动代码同样红。开工自检时 main 是 7426/0 失败，说明这是后来才出现的主机状况；等它恢复后这一条会回绿。
- 结论：除 `T3-8`（环境）外全部通过；本分支的改动没有引入任何测试失败。`T3-8` 这一条红是**未解决**的，原因在主机而不在代码，需要主 Agent 知悉。

# AGENT-sound-fix：声音三路合流后探针不稳定的定性与修复

分支 `claude/sound-fix`，起点 `703c03f5`（main + Doger 声音实现 + 验证分支 + 声音 A/B 的合流）。任务：查清 `sound-preview-probe` 合流后不稳定失败的根因（产品缺陷还是探针脆弱）并修好；查 `sound-ab-probe` 第一次的 `Failed to fetch`。不推送、不合并、没有连任何远端。

## 结论

- 合流后的不稳定不是 A、B 两处改动带进来的：在线形态单独跑 3 次全过，失败集中在机器忙的时候和「重开项目」那一页。根因分三类：**三处产品缺陷**（都在 main 上就有，合流只是让它们更容易露出来）、**探针自己的四个问题**、以及一处另一个探针的判法问题。
- `Failed to fetch` 是真实缺陷，已复现并修掉：编辑器进程在发素材文件时会因为文件被删而整个退出。
- 改完后三个声音探针各连续 3 次的结果见「交付标准」。

## 复现（改动前的基线）

在起点 `703c03f5` 上只给探针加了采样落盘，不改断言。两路并行跑（机器上同时还有别的会话在跑）：

| 模式 | 次数 | 结果 |
|---|---|---|
| `--mode both` | 3 | 0 次全过。第 1 次 6 项、第 2 次 11 项、第 3 次 2 项失败 |
| `--mode online` | 3 | 3 次全过（34 项） |
| `--mode desktop` | 3 | 2 次全过（41 项），1 次 1 项失败 |

每次失败的项不同，合起来是下面这几种（「reopened」指打包保存后在空数据目录的另一台编辑器里重开的那一页）：

| 失败项 | 出现在 | 根因（编号见下两节） |
|---|---|---|
| `reopened:P1 kbd 播放时元素 currentTime 与时间轴对齐` | both 第 1、2、3 次，desktop 1 次 | 产品 2；最重的一次播放头 6.6 秒没动，键盘声从头到尾放完了 |
| `reopened:P1 av / notif 对齐`、`reopened:P6 …有能量`、`…状态为 ready`（采样数 0） | both 第 1、2 次 | 探针 2：按墙钟睡固定时长，时间轴走得慢时后面的片段根本没播到 |
| `desktop:P1 notif 对齐`、`desktop:P1 提示音片段播放时有能量` | both 第 1 次 | 探针 3：提示音的元素 0.4 秒没加载好，位置读数恒为 0，被当成「没对齐」 |
| `desktop:P1 av 对齐`（中位偏差 0.170 秒） | both 第 2 次 | 探针 4：播放中才挂上的元素起声晚 0.11 秒，压在 0.15 秒线上 |
| `desktop:P6 声画卡内嵌声音播放时有能量`、`desktop:P5 其他片段照常出声`、`desktop:P5 恢复后键盘声重新出声`、`online:P4 中间播放时听到的…且没有漏`（能量恰为 0） | both 第 2、3 次 | 探针 1：采集音轨不出数据 |

主会话报告的三次失败对应：`online:P4 …没有漏`、`reopened:P1 提示音…有能量` 是探针 1；`online:P6 声画卡从中间播放 avMin 0` 是探针 3（元素重新挂上的那一两拍位置读数是 0，并没有出声）；`第7条 … 34 个采样里 29 个在 0.15 s 内` 是探针 4。

## 产品缺陷（已修）

### 产品 1：发素材文件时文件被删，编辑器进程整个退出（`Failed to fetch` 的根因）

- 现象：`sound-ab-probe` 桌面段第一次 8 项失败，全是 `Failed to fetch`。那一次的 dev server 日志末尾是未捕获异常：`Error: ENOENT … open '…\out\media\be39c2ff….wav'`，`Emitted 'error' event on ReadStream instance`，随后进程退出。
- 根因：`server/vite-plugin-media.ts` 的 `serveFile` 先 `stat`、再按路径另开读流，读流的 `error` 没有处理。探针删掉提示音文件的那一刻，预览里的声音元素正在请求它，文件在两步之间没了。这不是只有探针会碰到：素材被清、内容库换目录时都可能。进程退出后页面上所有请求都失败。
- 修法：先打开句柄，在句柄上取大小，再从同一个句柄读。打不开回 404；打开之后文件被删仍然读得完；读到一半出错只断这一条响应。
- 单测：`server/test/media-serve-file.test.mjs` 4 条（SF1～SF4）。在响应头写出的那一刻删文件，确定性地复现这个时序；不带修复时 SF2、SF3 失败（未捕获的 ENOENT），带修复 4 条全过。
- 定性：真实的竞态，不是端口或负载偶发。机器忙只是让请求和删除更容易撞上。

### 产品 2：起播后舞台还没动，声音已经放出去了

- 现象：重开的那一页第一次播放时，舞台起步慢（新开的编辑器、冷的舞台）。基线里最重的一次播放头 6.6 秒停在 0，键盘声 3.9 秒从头到尾放完；轻的几次是声音先放出去 0.5～0.7 秒，等播放头动起来偏差过了 0.5 秒，又被硬 seek 拉回去重放一遍。
- 根因：播放头由舞台逐拍推进，声音元素走墙钟。`src/editor/Preview.tsx` 里 `playing` 一翻，主文档的音频立刻起播；而已有的「晚到超过 40 ms 就掐住音频」是在晚到的那一拍**到货时**才判的，卡住的那段时间里音频照放。这与 `docs/semantics/mechanism/rendering.md`「音频跟随时刻」（舞台的某一拍比应到时刻晚出超过 40 毫秒就暂停音频）不符，按语义改代码。
- 修法（`src/editor/Preview.tsx`）：
  1. 这一轮播放的第一拍到之前，主文档的音频不起播。只管主文档的音频，不动舞台里的素材层。
  2. 看门狗：上一拍（或 `play` 回包）之后过了「名义拍长 + 40 ms」还没有下一拍，当场按卡顿掐住。判据与到货时那一条相同，只是不等它到；卡顿计数的口径不变。
- 验证：探针新增 `P1 起播时声音不抢在播放头前面(等舞台的第一拍)`，四种形态都验。改后重开的那一页舞台起步等过 165～532 ms（另有一次 1619 ms），第一拍之前在放的声音元素是 0 个，第一拍之后 1.5 秒里声音落后播放头 0.012～0.029 秒、没有超前。没有单测：这段逻辑在 React 组件里，靠探针覆盖。
- 两种在线声音来源、桌面形态同样受益。

### 产品 3：放到素材尽头的元素被从头重播

- 现象：声音比播放头快一点、先放到素材尽头时（采样里：播放头 3.700 秒，键盘声元素已在 3.945 秒放完），下一拍元素位置回到 0、又被 seek 回 3.733 秒。片段末尾会冒出一下开头的声音。
- 根因：`src/render/mediaSync.ts` 的 `planSync` 在播放态对暂停着的元素一律回 `play: true`；浏览器对放完了的元素调 `play()` 是回到 0 重播。片段比素材长时同样会触发。
- 修法：`SyncInput` 加 `ended`。放完了、且播放头没有退回超过硬 seek 门槛，就什么都不做；播放头真的回到了前面才 seek 回去再播。`src/render/mediaDrive.ts` 把 `el.ended` 递进去。
- 单测：`mediaSync.test.mjs` 2 条、`mediaDrive.test.mjs` 1 条；不带修复时 3 条都失败。探针新增 `P1 放到素材尽头的元素没有从头重播`。
- 这一处在 `src/render/` 里，舞台的视频槽位也走它，但只改了「播放中、元素已放完」这一个分支；暂停态（导出、取帧用的那一路）没有动。按任务书没有跑全量渲染附加项。

## 探针问题（已改）

### 探针 1：采集音轨不出数据，「有能量」类断言读到恰好 0

- 探针用 `captureStream` 从声音元素上采能量。Chrome 152 上实测（单独写了实验复现）：元素重新加载（换地址、原地址重设、`load()`）之后，原来那条采集音轨不再出数据，`readyState` 却仍是 `live`，30 轮里 20 轮（凡是重新加载的都中）。另一种是接得太早的采集从一开始就读 0，单独复现不出来，只在整套探针里出现。
- 这不是元素没出声：对读 0 的元素重新 `captureStream` 一条就读到能量了。改后最后三趟 `--mode both` 里，每趟 40 个声音元素中有 4 个靠重采恢复，没有一个出声超过 20 拍却始终读 0。
- 改法：
  - 握着采集流，`addtrack` 时重接，接最新的一条；元素在出声而读数连续为 0 时重新采一条，每个元素最多 3 次。
  - 「听到了没有」不再靠实时采样判。听到 = 元素在出声的拍落在这个事件的媒体时间窗口里，**并且**元素播的那份字节解码后这个位置上有能量。位置跳过了某个事件、或播的那份声音在这里是空的，都算漏。
  - 实时采样降为旁证：每条断言的证据里带 `liveRms` / `liveHeard`，套件末尾另有一条 `实时采样(captureStream):三段声音都从元素上采到过能量`，哪一段整个套件里都没采到就单独再播，最多 3 遍。
  - 还留了一条旁路：P4 实时采样整段读 0 时，把元素直接接进 Web Audio 量它的输出，分清「元素没出声」和「采集不出数据」。改后的运行里没有触发过。

### 探针 2：按墙钟睡固定时长

播放头由舞台推进，机器忙时走不到实时。原来「播放后睡 6.6 秒」在时间轴只走了 4.3 秒时，后面的提示音、声画卡根本没播到，采样数是 0。改成等播放头走到指定位置。

### 探针 3：没加载好的元素也算进了对齐

元素还没加载好时 `currentTime` 读出来是 0，它并没有出声。原来这些拍也算「没对齐」。改成只算「在出声」的拍：时间轴在播、元素没暂停、`readyState ≥ 3`、不在 seek、音量不为 0、没被静音。「不从头重来」类断言同样只看这些拍，但不带重量：真的从头放了一次就是没过。

### 探针 4：播放中才挂上的元素，起声延迟压在线上

见下「阈值」。

### 另外补的

- 元素按片段归类，不看地址。原来用地址里的哈希认片段，浏览器合成的临时声音是 blob 地址，认不出来。为此产品里给声音元素加了两个只读标记：`data-pc-audio-clip`（片段 id）、`data-pc-audio-source`（`product` 已入库的产物 / `live` 当场合成）。
- **在线形态现在跑两遍同一套断言**，对应两种声音来源：
  - `online`：已入库的产物；
  - `online-live`：代理把三份声音的字节挡成「素材服务里没有」，另开一个成员页加入，三段声音都由浏览器合成。
  每一遍都断言三段声音的来源确实是这一遍要验的那种，并解码它播的那份字节核对事件位置。
- 新增断言：出声之后元素没有在播放中重新加载；拖动松手后元素停在指针对应的位置；恢复静音后接着当前位置。
- 带时间的断言没过、或这一遍时间轴速率低于墙钟的 0.9 倍时，该段整段重量，最多 3 遍。每次重量打一行 `RETRY` 并记进结果的 `retries`。不带时间的断言（来源、不从头重来、不重新加载、标记、暂停即停）不因此重量。
- `sound-ab-probe` 的 `D3 导出任务只开了一个`：原来把导出目录下除 `media` 外的目录都数成导出任务，`frame-library`（预渲染进程的快照库）也在里面。它建在导出前还是导出后看机器忙不忙：这次三轮里两轮是「前 0、后 2」而失败。改成只数 `export-` 开头的目录。

### 阈值

| 项 | 改前 | 改后 | 原因 |
|---|---|---|---|
| 起播前就挂着的元素（P1 键盘声、P4、P6 中间、P5 恢复）对齐 | 偏差 ≤ 0.15 秒的采样占 ≥ 90% | 数值没改，分母换成「在出声」的拍 | 探针 3 |
| 播放中才挂上的元素（P1 提示音、声画卡，第 7 条 Agent 的声音）对齐 | 同上 | 偏差中位数在 [−0.25 秒, +0.05 秒]，且 ≥ 90% 的拍离中位数不超过 0.08 秒 | 它的元素在播放头进片段那一刻才建，起声晚的是加载时间，之后由驱动用 ±10% 变速慢慢追（偏差 0.5 秒内不 seek）。空闲机器上中位数就有 0.10～0.13 秒，压着 0.15 秒线。新口径多了两条约束：不许超前、起声之后必须平稳往前走。0.25 秒是硬 seek 门槛的一半 |
| 键盘声事件「听到」的比例 | ≥ 80%（靠实时采样） | P1 ≥ 95%，P4、P5 恢复要求一个不漏 | 判法不再受采样间隙影响，可以收紧 |
| 时间轴速率 | 无 | ≥ 墙钟的 0.9 倍，否则这一遍不作数 | 驱动的变速只有 ±10%，低于它测的是机器不是产品 |

## 两种在线声音来源的行为对比

最后一趟 `--mode both` 里量到的（偏差 = 元素位置 − 应在位置，负数是声音落后于播放头）：

| | 已入库的产物 | 浏览器合成 |
|---|---|---|
| 来源标记、地址 | `product`，素材服务地址 | `live`，blob 地址 |
| P1 键盘声偏差中位数 | −0.049 秒 | −0.040 秒 |
| P1 提示音（播放中才挂上）偏差中位数 | −0.099 秒 | −0.188 秒（另一趟 −0.165） |
| P1 声画卡（播放中才挂上）偏差中位数 | −0.057 秒 | −0.172 秒（另一趟 −0.153） |
| 暂停、拖动、从中间开始、静音与恢复 | 全过 | 全过 |
| 解码核对（35 个键盘事件、提示音、声画卡） | 全有能量 | 全有能量，时长与产物相同 |

合成来源在「播放中才挂上」时起声比产物晚 0.06～0.12 秒：它要先等产物地址报 404，再合成。位置是对的，不从头重来。它离 0.25 秒的上限不远，机器忙时这一条会重量甚至不过。没有改这一点，见「没做的」。

几个词：

- **任务进程**：云端 Agent 的每条任务放进一个单独的操作系统进程里跑，一个进程只跑一条。一个**任务槽**上先后开过的每个进程算**一代**。
- **主服务**：`server/agent-service/main.mjs`，对页面开接口的那个进程。**主身份**：它连文档服务用的身份，只做控制、领不到任务。
- **root 入口**：节点上以 root 身份跑的进程，负责开任务进程、关任务进程、写「这一代确实关干净了」的记录。**发布器**：它用来写这些记录的那段代码（ChatGPT 留下的 `agent-run-scope-publisher.mjs`）。
- **槽调度**：决定哪个槽给哪个对话开一代、什么时候关的那段循环（块一的 `account-slot-scheduler.mjs`）。
- **结清**：文档服务读到 root 的关闭记录以后把这条任务记为结束、把对话的名额让出来。**放弃结算**：任务进程自己判断这条任务没法按正常路径结束。
- **〔裁〕**：文档没写到、我自己定的地方，等主会话和用户审。

## 一句话结论

本机（Windows）能验的六段都做了、都有测试：生产的主服务装配加真子进程、真实运行器跑通了，验收里那两条原先不成立的行为（停止真的停下；共有对话里第二位发送者的任务接着开始）用同样的断言证明成立。**Linux 上的那一半一行都没跑过**：root 入口、任务槽的 systemd 单元模板、发布器看系统的那一半接到真的任务进程上——这些只有主会话到节点上跑自检脚本才知道通不通。所以现在的状态是「代码与部署材料齐了、本机全绿、节点上待验」，不是「可以部署」。

## 做了什么

### 1. 调度与任务进程之间的通道：加本机 HTTPS 那一种

- 任务进程（`account-task-worker.mjs`）在它已有的、只认 root 那张证书的本机 HTTPS 口上多认四条：`POST …/control/prepare`（领取）、`…/control/start`（开跑）、`…/control/close`（收尾）、`GET …/control/settlement`（长挂：结算结果出来就回，到时限回「还没有」）。闸和核身份那一条相同：证书指纹不对、带反向代理的转发头，一律 403。缺省不开；开不开只由入口的起法定，配置模块改不了。
- 入口（`account-task-worker-cli.mjs`）多一种起法 `--control https`：没有父进程通道也能起（systemd 起的就是这样）。原来走父子通道的起法原样保留。
- 新文件 `account-worker-control-client.mjs`：`createWorkerControlClient`（只管这条通道）和 `createAccountWorkerHttpsGateway`（自己起一个不带父子通道的子进程，形状和原来的 `createAccountWorkerGateway` 相同）。
- 块一、块二和真实运行器的两个集成夹具改走新通道：子进程不带父子通道，和生产上的入口是同一种起法。
- **顺带修了一处只有在 Linux 上才会暴露的错**：任务进程身份口的回应是裸的身份对象，而 root 发布器的读端（`asset-root-registry-publisher.mjs` 的 `freshIdentity`，真实 Linux 上跑过的那一段）要的是 `{ ok: true, result }`。照原样部署，root 每开一代都会在「核身份」那一步失败。改成发布器实际读的形状，四处测试里读身份的地方跟着改。

### 2. 主服务的生产装配

- 新文件 `account-master-assembly.mjs`：只做控制的主服务。里面有主身份的登记与读取控制、事件库、一个只绑回环的双向 TLS 内部口（任务进程往这里交事件；槽调度来这里问「哪些对话在排队、哪些任务要强制关」「这一条的强制终态」，后两条只认 root 那张证书，主服务原样转问文档服务）、附件存储。**这个进程里不跑任何任务。**
- `main.mjs` 的命令行入口在账号模式只装配它。要三样新配置：`PROMPTCUT_AGENT_INTERNAL_PORT`、`PROMPTCUT_AGENT_ROOT_FINGERPRINT256`、`PROMPTCUT_AGENT_SHARED_DATA`。
- **配置不全怎么办**（任务书让我定）：缺哪一样都拒绝启动，`config.error { reason: 'account-task-processes', missing: [...] }`；还带着「在主进程里跑任务」那一路的变量（`PROMPTCUT_AGENT_CONTROL_PORT`、`PROMPTCUT_AGENT_ACCOUNT_LOOK=1`、`PROMPTCUT_AGENT_RUN_ASSET_*`）也拒绝，并点名是哪个。文档服务不认主身份（没开这个模式、没登记）同样拒绝（`account-master`）。命令行入口不再有「在主进程里跑任务」这条路；`startAgentService({ accountExecutor })` 只留给进程内的调用方（测试夹具）。
- **运行中 root 入口不在了怎么办**：消息仍然由文档服务持久排队，`GET /v1/info` 的 `executorMounted` 回 `false`（页面对这个值已有一句现成的话：「消息会持久排队，等待执行服务」），`/healthz` 多报 `taskProcesses: true, scheduler: false`。不装作在执行。
- **附件**：页面传的附件由主服务存进各代任务进程共用的数据目录里这个对话的工作目录（和任务进程里算的是同一个位置）。消息带的附件地址只认这个目录里真有的文件，别的拒；核过的引用（名字、地址、大小）经文档服务记在消息上，任务进程从消息里拿到。为此文档服务的发消息接口多收一个 `attachments`（原来固定存空数组）。
- **停止**：页面点停止以后，主服务凭同一个请求号在服务器上等到 root 关掉进程、文档服务结清再回成功，最多等 15 秒；到时没办完照旧回「还在办」。

### 3. root 进程的入口

- 新文件 `account-root-slots.mjs`（哪台机器上都跑得了）：root 入口配置的校验、给某一代任务进程写的设置、槽的适配（把 `current / open / bind / close / forcedClose / retire / observeFailure` 接到发布器和指令通道）。看操作系统的那一半由调用方交进来，所以适配的次序和判断在本机测得到。
- 新文件 `account-root-main.mjs`：读 root 所有的配置、照槽建适配（发布器的 Linux 运行时、每开一代之前写设置文件、指令通道、看主进程还在不在）、起槽调度，经主服务的内部口去问排队与强制终态。三种跑法：常驻、`--bootstrap`（初始化槽）、`--status`（只读）。非 Linux、非 root 直接拒绝。
- 文档服务一侧：新文件 `server/hosted/agent-run-scope-config.mjs`，`server/hosted/main.mjs` 认 `PROMPTCUT_DOC_AGENT_RUN_SCOPES_FILE`。原来文档服务的生产入口根本没有打开这个模式的办法（只有测试夹具给得了配置）。

### 4. 部署模板

都在 `server/hosted/deploy/`：`systemd-promptcut-agent-task.service`（任务槽单元模板）、`systemd-promptcut-agent-root.service`、`agent-root.example.json`、`doc-agent-run-scopes.example.json`、`agent-account.env.example`；`README.md` 加了「Agent 服务（账号版：一条任务一个进程）」一节（身份与证书、用户目录权限、九步部署顺序、日常）。`server/agent-service/account-task-unit.mjs` 把单元模板填成一个槽的文件并算出它的 SHA-256（发布器每开一代都核这份文件没被换过）。

### 5. 「放弃结算以后槽卡住」

判断：任务进程放弃结算有两种来由，原来不分。一种是任务已经被停止或撤销（它就是因此才放弃的），文档服务随后会给强制终态，什么都不用另做——块一那七种交错靠的就是这一点。另一种是已读之后出了暂时性故障（事件交不上去、收尾没形成记录），这时文档服务不会来强制关，授权还有效、进程还活着，槽一直占着。

改法：调度记下是在第几轮放弃的，只看**放弃之后才去问的**那一次文档服务的回答。清单里有它：照旧只走强制。没有：让主进程停下、写失败观察，文档服务据此签「进程故障」的强制终态，结果记「失败」，槽让出来。「之后」是关键：停止先在文档服务落账、任务进程随后才因此放弃，所以放弃之后再问到的清单里一定已经有它；放弃之前就在路上的那一次回答不算数。

## 没做成的及原因

1. **Linux 上一行都没跑过。** root 入口、适配接到真的发布器运行时、任务槽单元模板、任务进程在 systemd 下凭 root 写的设置起来——全部要等主会话跑自检脚本。脚本本身我也只在本机验了参数、清理和「非 Linux 拒绝」，十一步检查的正文没有执行过一次，第一次跑很可能有脚本自己的毛病。
2. **单元模板里有四项是我读 systemd 的行为推出来的，没有实测**（〔裁 10〕）。要紧的一条：发布器在「主进程没了」以后要核原来那个 cgroup 还在；而 systemd 在单元进了 `failed` 或 `inactive` 以后会把 cgroup 收掉。照 ChatGPT 留下的做法（只在子进程还活着的两秒窗口里验过），任务进程干净地崩溃后 root 写不了失败观察、也强制关不了，槽就卡死。我在模板里用 `ExecStart=-…` 加 `RemainAfterExit=yes`（主进程怎么退单元都停在 `active (exited)`、cgroup 留着）、`KillSignal=SIGKILL`（关的时候不走会超时进 `failed` 的那条路）、`OOMPolicy=continue` 来避开。自检第 6、7、8 步验的就是它；不成立的话这三步会失败并打印单元当时的状态。
3. **自检验不到「正常结束」那条关法。** 它要任务进程签意向，任务进程要先从真的文档服务领到任务；自检里没有文档服务。这条在本机集成测试里验过，差的系统那一半和强制关是同一段代码。真要验得等部署后发一条真任务。
4. **节点重启以后，原来的槽不能接着用。** 发布器把记录链钉在一次开机上（`boot-transition`），文档服务的检查点又钉着锚点摘要。重启后每个槽要换新的 `authorityId`、空的登记目录、重新初始化、改文档服务配置并重启它；重启前没结清的任务结不了。这是 ChatGPT 的设计，我没动，写进了部署说明。上生产前建议定一下要不要改（见「要用户定的事」第 3 条）。
5. **root 入口或主服务重启，正在跑的任务会被记成「失败」。** root 入口再起来时没有上一代的通道，只能把它停下走失败观察；主服务重启期间任务进程交不上事件，会放弃结算。没有做「重新接上还在跑的一代」（指令通道是本机 HTTPS，技术上接得上，要改调度的接手逻辑）。部署说明里写了「重启前先等槽空」。
6. **上一个 root 进程留下的、还没绑定的一代，如果文档服务确实没有它的记录，槽会停在「故障」等人处理。** 和块一报告「没做成的」第 4 条是同一类：要给主身份加一个「问文档服务这一代有没有授权」的接口才能自动退，没加。出现的窗口很短（root 恰好在「开了进程、还没领完」的几秒里死掉）。
7. **退出登录那一块报告「没做到的」第 1 条没有顺带解决。** 那条要的是「旧的**主服务**进程确实没了」的 root 记录，而我的 root 入口管的是任务进程，主服务不在任何一个槽里。还差三样：主服务也由一个 root 发布器起停并留记录（像素材服务那样）；主身份登记时带上这条记录的引用；文档服务读这条记录并把旧实例名下的读取记为已关（实例权威里的 `confirmClosed` 还没有接验证方）。
8. **每一代的状态目录不会自动清**（`<stateRoot>/<槽>/epoch-<n>/`，里面是本机事件日志等）。没有让 root 进程去删任务用户可写的目录（有被换成链接的风险），写进了部署说明，要另配定期清理。
9. **部署没有脚本**。任务槽、root 入口、主服务（账号版）、文档服务的任务槽配置都是照 README 手工装。`scripts/remote/docservice.mjs deploy-agent` 是旧模式的，没改。
10. （已做，见「审查后补做的」）验收文件里那两条 todo 已换成生产装配的夹具、转成硬断言。
11. **文档服务发消息收 `attachments` 只有集成测试那一条正向和三种拒绝覆盖**，没有给 `conversation-authority.mjs` 单写用例（形状不对、超过 32 个、重复地址）。
12. **多个槽同时跑没有新验。** 调度的多槽仍只有块一的单测；我的集成测试只有一个槽。
13. 真实运行器块报告「没做成的」第 3、4、5、7～10 条（渲染服务不核任务授权、运行素材离生产还差的、素材服务暂存目录没人收等）这一块没碰，原样还在。

## 我做的裁定〔裁〕

第 1、2、3 条是二级（用户看得出区别，或决定了架构形状），其余三级。我没有调用播报（子 Agent），二级的三条请主会话决定要不要播。

1. **进程怎么分**（二级）。任务书第 3 条写 root 入口里有「槽调度、主身份的事件库与收事件接口」。我做成了：主身份、事件库、收事件的口在**主服务**那个进程里，root 入口只有槽调度和适配，它经主服务的内部口去问文档服务。理由：主身份是一个进程里的一把内存钥匙，页面的读取控制、收事件时回文档服务核对、调度问排队都要用它，只能在一个进程里；而对页面开接口的进程不该是 root。root 从主服务拿到的东西它都不信：强制终态是文档服务签的，发布器自己验签；排队的对话只用来决定「要不要开一代」。
2. **停止在服务器上最多等 15 秒**（二级；块一报告「要用户定的事」第 2 条的乙）。验收那条断言要求第一下回 200。到时没办完照旧回「还在办」，页面那句话不变。
3. **放弃结算又没人来强制关的任务，结果记「失败」**（二级）。见「做了什么」第 5 节。
4. 身份口的回应改成 `{ ok, result }`（修错）。
5. 指令通道的四条路径与回应形状；入口的 `--control https`；「收尾」先回应再收。原来的父子通道起法没删，现在只有一个单测文件在用，可以以后删。
6. 消息的 `attachments` 开始被填：`{ name, url, size }`，最多 32 个；不带附件时请求摘要和原来一样（旧的重发请求照旧对得上）。
7. 谁能传附件：项目里可写的成员；对话在他看得到的清单里时不能是「创建者只读地看别人的私有对话」；不在清单里的当新对话收下。残余风险：别人的私有对话他看不到也猜不到对话号，真猜中了也只是往里多放一个读不回来的文件（不覆盖已有的）。
8. `main.mjs` 账号版的三样新环境变量；旧路的变量一律拒绝；`/healthz` 加 `taskProcesses`、`scheduler`；`info.executorMounted` 跟调度此刻有没有在问走（15 秒没来问算不在）。
9. root 入口配置文件的形状；文档服务任务槽配置文件的形状和 `PROMPTCUT_DOC_AGENT_RUN_SCOPES_FILE`。主身份和任务身份必须是两把钥匙、两张证书。
10. 任务槽单元模板的四项：`ExecStart=-`、`RemainAfterExit=yes`、`KillSignal=SIGKILL`、`OOMPolicy=continue`。代价：正常结束时任务进程也是被直接结束的，不走它自己的收尾（那时它已经收完、文档服务已经签了终态）。
11. 槽的初始化单独一步（`--bootstrap`：开第一代随即退掉），调度不顺手初始化——锚点摘要要先配进文档服务，否则第一代登记不上。
12. 写失败观察之前主进程还活着就先让它停下（`systemctl kill --kill-who=main`，只动这个槽的单元的主进程）。
13. 账号版主服务不起 vite（它不载工具实现）。启动时要等到第一次向文档服务登记成功（事件库钉在文档服务的权威号上）；文档服务连不上就隔 2 秒再试，不退出。**初稿这里的「不退出」不成立**（等待用的定时器不拉住进程，而那时还没有监听口，进程会以退出码 0 自己退出），审查后改了并补了测试。
14. 自检脚本的 slice 前缀是 `pcclaudeprobe` 不是 `pc-claude-probe-`：连字符在 systemd 的 slice 名里表示层级，发布器也不许。单元名和目录名照任务书带 `pc-claude-probe-`。

## 要主会话到 Linux 上跑的（最终版）

### 一、节点自检（先跑这个；不碰现有服务）

本机打包（不需要 `node_modules`、不需要任何第三方包，有测试钉着这一点）：

```
git archive --format=tar.gz -o pc-claude-probe-src.tgz claude/v18-prod server src/kernel/agentScopes.mjs src/kernel/creativity.mjs scripts/probes/account-root-entry-linux.mjs scripts/probes/account-task-worker-config-linux.mjs
```

拷到节点。**放在 tmux 或 screen 里跑**（SSH 掉线时脚本收到 SIGHUP 会照样清理，但输出就看不到了）：

```
tmux new -s pcprobe
mkdir /root/pc-claude-probe-src && tar -xzf pc-claude-probe-src.tgz -C /root/pc-claude-probe-src
cd /root/pc-claude-probe-src && node scripts/probes/account-root-entry-linux.mjs --protect <账号、文档、素材三个服务的单元名，逗号分隔> 2>&1 | tee /root/pc-claude-probe.log
```

前提：root；`node` 要是一个非 root 用户也能执行、并且它自己和路径上每一级目录都归 root 的（比如 `/usr/bin/node`；装在 `/root` 下的不行）；有 `openssl`、`systemctl`、`busctl`、cgroup v2。任务进程缺省以已有的 `nobody` 跑（`--user <别的已有非 root 用户>` 可换；脚本不建用户）。

它会碰什么：`/run/pc-claude-probe-<编号>/`（代码副本、临时证书、记录、数据）、一个单元 `pc-claude-probe-<编号>-a.service`（文件在 `/run/systemd/system/`）和它的 drop-in 目录、五个临时 slice `pcclaudeprobe<编号>…slice`（slice 名不许带连字符）、三个向系统要来的回环端口。`systemctl daemon-reload` 共 7 次（布置 1 次、每开一代 1 次共 5 代、清理 1 次；只重读单元文件，不重启任何服务），开头会打印这一句。不联网、不读任何真实密钥、不碰现有单元、端口、数据目录、用户。全程大约一两分钟。

期望输出：

```
probe id <8 位编号>  (dir …, unit …, slices …, user nobody)
note 这次会执行 systemctl daemon-reload 共 7 次：…
ok 1 初始化槽：…
…
ok 11 root 入口常驻：…
note 跑之前在运行的 N 个服务里，主进程号或重启次数变了的：没有
cleanup stop pc-claude-probe-<编号>-a.service: stopped
cleanup …
left {"units":[],"unitFiles":[],"cgroups":[],"processes":[],"listeners":[],"directory":[]}
PASS account-root-entry-linux 11/11
```

退出码 0。第 11 步自己要等十秒左右（空闲八秒看它还活着）。

不过的话：`FAIL <哪一步> <原因码>`，后面跟几行 `  diag …`（单元当时的状态、登记目录里有什么、单元最近 25 行日志），其余步骤记 `skip`，照样清理，末行 `FAIL account-root-entry-linux <过的数>/11`，退出码 1。请把整段输出（`/root/pc-claude-probe.log`）带回来。Ctrl-C、SSH 掉线、被 kill 都会先清理再退。

清理没清干净（`left` 一行里有东西），或者输出丢了：

```
ls -d /run/pc-claude-probe-*          # 目录名的后八位就是编号
node scripts/probes/account-root-entry-linux.mjs --cleanup <编号>     # 可以重复跑，末尾同样打印 left
```

跑完：`rm -rf /root/pc-claude-probe-src /root/pc-claude-probe.log`。

最可能先坏的地方：第 1 步（单元起不来，看 `diag journal`）；第 6 步的 `unit-left-active-state`（我对 systemd 的推断不成立，见「没做成的」第 2 条）；第 10 步的 `root-code-untrusted`（node 或 `/run` 的属主、权限不合它的要求，`diag` 里有是哪个路径）。

## 要用户定的事

1. **点「停止」以后，页面要等多久才看到结果。**
   背景：任务放进独立进程以后，停止要等 root 真的把进程关掉、文档服务核对完才算办完，通常一两秒。
   现状：我让服务器替页面等，最多等 15 秒；多数情况点一下就显示停了。超过 15 秒还没办完，页面显示原来那句「已禁止新访问，相关服务关闭待确认。点击重试会沿用原请求。」
   选项：甲，照现在这样；乙，不让服务器等，页面第一下多半看到「待确认」，要再点一次（原来的行为）；丙，改页面，让它自己隔一会儿重试（要先定文字和行为）。
   后果：甲的停止请求会慢一两秒；乙要用户多点一下；丙要改界面。
   建议：甲。
2. **一条任务读完消息以后，因为服务一时故障没法正常结束，记成什么。**
   背景：比如任务跑到一半，主服务重启了，任务进程的过程记录交不上去。它已经改了的东西留在项目里，但它没法走完正常的结束手续。
   现状：我让节点把这个进程停掉，这条任务记「失败」，同一个对话里排着的下一条接着开始。原来的做法是什么都不做，这个对话就一直卡着，直到有人点停止。
   选项：甲，记「失败」（现在这样）；乙，保持原来的，等人点停止（那时记「被中断」）。
   后果：甲不会卡住对话，但用户会看到一条「失败」的任务，其中一部分修改可能已经生效；乙要人来处理。
   建议：甲。
3. **云节点重启以后，云端 Agent 要人手工重新初始化才能用，重启前没结束的任务结不了。**
   背景：节点上记录「每个任务进程确实关干净了」的那套东西，是按「这一次开机」来认的（ChatGPT 的设计，目的是不让重启前后的记录混在一起）。
   现状：重启后要有人到节点上重新初始化每个任务槽、改文档服务的配置并重启文档服务；重启那一刻正在跑的任务，对应的对话会一直显示有任务在跑。
   选项：甲，接受现状，把「节点重启」当成一次要人到场的维护；乙，上生产前先改成重启后自动接上（要改文档服务认任务槽的办法，是一块单独的活）。
   后果：甲在节点意外重启时云端 Agent 会停摆到有人处理；乙要多做一块。
   建议：0.7.18 先甲（现在没有外部用户），乙排进后面的版本；但请知道有这件事。

### 审查让查清的三件事

**一、文档服务的强制清单（`listScopeControls`）是不是对所有围栏种类都在任务进程放弃之前就列出。** 读的是 `server/account/run-authority.mjs` 的 `checkWithScope`、`fenceInState`、`reconcile` 和 `doc-agent-assembly.mjs` 的 `listPendingRuns`。

- **先列出的**（任务进程是因为它才被拒、才放弃的）：停止、切私有（请求自己的事务里当场落账）；改密退出、退出登录、移除成员或封禁、删项目、关 Agent 开关（都是账号事件，任务进程每一步过闸时文档服务先 `sync()`——把账号事件拉回来、落成围栏并提交——再判；主服务来问清单时同样先同步再列）；实例被撤销。这些结果是「被中断」。
- **晚列或不列的**，这类任务会被记成「失败」而不是「被中断」：
  1. 账号服务已经不认发送者的登录、而对应的账号事件还没到文档服务（过闸时向账号服务现核的那一步先拒了）。事件随后到：私有对话或还没读的任务会在下一次问清单时被列出（那就仍是「被中断」，因为判据用的是放弃之后才去问的那一次）；**共有对话里已读的当前任务按规矩本该保留继续做**，但任务进程已经放弃了，文档服务不会来强制关，于是被记成「失败」。这是任务进程一侧原有的缝（把一次还没落账的拒绝当成了撤销），不是这一块引入的；这一块之前的后果是槽一直卡着，现在是记失败。
  2. 服务登记表里把跑任务的那把钥匙撤掉（`service-revoked` 这一种围栏在代码里没有任何地方产生）。任务进程每一步都被拒、放弃，没有围栏，记「失败」。
- 没有改调度去多等几轮：等多久都是猜。要彻底对上得让任务进程区分「文档服务说这条任务被撤销了」和「这一次核对没过」，那是任务进程和文档服务之间的约定，没动。

**二、正常结束时任务进程报出结算结果以后还在不在往共用数据目录写，`KillSignal=SIGKILL` 会不会截断它。** 不会截断要紧的东西：

- 对话的模型历史（`history.json`）：`server/runners/api.mjs` 的 `saveHistory()` 是同步写，在这一轮返回之前做完；运行器收完（`drain()`）才形成收尾记录，收尾记录封存以后才开始结算。
- 用量流水：每次模型调用后 `appendFileSync` 同步追加，同上。
- 本机事件日志：结算之前已封存。
- **会被截的只有一样**：用量的累计缓存 `usage/totals.json`，它由定时器隔一会儿落一次（写临时文件再改名）。被直接结束时最后一段可能没落，或留下一个 `totals.json.tmp-<进程号>`；下一代起来时按流水文件的偏移补算，数不会错，只是多一个小的临时文件没人收。
- 被**强制**关的任务另说：那时它可能正写到一半。`history.json` 不是先写临时文件再改名的，写到一半被结束会留下半个文件，下一条任务读它时解析失败、按没有历史开始（模型不记得这个对话之前说过什么）。这和 SIGTERM 还是 SIGKILL 无关，原来的强制停止也一样；要补得改 `api.mjs`，不在这一块。

**三、「发布器失败后一律留锁、开一代的任何失败都要人工处理」在生产上最常见的触发，和运维照着做的恢复步骤。** 最常见的是开一代的时候：任务槽单元起不来或起来就退（证书、目录权限、设置文件读不到）、单元文件被人改过或加了 drop-in、节点很忙时任务进程迟迟没开始监听（发布器自己只重试几秒）、root 入口在一次发布做到一半时被结束。最后两种是日常就会碰到的，所以加了「先等任务进程开始监听」（`9e63b8df`）。恢复步骤写在 `server/hosted/deploy/README.md`「槽停住了」，分四种情形（看停在第几代什么阶段、登记目录里有没有 `reservation-<N+1>.json` / `terminal-<N>.json`）。**两点要知道**：这套步骤没有在节点上演练过；其中「开到一半」「关到一半」两种没有办法接着做，只能给这个槽换新的 `authorityId` 重新初始化（要重启文档服务），而「关到一半」时那一代绑着的任务在文档服务里结不了、现在没有工具能处理。也就是说，发布器的「不重试、不恢复」在生产上的代价比看上去大，值得排一块单独的活。

### 这一轮新增的裁定〔裁〕

16. root 入口的单元 `Restart=always`：配置不对时它每 15 秒以退出码 1 退出一次、打一行 `config.error`，不会停下不拉。
17. root 入口执行的代码必须归 root、组和别人不可写（含组是 root 的组可写也不行，和发布器核配置文件的标准一致）。`git archive` 解出来的文件缺省组可写，部署时要收紧。
18. 指令口的请求头 `x-promptcut-scope-slot / -epoch / -instance` 和回应里的 `scope`。它防串代，不是鉴权；同一个任务用户的别的进程拿得到身份证书和这三样，冒充得了「放弃」（后果是那条任务记失败）——要堵得让「放弃」也带任务进程内存里那把钥匙的签名，没做。
19. 开一代以后多等任务进程开始监听最多 30 秒。发布器核的东西一样没少，只是在它开始核之前多等。
20. 两条转硬断言的验收测试各另起一套一条任务一个进程的组合（端口 28691～28712、28713～28734，在分给我的段里），等待时限从原来的 15 秒放宽到 60 秒（每条任务要起一个带 vite 的进程），只为防卡死。

### 1.1 探针量了什么（对应契约第 6.3 节五项）

每种场景 × 每种尺寸，各 90 帧、30 fps：

1. Chrome 版本、是不是无头壳、WebGL 的 UNMASKED_RENDERER，另有 CDP `SystemInfo.getInfo` 的显卡与视频编码状态。
2. `VideoEncoder.isConfigSupported`：基线（`avc1.4200LL`）、主（`4D00`）、高（`6400`）三档 × 拼合后两种尺寸（960×1096、1920×2176，级别按 streamEncode.ts 的规则取 4.0 / 5.0）× hardwareAcceleration 取 `no-preference` 与 `prefer-software` × 编码模式取「固定量化」与「按码率」。
3. 浏览器自带的编码器：照 `streamEncode.ts` 的拼法（上半预乘色、下半不透明度，黑边 8 行），高档，先认固定量化、不认就退到按码率；每 15 帧一个关键帧。记每秒压多少帧、字节数；VideoDecoder 解回来多少帧；和原画比的颜色平均差、不透明度平均差（0～255，抽 8 帧比全图）。另按 `--hw` 再跑一遍 `prefer-software`。**没有封 fMP4**（甲一的 streamMux 不在探针范围里，编码块直接送解码器，封装耗时在这里没有算）。
4. 原始像素交给 ffmpeg：页面里读画布（2D 用 getImageData；WebGL 用 readPixels，再翻转并反预乘，得到 straight RGBA），`fetch` POST 到探针的 HTTP 口，探针喂 ffmpeg（`-f rawvideo -pix_fmt rgba`，后面的滤镜链和 libx264 参数抄自 `server/bakery/ffmpeg.mjs`，提交 37d5ce4f）。**按生产的做法每 15 帧一个 ffmpeg 进程，并预先拉起下一个进程**。分段记读、搬、编码；再用 ffmpeg 把产物解回来比同样两个差。
5. 现在的办法作基线：`Emulation.setDefaultBackgroundColorOverride` 透明背景 + `Page.captureScreenshot`（PNG、clip 到画布），PNG 经 image2pipe 喂同一条 ffmpeg 命令行（`streamSegmentArgs` 原样），同样分段、同样比差。

场景是真实卡片的**替身**，不是卡片本身：

- 粒子：2D 画布，400 个半透明小圆点，不透明像素约 6.5%～7%（稀疏）。
- 三维：WebGL 画布（`webgl`，MSAA、预乘 alpha），带光照的转动球体加一圈环，不透明像素约 63.5%（占画面一半以上）。无头 + 软件 WebGL 能起来（SwiftShader）。
- 两种都带透明背景，按帧号直接算。探针每次把中间一帧垫在棋盘格上存成 `preview-*.png`，可以人眼核对。我看过 960×540 的两张：球和环的朝向、光照方向、翻转都对。

### 1.2 口径（读数字前要知道）

- 「画」（把这一帧画到画布上）三条路一样，**不算进端到端**。软件 WebGL 的命令是拖到有人读像素时才执行的，所以画完后要读 1 个像素逼它画完（否则「画」会漏进「读」，三条路的对比不干净；第一版探针没做这件事，那一批数据作废重跑）。截图那条还要等两次 requestAnimationFrame 让合成器出帧，也算「画」。
- 「端到端每帧」= (从第一帧开始到最后一个字节产出的总墙钟 − 画的总耗时) / 帧数。读、搬、编码在流水线上重叠，所以三段之和可以大于端到端。
- 「搬（单量）」：同一帧原始像素连发 15 次 POST 给一个收下就丢的口，所以不含 ffmpeg 背压（960×540 一帧 2 MB，1920×1080 一帧 8 MB）。浏览器那条的「搬」是最后把全部编码块一次 POST 给 Node。
- 「编码（单量）」：缓存下来的前 15 帧循环喂满 90 帧给 ffmpeg，没有页面参与；浏览器那条没有这个数，给的是每秒压多少帧。
- 判据（契约第 6.3 节）：可用 = 编得出来、解回来帧数对、颜色平均差 < 1、不透明度平均差 < 0.5。颜色差按「解回来的色半区 对 原画 straight RGBA 乘 alpha 得到的预乘色」算，不透明度差按「解回来的透明度半区 对 原画 alpha」算。ffmpeg 产物的差用 ffmpeg 解回来（任务指定）；另给「交给浏览器的 VideoDecoder 解回来」的差作旁证（播放端就是浏览器解）。

## 2. 在节点上怎么跑

一条命令，需要的只有：这一个文件、Node（≥22，按 24 写）、Chrome 的路径、ffmpeg。

```
node canvas-encode-paths-probe.mjs --chrome /path/to/chrome-headless-shell --no-gpu --no-sandbox --ffmpeg /path/to/ffmpeg --out ./out
```

- 节点没有显卡：一定加 `--no-gpu`（等价于 `server/bakery/chrome.mjs` 里的 `--disable-gpu --disable-gpu-rasterization --disable-gpu-compositing --enable-unsafe-swiftshader`；不加的话 WebGL 场景多半起不来）。以 root 跑加 `--no-sandbox`。ffmpeg 在 PATH 里就不用写 `--ffmpeg`。
- 跑完标准输出最后一行是 `out/summary.json` 的路径，前面是一张汇总表；进度写在 stderr。
- 退出码：任一场景（某个尺寸）三条路全都「没跑出来」→ 1；参数不对或 Chrome 起不来 → 2；其余 0（某条路「不可用」不影响退出码）。
- 在这台 PC 上整遍约 1.5～2 分钟（90 帧，两种尺寸、两种场景）。可调：`--frames`、`--sizes`、`--scenes`、`--hw`、`--timeout`、`--chrome-arg`（可重复）。
- 结束时会结束 Chrome 和 ffmpeg 进程（包括出错、超时、Ctrl-C），并兜底按临时用户目录名找残留的 Chrome 进程；临时用户目录建在 `--out` 下，结束时删。
- 输出目录里还有：每条 ffmpeg 路的第一个分段 `*-seg0.mp4`（能直接播）、`preview-*.png`（场景中间一帧垫在棋盘格上）。

## 3. 验证

- `npx tsc -b --force`：退出码 0（探针是 .mjs，本来也不受影响）。没跑 `npm test`（没改产品代码）。
- 探针自检（都在这台 PC 上）：
  - 正常整遍三种条件，退出码 0（下节）。
  - `--chrome-arg --disable-3d-apis`（WebGL 起不来）：粒子照常量出来，三维三条路都记「不可用：场景起不来」，退出码 1。
  - `--ffmpeg nonexistent-ffmpeg`：浏览器那条照常，两条 ffmpeg 的路记「不可用：ffmpeg 不可用」，退出码 0。
  - `--timeout 4`（故意让每条路超时）：三条路都记超时「不可用」，页面被重载、不卡住，退出码 1，没有残留进程。
- 窗口与进程：开跑前、各遍之后、全部结束后都查了可见窗口（`Get-Process | Where MainWindowHandle -ne 0 ...`），一直是空；结束后没有带 `chrome-profile-` 的残留进程；临时用户目录都已删（开发过程中旧版本留下过两个，已手工删掉）。子进程全部 `windowsHide: true`，Chrome 用无头。
- **没在 ffmpeg 4.4.2 上跑过**：这台 PC 只有 ffmpeg 9.0.1。命令行抄的是现在产品里的那条（节点上 4.4.2 就在跑这条），没有用 `-vsync`、`-fps_mode` 之类新旧不一的选项；我自己加的只有解码用的 `scale=in_range=tv:in_color_matrix=bt709:out_range=pc,format=rgb24`，这几个选项 4.4 都认。节点上第一遍要先看 `ffmpeg.version` 和两条 ffmpeg 路是不是「可用」。

## 4. 这台 PC 上的结果

机器：i7-14700KF，20 个逻辑核，31.8 GiB，Windows 11 26200，显卡 RTX 3080，Node 24.19.0，ffmpeg 9.0.1，90 帧、30 fps。

**处理器占用（如实写）：这台 PC 上同时有别的子 Agent 在跑，每遍开跑前探针自己采样 1 秒的整机占用：A 遍 57.8%、B 遍 53.7%、C 遍 40.8%（最终采用的这一批）。**第一批（作废，原因见 1.2 第一条）开跑前占用曾高到 99%、95%、71%。所以耗时数字都带着干扰：同一条路在 A、B 两遍之间能差一倍（粒子 960×540「原始像素→ffmpeg」A 遍 13.4、B 遍 27.9 毫秒/帧），**不要拿单个耗时数字定结论，主会话在机器闲时重跑**。颜色差、不透明度差、字节数不受干扰（几遍之间几乎一样）。

三遍：

- A：无头壳（chrome-headless-shell 152.0.7977.75）+ `--no-gpu`（最接近节点）。
- B：同一个无头壳、不加 `--no-gpu`。**这台 PC 上无头壳不加 `--no-gpu` 也没有用上显卡**，WebGL 渲染器同样是 SwiftShader，所以 B 和 A 实质是同一种条件，两遍之差就是噪声的量级。
- C：系统装的 Chrome 154.0.8037.99（新无头，不是无头壳），缺省参数，WebGL 走 RTX 3080（D3D11），视频编码走硬件。这是「有显卡」的参照。

## 5. 看出来的（只写数字和事实，不替主会话下「用哪条」的结论）

以下数字取 A 遍（无头壳 + `--no-gpu`，最接近节点）；括号里的 C 遍是有显卡的系统 Chrome。耗时都是在机器有别的活的情况下量的，量级可信、个位数不可信。

1. **按判据，哪条路在这台 PC 上「可用」**
   - 浏览器自带的编码器：A、B、C 三遍的 4 个场景×尺寸全部可用（含「只用软件」那一遍）。解回来 90/90 帧，颜色平均差 0.23～0.94，不透明度平均差 0.02～0.24。
   - 原始像素→ffmpeg、截图→ffmpeg：粒子两种尺寸、三维 1920×1080 可用；**三维 960×540 不可用，原因是颜色平均差 1.11（C 遍 1.108）不小于 1**。这两条路在这一格得到同一个数，**现状（截图）那条也不过**。用浏览器的 VideoDecoder 去解同一份 ffmpeg 产物，这一格是 0.937（C 遍 0.675），就过了。也就是说「颜色平均差不到 1」这条判据取决于场景内容（三维替身有细条纹和抗锯齿边，4:2:0 色度压缩损失大）和用哪个解码端，不是这三条路的区别。
2. **原始像素 vs 截图（画质）**：两条路解回来的颜色差、不透明度差逐项相同（小数点后三位），产物字节数几乎相同（粒子 960×540 都是 1,535,077 字节；三维 960×540 为 790,978 对 790,976）。这几个场景里读出来的像素和截图的像素是一回事，原始像素这条路没有画质代价。
3. **端到端每帧耗时（毫秒；A 遍 / C 遍；浏览器编码器 · 原始像素→ffmpeg · 截图→ffmpeg）**

   - 原始像素比截图快 2.0～7.7 倍（A 遍 3.7、6.7、2.2、5.0 倍）；三维那格截图一帧要 87～217 毫秒，基本全是 `captureScreenshot` 本身。

4. **无头壳 152 不认固定量化模式**：`isConfigSupported` 在基线、主、高三档、两种拼合尺寸、「不限」和「只用软件」下，固定量化都是「否」，按码率都是「是」（A、B 遍）。`streamEncode.ts` 会退到按码率（每像素每帧 0.2 比特），结果产物比 ffmpeg（crf 16）大得多：码率 6.2 / 4.3 / 17.9 / 11.3 Mbps（粒子 960、三维 960、粒子 1080、三维 1080）对 ffmpeg 的 4.1 / 2.1 / 7.7 / 5.3 Mbps，大 1.5～2.3 倍。系统 Chrome 154（有硬件编码器）在「不限」时认固定量化，产物 4.1 / 1.7 / 7.9 / 4.0 Mbps，和 ffmpeg 同量级；但它的「只用软件」同样不认固定量化，码率回到 6.2 / 4.2 / 17.9 / 11.0 Mbps。**节点（无头壳、没有显卡）多半和 A 遍一样**，到时看 `encoderSupport`。
5. **三档 H.264 都认**：按码率模式下基线（`avc1.420028` / `420032`）、主（`4D0028` / `4D0032`）、高（`640028` / `640032`）对 960×1096 和 1920×2176 全都「是」。
6. **这台 PC 上无头壳没用上显卡**：B 遍（不加 `--no-gpu`）的 WebGL 渲染器也是 SwiftShader，`SystemInfo` 里 `video_encode` 是 `disabled_software`。要量有显卡的情形只能用 C 遍（系统 Chrome 154，新无头）。
7. **浏览器解回来的差和 ffmpeg 解回来的差不是同一个量**：同一份 ffmpeg 产物，三维的颜色差浏览器解得更小（960×540：A 遍 0.937 对 1.112，C 遍 0.675 对 1.108；1080p：A 遍 0.778 对 0.989，C 遍 0.526 对 0.987）；粒子两种解码端相差不到 0.03。播放端是浏览器解，实际看到的是浏览器解的那个数。
8. 不透明度平均差全部不到 0.25，离 0.5 的线很远；粒子场景的不透明度差（0.1～0.25）比 `render-standard.md` 记的「不到 0.04」大，场景不同，不是同一个量。

## 6. 没做成的、没量的

- **节点那一遍**（任务明确留给主会话），以及 **ffmpeg 4.4.2 上的实测**：这台 PC 只有 ffmpeg 9.0.1。
- **Linux 上没跑过**：探针里 Linux 分支（Chrome 放进独立进程组再整组结束、按 `/proc/*/cmdline` 兜底找残留进程、`lspci` / `nvidia-smi` 查显卡、`--no-sandbox`）只写了，没有执行过。
- 没有重复多遍取中位数：每种条件只跑了一遍，而且机器有别的活。
- 浏览器那条没有算 `streamMux` 封装和分段上传，只量到「编码块交给 Node」。
- 没量 `hardwareAcceleration: prefer-hardware`，没试 WebSocket 二进制 / CDP 二进制代替 `fetch` POST，没量真实的 `particles-*` 卡和 `scene-3d`（用的是替身）。
- 没用甲一分支的 `browser-stream-encode-probe.mjs`：它依赖 puppeteer 和仓库源码，拷一个文件到节点跑不起来。探针里自己写了等价的拼合、编码、解码。口径有一处不同：本探针颜色差、不透明度差是**全图**逐像素平均，甲一那个是每 7 个像素取 1 个。

## 7. 对任务书、语义的更正建议

- 契约第 6.3 节第 3 项「用甲一分支上的 browser-stream-encode-probe.mjs」：改成「用 `scripts/probes/canvas-encode-paths-probe.mjs`」（本探针，一个文件，三条路一起量）。

- 契约第 6.2 节「浏览器自带的编码器」的风险列可以补一句实测：无头壳 152 不认固定量化，只能按码率，产物比 ffmpeg（crf 16）大 1.5～2.3 倍；`streamEncode.ts` 的固定量化分支（缺省 20）在这种浏览器上不会生效，只有有硬件编码器的 Chrome 才走到。
- 没有发现和语义文档冲突的地方。

**画布卡的像素走「原始像素交给 ffmpeg」这一条。**

- 它在两台机器上都比现在的办法快 1.5～7.7 倍，编码器、画质、产物大小、清单、分段签名、先稀疏后收紧的两趟都不用变，要改的只是像素从哪儿来。
- 浏览器自带的编码器更快（契约的判据是快出五成以上才考虑它），这次不用：它在无头壳里只能按码率压，产物大 1.5～2.3 倍；要换编码器名字和分段签名；桌面这条路上现有的稀疏、收紧两趟都得另写一遍。记成以后的优化。
- 原始像素那条在 1080p 时最大的一段是把像素从页面搬到 Node（探针用的是 fetch 往本机端口发），实现时换更快的搬法值得试，耗时写进「己一」的报告。
- 用的是两种替身画面，不是真的粒子卡和 `scene-3d`；「己一」用真卡把改前改后的预渲染耗时各量一个数。

## 更正（主会话 2026-10-13，己一接进真管线以后）

本报告里「原始像素交给 ffmpeg 比现在的办法快 1.5～7.7 倍」只在本探针的口径里成立，放到真实的产流里不成立：本探针拿来当「现在的办法」的截图是 `Page.captureScreenshot`（每帧 48～217 毫秒），预渲染进程产流用的是受帧控制的截图，每帧只要 3.5～18 毫秒；本探针里「搬」这一段的做法也和真管线不同。己一做完以后在真管线里量到的是：粒子卡整条流省 12%～21%，`scene-3d` 960×540 省 5%、1080p 反而慢 8%（所以做成每个分段先量、划算才走直取）。数字见 `AGENT-rr-canvas-direct.md` 第 3 节。三条路「编得出来、解回来帧数对、颜色差在量级以内」的结论不受影响。

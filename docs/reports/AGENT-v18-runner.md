# 0.7.18：真实运行器进任务进程，账号模式接上看画面和运行素材

分支 `claude/v18-runner`，从 `main` `d7075a58` 分出，2026-10-13。只在这个工作区里干活；没连节点，没读 `docs/local.md` 里两个环境变量以外的内容，没动 ChatGPT 的分支和工作区，没改语义文档和 `docs/plan/`。端口只用了 28220～28259。

几个词：

- **任务进程**：云端 Agent 的每条任务放进一个单独的操作系统进程里跑，一个进程只跑一条。一个任务槽上先后开过的每个进程算**一代**。
- **真实运行器**：带模型调用、工具、到文档服务的项目数据连接的那一个（`account-runner.mjs` 的 `createExistingHostedRunnerFactory`）。块一（`AGENT-v18-worker.md`）的任务进程里跑的是照脚本走的替身。
- **主身份**：Agent 服务里只做控制、自己不跑任务的那个身份。**root**：节点上以 root 身份开进程、关进程、写关闭记录的那一侧。
- **结清**：文档服务读到 root 的关闭记录以后把这条任务记为结束、把对话的名额让出来。**收尾记录**：任务进程自己形成的「终态事件已被主服务确认、运行器已收完、最后一次落盘成功」的记录。
- **看画面**：云端 Agent 的 `see_frames` 等工具向渲染服务要一帧。**运行素材**：一条任务凭这条任务的授权读写所在项目的素材，不借成员的票据。
- **〔裁〕**：文档没写到、我自己定的地方，等主会话和用户审。

## 做了什么

### 1. 真实运行器进任务进程

- **任务进程的生产配置**（新文件 `server/agent-service/account-task-worker-config.mjs`）。`account-task-worker-cli.mjs --configuration-module <它>` 载入，凭环境变量 `PROMPTCUT_AGENT_WORKER_SETTINGS` 指向的一份 root 写的 JSON 设置，给进程装上：任务身份、root 核身份用的本机口、本机事件日志与交事件的通道、进程内不带插件的 vite（只用来载工具实现，和 `main.mjs` 同一个起法）、模型配置（现读数据目录里那一份）、可选的看画面与运行素材。vite 在「领到任务、root 绑定之后」才起，没领到任务的一代不付这份开销；进程收尾时在执行器关完之后关掉它。设置文件的形状写在文件头。只在 Linux 上能用（root 写的文件要核属主）；别的平台直接拒绝。
- **数据目录分两份**〔裁 3〕：`dataDir` 各代共用、长期保留（对话的模型历史、工作目录、用量流水、额度——下一条任务是新的一代进程，历史必须接得上）；`stateDir` 只属于这一代（已读意向等本机状态库），免得几个槽的进程同时写同一个库。
- **集成测试**：`server/test/account-runner-process.test.mjs`，见「验证结果」。子进程走的就是上面那份生产配置代码，设置文件也是生产的形状，只换了两处这台机器做不了的：读 root 记录（不核属主）、模型（仓库里的模拟提供方，照用户消息里的脚本调工具，不连真的模型服务、不用任何密钥）。

把真实运行器放进子进程、对着真的文档服务装配跑，**暴露了四处原来只有受控夹具验过的问题**，都改了：

| # | 问题 | 现象 | 改法 |
|---|---|---|---|
| A | 文档服务的生产装配（`doc-agent-assembly.mjs`）没有把「一条任务一个进程」要的六个接口（领分配、查结束、签准备、取终态、主身份取强制终态与事件来源）交给内部口 | 开了这个模式，任务进程领完任务去问分配就是 503 `run-scope-unavailable`，一条任务也跑不了。块一的夹具是自己拼的文档服务一侧，没走这个装配，所以没发现 | 开了模式时把这六个交给内部口；不开时照旧 503 |
| B | 任务范围的刷新（`agent-run-scope-doc.mjs` 的 `refresh`）并着来会出假故障 | 主身份定时来问、任务进程每一步过闸都会触发刷新。后一个刷新一开始就把前一个刚读好的结果清掉，紧接着的请求读不到（503 `run-scope-source-unavailable`）；两个刷新读到同一个旧检查点先后提交，后一个 409。实测十次里两三次任务根本起不来 | 同一个槽的刷新排队、一次做一个；结果只在刷新失败时清掉〔裁 7〕 |
| C | 事件通道（`worker-event-sink.mjs`）原样复制事件 | 真实运行器发的事件常带值为 `undefined` 的字段，主服务按「和这段 JSON 意思完全一样」来核，回 400 `worker-event-packet`；事件通道随即锁死，任务被当成中断 | 发之前按 JSON 的意思规整一遍（这些字段去掉，别的不变） |
| D | 单任务进程里，领取、等绑定、已读确认这几步遇到文档服务一时答不上（503）就放弃 | 放弃以后这一代进程还活着、任务授权还有效，没有人会来强制关它，槽一直停在「在跑」，要人按停止 | 这几步凭固定请求号可以原样重发，遇 503 退避重试（250 毫秒起，逐次加倍，上限 5 秒）〔裁 10〕。「还没绑定」「没配模型」「记录对不上」这类要调用方或人处理的状态不重试，原样抛出 |

D 只管到已读确认之前。已读确认之后才出的暂时性故障仍会落到「放弃结算、等人按停止」，见「没做成的」第 6 条。

### 2. 账号模式接上看画面

- **客户端建起来并交给执行器**。`main.mjs`：账号模式设了 `PROMPTCUT_AGENT_LOOK_URL` 就建看画面的客户端（原来只在非账号模式建）；任务进程：设置里写了 `look` 就建。执行器装配本来就把它往下传（`...runnerOptions`），缺的只是没人建。
- **绑运行授权**〔裁 1〕。设计（`three-versions-018-design.md`「渲染容量排队与 Agent 优先」「素材协议」表倒数第四行）要求：看画面请求的项目由「已验证的服务加任务授权」取、请求体换不了；队列里的请求带任务授权。做成了这样：
  - 项目号取自文档服务签的任务授权（`grant.projectId`），工具参数改不了；
  - 登记之前、每一趟去问之前都先过一次授权闸（执行器去问文档服务「这条任务现在还能不能读」）。不过就把排着的请求撤回、给模型一句明确的话。加上块八已接的停止信号，任务被停、被撤销以后不再出图；
  - 请求体带上 `run`（任务授权号、任务号、对话号），渲染服务把它记在这条请求上：落盘、重启后还在、日志和状态里看得到；
  - 签名里的实例号填这条任务所在进程在文档服务登记的那一个，渲染服务按它给请求分主人。**这不是隔离**：实例号是调用方自己填的，渲染服务不核它和钥匙的对应，各任务进程又共用一把私钥，填别人的实例号也签得出来。实际挡着别的任务进程来问、来撤的，是请求号是现生成的随机串，别人猜不到。（初稿这里写成「一个任务进程问不到、撤不了别的任务进程登记的请求」，说得过满，审查后改。）
  - 授权闸有三种结果：行；不行（撤回、告诉模型任务被停或没权限）；文档服务一时问不到（按退避再问三次，都问不到也撤回，但告诉模型的是「确认不了」）。
- **没做到的一半（要主会话定）**：渲染服务那一侧现在只核服务私钥的签名，**不向文档服务核这条任务授权**。它记下的 `run` 是调用方的说法。原因：渲染服务在账号模式下还没有连文档服务的身份（摸底报告「五项之外」第 2 条：托管方的渲染服务看不到账号项目）。后果见「要主会话决定或注意的事」第 1 条。

### 3. 运行素材接线

照 `AGENT-v18-worker.md` 第 5 节的挂点和先后接的：

- 传输层挂在 `account-executor-assembly.mjs`，紧跟 `resources = createRunResources(…)` 之后：用这个进程自己的 `runClient`（每个请求用它内存里的钥匙签）和同一个 `resources`（素材的连接和流登记在它名下，任务被下围栏时 `abortForFence` 关得到）。配置项 `runAssets` 缺省不给；给了必须配齐，而且只能和真实运行器一起用，否则直接拒绝。
- 「项目素材」对象在 `account-runner.mjs` 的运行器工厂里建，和 `createHostedTools` 并排。执行器把这条任务的上下文（`entry.context`）和 `resources` 交给工厂（原来没交）。
- **关闭放进运行器的 `drain()`**，在收尾记录形成之前：等它名下的流真的关完。关不干净就抛出去，执行器据此不形成收尾记录，这条任务只能由强制路径收口。
- **调用方**：素材那几个工具在账号模式改走「项目素材」——导入素材、配音与音效入库（写）、按素材读取（量响度用，读）。原来它们向文档服务要成员的素材票据，而任务的数据连接要不到那种票据，所以账号模式下这几个工具原本是坏的。
- `main.mjs`：账号模式加两个环境变量 `PROMPTCUT_AGENT_RUN_ASSET_ORIGIN`、`PROMPTCUT_AGENT_RUN_ASSET_FINGERPRINT256`，缺省不设；只设一个或格式不对直接拒绝启动。

Agent、文档服务、素材服务三方**第一次真的连起来**（原来各自的测试里对方都是受控的），又暴露了三处，都改了：

| # | 问题 | 现象 | 改法 |
|---|---|---|---|
| E | 文档服务解析素材引用时固定按「读」核权限（`doc-assembly.mjs` 的 `resolveRunMedia`） | 导入的请求签的是「写」，按「读」去核对不上这次请求的签名，被实例登记那一层拒（403）。导入一次也成不了 | 按这次请求签的那个动作去核〔裁 9〕 |
| F | Agent 一侧的传输层（`run-asset-transport.mjs`）不许凭「核对引用」的票据问「这份字节收到哪几片了」 | 「项目素材」的导入第一步就是这样问的，在本机就被拒 | 放行这一条只读的查询〔裁 9〕 |
| G | 素材服务定时对账时一开始就把「账已对上」的标记放下（`asset-run-access.mjs` 的 `drain`） | 定时那一趟大多数时候没有新事件；正好撞上的素材请求被判成「账还没对上」（503），那条租约随即被记成「不明」，运行素材从此对所有任务停摆，直到素材服务重启。缺省每 100 毫秒对一次，撞上的概率很高（我第一次连通就撞上了） | 只在该放下时放下：生命周期核不过、有不明的租约、有没确认完的回执、读到了新事件（处理完之前）、这一趟出错。没看到的新事件不会因此被放过：每个素材请求另拿文档服务当场给的两个账头和本地游标比〔裁 8〕 |

## 没做成的及原因

1. **Linux 的 root 入口没有做。** 现状：root 发布器（开一代、绑定、关、强制关、退槽、失败观察的事务）和它在 Linux 上的运行时（`agent-run-scope-publisher.mjs` 的 `createAgentScopeRuntime`：systemd 单元、cgroup、root 所有的记录文件）是 ChatGPT 留下的，真实 Linux 上只跑过关闭那一段；槽调度（块一）和任务进程的生产配置（这一块）也有了。**还差三样**：
   - 调度和任务进程之间的通道。现在是 Node 父子进程之间的通道（`account-worker-gateway.mjs` 用 `fork`），任务进程的入口 `account-task-worker-cli.mjs` 没有父进程通道就直接退出。systemd 起的进程没有这条通道。打算的接法：在任务进程已有的那个只认 root 证书的本机 HTTPS 口上加「领取、开跑、收尾」三条指令和一条长挂的「结算结果」，另写一个和 `createAccountWorkerGateway` 同形状的客户端。这一半能在本机验（子进程照旧 `fork`，指令改走 HTTPS）；
   - root 进程的入口：读配置、照槽建适配（`current / open / bind / close / forcedClose / retire / observeFailure` 接到发布器和上面的客户端）、起调度、主身份的事件库与收事件接口；
   - 部署模板：任务槽的 systemd 单元片段、root 入口的单元、每一代的设置文件由谁写到哪。
   没做的原因：前两件事（真实运行器进子进程、运行素材三方连通）各自暴露了要改生产代码的问题，改完验完已经到了这一轮的量。**所以生产入口现在仍然是「还开不了」。**
2. **主服务的生产装配没做**（块一就列着）。`main.mjs` 的账号模式仍是在主进程里跑任务的旧路；「主身份 + 事件库 + 收事件接口 + 槽调度」只在测试夹具里拼在一起。连带一件事：一条任务一个进程以后，用户上传的附件要由主服务存进**各代共用**的数据目录（任务进程从那里读）；集成测试里是测试直接把文件放进去的。
3. **渲染服务不核任务授权**（第 2 节）。另外生产上渲染服务还看不到账号项目，所以账号模式的看画面在节点上还走不通，这一块只保证了 Agent 一侧接好、请求进得了队列。
4. **运行素材离生产还差的**（素材块报告 5.1 的五处，第 1 处这次做了，其余没动）：根登记第二版没挂；部署清单里没有它；异常停机的衔接没定；Linux 上的整条链没跑过。这次测试里「现在是哪个素材进程」是注入的，素材服务的生产入口打开运行素材仍要求 Linux 加 root 的登记文件。
5. **运行素材另外看到、没改的三处**：
   - 「项目素材」的 `verifyRef`（核对一份引用）到不了素材服务：素材服务只把 `/internal/v2/asset/run/media/` 交给运行素材的处理函数，`/internal/v2/asset/run/refs/verify` 落到只认文档服务证书的那一段，回 403。现在没有工具用它，没改；
   - 一条租约一旦被记成「不明」（素材服务到文档服务的那条连接断了、文档服务重启过），文档服务这一侧恢复不了（装配里没有给恢复用的核对函数），素材服务从此每次对账都失败，运行素材停摆到重启。G 修掉了最常见的成因，这个状态本身还在；

## 「文档服务签终态要不要等素材租约关完」

现在是**不等**：签终态只等文档服务自己那一侧的连接关完。这次照这样接的，没改。两种选法的后果：

- **不等（现状）**。正常路径上没有差别：任务进程在形成收尾记录之前已经把素材的连接和流都关完了，素材服务看到连接关了就向文档服务报关闭，本机测到的是几十毫秒内全部关闭。差别出在不正常的时候：任务进程被强制关、或者素材服务和文档服务之间的连接断了，租约可能停在「已放行」或「不明」，而这条任务照样结清、名额照样让出来。那以后的后果有两条：这条任务被撤销的那次控制，素材服务一侧的确认会一直欠着（退出确认里「素材」那一项因此可能办不完）；素材服务会停在「恢复待定」直到重启（第 5 条第二点）。文档服务已经不会再给这条任务签新的素材访问，所以不是越权的口子，是「收不干净、后面的人被拖住」。
- **等**。把素材租约加进 `agent-run-scope-doc.mjs` 里 `docClosed` 看的清单。好处：结清的那一刻素材一侧也确实收干净了，和「收尾记录写的是本机资源已收干净」对得上。代价：素材服务不在线、或者租约落到「不明」时，这条任务结不清，对话的名额让不出来，后面的消息全排着——而「不明」现在没有恢复的办法。所以要选「等」，得先把租约的恢复做出来。

我的建议：先保持不等；把「不明的租约恢复不了」排进运行素材上生产之前必须做的事里，做完再改成等。

## 要用户定的事

1. **云端 Agent 的每个任务进程能不能读到「向渲染服务要画面」用的那把私钥。**

   建议：乙，排在渲染服务接入账号项目的那一块一起做；在那之前账号模式的看画面在节点上本来也还走不通。
2. **任务做完的那一刻要不要等素材那一侧也确认收干净，才把对话的名额让出来。** 背景、两种选法和后果见上面「文档服务签终态要不要等素材租约关完」一节。建议：先不等。

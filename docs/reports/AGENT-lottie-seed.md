# AGENT 报告:Lottie 覆盖随机数种子(分支 `claude/lottie-seed`)

任务:试「覆盖随机数种子」能不能让 Lottie 直接跳到任意一帧时,和从头顺着推到这一帧的画面完全相同;可行就留下原型。
出处:`docs/plan/render-refactor-task.md`「癸:Lottie 改成 remotion 式」(渲染重构十项里的第十项)的「要留意的一处」。

用户 2026-10-12 先后说的几句,对应原型里的几样东西:

- 「我觉得可以覆盖随机数种子。」→ **开关一**:给播放库内部那一串随机数播种。
- 「能不能用替换方式直接覆盖,比如替换 random 为 random_in_card()」→ **开关三**:改写表达式,把随机函数换成卡片自己的。
- 「你帮我在外面也兜住,把播放库的随机数也固定。」→ **外面那一层**:播放库自己直接取随机数的地方,开关一和开关三共用。
- 原则:固定随机数只为让每次结果一致,不改变原来的观感。「我认为 wiggle 是固定了随机种子,实际上还是随机跳,只是每次播放都是一致的。」→ 开关三里卡片自己的随机函数照播放库现在的样子做。
- 对 `happy2016` 那个 0.00001 的门槛:「不要差像素。」→ **开关二**(属性值不留旧数)并入正式的一组。

**正式的一组 = 开关三 + 外面那一层 + 开关二。** 三个开关各自仍可单独开关,缺省都关。

日期 2026-10-12。机器:PC,Intel i7-14700KF,20 个逻辑核;Chrome 152.0.7977.75;lottie-web 5.13.0。

## 结论

**正式的一组可行,全部通过。** 五份测试素材和 5 个自带素材,顺着推、回跳、同页新建一份再跳、新开页面再跳、页面里先有别的卡取随机数、先有别的 Lottie,所有 N 上画面都相同(逐像素相同,看得见的 SVG 文本逐字节相同)。原型在 `src/cards/native/lottie.tsx`。

**开关三照「只固定、不改观感」重做以后,相对播放库现状,观感上只剩一处变化**(另外数本身一定会换一次):

- **只有 `wiggle()` 的表达式,如果每帧正好排在另一个调了 `seedRandom()` 的表达式后面求值**:播放库现在让它接着那个表达式留下的、不带时间的那一串取数,看起来是连续晃动的;开关三下各表达式互不相干,它照旧逐帧跳。实测 fixture 的 `wiggle-pos` 那一层相邻帧最多差:关 26.3,开关一 25.6,开关三 411.7。这是「表达式之间串随机数」的一个副作用,正是开关三去掉的东西;开关一因为用的就是播放库那一串,所以保住了。**要不要连这一处也保住,记待用户项。**

其余都和播放库现在一样:`wiggle()` 照旧逐帧跳(相邻帧最多差 753.6,关着 927.4);`seedRandom(n)` 不看第二个参数、不随时间变;同一个表达式里先 `seedRandom` 再 `wiggle` 照旧是连续的(15.3,关着 14.7);同一个合成放几份照旧各动各的;表达式里用 `gaussRandom` 照旧报「gaussRandom is not defined」。

做「癸」之前要知道的几件事:

1. **自带的 5 个素材都没有活的随机表达式,也没有随机顺序的文字。** `navidad` 有 50 个表达式,全在图层样式(`sy`)里,播放库的 SVG 画法不建它们,一个都不执行。开关一、开关三对这 5 个素材的画面没有任何影响;正式的一组里只有开关二动了 `happy2016` 和 `bodymovin`(见「验证」)。
2. **播放库表达式用的是它自己内部的一串随机数,不是全页的 `Math.random`。** 只在 `pinEntropy.ts` 里罩住 `Math.random` 管不到表达式。
3. **主会话推测的「图层是用到才建的」不成立**:卡片用 `progressiveLoad: false`,装载完成时全部建好。变的是建的时候那一串走到哪了。
4. **`happy2016` 那 0.0036% 的差异和随机数无关**,是播放库「新旧值差不到 0.00001 就不更新」。开关二去掉它。
5. **文字的「随机顺序」只按帧号播种反而会错**:它每份文字内容只算一次,带关键帧的在第一次画到那份内容时才算。只按帧号播种,顺着推和直接跳是在不同的帧算的(实测 11 个 N 里只有 6 个相同)。所以外面那一层里给它单独按(素材、图层、文字内容)固定。

**什么样的素材会出问题:**

- 表达式里有 `random` 这个词:同一份实例里怎么推都一样;但新建一份、别的卡或别的 Lottie 先动过,画面就变。
- 表达式里只有 `wiggle()`:连同一份实例顺推和跳着推都不一样。
- 文字图层用了「随机顺序」的动画器:新建一份、别的卡先取过随机数就变;文字内容带关键帧且不止一层时,顺推和直接跳也不一样。

### 对主会话几条推测的核实

- 「每个带表达式的属性在初始化时取一个 `randSeed`,求值时按它加时间播种」:对(`lottie.js` 第 14634、14680 行)。补两点:不管表达式里用没用随机都取;只有表达式文本里出现 `random` 这个词才在求值前播种(第 14380 行),只有 `wiggle()` 的不播种。
- 「`randSeed` 取自 `Math.random`」:**不准确**。那段代码在 `ExpressionManager` 的作用域里,第 14020 行 `var Math = BMMath`,取的是播放库内部那一串。它在模块加载时等于全页的 `Math.random`(第 202 行),第一次 `BMMath.seedrandom(...)` 之后换成播放库自带的发生器,再不回头。
- 「图层是用到才建的」:**不成立**,见结论第 3 条。探针核对了建好后的图层数:8/8、16/16、3/3、59/59、387/387、15/15、46/46、240/240。
- 表达式是 `eval('[function _expression_function(){' + val + ';scoped_bm_rt=$bm_rt}]')[0]` 编译的(第 14422 行),`random` 在第 14326 行、`wiggle` 在第 14425 行、`seedRandom` 在第 14596 行:核对无误。播放库没有 `gaussRandom`。

## 播放库里的随机来源(`lottie.js` 5.13.0 全文过了一遍)

搜的是 `Math.random`、`.random()`、`seedrandom`、`crypto`、`getRandomValues`、`randomUUID`、`new Date`、`Date.now`、`performance.now`。「开关三下由谁固定」一栏里,「表达式层」指改写表达式遮住的,「外层」指外面那一层。

| 行号 | 是什么 | 什么时候执行 | 进画面吗 | 开关三下由谁固定 |
|---|---|---|---|---|

## 原型怎么做的

### 开关三:替换表达式里的随机函数

- **改写**(`rewriteLottieExpressions`、`wrapLottieExpression`):交给播放库之前,把素材里每个表达式的原文包成

  ```
  var $bm_rt = (function (random, seedRandom, wiggle, Math) {
  var $bm_rt;
  <原文>
  ;return $bm_rt;
  }).apply(null, __pcLottieFn(<素材种子>, <表达式编号>, time, value, Math, function () { return time; }));
  ```

  用的是「包一层、把名字遮住」,没有逐处替换。和主会话建议的写法有三处不同:(a) 四样东西由一次调用一起给,这一次求值里它们共用一串随机数(播放库里也是同一串);(b) 第一个形参 random 里的字母 a 在文本里写成了 Unicode 转义,文本里不出现这个词——播放库看表达式文本里有没有这六个字母决定求值前要不要给它自己那一串播种,这样包完以后它的判断和包之前一样;(c) 最后多给一个「现在的 time」,因为表达式里调 `posterizeTime` 会改 `time`,播放库的 wiggle 读的是改过以后的。不遮 `gaussRandom`。原文后面先换行再接 `return`,原文最后一行是 `//` 注释也不会把它注释掉。
- **表达式编号** = 它在素材里的位置的散列。**同一个合成放了几份时**,播放库现在给每一份里的表达式各取一个 `randSeed`,几份各动各的;为保住这一点,带随机表达式的合成每被引用一次就复制一份、各自编号(编号里带上是从哪个图层进来的),原件没人引用了就拿掉。不带随机表达式的合成不复制(`navidad` 一份都没复制)。
- **卡片自己的函数**(`lottieExprRuntime`,挂在全局名字 `__pcLottieFn` 上,每个页面——舞台、导出页——各装一次,不记任何状态)。都照播放库现在的样子:
  - 每次求值开一串新的,种子 =(素材种子、表达式编号、时间)。
  - `random`:四种调用形式照播放库的,连着调取这一串里的下一个。`Math.random()` 同一串。
  - `wiggle`:算法照播放库的(频率写死成 5,累加 floor(时间×5) 组随机数,再加下一组乘小数部分),随机数就从这一次求值的那一串里接着取。每一帧各取各的,照旧逐帧跳。
  - `seedRandom(n)`:不看第二个参数,把这一串换成只跟(素材、表达式编号、n)有关、不带时间的一串。后面的 `random` 每帧同一个数;后面的 `wiggle` 也从这一串取,所以是连续的——和播放库现在一样。
  - `Math`:继承播放库的 `Math`,只把 `random` 和 `seedrandom` 换掉。
- **`this.pv` 和 `value`**:播放库的 wiggle 用 `this.pv`,卡片的函数拿到的是表达式变量 `value`。探针核对:带关键帧的属性两者是同一个对象;不带关键帧的多维属性 `pv` 是 `value` 取单精度的样子(最大差 0)。卡片的 wiggle 先取单精度再算。
- 开关三**不取**播放库内部的随机源,**不给**它播种,不用装载后重画。

### 外面那一层(开关一、开关三只要开了一个就有)

- 建实例、装载完成(含异步装载时播放库自己的回调,包的是这份实例的 `checkLoaded`)、每次跳帧,都包在 `withSeededRandom` 里。建图层用(素材种子)一串,画第 N 帧用(素材种子、N)一串。全页共用的那一串不被 Lottie 挪动。
- 文字的「随机顺序」(`hookTextOrder`):`TextProperty` 没有导出,所以建一份只有一个文字图层的一次性动画(图层入点在动画之外,只建不画),从它身上取到原型,包住 `completeTextData`:算哪一份,就用(素材种子、图层、文字内容)播种。全页只包一次;没开开关的 Lottie 不受影响;素材里没有随机顺序的文字时不做。

### 开关二:属性值不留旧数

- 用 `lottie.__getFactory('propertyFactory')` 在播放库建属性的口子上包一层(播放库自己就是这样给属性加表达式的),开着的实例把属性的 `setVValue` 换成「不相等就更新」。

### 开关一:给播放库内部那一串播种(不在正式的一组里,留着对照)

- 建一份只有一个空图层的一次性动画,让它的表达式执行 `globalData.__pcLottieMath = Math`,取到 `BMMath`。
- 建图层之前按「种子 + build」播种;每画一帧之前按「种子 + 帧号」播种;装载完成后按帧号重画一遍当前帧(`renderer.renderFrame(null)`)。

### 公共的

- **种子 = 素材内容的散列**(`lottieSeedOf`:解析后的数据 `JSON.stringify` 再做 FNV-1a)。同一份 JSON 无论地址、机器、换行符,种子相同。速度、循环、适配不进种子。
- 三个开关都关着时 `loadLottie` 就是原来那两句 `lottie.loadAnimation` 和 `goToAndStop(frame, true)`。没改 `frameMode`,没改画法。

### 开关怎么开

缺省都关,互相独立,不在用户界面上。在建实例之前生效:

| | 页面地址参数 | 或设全局变量(压过地址) |
|---|---|---|
| 开关一 | `lottieSeed=1` | `window.__pcLottieSeed = true` |
| 开关二 | `lottieExact=1` | `window.__pcLottieExact = true` |
| 开关三 | `lottieExpr=1` | `window.__pcLottieExpr = true` |

正式的一组:`lottieExpr=1&lottieExact=1`。代码里直接调 `loadLottie(容器, 数据, 适配, { seed, exact, expr })` 可以不看开关。`debug: "no-outer" | "no-text-key"` 只给探针对照用。

### 全页随机状态恢复的两种办法,选了哪种

- 甲:恢复成没被动过。在 Lottie 之后才取随机数的别的卡,拿到的数会比现在靠前。
- 乙:恢复以后把被吃掉的那几步补回去,别的卡不变。

**实现的是甲。** 乙补不准:现在被吃掉几个跟先画哪一帧有关(fixture 6 个,fixtureip 21 个,textrandom 40 个),「癸」之后先画哪一帧本来就不固定。甲才是要的性质:别的卡的画面不该因为页面里有没有 Lottie 而变。受影响面小:内置卡里没有靠全页 `Math.random` 出画面的(粒子卡用自己的 seed)。

## 开关一和开关三

| | 开关一(给内部那一串播种) | 开关三(改写表达式) |
|---|---|---|

### 开关三相对播放库现状,观感上还有没有变化

逐条(实测都在 exprcases 和 fixture 上,第 28～42 帧或第 42～56 帧):

| | 播放库现在(关) | 开关一 | 开关三 | 变了吗 |
|---|---|---|---|---|
| 数本身 | — | 换一次 | 换一次 | 一定换,躲不开 |
| `wiggle(5, 160)`,前面没有别的表达式播过种:相邻帧最多差 | 927.4 | 761.9 | 753.6 | 没变:照旧逐帧跳,同一个量级 |
| `seedRandom(7)` 后的 `random()` | 不随时间变 | 不随时间变 | 不随时间变 | 没变 |
| `seedRandom(7, true)` 后的 `random()` | 不随时间变 | 不随时间变 | 不随时间变 | 没变 |
| 同一个表达式里先 `seedRandom(3, true)` 再 `wiggle(5, 100)`:相邻帧最多差 | 14.7 | 14.7 | 15.3 | 没变:照旧连续(上限是幅度的六分之一 16.67) |

| 同一个合成放两份,里面的 random、wiggle | 两份各动各的(15 帧里 15 帧不同) | 15/15 | 15/15 | 没变 |

| 表达式里自己声明 `var random`、`function wiggle` | 用它自己的 | 同 | 同 | 没变 |
| **只有 `wiggle()` 的表达式,每帧排在另一个调了 `seedRandom` 的表达式后面求值**(fixture 的 `wiggle-pos`):相邻帧最多差 | 26.3(连续) | 25.6(连续) | **411.7(逐帧跳)** | **变了** |

最后一行是唯一的一处。原因:播放库里所有表达式共用一串,一个表达式调了 `seedRandom`,把那一串换成不带时间的,紧跟着求值的、自己不播种的表达式(文本里没有 `random` 这个词的,也就是只有 wiggle 的)就接着这串不带时间的数取,于是变成连续晃动。这是表达式之间串了随机数,不是哪个表达式自己写出来的;换一下图层顺序它就没了(我第一版测试素材里 `wiggle-only` 那一层就因为排在这样一层后面,关着时相邻帧只差 22.8,挪了位置以后才是 927.4)。同一类的还有:一个表达式求值到一半去读另一个带随机表达式的属性,后者会在中途把那一串重新播种。

**要连这一处也保住,有两条路**(都没做,因为和派活时写的「wiggle 的种子由素材、表达式编号、时间算出」冲突,等主会话定):

- 在开关三里把「同一帧里各表达式共用一串」也照着做:卡片这边留一个「这一帧现在用的那一串」,每次跳帧开头清掉;文本里有 `random` 的表达式求值前换成自己的(素材、编号、时间)那一串,没有的接着用上一个表达式留下的;`seedRandom` 换的也是这一串。约 15 行。代价是一个表达式的值又跟「同一帧里谁先算」有关了(和播放库、开关一一样),不过不需要装载后重画。
- 改用开关一:它用的就是播放库那一串,这一处天然保住(上表 25.6)。代价是上面那张表里的脆弱。

**建议:正式用开关三加外面那一层加开关二(就是现在正式的一组),这一处由用户定要不要再补。** 开关三不碰播放库内部对象;开关一我做的时候错过两次,都错在对播放库内部时机的理解上(见「第一次没过的」第 4 条),这类错不报错、只让画面悄悄不对。叠着开没有额外好处:三个开关都开和只开开关三加开关二的画面相同(3/3)。

- **「癸」的验收写法要跟着改**:「改之前先留底,改之后逐帧相同」——留底如果是关着顺推出来的,`happy2016` 会差 74 个像素。要么留底时就开着开关二,要么这一项对 `happy2016` 改成和「改之前直接跳」的画面比。
- **导出的像素基线**:演示项目 `src/demo.ts` 里没有 Lottie,全量比对测不到它,几个开关开不开基线都不变。Lottie 以探针这份针对性的比对为准。
- **别的卡**:带活表达式或随机顺序文字的 Lottie 后面跟着取全页 `Math.random` 的自建卡时,那张卡的画面会变一次。
- **预览和导出**:「癸」里要在真管线上验一遍,桌面和在线各一遍。
- **在线的声音线程**:`mechanism/cards.md` 说 `lottie-web` 在那里是占位。`lottie.tsx` 新加的代码在模块加载时不碰播放库,都是用到才做。

## 风险

- **开关三改写的是用户的表达式文本。** 包一层以后原文的 `this`、严格模式、能看到的名字都没变;但写法古怪的表达式(顶层 `return`、括号不配对)本来就有问题,包了以后的表现可能不同。
- **开关三会复制带随机表达式的嵌套合成**(放了几份就多几份数据)。素材里这种合成又大、放得又多时,建实例会变慢、占的内存变多。没有量过大素材;自带素材里没有这种情况。
- **开关三的 wiggle、random 是照着播放库现在的写法另写的一份。** 播放库以后改了算法,卡片这份不会跟着变(画面仍然确定,只是和「不开开关的播放库」不一样)。
- **外面那一层的文字部分依赖播放库内部**:`renderer.elements[0].textProperty` 的原型上有 `completeTextData`、`elem.data.ind`、`elem.comp.data.refId`。取不到会警告(探针把页面警告算失败)。只有素材里有随机顺序的文字时才用到。
- **开关二依赖** `lottie.__getFactory('propertyFactory').getProp` 和属性上的 `setVValue`。`package.json` 里是 `^5.13.0`,升级前先跑探针。
- **种子换了,带活随机的素材画面一定会变一次**(开关打开那一次)。
- 种子是 32 位散列,两份不同的素材撞上只是用了同一串随机数,不影响各自的确定性。

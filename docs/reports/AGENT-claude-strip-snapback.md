# 手机版缩略时间轴滑不动：定位与修法

用户 2026-10-24 报：**手机版传统式编辑器的缩略时间轴，用触屏没法滑动查看**。他用 iPhone（iOS 18.1.1）。

## 走过的弯路（两次没打中）

| 第几次 | 当时的判断 | 为什么不对 |
|---|---|---|
| 一 | `touch-action: none` 把浏览器原生横滑关掉了，手动推 `scrollLeft` 那条路在手指上不稳 | 改成 `pan-x` 之后用户实测**还是不动**。这条本身是改进（原生横滑带惯性），但不是病因 |
| 二 | 同步「滚动位置 ← 当前时间」那个 effect 每次渲染都跑，惯性那一段 `dragging` 已是 false，把人划的距离吃回去 | 也是真问题（已一并修），但同样不是病因 |

**转折点是用户的一句话**：「我点了播放，尽管播放到了 5 秒，下面缩略时间轴还是停在 0。」
播放时是**程序**在设 `scrollLeft`，它也不生效 —— 那就与触屏无关，整条滚动是死的。前两次都在触屏那一侧找，方向错了。

## 定性：`scrollWidth === clientWidth`，根本没有滚动区

做了一个托管在线上的诊断页（`https://visuhive.com/download/strip-test.html`，源码在本次会话的 scratchpad），
把 `.strip-scroll` 那一串结构与 CSS 原样抄过去，打开即自测并把读数写在页面上。用户在 iPhone 上开出来：

```
client 414 / scroll 414 · 可滚 0 px · JS 设 40 → 0
```

同一页在 Blink（无头 Chrome，375 宽）上是 `client 375 / scroll 455 · 可滚 80`。

## 定因：WebKit 不把那两个占位 div 算进 scrollWidth

诊断页第二版摆了**五种写法**让用户在真机上逐一实测：

| 组 | 写法 | iPhone（WebKit） | Chrome（Blink） |
|---|---|---|---|
| ① | 占位 div，宽度用百分比（**= 改之前的现状**） | 可滚 **0** | 80 |
| ② | 内层包一层 `width: max-content`，占位用 px | 可滚 **0** | 95 |
| ③ | **不用占位 div，容器写 `padding-inline: 50%`** | **可滚 126 · JS 设 40→40 · 手指划到过 134** | 126 |
| ④ | 内层包一层 `display: inline-flex`，占位用 px | 可滚 **0** | 95 |
| ⑤ | 占位 div 改用 `flex: 0 0 <px>`（不写 width） | 可滚 **0** | 95 |

**只有容器 padding 那一种能滚。** 百分比还是固定 px、外面包不包一层，都不影响结果 ——
所以不是百分比解析的问题，是**那两个占位元素本身不被计入滚动溢出**。

与之吻合的一条实测：这两个占位是**零高度的空盒**。容器是 `align-items: center`，占位没写 `height`，
量出来是 `141.5×0` 和 `187.5×0`（375 宽时）。WebKit 算滚动溢出时当它们不存在，Blink 算。

## 改法

`src/mobile/mobile.css`：把左右留白从占位 div 换成容器自己的 padding，并删掉 `.sp-l` / `.sp-r`；
`src/mobile/ThumbStrip.tsx`：删掉那两个 `<div>`。

```css
padding: 6px 50% 10px calc(50% - 46px);
```

左边是 `calc(50% - 46px)` 而不是 `50%`：前面还有一颗 40px 宽、右外边距 6px 的「＋」，
减掉它首卡的左缘才正对正中那条线。**几何与改之前完全一致** —— 改完在 Blink 上量出来仍是
`client 375 / scroll 455`，首卡的 `offsetLeft` 也不变，所以 `ThumbStrip` 里按 `offsetLeft`
算位置的 `scrollForPos` / `posFromScroll` 一行都不用动。

## 一起修掉的第二个真问题

同步「滚动位置 ← 当前时间」那个 `useLayoutEffect` 没有依赖数组、每次渲染都跑，原来只在手指按着
（`dragging`）时让开。交给浏览器原生横滑之后这不够用：**松手后的惯性那一段 `dragging` 已经是 false**，
这期间任何一次重渲染都会把人划的距离弹回去。现在多记一个 `userScrollAt` 时间戳，
最近 400 毫秒内有用户自己的滚动就不去碰它。

## 守门

`scripts/probes/mobile-ui-probe.mjs` 补了一组「只剩一段也要能从头滑到尾」：
把项目裁成一段（用 `removeClip`，不原地改项目对象），从中间位置往两个方向各划一次，
判「划得动」与「松手之后不回弹」，再 `undo` 还原三段给后面几步用。

**要如实说明这组守门的局限**：它在 Blink 上修前修后都过（修前 40→64 / 40→16，修后 40→63 / 40→17），
**挡不住这次这个病** —— 因为无头环境是 Blink，而病只在 WebKit 上犯。
它挡得住的是另一类回归：「一段时左右留白没留够、根本没有可滚余量」。
要真正挡住 WebKit 这一类，得在本机装 Playwright 的 WebKit 才行（要下载约 90 MB，记为待用户项）。

## 这次学到的

1. **「手指划不动」先别当手势问题。** 让用户点一下播放：如果程序自己推也不动，病在滚动区本身，不在手势。这一步能省掉两轮返工。
2. **无头 Chrome 复现不出来 ≠ 没有问题。** iOS 上所有浏览器都是 WebKit，Blink 的仿真覆盖不到。
   遇到「只在 iPhone 上犯」的毛病，做一个**托管在线上、打开即自测、结论写在页面最上面**的诊断页，
   让用户截一张图回来 —— 比来回问「动了吗」快得多，也不会被「读数条没刷新」误导。
3. **空的占位元素不可靠。** 要撑开滚动区就用容器 padding 或有实际尺寸的元素，别用零高度空 div。

## 1. 量法与工具

- 帧:从探针里抽出那 15 张 1080p 粒子背景 PNG(`clip-bg` 第 30～44 帧,每张约 270 KB;临时改一份探针副本把 `pngs` 落盘,副本没入库),另有 15 张药丸(`clip-pill`,560×374)和单测同款的合成帧(随机 RGBA、渐变、全透明 / 全不透明块;256×64、330×190、1920×1080 各 3 张)。
- 逐字节比较:同一批 PNG 过两条命令行,比 ffmpeg 输出(滤镜链比 `-f rawvideo` 的原始 YUV,整条命令行比 fMP4)的 md5。
- 小基准:同一批 15 张 PNG,命令行交替跑;进程先拉起等 400 ms(相当于预拉),起表 → 逐张写 stdin → 输出以 mfra 收尾为止,和探针的口径一样。
- 空闲门:每轮开跑前 5 s 平均 CPU(`os.cpus()` 时间差)< 15%,过不了每 15 s 再测。今天笔记本上另有别的会话的批次(`lt-M8` 的 vite、puppeteer 的 Chrome)和屏保,空闲时约 8%～12%,忙时 30%～90%;下面凡是没注明「过门」的数都是在 25%～35% 负载下的**相对**对比。

## 2. 耗时拆在哪儿(笔记本)

- 解码 15 张 PNG 只要约 33 ms、CPU 0.03 s(截图大半透明,PNG 很小)。
- 滤镜链(main 的写法)单线程 30 帧约 580 ms,即每帧约 19 ms;按步拆(单线程、30 帧增量):`rgba→gbrap` 23、预乘 24、`→rgb24` 44、**`alphaextract` 128**、`gray→rgb24` 48、两次 `pad` 与 `vstack` 约 30、最后 `rgb24→yuv420p`(1920×2176)约 250。
- `alphaextract` 贵得离谱,查 `-loglevel debug`:ffmpeg 8 起帧上带 alpha 模式,`premultiply=inplace=1` 出来的帧标成「已预乘」,而 `alphaextract` 只收「未预乘」,滤镜图于是在它前面**自动插了 `auto_premultiply_dynamic`,把整帧反预乘一遍**,结果随后被 `alphaextract` 丢掉(alpha 平面本来就没变)。
- x264 单独编同一批已转好的 YUV(`-f rawvideo` 读文件):rtime 142～170 ms,utime 约 0.5 s、**stime 0.23～0.47 s**、maxrss 1.12 GB(auto 线程 24)——每段一个新进程,x264 分配的内存每段都要缺页清零,这部分只随线程数变(改线程数就改字节)。
- 整条(解 + 滤 + 编):CPU 合计约 1.2～2.0 s(utime 0.73～0.88、stime 0.39～1.23),16 线程的机器上本来就接近吃满;所以滤镜多线程、滤镜分段并行这类「换个方式排活」的办法都没用,只有**少干活**有用。
- **ffmpeg 开输入时要先读够 5 MB(或 5 s)才开工**(`avformat_find_stream_info` 的缺省 `probesize` / `analyzeduration`):一张 PNG 两三百 KB,一段 15 帧凑不够,所以**不管帧来得多早,stdin 关掉之前 ffmpeg 什么都不做**;再加上 PNG 帧级多线程解码要先攒够「线程数 − 1」(16 线程的机器上是 15)个包才出第一帧。按出帧节奏喂(每张间隔 60 ms)时实测:第一个输出字节在关 stdin 之后才出现(约 1000 ms,喂完是 950 ms),喂完到出完字节 256～289 ms。

## 3. 试过的路(都先核字节)

「字节」一栏:滤镜链比原始 YUV(`clip-bg`、`clip-pill`、三组合成帧,`yuv420p` 与 `nv12` 两种尾巴),命令行比整段 fMP4 的 md5;「相同」指全部组合都与 main 相同。耗时是小基准(第 1 节)交替跑的中位数,除注明外 7～9 轮、过空闲门。

| 路 | 字节 | 实测 | 结论 |
|---|---|---|---|
| 滤镜图切片线程 `-filter_complex_threads` 1～16(main 的链) | 相同(1、2、4、6、8、12、16 片) | 25%～35% 负载下 4～16 片互相分不出(268～287),2 片 338,1 片 819 | 单改它没用;和下面几条合起来有用(见后) |
| swscale 自己的线程(`scale=...:threads=N`,链里全部 scale 都加) | 相同 | 分不出(187 / 189 / 178 / 193,只滤不编) | 不用:滤镜图的切片线程已经在切 scale |
| 把滤镜链拆成 2～6 段 `-filter_complex`(ffmpeg 9 支持一段的输出接另一段的输入,一段一个线程,流水并行) | 相同 | 只滤不编 60 帧 461 → 419～442;整条编码 256 → 271～301(更慢) | 不用:CPU 本来就吃满,多开线程只是多抢 |
| 两半各自转 `yuv420p` 再上下拼(`halves`) | **不同**(合成帧上色半区最后两行的色度采到了黑边) | — | 不用 |
| 同上,但先补黑边再转(`halvesPad`) | 相同 | 只滤不编 193 vs 184,不快 | 不用 |
| 色半区 / alpha 半区改用平面 `gbrp` 拼(`gbrpDirect`) | 相同 | 单独改分不出 | 和「alpha 在预乘前分叉」合起来用(见 B5) |
| `shuffleplanes` 零拷贝取 alpha 再转 `gbrp` | **不同**(ffmpeg 9 把未预乘的 `gbrap` 去掉 alpha 时自动预乘,mask 被乘了一遍 alpha) | — | 不用 |
| **alpha 在预乘之前分叉**(A1)/ 预乘后 `setparams=alpha_mode=straight` 再取 alpha(A2) | 相同 | 单线程只滤 30 帧 653 → 528 / 524;整条编码 249 → 243 / 240 | 采用 A1 的写法:A2 靠 `setparams` 的 `alpha_mode` 选项,旧版 ffmpeg 没有,链会直接起不来 |
| A1 + 两半用 `gbrp`(B5,最后采用的链) | 相同 | 和 A1、A2 在整条编码里分不出(222 / 225 / 220) | 采用:单线程只滤比 A1 还省(B1 同构的链 532 vs 618) |
| **输入端 `-probesize 32 -analyzeduration 0`**(pr) | 相同 | 批量喂(探针的量法)260 vs 251,分不出;按出帧节奏喂:第一个输出字节从关 stdin 之后(~1000 ms)提前到第 2 帧到达后(~113 ms) | 采用(生产里的主要收益) |
| **PNG 单线程解码 `-threads 1`**(d1) | 相同 | 批量喂:pr + d1 240 vs 251;按节奏喂:喂完到出完字节 201(只有 pr)→ 71 ms | 采用 |
| pr + d1 + A2 / B1 | 相同 | 219 / 229 vs base 251(9 轮,过门) | 采用(B5 与之等价) |
| 候选再加滤镜切片封顶 2 / 4 / 6 / 8 | 相同(1、2、3、5、7、8、13 片都比过) | 两次各 7 轮:244～269 / 211 / 203～210 / 204～208 vs 不封顶 220～222 | 采用封顶 8(按核数封顶,8 核以下不变) |
| 预拉进程改在 `finish()` 时补拉(不在开编码器时补拉) | 相同(同一条命令行) | 仿探针量法(见下)3 次:232 / 226 / 228 vs 不改 224 / 225 / 225 | 不用 |
| x264 `sync-lookahead=0 / 4 / 15`、`lookahead-threads=8`、显式 `-threads 24` | 相同(本机) | x264 单独编:分不出(负载 56%,只看字节) | 不用:不快;`lookahead-threads=1 / 2` 改字节 |
| 输入整段一次 `write` | 相同 | 264 vs 259～268(负载下) | 不用:探针按张写,这不在编码器这一侧 |

- 仿探针量法(`probelike`):用两个版本的 `ffmpeg.mjs`(含预拉进程)各自先编一段当「生产」、等 1.4 s(截图),再背靠背编 3 次取中间那次;交替 3 × 3 轮。main 253 / 261 / 256,候选(提交 `2adefeab`)224 / 225 / 225。
- 真探针比仿探针多出约 30～50 ms:探针在截完 15 张之后**立刻**开始计时,那一秒里本机总 CPU 30%～45%(在探针副本里插桩量的:截图前 10%),是探针自己的 Chrome 截图收尾;在计时前多睡 3 s 反而更慢(322),推测是 CPU 进了低功耗档。这两样都不在编码器这一侧。

## 4. 采用的改法(提交 `2adefeab`、`c1ac7982`、`37d5ce4f`)

只改 `server/bakery/ffmpeg.mjs` 的命令行:

1. **输入端不攒包**:`-probesize 32 -analyzeduration 0 -threads 1`(放在 `-i pipe:0` 前)。去掉「先读 5 MB 才开工」和「帧级多线程解码先攒 15 个包」,帧一到就进滤镜和编码器。批量喂(探针的量法)时只省十来 ms;**按出帧节奏喂(生产的真实情形)时,喂完最后一张到出完字节从 256～289 ms 降到 71～74 ms**,第一个输出字节从关 stdin 之后提前到第 2 帧到达后约 110 ms(`slowfeed`,每张间隔 60 ms,字节与 main 相同)。
2. **滤镜链(B5)**:`[0:v]format=gbrap,split=2[p][a];[p]premultiply=inplace=1,format=gbrp,pad…[rgb];[a]alphaextract,format=gbrp,pad…[mask];[rgb][mask]vstack…,scale=…`。alpha 在预乘之前分叉,免掉 ffmpeg 8 起自动插入的整帧反预乘;两半用 `gbrp` 拼。只用老版本 ffmpeg 也有的滤镜和选项(没用 `setparams=alpha_mode`),换了 ffmpeg 版本也不会起不来。`streamFilterIdentity` 没动,所以 `encoderParamsHash` 不变。
3. **滤镜切片线程封顶 8**:`-filter_complex_threads min(8, 逻辑核数)`;`PROMPTCUT_STREAM_FILTER_THREADS` 可以手动指定(0 = 交给 ffmpeg)。8 核以下的机器不变;切几片不改产出(1、2、3、5、7、8、13 片都比过)。真探针 A/B(同一 worktree 用环境变量切,交替 5 轮):不封顶中位数 266,封顶 8 是 253。
4. 编码器对象加一个只读的 `received`(已收到的字节数),给「帧一到就开工」的单测用。

没采用、但量过的:预拉进程改在 `finish()` 时补拉(不更快);把 ffmpeg 进程调到「高于正常」优先级(临时补丁、没提交:真探针交替 4 轮,245.5 vs 249.5,分不出,且会和编辑器抢 CPU)。

## 7. 改字节的选项(没做,列给主会话)

笔记本、小基准 7 轮、过空闲门(空闲约 11%);在最终候选的命令行上只改 x264 参数:

| 选项 | 耗时中位数 | 段字节(clip-bg) | maxrss | 作废盘上分段 | 跨机器字节 |
|---|---|---|---|---|---|
| 最终候选(x264 auto 线程,笔记本 = 24) | 206 | 428801 | 1171 MB | — | 现状就不一致:auto 线程随核数变(PC 与笔记本的 x264 线程数不同),两边编出的字节本来就不同 |
| `-threads 8` | 254 | 429404 | 584 MB | 会(参数进了 `spec.args` 就进哈希) | 固定线程后各机器一致(同 ffmpeg 构建) |
| `-threads 12` | 222 | 429356 | 723 MB | 会 | 同上 |
| `-threads 16` | 212 | 428317 | 881 MB | 会 | 同上 |
| `-rc-lookahead 5` | 201 | 420560 | — | 会 | 仍随 auto 线程变 |
| `-x264-params sliced-threads=1` | 220 | 463719 | — | 会 | 同上 |
| `-threads 16 -rc-lookahead 5` | 202 | 420130 | — | 会 | 固定 |

笔记本上没有一个改字节的选项比候选明显更快(最多 `rc-lookahead 5` 省 5 ms,且 mbtree 看得更短),所以不建议改。唯一值得主会话留意的是最后一列:**x264 auto 线程让不同核数的机器产出的分段字节不同**,而分段签名里没有线程数,跨节点去重时两台机器的分段会被当成同一份(画面等价,字节不同)。这是现状,不是本次引入的。

## 9. 对任务书的说明

# H07 对抗性安全审查

审查对象：分支 `claude/h07-logout-stall`，`28291210..c8a11f0c` 共 6 个提交，实施报告 `docs/reports/AGENT-claude-h07-logout-stall.md`。2026-10-22，Opus 审查。只读了代码、跑了测试、写了一次性探针和一次性用例，没改功能代码。

几个词（同实施报告）：

- **H07**：裁定「Agent 服务重启时有人开着云端对话页，这个登录之后的改密退出一直停在 `revoking`」。
- **读取**：文档服务账本里记的「哪个 Agent 实例给哪个登录开着一条对话读取」。退出时点名要关，那个实例关了并确认，Agent 这一项才算确认。
- **收口**：文档服务把一个实例名下的读取记成已关、把等它的控制记录补上回执。
- **租约 / `lease`**：实例向文档服务报「我握着哪把数据目录锁（锁号）、在哪台机器（机器码）」。
- **交接 / `handover`**：后继实例向文档服务说「前一个实例的进程已经不在了」，凭的是它现在握着同一把锁。
- **F2～F5**：本审查写的一次性用例编号，见第三节。

## 一、结论

**改了一处才能合入**（第二节「确实是问题」第 1 条：机器码明文进了文档服务账本）。改法很小，不影响撤权逻辑。其余各条都是「卡住」方向或部署前要核的事，不挡合入。

**有没有任何一条路径能在页面还读得到的时候报出「已退出」？**

在受支持的部署下（一个 Agent 主服务、数据目录在本机盘）**没有**。走得通的只有一条理论路径，要五个条件同时成立，每一条都是部署错误：

1. 数据目录放在网络盘（NFS／SMB）上，并且锁失效（`nolock` 挂载，或断网超过网络盘的租期、服务器把锁放了）；
2. 两个 Agent 主服务同时在跑，用同一个数据目录；
3. 两台机器的机器码相同（同一台机器，或克隆出来没重新生成 `/etc/machine-id`、没 sysprep 的 Windows、镜像里固定了 machine-id 的容器），而且网络盘在两边的设备号也相同；
4. 交接那一刻，文档服务这边恰好看不到前一个实例的订阅流（订阅流抖了一下，或文档服务刚重启、前一个还没重连上，见 F5）；
5. 前一个实例自己还没察觉断线（最长约 5 秒，订阅请求的空闲超时）。

即使五条全中，泄露的也只是前一个实例在被收口之前已经从文档服务取到、还没写给页面的那一批内容：页面的事件流每推一批都要先经读取控制向文档服务读一次（`server/agent-service/http.mjs` 第 222～262 行的 `pollWork`），收口以后这一步被拒（`instance-revoked`，而且被退出的登录本身也已作废）。

**这个改动相比 main 现状，是变安全了还是变危险了？变安全了。** main 上 `6841cbd9` 那条推断（新一代只做控制的主服务一订阅，就把更早各代全记成已收口）不需要任何部署错误就能误报：旧主服务活着、连着、开着读取时，新一代订阅一次就收口它（实施报告有实测，主会话也核过）。本分支把它换成了操作系统锁的证据，误报需要上面五个部署错误同时成立。代价是几处「卡住」方向的新情形（第二节第 2～6 条），都不会假报。

## 二、问题清单

### 确实是问题

**1. 机器码明文存进了文档服务账本（要改，合入前）**

- 是什么：`lease` 报的 `machine` 是 `machineCode()` 的完整输出（`server/agent-service/conversation-control-client.mjs` 第 65 行 `machineOf`，第 214 行发出），文档服务原样存进 `agentReadsV1.leases[实例].machine`（`server/account/agent-read-control.mjs` 第 400 行），活着的实例的租约一直留着。
- 为什么是问题：这串码就是这台机器的「配置分发解密口令」。`server/runners/machine-id.mjs` 第 107 行明文写着整串写出去「等于附赠一把钥匙」，诊断报告都只给脱敏的前两组；Agent 节点导入服务密钥时正是用它解分享密文（`server/agent-service/service-keys.mjs` 第 116 行 `importServiceKey({ code = machineCode() })`）。现在它进了文档服务账本，账本的备份、导出、排障转储都会带着它，拿到账本又拿到一份发给这台节点的分享密文的人就能解出 API 密钥。
- 方向：不是撤权问题，是本次新引入的密钥卫生问题。
- 怎么改：换成专用的摘要，例如 `sha256('promptcut-agent-lease-machine-v1|' + machineFingerprint())` 的十六进制。文档服务只比相等，语义不变；`reference` 正则也放得下。单元测试里的 `MACHINE` 常量不用动。

**2. 部署前遗留的「登记了、没订阅过、没收口」实例：部署后每一次退出都永远办不完（卡住，所有人）**

- 是什么：`fenceInState` 对「代次 ≤ `inventorySinceGeneration`、不在 `t.instances`、没收口、不是 `run-worker`」的实例照旧建「来历不明」目标（`agent-read-control.mjs` 第 345～358 行），谁都确认不了，交接也核不过（它没报过锁）。main 上下一个只做控制的主服务一订阅，`supersedePriorControlOnlyInState` 就会把更低代的这类实例收口；本分支去掉了它，这类实例从此永远挡着每一次点名。
- 怎么触发：部署那一刻文档服务账本里已经有这样一行（例如某个主服务登记后、订阅前被杀）。一次性用例 F3 复现：`completion().complete` 一直是 `false`，实例一直 `active`。
- 方向：卡住，不会假报。但范围是所有人的退出，不只是开着页面的那个人。
- 怎么办：不必改代码。部署 0.7.20 之前在节点上查一次文档服务账本：`agentInstancesV2` 里状态不是 `closed`（或没有 `closure`）、`purpose` 不是 `run-worker`、又不在 `agentReadsV1.instances` 里的行。正常应该一行都没有（main 的推断会持续清掉它们）。有的话先告诉用户再定。

**3. Agent 先于文档服务升级时，一次性缺口多延续一代（卡住）**

- 是什么：新 Agent 连旧文档服务时，`lease` 回 404，客户端照样把 `leaseDeclared` 置真（`conversation-control-client.mjs` 第 216 行），本进程以后重连也不再报锁；`handover` 回 404 被算成「永远收不了口」，本地那一笔租约被删（第 233 行）。
- 后果：文档服务随后升级上来，这个 Agent 实例在文档服务那边没有租约，它下一次被重启时页面开着的话，退出照样卡住。实施报告说的「部署那一刻」的缺口就多延续了一次重启。
- 方向：卡住。核过，没有任何放行。
- 怎么改（二选一）：只在 `lease` 成功时置 `leaseDeclared`，404 时下次 `start()` 再报，`handover` 遇到 `read-control-no-route` 留着本地那一笔不删；或者部署清单写明先换文档服务、再换 Agent。

**4. 「后拿到锁的是更低一代」时交接被拒（卡住）**

- 是什么：`handover` 要求前一个比后继代次更低（第 423 行）。账号主服务是先登记、后拿锁（`account-master-assembly.mjs` 第 104 行登记，`conversation-control-client.mjs` 第 253 行拿锁），两个主服务交叠启动时，代次高的可能先拿到锁、正常收口后，代次低的才拿到。正常收口时页面读取在本地关了，但不回报文档服务（第 97 行 `onClosed` 在 `closed` 为真时直接返回），账本里那几条读取还开着，只能靠交接收口，而低一代交不了高一代。
- 怎么触发：一次性用例 F2 复现，`read-handover-forbidden`，退出一直等。
- 方向：卡住，概率低（要两个主服务交叠启动）。
- 怎么改：把「代次更低」换成「租约报得更早」（文档服务给每次 `lease` 记一个递增序号）。锁只在握着时才能报租约，所以租约先后就是握锁先后，比代次准，安全论证不变。或者在主服务里先拿锁再登记。

**5. 拿锁时所有 SQLite 错误都报成 `read-control-owner-busy`（运维可见性）**

- 是什么：`acquireDataDirLock` 的 `catch` 除了「锁号格式不对」以外一律抛 `read-control-owner-busy`（第 60 行）。磁盘满、目录没权限、`.owner` 文件损坏也报成「有别的进程握着」。
- 后果：Agent 主服务一直起不来读取控制、对话一直 503，日志却说「有人握着锁」，会误导排查。安全方向。
- 怎么改：只有 SQLite 的 BUSY／LOCKED 报 `owner-busy`，其余带原码报 `read-control-owner-error`。

**6. 锁号会因设备号变化而重生（卡住，让 H07 在某些部署下仍然复现）**

- 是什么：锁号绑在 `stat.dev:stat.ino` 上，设备号变了就换新锁号，旧实例的租约对不上。
- 什么时候会变：Agent 数据目录在容器的 overlay 层里（每次起容器设备号都不同）；Linux 重启后块设备编号变了（LVM、多块 NVMe 枚举顺序变化）；换服务密钥（`serviceKid` 变了，交接要求同一个 `serviceKid`，`server/hosted/deploy/README.md` 第 233 行的轮换流程就会碰上）。
- 方向：卡住，都是修前的样子，不泄露。现在的节点是宿主机上的 ext4、systemd 单元，不受影响。建议写进语义里的「已知不收口的情形」。

### 我不确定、要主会话定

**A. Linux 上没实测锁的行为。** 本机没有 WSL，我没有连生产节点（任务没授权）。按 SQLite 的 unix 文件系统接口推断：用的是 POSIX `fcntl` 记录锁，进程退出（含 `SIGKILL`）时内核放锁；锁属于进程、不随 `fork` 继承，子进程不会替父进程握着。Linux 上有一个 Windows 没有的坑：**同一进程里用别的文件句柄打开再关掉同一个文件，会把这个进程在这个文件上的全部 POSIX 锁一起放掉。** 现在的代码里只有 SQLite 和 `fs.statSync` 碰 `.owner`（`stat` 不打开文件），所以眼下不受影响；但以后谁在主服务进程里 `readFileSync` 这个文件，锁就会在进程还活着时悄悄丢掉，那是危险方向。建议：(1) 在 `acquireDataDirLock` 注释里写明「本进程不许用 SQLite 以外的方式打开这个文件」；(2) 主会话决定要不要在节点 `/tmp` 里跑一次我的探针（`timeout 240s node probe.mjs`，只动自己起的进程和 `/tmp` 下的临时文件），脚本在下面「探针」一节。

**B. 「连着订阅流」这一道比实施报告说的弱。** 实施报告第四节第 3 点的表里把它当成「最后一道」。F4、F5 说明：文档服务这边订阅流一断，或文档服务一重启（`streams` 是进程内的表，重启后是空的），这一道就不存在了，只剩锁。在锁可靠的部署下这无所谓；在第一节那五个条件下，它挡不住。要不要加强（例如要求前一个的订阅流断开后，文档服务至少见过它一次重连失败），由主会话定。我倾向于不加：时间不是证据，加了也只是缩窄窗口。

**C. 机器码不一定能区分机器。** 克隆的虚拟机、没 sysprep 的 Windows（`MachineGuid` 相同）、镜像里写死 `/etc/machine-id` 的容器，机器码都相同；取不到 machine-id 时退回「主机名＋网卡」，Docker 的网卡地址是按 IP 排的，主机名在 compose 里常被写死。实施报告的表里「两台机器机器码不同」这一条要加上这些例外。只影响网络盘上的误配，不影响受支持的部署。

**D. 非 `control-only`、非 `run-worker` 的实例被交接收口后，对任务结算的影响我没逐条核。** 交接直接把实例记 `closed` 并写入 `closure`（`closeGoneInstanceInState`），绕过了实例权威的 `confirmClosed`。main 上的推断也是这样直接写的，只是只对 `control-only`。生产配置下主服务都是 `control-only`，没有任务，不受影响；不开「一条任务一个进程」的配置（集成测试那一档）下，主进程自己跑任务，那时若有 root 的关闭记录要走 `confirmClosed`，会因 `closure` 已存在而 409。这与读取安全无关，属于任务结算，请主会话判断要不要另查。

## 三、逐项核对（对应任务书的七点）

### 1. 最要紧的一条：逐条走

| 情形 | 结果 | 依据 |
|---|---|---|
| 旧进程卡死但活着 | 卡住，不假报 | 进程活着就握着锁，后继拿不到锁（`read-control-owner-busy`），交不了证据。探针 B：事件循环永久阻塞的持锁进程，3 秒 22 次都拿不到；探针 S：被 `NtSuspendProcess` 挂起的持锁进程，挂起中和 2 秒后都拿不到，杀掉以后立刻拿到 |
| 旧进程断网但活着（本机盘） | 卡住，不假报 | 断网不影响本机文件锁；断开订阅流时它自己撤掉全部页面读取（`conversation-transports.mjs` 的 `disconnect`），恢复后收到点名自己关、自己确认 |
| 旧进程在另一台机器上（各自本机盘） | 卡住，不假报 | 锁号是各自锁文件里的随机号，不同；文档服务核锁号不等就 `read-handover-unproven` |
| 两个主服务同时跑（同一数据目录） | 第二个起不来 | 集成测试丙实测 `read-control-owner-busy`；它登记过但没订阅，按〔裁 2〕不成为点名目标，也开不了读取 |
| 两个主服务同时跑（不同数据目录） | 各管各的 | 锁号不同，谁也交不了谁的证据；集成测试丙的「另一个数据目录上更新的一代」4 秒 16 次都不办完 |
| 数据目录在网络盘上 | 第一节那条理论路径 | 见第一节五个条件；单机器、或两台机器设备号不同时，后拿锁的那边会因 `file_id` 不同换新锁号，反而卡住 |
| 机器码重复 | 只在网络盘误配下有意义 | 见第二节 C |
| 锁被别的东西持有 | 卡住 | 别的进程握着就一直 `owner-busy` |
| 锁被子进程继承 | Windows：不继承（实测）；Linux：POSIX 锁本来就不随 `fork` 继承 | 探针 D：持锁进程起一个继承了标准输出、脱离父进程的孙进程，硬杀持锁进程后孙进程还活着，锁立刻拿得到。两边行为不同之处只在「谁握着」：Windows 上如果句柄真被复制给了别的进程，锁要等最后一个句柄关掉才放（卡住方向）；Linux 上锁只属于拿锁的那个进程。两种都不会让锁在拿锁进程活着时被放掉 |
| 锁文件被拷走、删掉、改名 | 拷走：副本换新锁号；握着时删、改名：Windows 上 `EBUSY` 失败 | 探针 F/G。Linux 上握着时可以删掉，删了以后新进程在新文件上拿新锁号，交不了证据：卡住 |

### 2. 锁的可信度

Windows 实测（本机，Node v24.19.0，脚本见末尾）：

- **硬杀以后真的放锁。** 探针 A 重复 5 次：持锁进程活着时另一个进程拿不到（5/5 `owner-busy`）；`kill('SIGKILL')`（Windows 上是 `TerminateProcess`）后，收到退出事件约 5 毫秒，之后第一次尝试就拿到（0.5～0.8 毫秒，5/5），锁号与之前相同。
- **冻结、卡死的进程仍握着锁。** 探针 S（挂起）、B（事件循环阻塞）见上表。实施报告「冻结或断网的进程仍握着锁，所以没有后继者能接管」在本机盘上成立。
- **同进程用普通文件接口打开、关闭同一份锁文件**（Linux 上会丢锁的那种操作）：Windows 上锁还在（探针 E，`owner-busy`）。

Linux 没实测，推断见第二节 A。网络盘：NFS 上的锁靠网络盘服务器维持，客户端断网超过租期服务器就放锁，而那个进程可能还活着；`nolock` 挂载时锁只在本机有效；SMB 也是会话超时后服务器放锁。**所以实施报告那句话在网络盘上不成立**，这是第一节那条理论路径的来源。

### 3. `lease` 与 `handover` 两个新接口

- **谁能调**：只有 Agent 服务身份（mTLS 证书，`transport()` 取）下登记过、状态为 `active` 的实例（`verifyInState` → `current()`），每个请求由实例私钥签名，签名覆盖整份请求体的摘要并绑定这条 TLS 连接的导出值（`authenticate`）。`run-worker`（一条任务一个进程，跑的是带工具的任务代码）被 `authenticate` 拒掉：它拒的是 `Object.values(conversationControlOperations)`，新加的两个操作名在这张表里，自动覆盖。
- **重放**：一次性随机数（账本里记、进程里也记）＋签名绑定 TLS 连接，旧签名换一条连接就对不上。和原来四个接口同一套，原有用例「nonce replay rejects」覆盖。
- **伪造、冒名**：别的服务（素材、渲染）是不同的 `serviceId`，交接要求同一个 `serviceId` 与 `serviceKid`；后继伪造不了前一个的租约，因为前一个的租约是前一个用自己的实例私钥签的，而且报过不能改（`read-lease-mismatch`）。
- **文档服务几项核对有没有可绕的**：逐条读了 `handover`（第 412～437 行）：代次对不上 404；自己交自己、身份不同、`run-worker`、用途不同、代次不更低 403；两边租约缺一、锁号不等、机器码不等 403；前一个连着订阅流 409；任何一条不符都在事务里抛错，账本回滚，不改任何东西。已收口的前一个直接回 `closed: true`，不改状态。没找到绕法。**文档服务能核的只有「两个实例都说自己握过同一把锁」，核不了「后继此刻真的握着」；这一点完全靠 Agent 那一侧的代码诚实，和整套实例证书体系的信任前提相同。**
- **版本不匹配**：旧文档服务对未知路径回 404 `read-control-no-route`（`createAgentReadControlHandler` 在解析操作名时就失败，main 上同样有这一行）。新 Agent 收到后不报锁、不交接、照常订阅；文档服务那边没有租约，任何交接都 `read-handover-unproven`。旧 Agent 对新文档服务：不报锁、不交接。**两种都只会退回等待，没有放行**；只是第二节第 3 条那样把缺口多延续一代。

### 4. main 那条推断删干净了没有

- `grep -rn "supersede" server/` 在读取控制、实例权威、文档服务组合里都已无匹配（剩下的全是渲染队列等无关模块）。订阅时、文档服务启动时两处调用都去掉了。
- 账本里能把读取记成已关、把控制目标补上回执的，只剩三处：实例自己 `closeReads`（要 `sameInstance`）、实例自己 `acknowledge`（要 `sameInstance`、拒「来历不明」目标）、`closeGoneInstanceInState`（只由 `handover` 在核完证据后调）。另有实例权威的 `confirmClosed`，要关闭记录的核验函数，未改。

### 5. 反向用例是不是真的反向

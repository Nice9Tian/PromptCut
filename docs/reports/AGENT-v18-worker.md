几个词：

- **独立任务进程**：云端 Agent 的每条任务放进一个单独的操作系统进程里跑，一个进程只跑一条。ChatGPT 的报告里叫 worker。
- **一代**：一个任务槽上先后开过的每一个任务进程算一代，root 给每一代编号（第 1 代、第 2 代……），一代只绑一条任务。
- **root**：节点上以 root 身份运行、负责开进程、关进程、写下「这一代确实关干净了」的记录的那一侧。
- **主身份**：Agent 服务里只做控制、自己不跑任务的那个身份（ChatGPT 的报告里叫 master）。
- **终态**：文档服务签的「这条任务可以关了」的证书；**强制终态**是它在任务被停止、被撤销、进程死掉时签的那一种。**意向**是任务进程用自己内存里的钥匙签的「我同意按这份终态关」。
- **结清**：文档服务读到 root 的关闭记录以后，把这条任务记为结束、把对话的名额让出来。让出来以后下一条才领得到。
- **收尾记录**：本块新加的。任务进程自己形成的一条不可改的记录，内容是「这条任务的终态事件已经被主服务持久确认、运行器已经收完、最后一次事件落盘成功」。

### 2. 摸底报告「还差」的第 1～5 条

**第 1 条，执行器形成不可变记录**（`server/agent/service/account-runner.mjs`）。单任务进程里，任务真做完以后不再有意抛 `run-outcome-unavailable`：

- 运行器结束后，执行器发出这条任务的最后一条事件 `runner_done`，带上结果（`done` 做完、`failed` 失败、`interrupted` 被叫停）〔裁 2〕，等主服务把它持久确认，拿到这一行的编号和摘要。事件没能被确认就没有结果，照旧抛错，这条任务只能由强制路径收口。
- 运行器收完、最后一次事件落盘成功、终态事件已确认，三样齐了才形成收尾记录（`server/agent-service/worker-settlement.mjs` 的 `createRunDrainRecord`）；缺一样只报告状态、不形成记录。
- 任务进程把收尾记录封存进自己的本机事件日志（`worker-event-journal.mjs` 的 `sealTerminal`）：只有全部事件都被确认、并且终态事件就是最后一条时才封得上；封了以后不能换内容、不能再加事件，重开日志只能读。
- 旧的多任务路径（不是一条任务一个进程）没有结算方，行为不变，仍然抛 `run-outcome-unavailable`。

**第 2 条，「结束、准备、终态、控制」四个接口的调用方**：

- 任务进程这一侧（`worker-settlement.mjs` 的 `createWorkerSettlement`，由 `account-task-worker.mjs` 在收尾记录封存后启动）：依次调「结束」→ 用自己的钥匙签「准备」（签之前由私有来源核对：只认日志里封存的那条收尾记录）→ 等文档服务关完它那一侧的连接后取「终态」→ 签「意向」。四个请求的编号都由任务授权号算出，回应丢了就原样重发。文档服务明确拒绝（任务已被撤销）就放弃正常结算，不补签、不换成别的结果。
- 主身份这一侧：「控制」接口（取强制终态）和「待办」接口由槽调度调用，见下一条。
- 任务进程把「终态 + 意向」经它和调度方之间的进程间通道主动报出去（`account-task-worker-cli.mjs`、`account-worker-gateway.mjs`）。这两样 root 都能独立验签，经手的人改不了。

**第 3 条，节点上的调度入口**（新文件 `server/agent-service/account-slot-scheduler.mjs`）。它只做四件事：

1. 有排队的对话、又有空槽：让 root 开一代新进程，叫它去文档服务领这一条任务，把文档服务签的分配交给 root 绑定，再让它开跑。
2. 任务进程交来「终态 + 意向」：让 root 真的把这一代关掉、写下关闭记录。
3. 文档服务那边出现强制终态（主身份每一轮问「待办」时能看到）：取来交给 root 强制关。
4. 每关掉一代再问一次文档服务，由它读 root 的关闭记录去结清。

它不判断权限、不产生证明。root 那一侧写成一组口子（`current / open / bind / close / forcedClose / retire / observeFailure`，文件头有逐个说明），本机测试用受控的实现；Linux 上的实现还没有，见「没做成的」。

文档服务这一侧补了三处，都在「一条任务一个进程」模式下才走到：

- `server/account/run-authority.mjs`：强制停止的那条控制记录，原来在任务结清以后永远停在「待办」；现在它撤掉的每条任务都凭 root 的关闭记录结清了，就记为办完并带上关闭记录的摘要〔裁 6〕。停止、切私有的接口是凭它回成功的。
- `server/hosted/doc-agent-assembly.mjs`：文档服务关自己那一侧连接这一步，第一次没做成的（当时出错、进程重启过），主身份每次来问时补做；停止、切私有的接口在回答前先读一次 root 的关闭记录。

**第 4 条，正常结束和强制停止交错时的顺序**。规矩：

- 每个槽的关闭类动作排成一条队，一次只做一个。先到的先做；这一代一旦关了，后到的不再做。所以同一代不会被关两次，也不会出现两份互相矛盾的关闭记录。
- 任务进程发现自己被撤销以后只放弃，不抢着补签正常结算。
- 结果记「做完」还是「被中断」由文档服务按它自己的记录定：停止在结清之前生效的，一律记「被中断」，哪怕任务自己已经报了做完、甚至 root 是按正常终态关的。任务自己报的结果原样留在回执里，不被改写。这条是 ChatGPT 定的规矩，我照着接的，见「要用户定的事」。
- 进程在 root 动手之前自己没了：不按正常关（正常关要亲眼看着这一代主进程停下），改写失败观察，由文档服务签「进程故障」的强制终态。

**第 5 条，完整的一条独立进程任务跑通**：见下一节的集成测试。

### 4. 给下一块（改密选「退出」后各服务逐个确认）留的口子

下一块不用新增 Agent 一侧的调用，接下面这几处：

1. **起点**：账号服务的「旧登录作废」事件进文档服务后，`runProvider.applyAccessEvent(event)` 已经会给相关任务下围栏，产生请求号为 `access:<事件号>` 的控制记录。记录里 `revoked` 是要中止的任务（私有对话的、还没被读到的），`retained` 是保留下来继续跑的（共有对话里已读的当前任务）。
2. **文档服务自己这一侧**：`deliver(control)` 关它自己的连接。已接，本块加了失败后补做。
3. **Agent 这一侧不用主动调**：主身份定时问「待办」（`pending()`），调度据此让 root 强制关掉被撤销的那一代，文档服务读到关闭记录后结清，并把这条控制记录记为 `complete`，回执里有每条任务的关闭记录摘要（`receipt.closures`）。
4. **「Agent 这一项已确认」怎么判**：请求号为 `access:<事件号>` 的控制记录全部 `state === 'complete'`，或者 `revoked` 为空。保留的任务不在等的范围里（任务书：确认设备已退出不要求等共有任务做完）。
5. **往账号服务回确认的地方**：`doc-agent-assembly.mjs` 的 `completeReadAccessEvents()`。它现在只看「读取」关没关，回执里的 `stoppedRuns` 固定是空数组。下一块在这里加上第 4 点的判断，没办完时抛 `agent-run-closure-pending`（这个码已经在它的容忍名单里，会保持待办、下次再试），办完时把 `receipt.closures` 里的任务填进 `stoppedRuns`。
6. **重启后续办**：控制记录、关闭清单都在账本里；文档服务启动时 `start()` 会重新投递并结清；调度启动时会接手上一个调度进程留下的一代（等它主进程退出、写失败观察、凭强制终态关）。

块五（删对话「有任务在跑先停再删」）可以用同一个办法：在对话权威里对这个对话下一条围栏（`runHooks.fenceInState`，`kind: 'stop'` 带 `runId`，和现在的停止一样），等那条控制记录 `complete` 再删、再让出名额。

### 5. 运行素材的调用方该挂在哪（给后面接这条线的人）

「运行素材」是云端 Agent 的一条任务凭这条任务的授权读写所在项目的素材（块六的报告 `AGENT-v18-assets.md` 第 5.1 节，还差五处里的第 1 处是「Agent 服务一侧没有调用方」）。这次没有接，下面是从本块的装配看该怎么接。

**挂在哪**

1. 传输层挂在 `server/agent-service/account-executor-assembly.mjs` 的 `createAccountExecutorAssembly` 里，紧跟 `resources = createRunResources({ runClient, … })` 之后、`createHostedAgentService(…)` 之前：
   `createRunAssetTransport({ runClient, assetOrigin, assetTls, assetFingerprint256, resources })`，再包一层 `createRunAssetClient({ transport, maxResponseBytes })`。
2. 「项目素材」对象（`createProjectAssets`）要的工作区和导入额度是在 `server/agent/service/account-runner.mjs` 的 `createExistingHostedRunnerFactory` 里建的（`workspaces`、`gate`），所以它在那里建，和 `createHostedTools` 并排；把第 1 步的客户端经装配的 `runnerOptions` 传下去。
3. 文档服务一侧的入口是 `doc-agent-assembly.mjs` 的 `mountRunAssets`，这次合并后它和独立任务进程并存（见「把 main 合进来」）。

**要传什么**

- `runClient` 必须是这个进程自己的那一个（装配收到的那个参数）。运行素材的每个请求都用进程内存里的钥匙签，文档服务据此认「是哪一个实例、哪一条任务」。在任务进程里它就是任务身份；主身份（只做控制）不能用运行素材，会话层和文档服务两头都会拒。
- `resources` 必须是装配里同一个 `createRunResources` 对象：素材的连接和流登记在它名下，任务被下围栏时 `abortForFence` 才关得到它们。现在 `createAccountRunnerService` 把 `resources` 只交给了任务管理器，没有交给运行器工厂，要补传。
- 每条任务的上下文（`resources.contextFor({ projectId, runGrantId })` 的返回值，执行器里是 `entry.context`）现在没有交给运行器工厂；工具调「项目素材」时每次都要带它，要在 `runnerFactory({ grant, record, … })` 的参数里加上。
- `assetOrigin / assetTls / assetFingerprint256`：素材服务的内部地址、这个进程连素材服务用的客户端证书、素材服务证书的指纹。只从入口的本机配置来（任务进程是配置模块里的 `createAssemblyOptions`），不从进程间消息或任何请求体来。任务进程连素材服务的证书和它连文档服务的是同一个任务身份，文档服务那边 `mountRunAssets` 认的是 `account.agent.fingerprint256`。
- 导入用的 `reserveImport`、`maxImportBytes`、`verifySourceJob` 由工具包那一侧定，这里不规定。

**和收尾记录的先后（必须守）**

本块的收尾记录写的是「本机资源已收干净」。素材的连接和流也是本机资源，所以「项目素材」的关闭（`projectAssets.close()`，等它名下的流真的关完）要放进运行器的 `drain()` 里，在执行器形成收尾记录之前完成。放在别处，收尾记录就会在还有素材连接开着的时候形成。

**接的人要先定的一件事**

任务报了「结束」以后，文档服务就不再给这条任务签发新的素材访问（授权检查里有这一条）。但素材服务那一侧已经发出去的租约什么时候算关完，和文档服务签终态之间没有先后约束：现在签终态只等文档服务自己那一侧的连接关完，不等素材租约。要不要等，是接这条线时要定的；要等的话加在 `agent-run-scope-doc.mjs` 的 `docClosed` 所看的清单里。

## 没做成的及原因

1. **真实的运行器没有放进子进程里验。** 子进程里跑的是照脚本走的受控运行器。真实的那一套（SSR 加载、模型调用、工具、到文档服务的项目数据连接）要在子进程里起 vite 和一整套带账号的文档服务，而且文档服务的「一条任务一个进程」模式读 root 记录的代码只在 Linux 上跑（`agent-run-scope-reader.mjs` 写死 `linux-required`，装配里没有留测试用的替换口）。这一块不连节点，所以没做。受控运行器走的是同一个任务管理器、同一道闸、同一份日志和同一条结算链，差的是「真实工具在这个进程里能不能跑」。
2. **Linux 上 root 那一侧的实现没有。** 调度要的那组口子，Linux 上应该由 root 进程用现有的 `createAgentScopeRuntime`（systemd 单元、cgroup、root 所有的记录文件）实现。还差两样：一是任务进程在 systemd 单元里启动以后，调度怎么给它下「领取、开跑」的指令并收它的「终态 + 意向」——现在这条通道是 Node 父子进程之间的通道，systemd 起的进程没有父进程通道，要换成别的（比如任务进程已有的那个只认 root 证书的本机 HTTPS 口）；二是 root 进程本身的入口、配置和部署模板。真实 Linux 上的整条链一次也没跑过（ChatGPT 跑过的三轮只是关闭那一段）。**所以生产入口现在不是「关着没开」，是「还开不了」。**
3. **`doc-agent-assembly.mjs` 的两处改动没有被带「一条任务一个进程」模式的测试覆盖到。** 原因同第 1 条（Linux 才能读 root 记录）。同样的逻辑在集成测试的夹具里照着写了一份并验过，装配文件本身只有不带这个模式的旧测试在跑（都过）。
4. **领取的回应不确定、而文档服务又确实没记下这次领取时，槽会一直停在「故障」。** 这种情况下调度不敢退槽（万一文档服务记下了，退了那条任务就永远结不清），只写失败观察、等文档服务签强制终态；文档服务没记录就不会签，槽就一直等。是往安全的方向卡住，要人看一眼后手动退。没有给主身份加「问文档服务这一代有没有授权」的接口，那要改文档服务的对外接口。
5. **root 的关闭动作失败后槽停下等人看。** 发布器失败时故意留着锁，调度不自动重试，把槽标成 `stuck`。进程恰好在「检查它还活着」和「root 动手」之间死掉也会落到这里。
6. **调度进程重启后的接手只有单测**，没有端到端验（要先有第 2 条）。
7. **多个槽同时跑多个对话只有调度的单测**（两个槽各占一个对话），集成测试只用了一个槽。
8. **这条分支另两个测试文件的端口仍写死**：`agent-run-scope-doc.test.mjs`（6712）、`agent-worker-settlement-client.test.mjs`（6713）。各自只有一个文件用，同一次全量里不撞；但几个工作区同时跑全量会撞，和 58xx 那几个是同一类。改它们要重排这两个文件的建连顺序，没动。
9. **主服务的生产装配没做**：「主身份 + 事件库 + 收事件接口 + 槽调度」现在只在测试夹具里拼在一起，`main.mjs` 里没有这种挂法。

## 要用户定的事

1. **任务自己做完了、但在结清之前被停掉，记成什么。**
   背景：一条任务从「自己做完」到「名额让出来」之间有一小段（要等任务进程被关掉、文档服务核对完）。如果恰好在这一小段里有人点了停止、把对话切成了私有、或者发任务的人被踢、改密退出，这条任务的修改其实已经全部落到项目里了。
   现状：记成「被中断」。这是 ChatGPT 定的，用户没审过；我照着接的，并有测试固定了这个行为。
   选项与后果：甲，保持「被中断」——规则简单（只要停止在结清前生效就算中断），但用户会看到一条明明改完了的任务显示被中断；乙，改成「做完」——更符合用户看到的事实，但要让文档服务区分「做完后才被停」和「做到一半被停」，要改文档服务的结清逻辑和对应测试。
   建议：先保持甲。这个窗口很短（本机测到的是一两百毫秒），生产入口也还没开；等界面开始显示任务结果时再定。
2. **点「停止」第一下多半回「关闭待确认」。**
   背景：任务放进独立进程以后，停止要等 root 真的把进程关掉才算办完，这要一小会儿（调度每隔一段问一次文档服务）。
   现状：停止接口在没办完时回「还在办」，界面显示「已禁止新访问，相关服务关闭待确认。点击重试会沿用原请求。」，要用户再点一次。权限是第一下就生效的，任务不会再改任何东西，只是界面上要点第二下才看到「已确认」。
   选项与后果：甲，保持——不用改；乙，让停止接口在服务器上多等几秒再回——多数情况下点一下就成，但这个请求会变慢几秒；丙，界面自己隔一会儿重试——要改界面（一级语义，要用户先定文字和行为）。
   建议：乙或丙，等生产入口能开时再定；现在不影响任何人。

## 当前明确阻断与最小 owner

1. **同一实例权威的 observed 认证**：`doc-agent-assembly` 目前不导出当前 registry/私有 subject 到 A；A 不能用另建的 instanceAuthority 或 asset body 自报的 `authenticationId`。G 独占该文件增加只供 `createRunAssets` 的窄认证 callback，A owner只确认其现有签名输入与cap释放；真实 asset mTLS、Agent→asset TLS exporter/服务 key/instance generation 要同请求一致。缺此 callback，A 构造 503。
2. **当前 asset registry 与恢复见证**：`combo/main` 尚无 pin 后 `resolveObserver` 和 asset 当前实例世代的可信来源；B 的 `verifyLifecycle` 也不能用新进程空 Map、`recoveryFence` 文件存在或 self-report `complete:true` 替代旧 OS/cgroup 空证明。G 的 combo/main/asset-runtime owner只接经现 serviceRegistry、asset lifecycle 与固定实例登记可核的身份；若需新增历史 witness API，先向 root 报精确 `asset-lifecycle` 租约及证据格式。未知就 `runAssetsReady:false`/503，控制 ACK pending。
3. **lease/控制真实关闭**：A 的 `verifyLeaseClosure/verifyControlReceipt/verifyRecoveryClosure` 仍是必需 callback。B 的 `prepareClosure` 在真实 TCP close 后 fsync 本地记录，但 G doc 不能仅核 receipt 里 `complete:true`；需通过当前 asset 证书/同 observer socket、精确 leaseId/assetInstanceId/持久 B receipt 与已关闭资源事件作可信见证，必要时 B owner补只读内部状态查询；历史 unknown 还需 root 的旧实例外部见证。`docAgentAssembly.deliver` 当前只记 doc transport/operation 的 pending，G 将 asset participant 的真实回执并入原 control 完成条件，不能直接给真 ACK。
4. **双 head 与撤销夹缝**：B `createAssetRunAccess` 每请求先同步 human access 与 run outbox；`status` 现仅 run head，`asset-runtime.status` 现仅 access head。G 的 assetRuntime/asset-ready status 组合两者，Agent 数据入口同步齐头后方可开；access 通知先 pause run lease，独立 doc 请求重验合法 retained 后续读，private/stop/off/服务撤销实际 close 后才 ACK。失联或 gap 不按 TTL 缓存开口。
5. **媒体历史与工具登记分离**：ProjectAssets.import 的 `{state:'stored'}` 只说明素材字节完整；doc `exec.mutate addMedia` 仍是另一成功点，必须用当前 run actor 与预期项目版本，经 doc 接受后才说项目含此素材。`openRead` 的 selector 必须从已接受项目 history 查，而非直接读 path/hash。这个界面与 runner/tool 路径不在本轮租约；缺正式接入 503。
6. **部署闭包与公开状态**：doc `HOSTED_DEPLOY_DIRS` 已含 `server/account`，asset literal 清单未含 A/B 新源码；Agent 的 `main` 还未收 ProjectAssets 可信配置。G stage 不能把主仓库向上 import 成功当独立服务可部署；无各服务自己证书/配置仍不 ready。当前 `runTicket` 在 `doc-agent-assembly.mjs` 明确返回 `run-data-proof-unavailable` 503，G 不借资产签名放开它；普通 `auth.ticket` 的 accountMode 禁令同样保留。private 对话里的 visual/snap/px ACL 另包，不借本 media 票据。

## G 中央接线机制（基于 `5ad558a2`，待根审后实施）

doc 在现有 `accountRuntime.ledger` 上创建唯一 A `createRunAssets`，复用 `docAgentAssembly.runProvider` 和同一个 `instanceAuthority`；`authenticateDirect/Observed/verifyObserver` 全部由 `createRunAssetAuthentication` 给出。A 的 `/internal/v2/run-assets/*` 只在独立内部 HTTPS 链上装配，Agent direct 和 asset observer 各按真实 mTLS 证书、当前服务身份、RAM 实例签名及实际 TLS exporter 核验。独立 asset 进程保留人类 public 路由，在内部 HTTPS 装 B `createAssetRunAccess`；人类 `createAssetRevocationConsumer` 仍为 access 事件唯一 ACK writer，B `handleAccessEvent` 只作为关闭参与者，run control outbox 由 B 自己顺序 ACK。任何旧 username/ticket 路由不得接到这些入口。

当前 asset 身份不能取环境常量、请求体或同证书旧 OS 的声称值。候选登记流程是：`openAssetLifecycle` 成功后，asset 用自己的 doc mTLS 证书提交 `lifecycle.state` 的 `serviceIdentity/instanceId/pid/startedAt/fingerprint256`，doc 再以自己的证书独立连接 pin 的 asset 内部 identity 只读 RPC，对照实际打开的 lifecycle 状态；doc 同 ledger 持久 current 实例和代际。每个 A observer 请求先按实际 socket 核 asset pin，再独立探测当前 asset endpoint，并把已核登记绑定该 socket 的 RAM 记录；A 事务里的同步 `currentAsset({socket})` 每次比对该记录和持久 current 登记，socket 关闭立即撤记录。若独立探测与当前 observer TLS socket 不能证实同一 OS，保留 503，不能凭证书相同放行。新 asset 实例只有旧实例 clean 或 root/cgroup 的旧 PID、服务身份与进程树/FD/TCP 空见证完成后才可切 current；G 不把本地空集合或新 PID 替代旧实例见证。

资产内部 doc-only read RPC 分三组：当前 identity；`GET /internal/v2/asset/run/metadata?projectId=...&hash=...&tier=small` 从 `projectStores.project(projectId).stores.media.stat(hash)` 读取实际派生文件的 size/ext/contentType；精确 leaseId/eventId 的 B `closureWitness/controlWitness`。RPC 仅 doc 证书和 pin 的当前 asset 实例可用，不调用 B `consumer.sync()`、人类 consumer.sync() 或 A run.check，避免 doc coordinator/ledger 和 asset 同步队列反向锁环。doc 在 A closure callback 中于账本事务外请求 B 已经实际关闭且 fsync 的 witness，比较 exact assetInstanceId/serviceIdentity、leaseId/binding、receipt digest、观察 socket identity 后再允许 A 落 closed/ACK。metadata 只返回物理属性，项目/ACL 和 mediaRev 仍由 doc `resolveRunMedia` 在 coordinator.read 前后重验。Agent↔asset 字节完全不经过 doc。

开入口顺序：asset human consumer 与 B run consumer 分别 start/sync；分别比对各自 cursor 与 doc 的 access/runAsset head；当前实例登记有效后才允许 B data handler。status 只能报告这次核验的非秘密 head/instance/ready，不能把 getter 或曾经成功的探针当未来永久授权。access 事件先 pause B run lease，再等真实关闭或当前 retained 的逐步重验；独立 ACK 各自按实际持久 receipt 写。任何 upstream、当前登记、双 head 或 closure witness 不齐都 503/pending。

目前跨 owner 的最小缺口：`serviceRegistry` 只登记 agent/render，没有 current asset OS；`asset-lifecycle.mjs` 虽有 root 的上次实例恢复检查，却未提供 doc 可独立核的 current 登记/旧实例进程树证明。需要 root/ops 指定可验证的运行身份及旧 cgroup 空证据接口，不能由 G 自签。B `createAssetRunConsumer.start` 对新 `assetInstanceId` 且旧 leases **包括已 closed** 一律 `asset-run-recovery-pending`；需 B owner只对已持久 closed receipt 给归档/续认窄规则，pending/unknown 不得改名或消除。B `controlWitness` 当前仅 RAM 最后一次 `durableControlReceipt`，重启后需要 B owner给精确 eventId 的持久只读查询，不能凭 A 账本 ACK 倒推 B 实际关闭。B 的异步关闭异常正在独立修，本叶不覆盖。以上缺缝未收到可靠接口之前，G 不给生产 `verifyRecoveryClosure` 成功，也不宣称 run assets ready。

私有读返回字段建议：`identity` 的 `result` 是 `{v,serviceId,serviceIdentity,instanceId,pid,startedAt,docClientFingerprint256,internalServerFingerprint256,state}`，前一个指纹来自 `openAssetLifecycle` 中 asset→doc 客户端证书，后一个来自实际 asset 内部 HTTPS 服务证书；两者不能混用。small `metadata` 的 `result` 为 `{projectId,hash,size,ext,contentType,assetInstanceId}`，只取本项目已完成物理文件。lease closure 的 `result` 为 B 的 `{assetInstanceId,serviceIdentity,receipt,binding:{projectId,runGrantId,instanceId,instanceGeneration}}`；control closure 的 `result` 为 `{assetInstanceId,serviceIdentity,receipt}`。均是 doc pin 只读接口，无正文、票据或人类 principal。拟持久 current asset 登记至少绑定 serviceIdentity/instanceId/两种证书指纹/PID/startedAt/代际/docEpoch，并由旧 OS 外部关闭见证门控换代；actual asset→doc observer 每请求仍需同 socket RAM 实例签名并与登记对照，不能以另一条相同证书连接的 identity 响应替它证明 OS。此 wire/schema 是三级实现建议，不是用户逐字段批准。

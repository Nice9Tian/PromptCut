## 0. 智能体使用规则

用哪种子 Agent 由用户按任务指定（`guide_files/multi_agent.md` 第 5 行）。下面是用户为 M5～M8 这一系列任务指定的分工。派出之后的协议（worktree、报告、提交、合并）照 `multi_agent.md` 执行，本节不重复。

### 0.1 角色

| 角色 | 实际调用 | 职责 | 不做什么 |
|---|---|---|---|
| **主会话（Master / Coordinator）** | 本会话 | 状态流转；定稿每阶段的契约节；派活与回收；逐个读 diff；在集成分支上重跑基线；执行回退梯次；向用户汇报、申请合并与部署；给 Worker 写跨机指令并收回执 | 不在主工作区改业务代码；不写生产代码和测试；契约与计划文档除外 |
| **工程主力 Opus 5.5** | Agent 工具，`subagent_type: opus-dev`（effort medium）；核心难点用 `opus-dev-high`（effort high）。思考等级**不低于 medium** | 写代码、重构、写测试、跑基线。每个任务一个 worktree，建在 `.worktrees/<分支名去掉 claude/ 前缀>`，一个分支 | 不推送、不合并、不部署远端、不装依赖 |
| **查资料与攻坚 GPT / codex** | `/subagent-gpt`（`gpt-manager`），模型**强制** `gpt-6-sol`，推理 `high`。<br>查资料用只读模式，允许联网检索；攻坚用 worktree 模式 | **查资料**：写契约前查外部规范与平台行为，交付「解决路径」（0.2 节「查资料先行」）。<br>**攻坚**：接手需要反复试错的问题，在交给它的 worktree 分支上自己改、自己跑，直到该用例通过且基线不变红（0.2 节第 2 级）。worktree 模式下 manager 只传话、替它提交，不干预 | 不碰没交给它的分支；不做架构决策；不写各阶段 `*-tests` 分支 |
| **交互、文案与发散 Gemini** | `/subagent-agy`（`agy-manager`），模型**强制** `gemini-3.1-pro-high`；只用内置读取工具，产出写文件交付到 scratchpad | **用户体验**：交互流程稿与界面文案（C6.5、C10 的用户侧流程，C6.5 设计稿里「用户感知到的撤销 / 重做行为」一节）。<br>**发散**：卡死时给出至少三条彼此不同的解法，每条写清前提和代价，不做取舍（0.2 节第 3 级） | 不改代码；**不做架构审查**。产出一律当假设：主会话先验证、核对与语义一致，再进计划或交 Opus 实现；改语义仍逐句交用户确认 |
| **Worker（笔记本端）** | 笔记本上的另一个 Claude 会话，经会话间通信层与主会话收发消息（第 6 节） | 只按主会话下发的跨机指令在笔记本上 `git pull`、跑节点、主机、浏览器节点或探针，原样回传输出 | 不改代码、不提交、不推送；指令外的操作一律不做 |

**分工**（用户 2026-09-26 重定，取代原来的「检索与排错攻坚 GPT」「架构外脑 Gemini」两行）：
- **Opus**：写代码、写测试、跑基线，是工程主力。各阶段的 `*-tests` 分支仍由单独的 Opus 做，不交 codex。

- **独立评估不变**：外部模型的建议和改动，都由主会话核实后决定采纳、修正或否决（11.1 节第 3 条）。

### 0.2 回退梯次

计数单位是**同一分支上的同一个测试用例**（测试名或探针断言编号）。「一次失败」= 修改后重跑该用例仍失败。换了用例不累计，用例通过后清零。

| 级 | 触发条件 | 谁处理 | 做法 | 出口 |
|---|---|---|---|---|
| 1 常规重试 | 用例第 1 次失败 | Opus 5.5 自己 | 自行定位、修改、重跑；每次修改都提交在分支上 | 通过 → 继续；连续第 2 次失败 → 第 2 级 |
| 2 codex 攻坚 | 同一用例**连续第 2 次失败**；**或**同一问题排障超过 1 小时没有根因。<br>**直接进第 2 级、不等两次失败的**：偶发失败、时序竞态、端口与网络环境相关、跨进程或跨机才复现的问题 | 主会话把该 worktree 分支交给 `/subagent-gpt` 的 worktree 模式（`gpt-6-sol` / `high`） | Opus 5.5 先提交现状，此后**不动这个分支**。<br>主会话把失败用例名、完整报错、相关 diff、契约对应节交给 codex。codex 在分支上自己改、自己跑、反复试，直到该用例通过且基线不变红；manager 只传话、替它提交，不干预。<br>codex 做完后，主会话读它的 diff，核对不违反语义和契约，再让 Opus 接着往下做 | 通过 → 清零，交回 Opus；codex 反复尝试后仍不过 → 第 3 级 |
| 3 发散求解 | codex 反复尝试后仍不过；**或**出现跨机物理通信、协议层面的阻断（公网握手不通、代理剥掉 Upgrade 头、NAT 或防火墙导致半开连接或素材服务不可达等），这类直接进第 3 级 | 主会话调 `/subagent-agy`（`gemini-3.1-pro-high`） | 交给它：问题陈述、第 1、2 级的全部记录、相关设计与契约节。<br>要它给出**至少三条彼此不同的解法**，每条写清前提和代价，不要它做取舍。<br>它的结论一律当假设：主会话先验证，再选一条交回 Opus 或 codex 执行；涉及语义、设计或对外接口的改动，先向用户做 dry run | 通过 → 清零继续；选定的解法执行后仍达不到验收 → 第 4 级 |
| 4 强制中止 | 第 3 级选定的解法执行后仍不达标 | 主会话 | 整个主流程挂起：分支保留；写清三级各自的尝试与结果；按全局约定调用 `task-announce` 播报；等人类介入 | — |

补充：

### 0.3 所有 Agent 共守的硬约束

- 写 main（提交、合并、推送、改写历史）须用户授权；合并用 `--no-ff`，合并提交写成「合并 <分支>:摘要」。
- **三件事由人工在物理机上做**（用户 2026-09-24 批复第 5 条），Agent 不做：
  - **推送 Git 分支**：Worker 靠 `git pull` 取代码。下发 W 指令前，主会话在对话里写明要推送的 `claude/*` 分支和提交哈希，由用户推送；推送完成后才下发指令；
  - **防火墙**：主 PC 的 Windows 防火墙入站规则、阿里云控制台的防火墙；
  - **集群令牌**：`PROMPTCUT_CLUSTER_TOKEN` 在每台机器上的配置。令牌的值不进仓库、不进对话、不进跨机消息。
- **部署到远端主机 `8.219.80.16` 是对外操作**，每次都要用户在对话里授权；重启远端文档服务会断开所有连接，也要授权。
- 新增依赖、安装系统软件先问用户。
- 不碰用户常驻的 5190～5192、桌面版运行时副本、用户数据目录；不结束不是自己启动的进程。
- 子 Agent 不建 `node_modules` junction、不跑 `npm ci`；删 worktree 前按 `verification.md` 检查 junction。

## 1. 现状（M4 与卡片级指纹锁之后）

**已在 main**（`9a95ed8`）：

- M1 队列本体、M2 节点纯逻辑、M3 进程内联调、M4 环境指纹进结果键、卡片级指纹锁、旧缓存清理脚本。
- 全量测试：2194 条，通过 2193，跳过 1（需要 5190 的 dev server），失败 0。
- 结果键：`resultKey = sha256(contentKey + "\n" + envFingerprint)`。本机预渲染 Chrome 的指纹是 `258acaaa7c5fe509`（Windows、SwiftShader、Chrome 152）。
- 卡片级指纹锁：
  - 锁键 `<kind>:<内容键>`，谁最先产出谁得锁；
  - 别的环境不能替锁定方产剩余帧：认领时拒 `card-locked`（契约 F.1 第 3a 步），发布时拒建（F.7）；
  - 节点会话收到 `card-locked` 就丢掉这个候选（N4）；
  - **跨机复用靠这把锁**：另一台机器指纹不同，只能投递锁定方已产齐的结果，或者接手重产。
- 队列的可见性已经按项目过滤了一层（契约 A.9）：增量只发给 `queue.watch` 了该项目的节点连接；`watch: 'all'` 的连接收全部。

**文档服务骨架**（`server/docservice/`）：

- `ws.mjs`：自写的 RFC 6455 服务端，只收文本帧，单条上限 1 MB。
- `service.mjs`：
  - `authenticate(req)` 在建连时定 `principal`，缺省所有人都是匿名；角色在 hello 之后才有；
  - `mountRenderQueue(q)` 挂队列、按 5 s 驱动 `tick`；
  - `/healthz` 报连接数、发布方数、节点数；
  - 心跳 30 s，半开连接最长约 60 s 才被判断开。
- 部署：`8.219.80.16:8787`，PM2，UFW 只放行 22、8787；脚本 `scripts/remote/docservice.mjs`；探针 `scripts/probes/ws-client-test.mjs`。
- **公网上现在是明文 `ws://`、匿名身份**。

**还不存在的**：

- 节点侧的真 WebSocket 客户端；
- 鉴权；

## 5. 高并发与阻塞防御

目标：多个节点、多个发布方同时围着同一个项目转时，文档服务的出站队列不积压，节点不在注定失败的认领上空转，存储不被单机 I/O 卡死。三项分别落在 C6、C5、M5b。第 5.4 节是它们共同的前提：文档服务的通用化，从 M5a 起做。验收都并进各阶段（第 7 节）。

### 5.1 信令隔离：按频道的 Pub/Sub（C6）

**现状**：
- 队列的增量已经按 `queue.watch` 的项目过滤；
- 但 `watch: 'all'` 的连接收全部；
- 文档服务本体（项目操作、`projectRev` 通知、内容库变更）还不存在，没有任何隔离；
- 出站没有背压：慢连接的待发数据会无限堆在进程内存里。

**要求**：

1. **频道是唯一的出站路由**。文档服务里所有非回包的出站消息，都经核心层的频道分发器发出（第 5.4 节的 `ctx.publish`），各模块的消息都一样，队列的 `send` 也接到它上面。频道名的前缀由模块自己定，核心不认识具体频道。本计划用到的频道：
   - `project:<projectId>`：项目操作、`projectRev`、队列任务增量、内容库变更；
   - `cluster:endpoints`：服务地址登记（D7）；
   - `conn:<connId>`：点对点回包。
2. **订阅显式、订阅时鉴权**。连接只能订阅自己有权看的频道。`queue.watch` 变成对 `project:*` 频道的订阅。纯浏览器节点在分发器这一层就过滤掉非本人的任务，队列里现有的 Q2 过滤保留，作为第二道。
3. **`watch: 'all'` 只给独立主机（`profile: 'host'`）**，而且只收**按项目聚合的摘要**：每个项目每个扫描周期至多一条，内容是 `open` 任务数、最高优先级、按指纹分的计数。设计第 7 节「文档服务负载」写的「节点多了以后改成按项目分组、只推摘要」在这里落地。主机按摘要挑项目，再单独订阅那个项目的频道。
4. **每条连接的出站队列有上限**（常量进 `constants.mjs`，以后按设计第 8 节的方式抽成环境变量）：
   - 待发字节上限，基线 1 MB；
   - 超过上限时，先合并可被取代的消息：同一任务的状态增量只留最新一条；
   - 合并后仍超限，就用 `1013 Try Again Later` 关闭这条连接。节点重连后走 `resume` 和 `queue.snapshot` 恢复，不丢状态。
5. **广播量可观测**：`describe()` 和 `/healthz` 加上每个频道的订阅数、每条连接的待发字节、合并次数、因背压被关的次数。

### 5.2 存储接口抽象（C5）

**要求**：素材服务的 HTTP 层只认一个数据层接口 `BlobStore`，不直接碰文件系统。

- **接口**（JSDoc 定义在 `server/asset-service/store/blob-store.mjs`，契约写进 `cloud-task.md` 第 5 步对应的契约节）：
  - 读：`has(hash)`、`stat(hash)`、`read(hash, { start, end })` 返回可读流；
  - 分片上传：`beginUpload(hash, size, chunkSize)`、`putChunk(uploadId, index, stream)`、`listChunks(hash)`、`complete(uploadId)`（校验 sha256）、`abort(uploadId)`；
  - 管理：`remove(hash)`（留给以后的 GC）、`usage()`。
- **一开始就有两个实现**，用来证明插槽真能换：
  - `fs-store.mjs`：沿用 `out/media/<hash>.<ext>` 的现有布局，与 `vite-plugin-media.ts` 已有的按哈希落盘兼容；
  - `memory-store.mjs`：测试用。
- **OSS 或分布式文件系统只留插槽**：工厂 `createBlobStore({ kind })` 里 `kind: 'oss'` 回「未实现」，不装任何 SDK。
- **守门**：
  - HTTP 路由模块里不许出现 `node:fs`、`fs/promises` 的引用，加一条守门测试；
  - 一套符合性测试 `server/test/blob-store-conformance.test.mjs` 对两个实现跑同样的用例；
  - HTTP 端到端测试把实现换成 `memory-store` 再跑一遍，必须全过。
- **访问控制**（配合 D7 的主 PC 部署）：非回环来源的写请求（分片上传、`complete`、`remove`）必须带集群令牌；读按语义允许局域网跨源访问，按哈希寻址。浏览器端（M7）怎么带令牌到时候再定。

### 5.3 防锁风暴：按节点指纹前置过滤（M5b）

**现状**：
- 已锁定的卡，发布时拒建（F.7），认领时拒绝（F.1 第 3a 步）；
- 但已经在队列里的任务，事后被别的指纹锁上或被接手作废时，仍然照常广播给所有 watch 该项目的节点；
- 指纹不匹配的节点照样收到 `task.opened`、发起认领、被拒、丢候选；
- 节点多、卡多时就成了「广播 → 抢单 → 拒绝」的空转风暴，接手时还会有成批的 opened / closed。

**要求**（语义依据是第 3 节 S2 的批复，改动在 M5a 开工前写入）：

1. **可见性前置过滤**。队列给节点连接发 `queue.snapshot` 和增量时，下面两种任务不发：
   - `requires.envFingerprint` 与该节点 `node.hello` 上报的 `envFingerprint` 不同；
   - 任务的锁键已被别的指纹锁住。
   节点根本看不到这些任务，也就不会去抢。
2. **锁变更只做定向增量**。锁从 X 转到 Y 时：
   - 对指纹是 X 的节点，把这张卡的 `open` 任务作为 `task.closed { reason: 'card-locked' }` 撤回；
   - 对指纹是 Y 的节点，把匹配的任务作为 `task.opened` 补发；
   - 其它节点什么都不收。
3. **认领时的拒绝保留**（F.1 第 3a 步），作为纵深防御，只兜住过滤与锁变更之间的竞态。
4. **拒绝限流**。同一节点在一个扫描周期里被 `card-locked` 拒绝超过阈值（基线 20 次），之后的认领回 `error: 'throttled'`，直到下一周期。节点会话收到 `throttled` 就退避一个周期。
5. **节点侧过滤照旧**（设计 4.3、`filter.mjs`），作为第二层，不因队列侧过滤而删。
6. **开关**：前置过滤放在常量开关后面，缺省开。关掉时行为与现在完全相同，用来跑对照组。
7. **过滤写在队列模块里，不写进文档服务核心**（第 5.4 节）。这是 S2 批复的「特定队列」特例；别的模块默认不做这种过滤。

### 5.4 文档服务的定位：通用的文本 / JSON 调度分发中心（M5a 起）

**批复**：文档服务不能在底层逻辑里写死只服务于预渲染队列。它是一个通用的轻量文本 / JSON 调度分发中心。路由层必须通用，以后可以挂载与渲染无关的文本处理任务；挂载接口与消息结构要保持足够的抽象。

**现状的问题**：`service.mjs` 直接引用队列的东西：
- `QUEUE_DEFAULTS`、`parseInbound`、`NODE_TYPES`、`PUBLISHER_TYPES`；
- 按队列的消息类型写死了路由表，连接记录上写死了 `publisherId`、`node` 两种角色；
- 挂载入口只有 `mountRenderQueue`，而且只能挂一个。

**分层**：

| 层 | 文件（M5a 起） | 管什么 | 不管什么 |
|---|---|---|---|
| 传输 | `server/docservice/ws.mjs`（不变） | RFC 6455、只收文本帧、单条上限 | 消息含义 |
| 核心 | 新建 `server/docservice/router.mjs` | 连接登记、解析 JSON 信封、按类型把消息路由给模块、模块挂载与冲突检查、频道与订阅（第 5.1 节 C6 起）、出站上限与背压 | 任何具体业务。里面不许出现 `render-queue`、`task`、`node`、`publisher` 这类业务词的引用或分支 |
| 组装 | `server/docservice/service.mjs`，新建 `server/docservice/auth.mjs` | HTTP 与升级、鉴权定 `principal`、心跳、`/healthz`、诊断、旧接口 `mountRenderQueue` 的外观（契约 G.1〔裁〕） | 业务逻辑本身 |
| 模块 | 新建 `server/docservice/modules/render-queue.mjs`（队列适配）、`server/docservice/modules/endpoints.mjs`（服务地址登记，D7） | 各自的消息、各自的连接内状态、各自的订阅授权规则 | 传输与鉴权 |

**挂载接口**（在契约 G 节定稿；下面是约束，不是最终签名）：

```js
service.mount({
  name,                      // 模块名，唯一
  types,                     // 本模块认领的消息类型：精确名或前缀（如 'task.'、'service.'），挂载时与已挂模块冲突就抛错
  connect(ctx, connId, principal),
  disconnect(ctx, connId),
  handle(ctx, connId, message),   // 同步；需要异步的模块自己排队，不阻塞核心
  tick?(ctx),                     // 核心按模块声明的间隔驱动
  authorizeSubscribe?(ctx, connId, channel),   // C6 起
  describe?(),
}) → unmount()

ctx = { send(connId, msg), publish(channel, msg), now(), log(event, fields), constants }
```

- `mountRenderQueue(q)` 保留，改成对 `mount` 的一层包装。现有的 `docservice.test.mjs` 与契约 A 节不改一个字就要全过。
- 连接记录上的业务角色（`publisherId`、`node`）挪进队列模块自己的连接内状态。核心只记 `connId`、`principal`、订阅。

**消息信封**：
- 通用信封只规定三个字段：`type`（字符串，建议 `<命名空间>.<动作>`）、`reqId`（可选，回包原样带回）、其余是模块自己的负载；
- 核心的错误回包（`bad-message`、`unsupported`、`unauthorized`、背压）与模块无关；
- 队列现有的消息名（契约 A.6：`node.hello`、`task.claim` 等）原样保留，按类型前缀归到队列模块，不强行改名，免得破坏已合入的契约和测试。

**约束不变**：只传小的文本 / JSON 消息，单条 1 MB，二进制帧拒收，素材字节和预渲染产物永远不走这条连接（`document-service.md`「职责」）。

**验收**：并进 M5a 与 C6 的验收：
- **R1**：测试里挂一个与渲染无关的示例文本模块（例如回显、按行统计），和队列同时在线，互不干扰；
- **R2**：守门测试，核心文件里 0 处引用 `server/render-queue/`；
- **R3**：两个模块声明同一个类型前缀时挂载失败；

## 6. Worker 节点（笔记本端）通信与交互时机

### 6.1 通道（D5）

- **会话间通信层**：主会话和 Worker 都是 Claude 桌面版的会话，两边都开 Remote Control，经会话间消息按会话名或会话 ID 收发。主会话的会话 ID 在对话里登记，属于本机信息，不写进仓库。
- **可靠性规则**：
  - 送达不等于对方已读，沉默不算同意。每条指令都要求 Worker 回执，回执里带指令编号和它核对过的提交哈希；
  - 超时没回执：主会话在对话里报告，不重发第二遍，由用户决定；
  - 消息必须自包含：跨会话消息里 `@文件` 不会附带内容，命令、期望输出、回传格式都要写全；
  - 两边的权限模式不同时，消息可能被对方挂起等人批准。首次握手时核对一次。
- **代码同步**：
  - 主会话在对话里写明要推送的 `claude/*` 分支和提交哈希，由用户在主 PC 上推送（0.3 节）；
  - 用户确认推送完成后，主会话才下发指令；
  - Worker 在笔记本上 `git fetch && git checkout <分支> && git pull`，回报 `git rev-parse HEAD`，与指令里的哈希一致才继续。
- **令牌**：Worker 所在机器的 `PROMPTCUT_CLUSTER_TOKEN` 由用户手工配，消息里只出现变量名。

## 12. D9：用户、共享项目与权限（2026-09-26 定稿）

### 12.1 用户定下的十条（第 10 条是 2026-09-26 第三轮补的）

1. **隔离单位**是「共享项目」。M6 里的 `tenantId` 就是共享项目 id。
2. **两种进入方式**，创建项目时二选一：
   - **自由进入**：知道项目名和项目密码的人都能进，进入时自报用户名；
   - **限定进入**：创建者维护一份允许进入的名单，每条是用户名加密码，只有名单里的人能进。
3. **创建者**：创建者账户必带密码，特权绑「创建者用户名 + 创建者密码」。特权只有三项：
   - 改项目密码或名单；
   - 删项目；
   - 踢人。

   其余操作人人平等。
4. **设备名**：软件按硬件信息生成设备名。自由进入下用户名可以重名，重名者显示时自动带「(设备名)」。
5. **Agent**：
   - 沿用所属用户的凭证，显示为「用户名 · Agent · 第几个对话」，界面用标签区分真人与 Agent；
   - 写入身份沿用语义里的「哪个用户的哪个页面，或哪个 Agent 的哪个对话」。
6. **渲染节点**：
   - 加入项目的桌面版自动成为该项目的渲染节点，能认领本项目任何成员发布的任务；
   - 纯浏览器节点只替本人干活，语义不变。
7. **素材服务**：
   - 读和写都要凭项目凭证换来的票据，因为主机会暴露到公网（D10 修订后，暴露在公网的是阿里云托管端）；
   - 回环地址上的匿名访问保留。
8. **集群令牌**（同日两次修订，取代原文「降为底层门槛、与凭证叠加」）：
   - 集群令牌从数据面彻底退出，任何角色的连接都不带；
   - 只保留给阿里云的管理接口：地址登记、管理 HTTP、迁移导出；
   - 项目凭证是数据面唯一的门槛。
10. **角色绑在连接上，不绑在身份上**（用户 2026-09-26 定）：
    - 身份 = 用户名 + 设备名，凭项目凭证进入。
    - 每条连接另带角色：`page`、`agent`、`render`。`render` 连接可以标归属：归真人，或归某个 Agent 对话（对应语义里 Agent 的专用渲染实例）。
    - 一台设备可以同时开多条不同角色的连接：桌面版是「页面 + 渲染」两条，Agent 是「`agent` + 它的 `render`」。
    - 独立渲染主机（`profile: 'host'`）就是只开 `render` 连接的设备，凭项目凭证进入；限定进入时，由创建者在名单里给它加一条。
    - 成员列表按设备聚合一行，后面挂标签：[编辑中] [渲染中] [Agent ×n]。
    - 写入身份沿用语义：页面写入记「用户 + 设备 + 页面」，Agent 写入记「用户 + 设备 + 第几个对话」。
    - 纯浏览器节点「只替本人干活」，按用户名加设备判。
    - 局域网主机的管理接口只绑回环地址，不要求任何令牌。
9. **暂不做**第三方登录和密码找回。凭证的编码、票据有效期、握手细节由主会话定（见 12.2）。

### 12.2 主会话定的细节〔裁〕

| 项 | 定为 | 理由 |
|---|---|---|
| 限定进入要不要保留项目密码 | **不保留**。限定进入只认名单里的用户名加密码 | 名单每条已有自己的密码。再加一道共享密码，只多一样要传、要改的东西，却挡不住任何名单外的人（名单外的人本来就进不来）。撤销某个人只要删他那一条 |
| 创建者怎么进入 | 两种方式下，创建者都可以凭创建者用户名加创建者密码直接进入。限定进入下，创建者自动是名单的第一条，不能删 | 特权绑创建者凭证，创建者不该还要另记一个项目密码 |
| 口令怎么核对 | **挑战应答，密码不上线**。<br>项目所在的文档服务（阿里云托管端，或局域网主机）存 `scrypt(密码, 盐)` 的结果，按项目密码、名单每条、创建者各存一份。<br>连接建立后，文档服务下发盐和一次性随机数；客户端算 `HMAC-SHA256(scrypt(密码, 盐), 随机数)` 交回，文档服务比对。<br>都用 `node:crypto`，不引依赖 | S4 定了不加密，明文密码会原样过公网。挑战应答让截获者拿不到密码，也没法重放。<br>代价：磁盘上存的 scrypt 结果对本协议等同于密码。托管时它在阿里云的数据目录里（`PROMPTCUT_DATA_DIR/docservice/`），局域网模式时在创建者本机的用户数据目录里 |
| 特权操作怎么证明 | 每次特权操作都带一份新的创建者证明（重新挑战应答），不靠会话里记着的角色 | 绑「创建者用户名 + 创建者密码」的字面要求；创建者离开座位时，别人不能借他的会话删项目 |
| `userId` 怎么构成 | 两种进入方式、包括创建者，一律是 `用户名@设备 id`（第 10 条：身份 = 用户名 + 设备名） | 纯浏览器「只替本人干活」按用户名加设备判；自由进入下重名合法，同名不同设备算两个人 |
| `principal` 字段 | 身份部分，一台设备上的所有连接都相同：`{ userId, tenantId: 共享项目 id, username, deviceId, deviceName, creator: boolean }`。<br>连接部分，每条连接各带一份：`{ role: 'page' \| 'agent' \| 'render', conversation?: 第几个对话（agent 必填）, owner?: { kind: 'user' } \| { kind: 'agent', conversation }（render 可填） }` | 第 10 条。`creator` 只用于界面标记，特权仍按每次的证明判断。<br>写入身份用 `userId`，加上 `page`，或者加上 `agent` 与对话号 |
| 设备名 | 桌面版：取操作系统的主机名，加硬件标识的哈希前 4 位，写入用户数据目录后不再变。<br>浏览器拿不到硬件信息：取「浏览器名 + 系统名」加一个随机 4 位，存在页面本地 | 可读、稳定。浏览器那一种是 D9 第 4 条在浏览器上的近似，需要用户认可（见汇报） |
| 会话 | 凭证只在建立连接时核对一次，连接活着会话就有效；断线重连时重新挑战应答（客户端缓存 scrypt 结果，不缓存密码） | 与 M5a 的重连、`resume` 一致，不另造会话令牌 |
| 素材票据 | 形如 `v1.<base64url(JSON{ p: 项目 id, u: userId, r: 'r' \| 'rw', g: 代数, exp })>.<HMAC-SHA256>`。<br>密钥是创建项目时生成的 32 字节随机数。两种模式下，文档服务和素材服务都在同一台机器上（托管端，或局域网主机），共用这把密钥。<br>有效期 15 分钟，客户端在剩 1/3 时经文档服务连接续签。<br>放在 `Authorization: Bearer` 里；`<video>`、`<img>` 带不了请求头，改用查询串 `?t=`，只允许只读票据，素材服务不记录查询串 | 无状态校验，素材服务不用回头问文档服务。<br>查询串方式是浏览器媒体元素唯一可行的办法，限定只读、短期 |
| 票据作废 | 票据里带的代数：<br>改项目密码或名单时，该项目的代数加一，已发的票据全部作废；<br>踢人时，被踢者的代数加一 | 不用维护吊销表 |
| 踢人 | 断开被踢者的全部连接，作废其票据，把「用户名 + 设备 id」记进本项目的禁入表，创建者可以撤销。自由进入下，界面同时提示创建者：想彻底挡住，要改项目密码 | 自由进入下，设备名可以伪造，禁入表只挡诚实客户端，改密码才是硬手段 |
| 口令错误限速 | 按来源地址：1 分钟内错 5 次，冷却 60 s | 托管端暴露在公网，挡暴力猜测 |
| 集群令牌 | 按第 8 条的第二次修订：<br>数据面的任何连接（`page`、`agent`、`render`，包括独立主机）只带子协议 `promptcut.v1`，然后交项目凭证；带了令牌也不给任何额外权限。<br>令牌只守阿里云的管理接口，没令牌回 401。<br>M5a 的「失败即关」改为：绑非回环地址而未加载项目凭证存储时拒绝启动；没配令牌照常启动，管理接口全部回 401。<br>局域网主机的管理接口只绑回环地址，不要令牌 | 用户 2026-09-26 定 |

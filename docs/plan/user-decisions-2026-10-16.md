## 1. 起因

原话：「我发现之前对于渲染云端工作的定义好像有问题。因为云端渲染只有一个，但要同时服务多个项目。我之前设想的流程是先加载一个项目，再加载项目里的内容，然后再加载特定时间的某一帧。但我现在发现这样其实有很多资源浪费。实际上渲染队列只需要渲染那一帧所有涉及到的卡片，根本不需要去加载整个项目、测量项目里所有的卡片，它只要知道渲染请求里的那些帧包含哪些卡片就行，完全没必要让某一个项目去独占。所以渲染服务应该分为两种模式：1. 单项目模式 2. 多项目模式：采用队列式，先保存每个请求对应哪个项目的哪些帧，然后递归展开，里面会包含具体的卡片信息。每次只加载这些具体的卡片和素材，这样就能保证每个项目都可以进入队列」

主会话核实的现状（读代码，没有运行）：

- 带用户卡的项目由隔离工作进程渲，整个渲染服务同一时刻只装一个这样的项目，装着的项目闲满五分钟才让位，换项目时数据目录整个清空（`server/hosted-render/isolation.mjs`、`main.mjs`）。探针实测另一个项目的第一次看画面要 5 分 36 秒、5 分 53 秒（`docs/reports/AGENT-v18-queue.md`、`hosted-render-contract.md` 第 8a 节）。
- 每次看画面，Agent 把整份项目随请求发过去；渲染这边新开一页、灌进整份项目、加载这个项目的全部卡片代码、给所有卡算一遍计划。托管渲染服务不做轻重实测。
- 「加载某一帧」这一步已经只挂目标那几帧上在场的卡（`src/render/frameWindow.mjs`），素材也只给那一刻在场的元素加载。
- 预渲染那一路：每个任务按「项目@版本」取整份项目、给全项目的卡算键；独立渲染主机挑任务时没有跨项目轮流。

## 2. 0.7.19 起：渲染服务的两种模式

- 单项目模式、多项目模式照第 1 节原话。多项目模式不装整个项目，也不让哪个项目占着；每个请求只记哪个项目、哪一版、哪几帧，轮到时展开成用到的卡片、它们依赖的卡和素材，只加载这些。
- 各用在哪（认可）：桌面版的预渲染进程用单项目模式；托管方的渲染服务和独立渲染主机用多项目模式。
- 多项目模式的队列（认可）：看画面先于产流；同一类里各项目轮流；同一项目内先来先做。
- 版本（认可）：0.7.18 用第 3 节的暂行办法；原话「19版我们出多项目渲染节点」，取代原计划的「预算实测满足才双项目并行」；0.7.20 的「磁盘缓存与交替加载」取消。

## 3. 0.7.18 暂行：云端 Agent 按轮占用

原话：「我认为，云端渲染主要是给云端Agent用的，现在在线浏览器也可以预览具体的帧，和复用流。云端渲染一方面给纯低性能设备的浏览器端进行辅助。另一方面，也是主要方面是给云端Agent用的。所以我认为这个闲置五分钟，应该调整为另一个策略：一个项目的，无设备辅助渲染节点的项目，的云端Agent会话会独占渲染节点，直到会话结束（Agent结束任务，比如一次修改任务结束，我不知道现在能不能判断这一项内容）。其它同样情况（其它项目的，无设备辅助渲染节点）的Agent排队。上述内容作为18的暂时兜底。19版我们出多项目渲染节点。」

能不能判断「这一轮结束」：能。任务进程知道一轮的开始、说完话、等后台作业收完、被叫停（`server/agent/service/account-runner.mjs`），看画面请求已带着这一轮的编号；要补的是「还在」的心跳和「结束了」的通知。

### 3.1 谁来出图

- 原话：「这里修改一下，我记得有优先级，桌面端>桌面版浏览器>云端渲染节点>浏览器低内存（手机版）。」又：「按照优先级（桌面端，本地浏览器优先）」。
- 取代同一天早些时候的原话「这个调度只在有多个渲染任务同时在云端渲染服务中排队的时候。如果没有排队，也可以走云端渲染，并不是优先走本地。」
- 读法：云端 Agent 看画面按这个先后找出图的地方：成员的桌面版 > 身份为电脑的在线浏览器 > 托管方的渲染服务 > 身份为手机的在线浏览器。成员设备要满足的条件由块十（渲染服务接进账号项目、本地取帧）定；定下来之前只用托管方的渲染服务。这一条是临时的，见第 4 节第 1 条。

### 3.2 适用的项目

读法：渲染服务按项目分给两组进程，不按卡分。项目里有用户卡，整个项目（内置卡、用户卡、素材）交给隔离工作进程渲，`see_frames` 拿到完整画面；只有内置卡的项目交给常驻工作进程渲，同样是完整画面，它本来就同时服务多个项目，不用排。生产项目都带用户卡，所以实际上几乎所有项目都走本节。（用户问过这里的「项目」是什么：是渲染节点服务的用户项目，不是代码工程。）

### 3.3 占用与排队

- 从何时占（认可）：这一轮第一次向云端要画面时。原话「但是应该几乎每次任务都会看（改完也要检查）。」
- 占到何时（认可）：这一轮收尾才放开；被叫停立刻放开。等后台作业的那段时间也占，原话：「等后台作业的时候也占吧，避免比如识别一个15秒的视频中的语音，结果回来以后seeframes被占，单个Agent任务被阻断进入排队，等到恢复时，整个上下文缓存因为阻断失效，额外增加额度。」
- 排队（认可）：别的项目的 Agent 按先后排；同一项目同时跑的几轮共用，最后一轮收尾才放开；有别的项目在排队时，这个项目新开的一轮排到它们后面。
- 「有排队」的意思（认可）：有别的项目的看画面请求在云端等着；产流任务排着不算，产流本来就让着 Agent。
- 防卡死（认可）：这一轮跑着时每 30 秒报一次「还在」，连着 2 分钟没消息就当它结束。

### 3.4 计时与渲染超时

- 原话：「如果是因为排队不算作等待，只有真正开始渲染才计算时间。这是防止有一些卡片死循环，或者计算负担巨大。而且这里我的本意不是回复"没看成"。而是"渲染超时"并返回某些调试信息（具体什么信息我还不知道，你可以帮我看看）。」
- 认可：排队不计时、不设上限，只给渲染本身计时；到点回「渲染超时」和调试信息；Agent 一侧原来 35 分钟的兜底改成从渲染真正开始时算；只留一道防故障兜底：队列 10 分钟一点没动（没有项目占着、也没在渲，请求却没被接）当作调度出了故障，回「排队异常」并记日志。
- 不重试（原话「认可。改成一次，不重试。」「认可，修改。」）：取代 2026-10-09 的「每次一分钟、重试三次」。
- 时限：原话「读到这里我意识到30分钟渲染太长了，改成3分钟。」读法（待用户确认）：渲染一次、最长 3 分钟，从真正开始渲算；Agent 一侧的兜底比 3 分钟长一点，保证先收到渲染服务的回话。
- 渲染超时带回的调试信息（原话「暂时认可，记待办，将来需要仔细看。」）：卡死在哪张卡的源码哪一行（到时限先短问页面一句，不回就判主线程卡死，抓一次调用栈）；这几帧上挂着哪些卡，哪些要从挂载帧回放、回放了多少帧、推到第几帧；停在哪一步；这次渲染期间页面报的错和没接住的异常；在等什么（挂着的网络请求、没到位的素材）；是不是被内存上限掐掉。

### 3.5 产流与关掉装着的项目

- 产流（认可）：没有 Agent 在用时才为「生成轨道流」打开的项目产流；有 Agent 来排队，做完手里这一个产流任务就让出。
- 关掉装着的项目（认可「产满才关、不看是否活动」之后改定）：原话「两条门控1.轨道流，产满。 2. 5分钟没有修改。同时满足的时候关。」读法：只在没人排队时适用；没开「生成轨道流」的项目第一条自然满足，五分钟没有修改就关。
- 几个项目都要产流：原话「看是否多个项目满足：多个（人类）用户在线。如果不满足就独占直到完成。如果满足就5分钟轮换。（这里是临时的，以为后面发版会可以排队多个项目，不会再被项目独占）」读法：有真人成员在线的项目先产；同时有两个以上这样的项目要产流时每 5 分钟轮换，否则装着的那个一直产到满。

# 渲染标准：卡片怎么分、谁管什么

2026-10-09 用户定。起因：卡片的分类和名词太多（轻重、推帧、可定位、直接求值、活渲、各种形态……），文档和代码用的不是一套词。这份文档只记定下来的标准和还要做的事；它不在 0.7.18～0.7.20 三个版本的范围里，标准现在生效，代码等三个版本告一段落再按它改。

## 定下来的

### 一、2D 动效卡只分两种写法

| 写法 | 是什么 | 代码里对应 |
|---|---|---|
| **remotion 式** | 画面只由时间 t 和参数决定，不依赖前一帧或后一帧的状态；跳到任意一帧都是直接算 | `frameMode: "direct"` |
| **motion 式** | 有状态，要从起点一帧帧推进才能得到目标帧 | `frameMode: "stateful"` |

- **两种都是正式的写法，不分主次。** motion 式自由度高，有它存在的必要；不要求把 motion 式的卡改写成 remotion 式，现有的内置卡也不改写（2026-10-09 用户定，原话：「我不同意改写，motion 式自由度高，他有存在的必要」）。
- 「remotion 式」只是一种写法，**不使用 Remotion 这个库**（用户原话：「不是真的 remotion，只是依赖时间 t 而不依赖前后状态」）。
- 原先文档里的三分法（随机访问、可定位的推帧、只能逐帧推）不再作为对外的分类。中间那类「可定位」降为软件内部的优化：一张 motion 式的卡如果测出来能把进度一步拨到目标帧，软件就那样做，但它仍然算 motion 式。
- 现有东西的归类：Lottie 动画按帧号直接跳，算 remotion 式；粒子、纯 CSS 动画、Motion 的弹簧与进出场，算 motion 式。

### 二、3D 动效卡（搁置）

**2026-10-09 用户定：先搁置。** 用户在考虑把 3D 都统一在一个 3D 对象里，想好之前不动。下面是搁置前说过的，留着备查：

- R3F 是套在 Three.js 上的一层 React 写法，两者是同一套渲染。
- 3D 卡同样要守「同一时刻同一帧」：关掉它们自带的时钟，由舞台喂时间。
- 现状：卡片不直接用 Three.js，它只在底层给画布类卡片和素材效果卡提供统一的显卡通道。3D 动效卡是要新做的一类，另立计划。

### 三、舞台：CSS 管摆放，软件管时间

- 摆放和叠加用 CSS：谁在哪、多大、转多少度、谁盖着谁、怎么混合。
- 时间由舞台自己的帧时钟管：哪一帧轮到谁、每张卡走到第几帧。不交给 CSS，因为 CSS 动画跟着真实时间走，机器一卡就对不上帧。
- 这一条现状已经符合。

### 四、素材效果卡用 JS

- **素材效果卡**（原称「图卡」，2026-10-09 用户定名）：作用在素材上的效果。画面的滤镜、调色、转场、强调；声音的混音、音效、响度。
- 一律用 JS 写，画面部分配显卡着色器。它不算动效卡。
- 画面这一半现状已经是这样。声音这一半还有一部分在服务端，已有计划 `audio_structure_plan.md`（音频整体改成浏览器端 JS），没动工。
- **不在这一条里的**：理解素材（语音识别、镜头切分、追踪、主体检测）继续用 Python 加模型，用户同意不搬。解码、转码、生成小尺寸见下面「还没定的」。

## 还要做的

3. **单独写一个 remotion 式的框架**（2026-10-09 用户定）。remotion 式的卡只用这个框架写，框架里没有的东西就是不合法的。它包含两部分：
   - **一套工具**，让写卡的人不用 Motion 也顺手：按时间插值、带缓动的过渡、用公式直接算第 N 帧位置的弹簧、错开进场、带种子的随机。
   - **不合法的操作当场拒绝**：remotion 式的卡里出现下文「remotion 式的规矩」列的那些操作（Motion 的动画与弹簧、进出场组件、CSS 动画与过渡、真实时间、定时器、不带种子的随机数等），建卡时直接拒绝，告诉写卡的人哪一行不行。
   - 做法上接在现有的建卡检查上：`create_card` 现在已经会拒绝用了系统时钟、定时器的源码，源码引用了哪些模块也已经能查出来（`src/kernel/cardSourceParse.mjs`）。在这上面加：声明为 remotion 式的卡只许引用这个框架，不许引用 `motion/react`。
   - 这种检查只看源码、不用渲染，代价很低。
   - **防偷藏状态：不拦读，拦写**（2026-10-09 用户同意）。要累加状态就得往某个地方写，把卡片能写的地方都变成只读，一写就当场报错。三道：卡片文件顶层只许写常量（看源码就能查）；载入卡片时把顶层的对象整体锁成只读（只做一次，不是每帧）；框架不提供能跨帧存东西的工具。单独隔离跑一帧发现不了这种问题：全新的环境里变量找得到、只是从初始值开始，不会报错。
4. 〔作废〕原先想做「自动判定」：把一张卡从头推到第 N 帧、再直接跳到第 N 帧，比两次画面。用户 2026-10-09 否决，理由是代价太高。卡属于哪种写法以声明为准，由第 3 条的框架保证声明成 remotion 式的卡确实合法。
5. **把分类登记到一张表里**：现在的审阅表（`src/cards/capabilities.json`）只登记了「依不依赖下层」，写法和画在什么上散在别处。一张卡一行，登记全。
6. **现有内置卡**：42 张里 39 个文件用 Motion、28 个声明成有状态。照现状归为 motion 式，**不改写**（2026-10-09 用户定）。
7. **代码里的旧名词**：「图卡」在代码里有约 685 处、178 个文件，多数是注释，少数是用户在界面上看得到的文字（`src/editor/sync/cardRunStates.ts`、`labels.ts` 等）。等三个版本的在途分支合完再统一改，免得合并时到处冲突。
8. **3D 动效卡**：搁置，见上。
9. **桌面版的导出：哪个快用哪个**（2026-10-09 用户定）。桌面版现在用 ffmpeg，在线浏览器用浏览器自带的编码（WebCodecs）。在同一台机器、同一个项目上把两条路都量一遍，哪条快桌面版就用哪条。注意：换编码之后导出的画面会和现在不完全一样，导出的像素基线要跟着重新定。

## 还没定的

- 预渲染的产物要不要简化，见下一节。

## ffmpeg：能减少，不能摆脱（2026-10-09 用户接受）

用户问过能不能靠 WebGPU 摆脱 ffmpeg。结论：WebGPU 管的是画和算，不管编码解码。浏览器里管编码解码的是另一套（WebCodecs），在线浏览器的导出已经在用它，全程不经过 ffmpeg。但导入各种格式的素材、服务器上的转码和生成小尺寸，仍离不开 ffmpeg。用户原话：「我理解，我接受这个妥协。」

## remotion 式的规矩（给写卡的人和 Agent）

一句话：这一帧的画面，只许用时间 t、参数、输入素材算出来。

不许做的：

- 读上一帧留下的东西：跨帧累加的变量、随时间一点点更新的状态。
- 读真实时间：系统时钟、定时器、浏览器的逐帧回调。
- 用自带时钟的动画：Motion 的动画与弹簧、进出场组件、CSS 动画与过渡。
- 不带种子的随机数。
- 依赖「谁先加载好」：字体、图片要等齐了再画，不能先画一版再变。

「不读前后状态」是必要的，但不够：后面四条同样会让同一时刻渲出不同的画面。

## 预渲染的产物（2026-10-09 用户定了一部分）

现状：预渲染的产物有两种。**快照**：每张重卡每一帧存一份 HTML（卡片那一块的 DOM 树，样式算好内联进去，画布先转成图片嵌入），暂停、拖动时贴，播放时兜底，也是在线浏览器播放重卡的唯一来源。**轨道流**：每张重卡一条带透明的视频，播放时贴，现在只有桌面版和渲染主机能生成。

### 定下来的

| 卡 | 预渲染存什么 |
|---|---|
| remotion 式 | **不存每帧的 HTML。只登记整张卡的位置矩形**，画面当场直接算（用户原话：「只登记整个卡片的位置矩形，不需要每帧 HTML」） |
| 画面本身贵的卡、画布与 WebGL 的卡 | 轨道流（用户同意）。存成图片这条路用户存疑，没定 |
| motion 式 | 需要 DOM 树，快照保留；不改写成 remotion 式 |

- remotion 式的卡如果当场算不过来（慢在算，或者慢在画），会话的理解是它按上表第二行办，走轨道流；这一句是推出来的，待用户确认。
- 会话早先提过「结构一份，加一张每帧样式值的表」，用户没有采用，作废。

### 用户指出的两个毛病，还没解决

1. **DOM 树的效率。** motion 式的卡仍然要靠快照，每一拍把整块 HTML 换掉，浏览器要重新解析、排版、画。文档里记的成本是每层每拍约 2 毫秒（Lottie 6.5、画布卡 4），在线浏览器同屏十来个重层就把一拍的时间用完。
2. **浏览器这一头做不了。** 轨道流现在只有桌面版和渲染主机能生成，在线浏览器播放重卡只能靠快照，正好撞上第 1 条。

会话的提议（用户还没定，要先做实验）：

- 针对第 2 条：让在线浏览器也能生成和播放轨道流。缩小画面靠显卡重新采样，压成视频靠浏览器自带的编码（在线浏览器的导出已经在用），两样都不需要 ffmpeg。这样 motion 式的重卡在在线浏览器里播放时也贴轨道流，不用每拍换 HTML。
- 针对第 1 条：快照只留给暂停和拖动用，播放时不靠它。还可以把快照存得省一些：同一张卡各帧的 DOM 结构通常不变，只是数值在变，可以结构存一份、每帧只存变了的地方，贴的时候只改那几处，不整块替换。

### 动手之前要先做的实验

- 在线浏览器用自带编码生成轨道流，速度和画质够不够；没有显卡的服务器上行不行。
- 同一张 motion 式的卡，整块换 HTML 和只改变了的地方，每拍各花多少时间。
- 现有的重卡里，慢在「算」的和慢在「画」的各占多少。

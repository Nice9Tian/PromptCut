# C10a 在线浏览器模式与加入项目交互文案

## 第 1 节 开始页「加入别人的项目」

### 1. 界面与表单结构
*   **入口与导航**：在开始页上提供【加入别人的项目】的入口；加入界面提供【返回】或【取消】按钮以退回主菜单。
*   **表单字段区与操作区**：根据不同路径显示对应字段，底部为【加入】按钮。桌面版与在线浏览器模式一致。
*   **(a) 手动填，自由进入**
    *   **字段**：【项目名】、【项目密码】、【自己的用户名】。
*   **(b) 手动填，限定进入**
    *   **字段**：【项目名】、【用户名】（名单里的用户名）、【密码】（名单里的密码）。
*   **(c) 凭邀请链接进入**
    *   **流程**：打开带邀请码（在 `#` 片段中）的链接后，页面跳过部分字段。若邀请码无效，则界面回退到手动填写表单，并给出错误提示（见表单级状态）。

    *   **限定进入的链接**：只显示【用户名】与【密码】字段，隐藏项目名。

## 第 4 节 需要主会话或用户定的点

本节列出为了完成前述交互稿所发现的语义空白或需进一步确认的决策点，供主会话与用户裁定：

1. **默认勾选「放本机」与 C10a 仅做「放云端」的矛盾**
   *   **问题**：语义规定（workflow/project.md 等）勾上「多用户协作」时默认放本机。但 C10a 计划仅做放云端这一支。在 UI 呈现上应如何处理？
   *   **可选做法**：(a) 界面上放本机的选项置灰，并附提示“当前版本仅支持云端”；(b) 临时修改二级语义，使本轮默认放云端，隐藏放本机选项。
2. **创建者从第二台设备进入的表单容纳方式**
   *   **问题**：计划 12.2 节提到创建者可凭“创建者用户名 + 创建者密码”直接进入。开始页现有的加入表单（自由/限定）应如何为这条路径提供入口？
   *   **可选做法**：(a) 在加入表单旁提供单独的“我是创建者”入口；(b) 统一表单内检测如果用户名是创建者，则将密码框逻辑直接切为核对创建者密码。
3. **凭邀请链接进入时的表单动态渲染逻辑**
   *   **问题**：邀请链接中不带项目名与密码，仅有邀请码。页面在渲染表单前，是否先使用邀请码向服务器发起验证？验证失败是在填表前报，还是在点击提交后报？验证成功后是否对加入者展示该项目名？
   *   **可选做法**：(a) 页面加载时自动向服务器校验邀请码，成功后根据返回的项目模式直接渲染极简表单，并显示项目名；失败则拦截并展示完整表单和错误；(b) 等待用户填完用户名并点击“加入”时一并验证，只靠前端链接判断隐藏逻辑。
4. **桌面版凭邀请链接加入的交互入口**
   *   **问题**：用户点击邀请链接通常唤起的是浏览器。桌面版如果要实现“与在线浏览器模式一致”的凭邀请链接进入体验，是否需要提供一个粘贴邀请链接/邀请码的文本框？桌面版用户是否需要手动填写服务器地址以连接云端？
   *   **可选做法**：(a) 开始页提供“粘贴邀请链接”的解析框，解析后走前述逻辑，服务器地址从链接提取；(b) 仅支持在线浏览器端走链接跳转，桌面端用户只能用手填表单的方式。
5. **创建者特权操作的身份证明方式与邀请码可见性**
   *   **问题**：改名单或限时限量每次都要出示创建者凭证。这是指每次操作都弹窗要求手动输入创建者密码，还是由后台自动提取本机的会话缓存完成挑战应答？另外，非创建者的普通成员，是否能在项目设置里看到并复制邀请链接？
   *   **可选做法（凭证）**：(a) 强安全：每次修改强制弹窗要求重输密码；(b) 体验优先：利用本地缓存的凭证自动完成。
   *   **可选做法（可见性）**：(a) 所有人可见邀请链接，但只有创建者能作废重置；(b) 只有创建者能看见邀请链接面板。
6. **「密码自动生成并存在本机」的指代与分享位置**
   *   **问题**：workflow/project.md 提到勾上时的默认是“密码自动生成并存在本机”。这是指项目密码还是创建者密码？如果是自动生成的项目密码，创建者应该在界面的哪个位置查看项目名和项目密码，以便分享给走手动表单路线的成员？
   *   **可选做法**：(a) 专设一个“项目信息分享”面板以明文显示；(b) 在多用户协作的设置面板中，增加项目名和项目密码的展示与复制项。
7. **离线状态下勾选并保存「放云端」的系统行为**
   *   **问题**：语义写明离线时放本机的项目可以照常建立，未指明放云端支线在离线时该如何处理。
   *   **可选做法**：(a) 拦截操作，提示必须连接网络才能放云端；(b) 仅在本地排队，等恢复连网后再真正在云端建项，期间项目对外不可见。
8. **取消多用户协作或踢人时，项目内成员的界面反馈**
   *   **问题**：云端协作被取消，或某成员被踢出时，正在编辑的其他成员看到的反馈是什么？
   *   **可选做法**：(a) 强制中断所有操作，弹出遮罩说明“项目已关闭协作”或“你已被移出”并返回主页；(b) 转为只读/离线缓存模式。
9. **低内存档导出中重卡无预渲染原尺寸的处理及等待机制**
   *   **问题**：语义规定重卡使用已有的预渲染原尺寸且不重渲，如果导出时某些重卡的预渲染原尺寸根本不存在，系统应如何处理？“等待上传方”最多等多久？
   *   **可选做法（无预渲染原尺寸）**：(a) 用占位符或黑屏代替并记录失败日志；(b) 阻塞导出并提示缺失预渲染产物。
   *   **可选做法（等待超时）**：(a) 永久等待直到用户手动取消；(b) 设定 5 分钟超时，超时后自动按失败处理。
10. **手机浏览器后台导出中断处理与产物去向**
    *   **问题**：手机浏览器进行逐帧导出时，锁屏或切换应用极易导致进程挂起甚至被杀。是否需要特别提示保持前台？导出完成后，“打开产物目录”在手机上的等价行为是什么？
    *   **可选做法**：(a) 开始导出时强提示“请保持页面在前台，不要锁屏”；(b) 完成后直接触发浏览器的文件下载动作。
11. **低内存档「轻量修改」的边界与反馈表现**
    *   **问题**：什么是轻量修改？超出边界的重度修改在 UI 上如何被拦截或提示？修改发生后，没有任何渲染节点在线时，低内存档用户看到的最终画面是什么？
    *   **可选做法**：(a) 根据操作类型（如添加复杂特效）硬拦截并弹窗提示不支持；(b) 不拦截，但画面上无限期显示“等待渲染节点”占位符。
12. **加入表单中用户名的具体合规规则**
    *   **问题**：表单验证时，“不合规”的具体定义（如长度限制、允许的字符）在语义中未明确。
    *   **可选做法**：(a) 限制 1-32 个字符，不包含特殊控制符；(b) 仅限制非空，对字符集不做任何约束。
13. **邀请码三种失效情形是否合并提示**
    *   **问题**：邀请码作废、过期、次数用完是三种不同原因，提示语是否要精确区分并分别显示，还是可以为了简洁合并成一句大一统的失败提示？
    *   **可选做法**：(a) 前端详细拆分三种情况反馈；(b) 合并为“邀请码已失效，请获取新链接”。
14. **限定进入时用户名不在名单与密码错误的提示合并**
    *   **问题**：当用户填入一个不在名单里的用户名时，直接提示“用户名不在名单内”可能会暴露名单信息。出于安全考量，是否应将该提示与“密码错误”合并，对外统一模糊提示？
    *   **可选做法**：(a) 安全优先，模糊提示“用户名或密码错误”；(b) 体验优先，明确指出哪一项不对。
15. **取消多用户协作保存失败后的复选框状态**
    *   **问题**：用户取消勾选并点击保存，如果拉回本机失败（如断网），此时界面的 `[ ] 多用户协作` 复选框应该处于什么状态？
    *   **可选做法**：(a) 强制回滚为勾选状态，提示用户重试；(b) 保持在不勾选状态且项目处于“正在注销”的中间态。
16. **口令错误限速文案中是否写死冷却时间**
    *   **问题**：按 12.2 节规定的机制，冷却时间为 60 秒。UI 提示文案是否应写死“60秒”，还是应当做变量传入以便未来调整？
    *   **可选做法**：(a) 文案中硬编码“60秒”；(b) 文案写为“请稍后再试”，或采用服务端返回的 `{x} 秒`。
17. **项目设置「搬到云端」相关术语的区隔**
    *   **问题**：语义里“搬到云端”指现有的本地协作项目迁移至云端。在首次勾选多用户协作并直接选放云端时，为了避免混淆，是否应避免使用“搬到云端”这个词，而改用“正在设置多用户协作”等描述？
    *   **可选做法**：(a) 统一叫“正在搬到云端”以简化概念；(b) 严格区分，首次叫“正在设置”，后续迁移才叫“搬到云端”。
18. **针对普通档卡片的受限 UI 是否完全照搬到低内存档**
    *   **问题**：关于包含用户卡/图卡显示“需要本地 PC 渲染辅助”与不透明等规定，语义最初定于在线浏览器模式（普通档）。这一 UI 表现是否在低内存档下保持绝对一致？
    *   **可选做法**：(a) 照搬，统一浏览器体验；(b) 为低内存档进一步简化，连占位图标都不展示。

## 每一项

### 甲一：在线浏览器生成和播放轨道流（经过任务队列）

- 任务书是 `browser-stream-task.md`：还差的七处、语义要改的地方、怎么验，都照它。
- 起点是分支 `claude/browser-stream-encode`（比 `main` 多 7 个提交，试合无冲突）。分支上除了压和封装两个模块，还有一处修正和四个探针：
  - 修正：在线后台舞台生成一帧时，从挂载帧完整推到目标帧，不再被 6 秒补跑上限截断。它改的是浏览器节点为有状态的卡生成的画面，合入前用现有的浏览器节点探针（`scripts/probes/m7-*`）验一遍。
  - 探针：浏览器压流、快照差异的贴图耗时、有状态的卡推到第 N 帧的耗时、Lottie 两种画法的对比。
- `render-standard.md` 里留着两件没做完的核对，这次补上：
  - 「顺着做到第 N 帧」和「从头推到第 N 帧」的快照是不是一样，修了 6 秒上限之后没有重跑。重跑一遍，14 张有状态的内置卡都要过。
  - `mu-word-rotate`（循环轮换文字）从头推时结果不稳定，同一帧连做两次互不相同，原因没查。查清原因；是这张卡自己的毛病就修卡，并对这张卡做改前改后的逐帧比对；查不清记未达成。
- 合入以后线上不会马上生效，下面三件在 0.7.18 部署时做，到时候在节点上补验：
  - 文档服务、素材服务、在线编辑器重新部署。
  - 线上要有能切分任务的节点。
  - 独立渲染主机缺省不产轨道流（`scripts/render-host.mjs` 要带 `--streams`）。云端的渲染服务不开这个开关，线上就只有桌面应用和浏览器在产流。

### 甲二：本页产流（不经过任务队列）

**做成什么。** 线上没有能切分任务的节点时，身份为电脑的在线页面，对本页能运行的重卡，在后台舞台闲时自己生成单卡的轨道流，推到素材服务，自己播。别的成员的页面、之后上线的桌面应用和渲染主机，都能直接用这份产物。

**要求。**

- 和队列那条路产出的是同一种东西：同一条流不管从哪条路产，结果键相同、清单的形状相同、写进层表的方式相同。一条流产过了，另一条路不再产一遍。
- 能产的卡和浏览器节点能认领的单卡流一样（`browser-stream-task.md` 第一处的条件）。组流、画布卡、Lottie、判为「重」的卡照旧等桌面或渲染主机。
- 只在闲时做，用户播放、拖动时让路，规矩同浏览器节点认领任务。
- 有能切分的节点接了活，就不再自己产。
- 身份为手机的页面不做（它不当渲染节点，`product/platforms.md`）。
- 纯浏览器节点「不替别的用户干活」这条边界不变：页面只为自己打开的项目、自己要播的卡产流。

**已知的难点。** 流的计划（哪几张卡、范围、矩形、结果键）现在在 `server/frame-stream.mjs` 的 `planStreams` 里算，页面的构建不带服务端模块。现有的先例是把纯计算照抄一份到页面一侧，用单测和服务端那份逐字段对拍（`src/online/planPublisher.ts` 对 `server/render-queue/messages.mjs` 就是这样）。用哪种办法由执行方定。

**怎么判断「线上没有能切分的节点」**、等多久才自己动手，属于做法，由执行方定，写进 `browser-stream-task.md`，标〔裁〕。

**验收。**

- 单测：同一条流，页面一侧算出的结果键、清单，与切分方算出的逐字段相同。
- 端到端探针一：只起文档服务、素材服务和一个在线页面，没有桌面、没有渲染主机。页面自己产出流，内容库里有清单，播放时舞台上是流在画，不是快照在换。
- 端到端探针二：接着上一步，第二个在线页面打开同一个项目，直接贴上这条流，不重产；再让一个桌面预渲染进程连上来，它不重产这条流，能把它拉回去播。
- 端到端探针三：先有能切分的节点在线，页面不走本页产流这条路。
- 用户播放、拖动时本页产流停下让路（用断言验，不靠看）。

### 乙：remotion 式的框架

**现状。** 建卡检查在 `server/vite-plugin-cards.ts` 的 `checkCardSource`；云端 Agent 建卡走同一套，另加 `server/hosted-render/source-gate.mjs` 的一道。它只查有没有写 `frameMode`，不看写的是哪一种。它拒绝 `Date.now()`、`setTimeout`、`setInterval` 等几样；`Math.random`、`performance.now()`、单独的 `requestAnimationFrame`、`new Date()` 不拒绝。`Math.random` 在运行时被钉成带种子的（`src/kernel/pinEntropy.ts`），但它每调一次往前走一步，结果跟调用的先后有关，直接跳到某一帧时对不上。除了语法错误，报错都不带行号。现有的几条报错还在劝人「动画交给 motion/react」。

**做成什么**（`render-standard.md`「还要做的」第 3 条）。remotion 式的卡只用这个框架写，框架里没有的东西就是不合法的。三部分：

- 一套工具：按时间插值、带缓动的过渡、用公式直接算第 N 帧位置的弹簧、错开进场、带种子的随机。
- 不合法的操作建卡时当场拒绝，告诉写卡的人哪一行不行：声明成 remotion 式的卡只许引用这个框架，不许引用 `motion/react`；「remotion 式的规矩」里列的操作一条条对上。给 remotion 式的卡的报错要带行号，文案不再指向 Motion。
- 拦写不拦读，三道：卡片文件顶层只许写常量（看源码就能查）；载入卡片时把顶层的对象整体锁成只读（只做一次）；框架不提供能跨帧存东西的工具。

**边界。**

- 检查只在建卡、改卡时拒绝。已经在库里的卡（内置卡、用户以前建的卡）照旧载入、照旧运行，不因为多了检查而坏。
- 声明成 motion 式的卡，检查和现在一样，不加严。
- 现有内置卡不改写、不改声明。现在声明成 remotion 式的内置卡有 4 张（`av-pulse`、`caption-track`、两张合成声音的卡），都没有用 Motion，也都不是用框架写的，照旧。
- 框架放在哪一层、工具叫什么名字由执行方定，守 `constraints.md` 的分层。工具的名字和参数是写卡的人和 Agent 要照着写的接口，标〔裁〕，列给用户看。

**验收。**

- 工具的单测：同样的时间、参数、种子重复求值，结果逐位相同；先算第 N 帧再算第 M 帧，与按顺序算的结果相同。
- 「remotion 式的规矩」每一条各有一张违规的样例卡，建卡时被拒绝并指出行号；合规的样例卡通过。看源码查不出来的那一类（例如字体、图片谁先加载好），写明为什么查不出来、靠什么兜住。
- 三道只读各有用例：顶层写了不是常量的东西被拒；运行时往顶层对象里写当场报错；框架里没有能跨帧存东西的工具（守门测试）。
- 用框架写两三张示例卡（放测试夹具里，不进卡片库）：从头顺着做到第 N 帧，和直接算第 N 帧，画面逐像素相同。
- 桌面建卡和云端 Agent 建卡两条路都验到。
- 现有的内置卡全部照常载入；全量测试零失败。

### 丁：把卡片的分类登记成一张表

**现状。** 审阅表（`src/cards/capabilities.json`）是手改的，42 条，键是卡片 id 或前缀通配。每条只有两样：`compositing`（依不依赖下层）和 `canvasHeavy`（是不是画布卡，只有真假两个值）。写法一条都没登记。用户建的卡不在表里：写法取自源码里的声明，依不依赖下层一律当「未知」。读表的入口基本统一在 `src/kernel/frameMode.mjs`，Node 一侧另有一份加载（`server/vision-project.mjs`）。

**做成什么。**

- 内置卡在表里三样登记全：哪种写法、画在什么上、依不依赖下层。用前缀通配的照旧可以用通配。
- 现在不在表里、又没有说明的四张（`av-pulse`、`sound-notification`、`sound-keyboard`、`probe-slow`）补上。补登记会改变它们的分类，逐张写明改之前按什么处理、改之后按什么处理。
- 写法以卡的声明为准，登记进表里的值取自声明；表和声明对不上算错（守门测试）。另两样以审阅表为准，和现在一样。这句话要改进语义，见「语义文档要跟着改的」第 8 行。
- 两处读表的地方都认新字段。`src/cards/capabilities.md` 跟着改（它写默认注册 89 张、`caption-track` 是唯一的 remotion 式的卡，都过时了）。
- 用户建的卡这次不进表。审阅结果随源码同步是 `TODO.md` 里另立的专项。

**验收。** 全部内置卡在表里三样齐全；新增内置卡没登记，测试变红；表和声明对不上，测试变红。卡片的分类会进卡片身份的摘要（`src/kernel/cardGraph.mjs`）：除了补登记的那四张，别的卡的预渲染结果的键不许因为表里多了字段而变；变了等于旧缓存整体作废，要先报告。

### 戊、己、庚、癸共用的契约

这四项都改「预渲染存什么」，互相咬着，动手前先写一份短契约放在 `docs/plan/` 下（建议叫 `prerender-products-contract.md`），至少定清：

- 每一类卡存什么、不存什么（照下面三项）；键、清单、层表怎么变。
- **暂停和拖动时，每一类卡各贴什么。** 这是用户点名的关键路径。现状：拖动时重卡的画面只来自快照；轨道流的播放器里有取任意一帧的代码，但不在播放时父页不发流平面（`src/editor/snapshotFeed.ts` 的 `streamPlanesAt`），用不上。没有快照的卡拖动时画面从哪来，要写明，并有探针证明不比现在差。
- **判重、又进不了流的 remotion 式的卡怎么办**（见戊的现状第 2 条）。
- 旧的预渲染结果怎么作废；桌面和在线、新旧版本同时在线时各自怎么读。
- 基线脚本要不要跟着调，怎么调。`scripts/verify-unified-frames.mjs` 用一张 motion 式的 DOM 卡验「快照重放两次相同」「预渲染结果与看到的帧逐字节相同」，庚会碰到它。断言不许放松：产物的种类变了必须调时，新断言要覆盖同样的画面，调整前后各跑一遍，结果写进报告，记待用户审。
- 凡是用户看得到区别的地方单独列出来，标〔裁〕，当场播报。

### 戊：remotion 式的卡不存每帧 HTML

**现状。** 声明成 remotion 式的卡，代码现在就不给它产 HTML 快照（`server/snapshot-tier.mjs`）：判重时能有的预渲染结果只有轨道流，暂停和拖动时舞台直接露出活组件当场算。但这样声明的内置卡只有 5 张（含一张探针卡），都很轻，这条路几乎没被走过。乙做出框架、癸把 Lottie 改过来以后，走这条路的卡会多起来。有三处没接好：

1. **位置矩形没有地方登记。** 层表里没有任何矩形。占位符的位置靠流清单里的框；没有流时靠停下以后当场量的框；再没有就只在位置框中心放一个小徽标。
2. **判重、又进不了流的卡没有任何东西可贴。** 只有独立卡能产流。依赖下层的卡、审阅表没覆盖到的卡（Agent 新建的卡都是后一种），如果声明成 remotion 式又判重，既没有快照也没有流，播放时会一直显示占位符。
3. **产流时不区分写法。** 接不上前一段时一律从挂载帧回放（`server/bakery/bake.mjs` 的 `bakeStream`、在线的 `StageView.bakeFrame`），对 remotion 式的卡是白推。

**做成什么。**

- 给 remotion 式的重卡登记整张卡的位置矩形，占位符和别的要用位置的地方从这里取。登记在哪由契约定。
- 第 2 条不许留着：播放时不能一直占位。怎么补在契约里定；用户看得到区别，标〔裁〕并播报。
- 产流时 remotion 式的卡不从挂载帧回放。
- 这是对「预渲染的产物」那张表头两行的读法：remotion 式的卡一律不存每帧 HTML，当场算不过来（判重）时才多一条轨道流。读错了由用户更正。

**不许退步。** 这类卡在播放、暂停、拖动、导出、Agent 看画面时，画面和改之前一样；预览里不出现无提示的透明；占位符的规则不变；在线浏览器里同样成立（所以它等甲一）。

**验收。** 探针：一个带 remotion 式重卡的项目（独立卡一张、依赖下层或没登记的卡一张），预渲染完，帧库和素材服务里没有它们的每帧 HTML，有位置矩形；独立的那张有轨道流、播放时贴流；另一张播放时不是一直占位。暂停、拖动各取若干时刻截图，与导出同一时刻的画面一致，不透明。桌面和在线各验一遍。导出像素基线 0 不同。

### 己：画布与 WebGL 的卡直接流式压进 H.264

**现状。** 这类卡现在是粒子卡一族（`particles` 和 53 张粒子封装卡）和 `scene-3d`。它们都是独立卡，都有轨道流。产流时每一帧是在预渲染的 Chrome 里活渲、按矩形截成带透明的 PNG、经管道交给 ffmpeg（`server/frame-stream.mjs`、`server/bakery/bake.mjs` 的 `bakeStream`）。另外每帧还存一份快照，画布在里面是一张内嵌的 PNG（`src/render/snapshot/rasterizeCanvas.ts`），上限 1 MB。

**做成什么。**

- 产流时画面不经过 PNG：从画布直接取像素送进编码器。用浏览器自带的编码器，还是把原始像素交给 ffmpeg，由执行方定。带透明的流仍要拼成上半颜色、下半透明度。
- 卡片的画面全在画布里时才这样取；画布之外还有别的元素的卡照现在的办法。
- 不再为这类卡存每帧的快照。
- 快照没有了，拖动时这类卡的画面改从轨道流取：暂停和拖动时也把流平面接上，补上暂停态取任意一帧的测试。停下以后照旧回到精确的活渲。

`TODO.md`「性能方向」里有一条同方向的旧记录（2026-10-01）。它写的「快照里那张 PNG 可以留作占位」被 2026-10-09 的「不存图片」取代。导出整帧仍走截图，不在这一项里。

**不许退步。** 同戊；另外拖动这类卡时不能变成透明、不能长时间占位、不能露出没推到位的活组件。

**验收。** 同一张画布卡，新旧两条路产出的流逐帧比：解出来的颜色和透明度之差落在 `render-standard.md` 实测的那个量级里（颜色平均差不到 1，满分 255）。帧库和素材服务里没有画布卡的每帧快照。拖动时取若干时刻截图，与导出同一时刻的画面一致。预渲染耗时改前改后各记一个数。渲染附加项全过；导出像素基线 0 不同。

### 庚：快照改成「结构存一份，每帧只存变了的地方」

- **做成什么。** 还要存快照的卡（motion 式的 DOM 卡），结构存一份，每帧只存变了的地方；贴的时候只改那几处，不整块替换。
- **范围。** 每张卡自己的快照：共享档和本地档的落盘、浏览器节点产的那一份、素材服务里的快照块和清单、在线页面取用、舞台贴图。整场景的 HTML（Agent 看画面、量框用的那一份）不在这一项里。
- **拖动是跳着走的。** 任意一帧都要能直接贴出来，不依赖上一帧已经贴过。
- 实验里踩到的一处要带上：快照把样式整个内联了，里面可能带着过渡时长，只改一个数值会被浏览器当成要做过渡，得压住（`scripts/probes/snapshot-diff-apply-probe.mjs` 里已经这样做）。
- 体积上限（DOM 卡 300 KB）管的是一次投递的成本。换了存法以后这条上限怎么判，在契约里定，标〔裁〕。
- 换存法以后旧的预渲染结果整体作废、重渲一遍。这一步要用户授权，以开工指令为准；没有授权就做到能切换为止，不切。
- **验收。** 每隔若干帧核对：新贴法贴出来的内容，和整块替换贴出来的逐节点相同；跳着贴（先贴第 N 帧再贴第 M 帧）同样相同。暂停、拖动的截图与改之前一致，桌面和在线各验一遍。占用空间和贴一帧的耗时改前改后各记一个数。导出与快照重放一致的那一项照过；导出像素基线 0 不同。

### 辛：桌面版导出，两条路各量一遍

- **现状。** 两条路不只是编码不同，取画面的办法也不同。桌面版：在受控的 Chrome 里整帧截图成 PNG，先编成带透明的 ProRes 中间文件，再和素材合成、用 libx264 编成片（`server/bakery/export-unified.mjs`、`server/export-compose.mjs`）。在线浏览器：把整场景的快照包成 SVG 画到画布上，转成 YUV 交给浏览器自带的编码器，自己封装 MP4（`src/export/browserExport.ts`、`frameCompositor.ts`）。
- **只量，不换。** 在同一台机器、同一个项目上把两条整路各跑几遍：像素基线的演示项目一个，再加一个带重卡和画布卡的项目。桌面运行环境里已经有一个探针入口能走在线那条路（`window.__pcIo.exportVideoBrowser`），直接拿它量，不用另加开关。

- 结果写进报告，「换不换」记成待用户项。换了以后导出的像素基线要重新定，所以这一步等用户。
- 验收：报告里有上面这些数字；导出像素基线 0 不同（因为没换）。

### 癸：Lottie 改成 remotion 式

- **现状。** 通用的 Lottie 卡（`src/cards/native/lottie.tsx`）和 5 张自带的素材封装卡（`src/cards/assets/index.ts`）都声明成有状态。两处注释互相矛盾：前一个文件说每一帧都是时间的纯函数，后一个说播放器按自己的时间线推进。卡片实际的做法是前一种。
- **做成什么。** 两处声明改成 remotion 式，注释改对。改了以后它不再产快照（代码按声明走，见戊的现状），桌面版预渲染也不再每做一批都从挂载帧重推。画法不变，仍然用 SVG。
- 当场算一帧 Lottie 要多久没有量过。量出来，写进 `render-standard.md` 的 Lottie 一节。
- 浏览器节点现在按卡片 id 把 Lottie 排除在外（`server/render-node/split.mjs` 的 `BROWSER_EXCLUDED_CARD`），理由是快照超过体积上限。快照不存以后这个理由没有了；要不要放开让浏览器产 Lottie 的流，由执行方评估后写进报告，缺省不放开。
- **要留意的一处。** Lottie 的播放库在表达式里取随机数（`wiggle()`、`random()`），用的是被钉成带种子的那个随机源，结果跟调用的先后有关。改成 remotion 式以后是直接跳到某一帧，不再从头顺着推；带表达式的素材（自带的 `navidad` 就是）要专门验「直接跳到第 N 帧」和「顺着推到第 N 帧」画面相同。不相同的素材不能按 remotion 式办，列进报告，记待用户项。
- **验收。** 改之前先留底：5 个自带素材各取全长，逐帧截图。改之后逐帧相同；跳着取的若干帧也相同。像素基线的演示项目里没有 Lottie 的话，全量比对测不到它，以这份针对性的比对为准（`verification.md`「按改动范围验证」）。探针或日志能证明预渲染不再从挂载帧重推。播放、暂停、拖动各验一遍，桌面和在线都验。

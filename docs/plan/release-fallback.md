# release 快进不了时怎么办

临时文档，只管 0.7.18、0.7.19、0.7.20 三个版本连做这一次。**平时不用读，只有发版时 `release` 快进失败才读。** 三个版本做完后删掉。

2026-10-08 用户定：`release` 正常是从 `main` 快进；快进不了时**不要停工，也不要强推**，另建一条 `release_<版本号>` 分支，`main` 照常往下做。

## 什么算「快进不了」

发版时执行 `git checkout release && git merge --ff-only <这个版本的发版提交>` 报错，说明 `release` 上有 `main` 没有的提交。正常不会出现，因为 `release` 只从 `main` 前进。

## 做法

1. 不动 `release`：不强推、不重置、不删。
2. 在这个版本的发版提交上建分支并推送，名字用版本号，例如 `release_0.7.18`：
   ```
   git branch release_0.7.18 <发版提交>
   git push origin release_0.7.18
   ```
3. 安装包和补丁照常从这个发版提交构建。发版说明里把「release 指向这个版本」换成「`release_0.7.18` 指向这个版本」。
4. 查一下 `release` 上多出来的是什么，只看不改：
   ```
   git log --oneline <发版提交>..release
   ```
5. 在进度文件 `three-versions-progress.md` 的「待用户项」里记一条：哪个版本、`release` 停在哪个提交、多出来的提交是哪几个、新建的分支叫什么。
6. 这个版本的收尾播报里说一句。然后 `main` 接着做下一个版本，不等答复。

## 下一个版本发版时

先再试一次快进 `release`。还是不行，就再建一条 `release_<那个版本号>`，照上面办。之前建的 `release_*` 分支留着，不要删。

## 不要做的

- 不要 `git push --force` 任何分支。
- 不要为了让快进成立去改写 `main` 或 `release` 的历史。
- 不要因为这件事停下等用户。

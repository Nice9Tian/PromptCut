# 计划：音频图卡判重（轻 / 重分类）方案的测试与定稿

2026-09-23。用户决定音频处理整体改成浏览器端 JS（重构计划见 `audio_structure_plan.md`），并要求音频也判重、重卡由 PC 客户端预渲染后推送到素材服务。本文先用实测把判重方案里「能算能试」的前提核一遍，再列出剩下的测试步骤，照着做完就能把判重口径定稿、交给重构计划的 A6 步实现。

- 探针：`scripts/probes/audio-determine-probe.mjs`（`node --no-warnings scripts/probes/audio-determine-probe.mjs --json out.json`，约 6 分钟）。
- 本文引用的数字都来自这次运行的原始结果：`docs/plan/audio-probe-2026-09-23.json`（Chrome 152 无头，28 线程机器，Worker 里算，块长 0.5 秒，片段 60 秒）。
- 用词：RTF（实时倍率）= 算这段声音花的时间 ÷ 这段声音的时长。RTF 0.1 就是算 1 秒声音要 100 ms。
- 误差两个口径：`maxRel` = 最大逐样本差 ÷ 参考信号峰值（「最大差 8%」就按它读）；`rmsDb` = 差值的 RMS 相对参考信号的分贝数，只作诊断。

## 0. 实测推翻或修正的几件事（先看这里）

1. **画面卡「抽 16 帧取 p90」的办法不能照搬到音频。** 代价随位置变化的卡，抽样估计一会准一会不准；尾部突变的卡，抽样完全漏掉。
   出处：验证：`spiky`（平时 RTF 0.001，每 10 秒里有 1 秒 0.21）五组种子的抽样 p90 = `[0.2056, 0.2046, 0.2054, 0.0014, 0.0014]`；`tailSpike`（最后 1 秒 RTF 0.82）五组全是 `0.0014`～`0.0018`，整趟实测最大块 `0.8246`。
   出处："抽样永远无法安全拦截长尾性能毛刺"——Gemini 讨论第 1 轮。已核实：上面两张卡就是反例。
   **所以判重必须整趟跑一遍。** 好在音频整趟很便宜（见第 2 条），整趟跑出来的结果还能直接存成预渲染结果。
2. **音频计算比画面便宜一到两个数量级，整趟跑可行。** 最贵的合成卡（4096 抽头 FIR）RTF 0.21，意思是算 60 秒声音用 12 秒；解码素材的开销小到可以忽略。
   出处：验证：`fir4096.totalRtf = 0.2052`、`additive64 = 0.0652`、`chain = 0.1196`；WebCodecs 解码 `decRtf` AAC `0.0018`、Opus `0.0025`。
3. **有损编码之后逐样本比对没有意义，8% 阈值只能比编码前的 PCM。** AAC 192k 往返一次，纯音调信号最大差 2.5%，带噪声的信号最大差 54%。感知编码本来就不保留噪声的波形。
   出处：验证：`tonal:mp4a.40.2 maxRel 0.0251 / rmsDb -47.5`；`music:mp4a.40.2 maxRel 0.5407 / rmsDb -12.8`；`music:opus maxRel 0.9085`。
   这一条同时决定了**上传格式不能用 AAC / Opus**，见第 4.6 节。
4. **分段渲染加预滚可以做到误差近乎为零，8% 的门槛很宽。** 真实效果链（`src/audio/fxChain.ts`）按 10 秒一段分段渲，每段往前多渲一截「预滚」再扔掉：
   - 预滚 ≥ 效果尾巴的长度，误差就降到 1e-7 量级；
   - 不预滚，接缝处的最大差是 79%～86%。

   出处：验证：`all`（高通+压缩+回声+混响 1.5 s+限幅）预滚 0 / 0.5 / 1 / 2 / 4 秒的 `maxRel` = `0.864 / 0.086 / 0.0122 / 2.8e-4 / 1.8e-7`；`voice`（高通+均衡+压缩）预滚 2 秒 `maxRel = 0`，逐样本相同；`longTail`（回声间隔 0.4 s、反馈 0.6）预滚 4 秒 `0.0040`、8 秒 `1.8e-5`。
   这一条属于重构计划，放在这里是因为它说明了 8% 这个门槛的松紧：**只要预滚够，实际误差比 8% 小五个数量级以上。**

## 1. 假设（有不对的请直接改）

- 判重只针对**音频图卡**（`kind: "audio"` 的图卡节点，`cardAudio.ts` 的 `isCardAudioNode`）。普通配乐、视频原声、音频效果链都是实时跑也很便宜的东西，不参与判重。
  出处："每段一个 `<audio>`"——`src/editor/preview/MediaLayers.tsx` 文件头；效果链离线渲 60 秒约 0.2～0.7 秒（验证：`chunk.voice.oneShotMs 205`、`all 672`）。
- 「最大差 8%」读成 `maxRel ≤ 0.08`，也就是最大逐样本差 ≤ 参考峰值的 8%。**比的对象是编码前的 PCM**（混音、预渲染块），不是 AAC 成片。只管音频，画面的逐字节对账不动。
  出处："放宽逐字节比对，改为阈值，比如8%最大差"——你刚才说。范围和口径是我的解读，第 6 节列为待定。
- 判重的门槛按设备分开记，和画面卡的成本记录一样（`src/render/costDevice.mjs` 按机器 / 渲染路线分键）。这台 28 线程机器上量出的数，不能直接当 iPad 的门槛。
- 音频图卡的契约是「按区间随机访问的纯函数」：同一段采样，不管一次要还是切成几块要，结果都必须相同。
  出处："音频图卡:按采样区间产出交错的 Float32 采样块"——`src/kernel/types.ts` 的 `audio?`；`requestCardAudio` 按 `start/count` 缓存（`src/audio/cardAudio.ts`）。

## 2. 判重方案（待定稿的版本）

### 2.1 探针：整趟跑，跑出来的结果顺手存下

项目加载后，在音频 Worker 里对每个音频图卡节点从片段第 0 块推到最后一块（块长 0.5 秒），每块记计算耗时，得到四个数：

| 量 | 定义 | 用途 |
|---|---|---|
| `r_win` | 2 秒滑动窗口内平均 RTF 的最大值 | **判重的主依据**。播放缓冲能吸收单块尖刺，吸收不了持续 2 秒的高负载 |
| `r_p90` | 各块 RTF 的第 90 百分位 | 贪心排序、诊断 |
| `t_first` | 冷启动时第一块的耗时 | 起播 / 跳转延迟 |
| `pure` | 分块无关性（整块算 vs 切 7 块算，逐样本比） | 不纯的卡不能实时算 |

- **为什么用滑动窗口，不用单块最大值**：`spiky` 的单块最大 RTF 是 0.21，但只持续 1 秒，2 秒窗口平均只有 0.104；`tailSpike` 单块 0.82，2 秒窗口 0.41。播放时 Worker 会提前 2 秒算（重构计划 A3），短于缓冲时长的尖刺不会造成断音。
  出处：验证：`spiky maxRtf 0.2078 / maxWindow2sRtf 0.104`；`tailSpike 0.8246 / 0.4113`。
- **整趟的输出不白算**：判重的卡按下面第 2.4 节存成预渲染结果；判轻的卡输出只留在内存里，按 LRU 淘汰，不落盘、不上传，和画面「预渲染只做重卡并集」一致。
  出处："在所有位置都判轻的不产快照、不产流、不进就绪索引"——`docs/archive/user_pinned_goal.md` 卡片渲染 9。
- **整趟跑完之前**先给一个临时分类：只量首块、末块和随机 16 块，其中的最大块 RTF 就当 `r_win` 的估计值。整趟跑完再用真值替换；替换后判重的卡进入预渲染队列（照卡片渲染 6 的降级规则：就绪之前照常实时算）。
  出处：验证：首块、末块能抓住 `iirFromZero`（代价随位置线性涨，末块 0.0244 是中位数 0.0126 的约两倍）和 `tailSpike` 这类尾部突变；抓不住中段突变（`spiky`），所以临时分类只是临时的。

### 2.2 分派：按位置贪心，和画面卡同一个形状

1. 分段边界取所有音频图卡片段入点、出点的并集。每一段里，把正在出声的卡按 `r_win` 从小到大贪心收进轻管线，直到 RTF 之和超过音频预算 `B_a`。收不进的判重。
   出处："取所有卡片开始/结束位置的并集作为分段边界"——`docs/archive/user_pinned_goal.md` 卡片渲染 8；"使用贪心搜索，优先吸纳单帧最便宜……的卡入轻管线"——卡片渲染 3。
2. 这几种情况直接判重，不进贪心：
   - 单卡 `r_win > B_a`；
   - `pure = false`：实时分块算出来的结果和整趟不一样，只能用整趟的结果（验证：`impure` 卡 `pure: false`，其余八张 `true`）；
   - `t_first` 超过起播门槛 `T_first`（缺省值待第 3 节 T3 定）。
3. 卡接卡时，下游的计时里已经包含了上游（验证：`chain` RTF 0.12 ≈ `additive64` 0.065 + `fir1024` 0.052）。所以按拓扑序从上游判起：上游判重之后，下游读的是上游的预渲染结果，要按「上游已缓存」重新量一次。
4. 读素材输入的卡**不必强制判重**：JS 解码的开销可以忽略（验证：`decRtf ≈ 0.002`），计进 `r_win` 就行。

### 2.3 运行时降级（照卡片渲染 6）

播放时 Worker 记下每块的实际耗时。播放缓冲的水位（还剩多少秒已算好的声音）低于 0.5 秒时，把当前最贵的轻卡降为重卡：进预渲染队列，就绪之前照常实时算，预渲染集合只增不减。
出处："一秒窗口内累计超时……就把最贵的那张轻卡降为重卡。降级不立即生效：被降级的卡先进预渲染队列……死素材就绪前仍照常活渲"——`docs/archive/user_pinned_goal.md` 卡片渲染 6。音频用「缓冲水位」代替「每拍超时」，是因为音频不按拍走。

### 2.4 预渲染结果的键、存储、上传

- **缓存键**：卡片 id + 源码版本 + 实例参数 + 每一路输入的身份（素材内容哈希 + `mediaOffset` + 边上的 `offset`，或上游节点的键）+ 采样率 + 片段长度（采样数）。
  现有的 `versionKeyOf` 只收了源码版本，参数靠换项目对象失效。
  出处："缓存键带图卡源码版本:改了图卡源码之后 `project` 对象不变"——`src/audio/cardAudio.ts` 的 `versionKeyOf` 注释；"键里带依赖对象的身份，依赖没变就一直复用"——`docs/archive/user_pinned_goal.md` 卡片渲染 5。
- **存储格式**：16 位整数 PCM，再用浏览器自带的 `CompressionStream('deflate-raw')` 压缩，不用装库。
  - 量化误差是峰值的 2e-5 到 3e-5，离 8% 远得很。
  - 压缩率看内容：纯音调信号压到 1%，带噪声的信号只压到 85%。按最坏情况算，每分钟立体声约 11.5 MB。
  出处：验证：`storage.music s16Bytes 5760000 → s16DeflateBytes 4871919`（30 秒）；`storage.tonal → 66014`；`s16MaxRel 1.8e-5 / 3.4e-5`。
  WebCodecs 不能编码 FLAC（验证：`encoder.flac: false`），AAC / Opus 过不了 8%（第 0 节第 3 条），所以不用它们。
- **上传**：PC 客户端（桌面运行环境，有预渲染进程）判重的卡整趟跑完，把压缩块按键推送到素材服务。素材服务只存、只发，不做任何处理。浏览器模式按键拉取。拉不到时这张卡静音，界面标「预渲染中」，播放头不停。
  出处："其它本地用户可以把渲染好的结果上传到云端，云端合并所有用户预渲染结果。并负责分发"——`docs/archive/user_pinned_goal.md` 架构 3；"死素材缺失时该层透明、播放头不停"——卡片渲染 7。

## 3. 测试步骤

T0 已经做完。T1～T8 照顺序做，每步写明做什么、产出、判据和预计耗时。T2、T3、T4 各要一个新探针，端口按惯例用 5231 起的一段。

**T0 基线实测（已完成，2026-09-23）** — 产出：`reports/audio-probe-2026-09-23.json`。结论即第 0 节。

**T1 分块无关性检测在真实卡片上成立** — 做什么：
1. 用重构计划 A2 做好的真实求值路径（`evaluateCardAudio`），对仓库里全部音频图卡、加上探针的 9 张合成卡，各跑一遍「整块 vs 切 7 块」逐样本比较。
2. 再加一张「用了 `Math.random()` 的卡」，确认它被判为不纯。

产出：`scripts/probes/audio-purity-probe.mjs`，加进 `npm test` 能跑的纯函数部分。判据：纯的卡 100% 相同；两张不纯的卡都判 `false`。预计半天。

**T2 定音频预算 `B_a`** — 做什么：写一个最小的播放器，Worker 算块，AudioWorklet 环形缓冲播放，提前量 2 秒。
1. 同时实时算 N 张合成卡，让 RTF 之和分别是 0.1、0.25、0.5、0.75、1.0，各播 60 秒，数断音次数。
2. 同时在另一个标签页跑 `playback-probe` 给舞台加负载，模拟真实编辑。
3. 把断音为 0 的最大 RTF 之和记为 `R_max`，`B_a` 缺省取 `0.5 × R_max`，做成可调系数（照卡片渲染 5「保留可调系数」）。

产出：`scripts/probes/audio-budget-probe.mjs`，以及 `B_a` 的缺省值。判据：在 `B_a` 下连播三次 60 秒，断音都是 0。预计 1 天。

**T3 定起播门槛 `T_first`** — 做什么：在 T2 的播放器里测「按播放 / 跳转 → 第一声出来」的延迟，冷、热两种状态各测，并和现在 `<audio>` 元素的起播延迟对比。缺省值取「不比现在慢」。判据：新的起播延迟 p90 ≤ 现在的 p90。预计半天。
出处：验证：冷启动首块最多 `102.7 ms`（`fir4096`），热态一块是 `r × 500 ms`。

**T4 换设备** — 做什么：
1. 桌面壳 WebView2：`node --no-warnings scripts/probes/audio-determine-probe.mjs --connect`。
2. iPad Safari：`... --serve-only --host 0.0.0.0`，在 iPad 上打开 `http://<本机IP>:5231/`，用 Safari 远程调试读 `window.__probe`。

记录：每张卡的 RTF 相对本机的倍数、WebCodecs 编解码支持表、`CompressionStream` 能不能用。判据：拿到三台设备的数字；iPad 上 AAC 解码不可用的话，重构计划 A1 的解码层要写退路。预计半天，前提是手边有 iPad。

**T5 整趟探针的总耗时** — 做什么：在一个真实规模的项目上量加载后整趟探针要跑多久，比如 5 张音频图卡、每张 3 分钟，Worker 数 = `hardwareConcurrency − 2`。
估算：5 × 180 秒 × 平均 RTF 0.07 ≈ 63 秒 CPU 时间，分到多个 Worker 上是十几秒墙钟。判据：整趟在后台跑，**不挡加载遮罩**，只有临时分类（第 2.1 节，首块 + 末块 + 16 块）进遮罩，遮罩多出来的时间 ≤ 1 秒。预计半天。
出处："全部测完才进"——`docs/archive/user_pinned_goal.md` 卡片渲染 5。这条字面要求「测完才进」，而音频整趟可能要十几秒，**和它冲突，列为第 6 节待定 1**。

**T6 缓存键失效** — 做什么：给缓存键函数写单测，覆盖这几种情况：参数变、源码版本变、上游节点参数变、素材哈希变、`mediaOffset` 变、片段长度变（各自都要失效），以及无关片段变（不失效）。产出：`src/audio/cardAudioKey.test.mjs`。判据：全绿。预计半天。

**T7 存储和上传的往返** — 做什么：把一张判重的卡整趟跑完，压成 s16 + deflate-raw，写进 OPFS（本地）；模拟上传再下载一次，解压后和整趟的原始 Float32 比。判据：`maxRel ≤ 1e-4`（远严于 8%，量化误差本来就在 3e-5 左右）；每分钟立体声不超过 11.5 MB。预计半天。

**T8 8% 比对工具** — 做什么：写 `scripts/probes/audio-compare.mjs`：读两个 PCM（wav 或 s16 块），报告 `maxRel`、`rmsDb` 和最大差出现的位置（秒），`maxRel ≤ 0.08` 就算过。用三组已知答案自检：
- 同一文件：`0`；
- 预滚 0 的分段渲染：约 0.86，不过；
- 预滚 4 秒：约 1.8e-7，过。

这个工具后面所有音频验收都要用。预计半天。

## 4. 优点 / 缺点 / 限制

- **优点：判重和预渲染合并成一趟。** 整趟跑出来的结果，判重的卡直接存，不用再跑第二遍。
  出处："跑的时候就可以存下来当作预渲染"——`docs/archive/user_pinned_goal.md` 卡片渲染 5。
- **优点：和画面卡同一套形状**（按位置分段、贪心、运行时降级、预渲染集合只增不减），实现和审查都能对照已有代码。
  出处：`docs/archive/user_pinned_goal.md` 卡片渲染 3、6、8。
- **缺点：整趟探针要占 CPU。** 长片段、贵的卡可能要跑十几秒到几十秒。放在后台跑，就和「全部测完才进」的字面要求冲突（待定 1）。
  出处：验证：`fir4096` 整趟 60 秒要 `0.2052 × 60 ≈ 12.3 秒`。
- **缺点：临时分类会看漏中段突变**，要靠整趟跑完后替换、再加运行时降级兜底。整趟跑完之前，这类卡可能断音一次。
  出处：验证：`spiky` 抽样 p90 有两组种子是 0.0014。
- **缺点：带噪声的内容几乎压不动**，重卡存储最坏每分钟约 11.5 MB。
  出处：验证：`music s16DeflateBytes 4871919 / 30 秒`。
- **限制：浏览器里的计时精度和负载都不稳定。** 本探针在无头 Chrome 里量，而无头环境的 rAF 会退到 10 Hz，Worker 计时受后台节流影响也有波动。所以门槛只取统计值，并留可调系数。
  出处："无头 Chrome 的 rAF 会退到 10 Hz"——`docs/archive/restructure_planning/hand_off.md` 第 6 节「验收陷阱」。
- **限制：探针用的是合成卡，仓库里现在没有一张真实的音频图卡。** 判重门槛最终要用真实卡再校一遍。
  出处："89 张内置卡里**没有一张**是 Python 卡"——`archive/python-cards/README.md`；我搜过 `src/cards`，没有 `kind: "audio"` 的内置卡。

## 5. Gemini 讨论（第 1 轮）的处理

- **采纳**：「抽样拦不住长尾毛刺」→ 改为整趟跑（第 2.1 节）。已用 `tailSpike` 核实。
- **采纳（改了说法）**：「FLAC / Vorbis 缺 description 报 TypeError 是规范行为」→ 解码层必须从容器里取出初始化数据传给解码器，写进重构计划 A1。已核实：探针里 `decoder.flac` / `vorbis` 在不给 `description` 时都是 `throw:TypeError`。
- **采纳为可选项**：「有状态卡定期存内部状态，跳转时从最近的状态接着算」。这要给卡片接口加一个可选的状态存取钩子，放进重构计划的「以后做」，这一轮不做。
- **不采纳**：「按缓冲紧张程度动态降采样率 / 降精度」。理由："所以编辑台听到的就是导出的。这是整个音频效果系统成立的前提"——`src/audio/fxChain.ts` 文件头。预览降质会打破这个前提。
- **不采纳**：「用 Wasm / WebGPU 跑重 DSP」。卡片是用户用 JS 写的，平台没法替它换实现；Gemini 自己也标了「猜测」。
- **部分不同意**：「整趟缓存和分段预滚的结果交替使用，接缝会咔哒」。音频图卡的输出是按区间的纯函数，整趟算和分块算逐样本相同（验证：九张合成卡里八张 `pure: true`），拼接不产生接缝。预滚误差只出在**效果链**上，而效果链的输出不缓存，预览实时跑、导出统一分段渲，两条路从不混用。不纯的卡才会出问题，所以它们一律判重、只用整趟结果（第 2.2 节）。

## 6. 要你定的

1. **「全部测完才进」对音频放宽到「临时分类测完就进，整趟在后台跑」吗？** 不放宽的话，一个项目的音频探针可能让加载遮罩多停十几秒（T5 会给出实数）。我建议放宽，这样要改 `docs/semantics/architecture/rendering.md`「测量」里「测完才进入编辑」的措辞，改语义文档须先经你确认。
2. **8% 的口径**：我读成「编码前 PCM 的最大逐样本差 ≤ 峰值的 8%」，只管音频、画面仍逐字节。对吗？
3. **重卡的上传格式**：s16 + deflate-raw（无损，最坏每分钟约 11.5 MB），还是接受引入一个 JS 的 FLAC 编码库（要装依赖，要你同意）？我建议前者。
4. **要不要把「音频图卡也判重，重卡由 PC 客户端预渲染后推送到素材服务」写进 `docs/semantics/`**（pinned 已归档，被它取代）。要的话，我拟好原文弹窗给你勾选。

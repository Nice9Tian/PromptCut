## 1. 目标

1. **项目真身在文档服务**：文档服务持有每个项目的当前内容与操作日志；页面、Agent、其它客户端手里都是副本（语义「各方手里的项目都是它的副本」）。
2. **一切修改都是「操作」**：页面和 Agent 都向文档服务提交操作；文档服务排序、记版本、广播给各方。
3. **Agent 直接写文档服务（D1）**：写工具不再经页面执行；只读页面独有状态的工具留在页面。
4. **页面按操作收增量（D2）**：工具调用的「创建 / 完成」事件经文档服务推给页面，完整参数进内容库按需拉。
5. **撤销 / 重做按「谁做的谁撤」**：每个页面会话、每个 Agent 对话各有自己的撤销栈，撤销也是一次新的操作。
6. 共享项目的两项界面（D11）接上这套数据流。

## 2. 操作格式〔裁〕

**为什么选「路径操作」**：
- 页面现在是整份替换，最小改动是在 `setProject` 这一处算出新旧两份的差，变成路径操作。70 个 action 一个不用改。
- 文档服务是通用的 JSON 分发中心，不该认识项目的业务结构。路径操作只要一个通用的 JSON 引擎就能应用，文档服务不需要引入 `src/kernel`。
- 放弃的方案：
  - **命令式操作**（把 action 名和参数发给服务端重放）：服务端要能执行全部 action，等于把编辑器内核搬进文档服务；
  - **CRDT**：语义明确「最后写的赢，不做合并」，不需要。

**形状**：

```json
{
  "type": "project.op",
  "projectId": "…",
  "opId": "<客户端生成，全局唯一>",
  "expectRev": 41,
  "session": "<页面会话 id 或 Agent 对话号>",
  "undoOf": "<被撤销的 opId，可选>",
  "ops": [
    { "op": "set",    "path": "/tracks/@t1/clips/@c3/frame/x", "value": 120 },
    { "op": "remove", "path": "/tracks/@t1/clips/@c9" },
    { "op": "insert", "path": "/tracks/@t1/clips", "index": 2, "value": { "id": "c10", "…": "…" } },
    { "op": "move",   "path": "/tracks/@t1/clips/@c3", "index": 0 }
  ]
}
```

- **路径**：JSON 指针，但**数组里带 `id` 的对象按 `@<id>` 寻址**，不按下标。
  - 这样别人在同一数组里插删元素，不会把我的操作打到错的对象上。
  - 没有 `id` 的数组整体当一个值，用 `set` 整个替换。
- **四种操作**：
  - `set`：设值，路径不存在时连同缺的父级对象一起建；
  - `remove`：删掉；
  - `insert`：往带 id 的数组里按下标插；
  - `move`：同一数组里挪位置。
- **一次提交的多条操作原子生效**：要么全部落地、版本号加一，要么整批拒绝。
- **根替换**：`{ "op": "set", "path": "", "value": <整个项目> }`。
  - 用于打开旧 `.proc`、Skill 合并结果落地、差异太大（单次超过 500 条）时兜底。
  - 语义上它也是一次普通写入，照样记版本、照样通知覆盖。
- **差异算法** `diffProject(prev, next)`：放在 `src/kernel/`（纯函数、确定性），返回 `{ ops, inverse }`。
  - `inverse` 是把 `next` 变回 `prev` 的操作，撤销用；
  - 对象逐键递归，带 id 的数组按 id 比对插、删、挪，其余值比 `===`。
  - 单测要求：对任意 `prev`、`next`，把 `ops` 应用到 `prev` 等于 `next`，把 `inverse` 应用到 `next` 等于 `prev`（性质测试，1000 个随机项目）。

## 3. 文档服务一侧

- **`project` 模块升级**（按空间，M6a 的空间机制）：
  - 每个项目存一份当前内容快照，加一条操作日志（`projects/<id>.ops.ndjson`，每行一次提交）；
  - 每 200 次提交把快照落盘一次，日志随之截断到快照之后；
  - 重启时读快照再回放日志。
- **打开** `project.open { projectId }`：
  - 回 `project.state { projectId, rev, project, writers }`，其中 `writers` 是最近写入者摘要，并订阅项目频道；
  - 项目大时分片发回（沿用 M5b 快照分片与节流）。
- **提交**：
  - 成功：回 `project.op.ok { opId, rev }`；频道上广播 `project.ops { rev, opId, ops, actor, undoOf? }`，发给除提交者以外的所有订阅者；提交者靠 `ok` 就知道已落地。
  - 拒绝：回 `project.op.rejected { opId, reason, currentRev, since? }`。`reason` 取以下几种：
    - `stale`：带了 `expectRev` 而当前版本不等于它；`since` 列出其间落地的每次提交 `{ rev, actor, paths }`；
    - `bad-path`：路径指向不存在的父级，且不是 `set`；
    - `too-large`：单次提交超过 256 KiB；
    - `forbidden`。
- **期望版本**（语义「冲突」）：
  - Agent 的提交必带 `expectRev`，不符就拒绝，告诉它期间落地了哪些改动；
  - 页面的提交不带，按到达顺序落地；
  - 离线重放的第一条带（第 6 节）。
- **覆盖通知**（语义「发生覆盖时，覆盖方和被覆盖方都要知道」）：
  - 文档服务按「顶层实体」记最近写入者：
    - 片段按 `/tracks/@t/clips/@c`；
    - 序列按 `/tracks/@t`；
    - 效果库条目按 `/filters/@f` 等；
    - 项目元数据按 `/meta`，这是 `width`、`fps` 等顶层字段的归类。
  - 一次提交写到的实体，若最近写入者是**另一个写入身份**（用户 + 设备 + 页面，或用户 + 设备 + 对话），而且那次写入在 10 分钟内：
    - 覆盖方的 `ok` 里带 `overwrote: [{ entity, by }]`；
    - 被覆盖方单独收 `project.overwritten { entity, by, rev }`。
  - 被覆盖的页面收到后，先把自己那一版的该实体存成本地备份（草稿目录下 `backups/`），再应用新版本。这一步写在页面侧，语义原话是「被覆盖的一方在换成最新版本之前，先把自己那份存成本地备份」。
- **跟踪退出**：`project.follow { entity, on: false }`，语义「Agent 和用户都可以对某张卡退出跟踪」。
- **写入身份**：`actor` 取连接的 `principal`（M6a 第 6 节），外加 `session`。消息里自报的一律不认。

## 4. 页面一侧

- `src/store/core.ts` 的 `setProject(next)`，在「整份替换」之外多做一件事：
  - 调 `diffProject(prev, next)`，把 `ops` 交给新的 `docsync` 模块（`src/store/docsync.ts`）提交；
  - 本地先落地（乐观更新）。
- **收到别人的 `project.ops`**：
  - 把操作应用到本地 project，生成新对象，走 `set` 而不是 `setProject`，所以不进撤销栈、不回发；
  - 应用前若本地有**未确认**的操作，先把它们撤回、应用远端的、再把本地的重放。这就是乐观更新的标准做法；因为路径按 id 寻址，重放几乎总能成功，重放失败的那条丢弃并提示。
- **`.proc` 保存**：只在所有本地操作都拿到 `ok` 之后才写（语义「页面只在拿到文档服务对最新操作的确认之后才写」）；没确认完就等，超时提示。
- **本地项目**（没有共享）：页面连本机编辑器里挂的文档服务（`/docservice`，`local` 空间）。数据流和共享项目完全一样，只是没有别人。这样本地和共享走同一条路，不留两套。
- **离线**：连不上文档服务时，操作照常本地落地并进待发队列（第 6 节）。

## 5. Agent 一侧（D1、D4）

- **写工具的执行位置**从页面移到 Agent 服务端（编辑器 vite 进程里的 `vite-plugin-ai.ts`）：
  - 用 vite 的 `ssrLoadModule` 载入 `src/mcp/handlers/*` 和 store，在服务端起一份**项目副本**。副本随文档服务的 `project.ops` 保持最新，每个 Agent 对话读同一份副本。
  - 写工具在副本上执行 handler，`diffProject` 算出操作。以 Agent 对话的身份、带 `expectRev`（这个对话最后一次读到的版本）提交。
  - 被拒（`stale`）时，工具回错，附上 `since` 的摘要（谁、改了哪些实体），Agent 重读后再改。
- **只读页面独有状态的工具**留在页面，照旧经 SSE：选区、播放头交互、面板 UI、`web_handoff` 一类（`cloud-task.md` D1 的判据）。`mcp-tools.mjs` 逐条标 `side`。
- **D4**：`MIRRORED_TOOLS`（`get_layout` 等）搬到 Agent 服务端执行，读副本，不经页面。
- **读后写一致**：Agent 服务端的副本以 `project.op.ok` 的 `rev` 为准，读工具回包里带 `rev`，写工具用它作 `expectRev`。
- **Agent 对话的身份**：Agent 服务端作为一条 `agent` 角色的连接接入文档服务（M6a 第 5 节），每个对话一个对话号。本机 `local` 空间下由本机信任；共享项目下，凭页面签发的连接票据（`kind: 'conn'`, `role: 'agent'`, `c: 对话号`）进入。

## 6. 离线〔按语义〕

- 断线期间的操作按顺序进待发队列，记下断线时最后知道的版本 `offlineRev`。
- 重连后，第一条带 `expectRev: offlineRev` 提交：
  - 被接受：其余的依次提交（不带期望版本）；
  - 被拒（`stale`）：说明离线期间别人改过，整批停下，由用户决定「重放」（去掉期望版本依次提交）还是「丢弃」（本地回到服务端版本）。

## 7. D2：工具调用事件

- 新模块 `events`（类型前缀 `events.`），频道是项目频道。Agent 服务端每个工具调用发两条：
  - 创建：工具名、图标、目标片段、参数摘要；
  - 完成：状态、摘要、耗时。
- 完整参数同时写进内容库 `event-detail`，页面展开时再拉。
- 文字回复整条完成时推。页面 AI 栏按事件 id 更新对应记录，列表虚拟化。

## 8. 用户感知到的撤销 / 重做（Gemini 出稿，主会话核对后并入）

技术框架（主会话定，Gemini 在这个框架内写用户看到的行为）：
- **撤销栈按写入身份分开**：每个页面会话一个栈，每个 Agent 对话一个栈。用户按撤销，只撤自己这个页面会话做过的；Agent 的改动由 Agent 自己的撤销工具撤，或者用户在 AI 栏里对某一条进度条目点「撤销这一步」。
- **撤销就是提交 `inverse`**：带 `undoOf`，是一次新的写入，版本号照常加一，别人照常收到。
- **撤销前查冲突**：`inverse` 涉及的实体，若在这一步之后被**别的写入身份**改过：
  - 这些实体不撤，其余的照撤；
  - 告诉用户哪几处因为别人改过而没撤，谁改的。
  - 理由：语义「最后写的赢」，撤销也是一次写入，不能悄悄盖掉别人后来的改动。
- **重做**：同理，重做的是撤销的 `inverse`；中间有新的本地操作时，重做栈清空。
- **栈上限**：100 步，与现在相同；「一步」= 一次提交，拖动松手、数字框回车各算一步（数字框的连续输入合并成一步，300 ms 内的算同一步）。

（Gemini 稿待并入：撤销按钮与快捷键的行为说明、「这几处没撤」的提示文案、AI 栏里「撤销这一步」的交互、多人同时在线时撤销的可见反馈。）

## 10. 内容库写入区分会话

内容库与项目日志的 `actor` 统一记 `{ userId, deviceId, role, conversation, session }`（M6a 第 6 节），`content.changed.previousActor` 同样带全。这样同一用户不同会话的写入可以分清（第 11.2 节推迟项）。

## 12. 要用户知道的

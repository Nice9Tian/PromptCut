## 1. 目标

1. **项目真身在文档服务**：文档服务持有每个项目的当前内容与操作日志；页面、Agent、其它客户端手里都是副本（语义「各方手里的项目都是它的副本」）。
2. **一切修改都是「操作」**：页面和 Agent 都向文档服务提交操作；文档服务排序、记版本、广播给各方。
3. **Agent 直接写文档服务（D1）**：写工具不再经页面执行；只读页面独有状态的工具留在页面。
4. **页面按操作收增量（D2）**：工具调用的「创建 / 完成」事件经文档服务推给页面，完整参数进内容库按需拉。
5. **撤销 / 重做按「谁做的谁撤」**：每个页面会话、每个 Agent 对话各有自己的撤销栈，撤销也是一次新的操作。
6. 共享项目的两项界面（D11）接上这套数据流。

## 2. 操作格式〔裁〕

**为什么选「路径操作」**：
- 页面现在是整份替换，最小改动是在 `setProject` 这一处算出新旧两份的差，变成路径操作。70 个 action 一个不用改。
- 文档服务是通用的 JSON 分发中心，不该认识项目的业务结构。路径操作只要一个通用的 JSON 引擎就能应用，文档服务不需要引入 `src/kernel`。
- 放弃的方案：
  - **命令式操作**（把 action 名和参数发给服务端重放）：服务端要能执行全部 action，等于把编辑器内核搬进文档服务；
  - **CRDT**：语义明确「最后写的赢，不做合并」，不需要。

**形状**：

```json
{
  "type": "project.op",
  "projectId": "…",
  "opId": "<客户端生成，全局唯一>",
  "expectRev": 41,
  "session": "<页面会话 id 或 Agent 对话号>",
  "undoOf": "<被撤销的 opId，可选>",
  "ops": [
    { "op": "set",    "path": "/tracks/@t1/clips/@c3/frame/x", "value": 120 },
    { "op": "remove", "path": "/tracks/@t1/clips/@c9" },
    { "op": "insert", "path": "/tracks/@t1/clips", "index": 2, "value": { "id": "c10", "…": "…" } },
    { "op": "move",   "path": "/tracks/@t1/clips/@c3", "index": 0 }
  ]
}
```

- **路径**：JSON 指针，但**数组里带 `id` 的对象按 `@<id>` 寻址**，不按下标。
  - 这样别人在同一数组里插删元素，不会把我的操作打到错的对象上。
  - 没有 `id` 的数组整体当一个值，用 `set` 整个替换。
- **四种操作**：
  - `set`：设值，路径不存在时连同缺的父级对象一起建；
  - `remove`：删掉；
  - `insert`：往带 id 的数组里按下标插；
  - `move`：同一数组里挪位置。
- **一次提交的多条操作原子生效**：要么全部落地、版本号加一，要么整批拒绝。
- **根替换**：`{ "op": "set", "path": "", "value": <整个项目> }`。
  - 用于打开旧 `.proc`、Skill 合并结果落地、差异太大（单次超过 500 条）时兜底。
  - 语义上它也是一次普通写入，照样记版本、照样通知覆盖。
- **差异算法** `diffProject(prev, next)`：放在 `src/kernel/`（纯函数、确定性），返回 `{ ops, inverse }`。
  - `inverse` 是把 `next` 变回 `prev` 的操作，撤销用；
  - 对象逐键递归，带 id 的数组按 id 比对插、删、挪，其余值比 `===`。
  - 单测要求：对任意 `prev`、`next`，把 `ops` 应用到 `prev` 等于 `next`，把 `inverse` 应用到 `next` 等于 `prev`（性质测试，1000 个随机项目）。

## 3. 文档服务一侧

- **`project` 模块升级**（按空间，M6a 的空间机制）：
  - 每个项目存一份当前内容快照，加一条操作日志（`projects/<id>.ops.ndjson`，每行一次提交）；
  - 每 200 次提交把快照落盘一次，日志随之截断到快照之后；
  - 重启时读快照再回放日志。
- **打开** `project.open { projectId }`：
  - 回 `project.state { projectId, rev, project, writers }`，其中 `writers` 是最近写入者摘要，并订阅项目频道；
  - 项目大时分片发回（沿用 M5b 快照分片与节流）。
- **提交**：
  - 成功：回 `project.op.ok { opId, rev }`；频道上广播 `project.ops { rev, opId, ops, actor, undoOf? }`，发给除提交者以外的所有订阅者；提交者靠 `ok` 就知道已落地。
  - 拒绝：回 `project.op.rejected { opId, reason, currentRev, since? }`。`reason` 取以下几种：
    - `stale`：带了 `expectRev` 而当前版本不等于它；`since` 列出其间落地的每次提交 `{ rev, actor, paths }`；
    - `bad-path`：路径指向不存在的父级，且不是 `set`；
    - `too-large`：单次提交超过 256 KiB；
    - `forbidden`。
- **期望版本**（语义「冲突」）：
  - Agent 的提交必带 `expectRev`，不符就拒绝，告诉它期间落地了哪些改动；
  - 页面的提交不带，按到达顺序落地；
  - 离线重放的第一条带（第 6 节）。
- **覆盖通知**（语义「发生覆盖时，覆盖方和被覆盖方都要知道」）：
  - 文档服务按「顶层实体」记最近写入者：
    - 片段按 `/tracks/@t/clips/@c`；
    - 序列按 `/tracks/@t`；
    - 效果库条目按 `/filters/@f` 等；
    - 项目元数据按 `/meta`，这是 `width`、`fps` 等顶层字段的归类。
  - 一次提交写到的实体，若最近写入者是**另一个写入身份**（用户 + 设备 + 页面，或用户 + 设备 + 对话），而且那次写入在 10 分钟内：
    - 覆盖方的 `ok` 里带 `overwrote: [{ entity, by }]`；
    - 被覆盖方单独收 `project.overwritten { entity, by, rev }`。
  - 被覆盖的页面收到后，先把自己那一版的该实体存成本地备份（草稿目录下 `backups/`），再应用新版本。这一步写在页面侧，语义原话是「被覆盖的一方在换成最新版本之前，先把自己那份存成本地备份」。
- **跟踪退出**：`project.follow { entity, on: false }`，语义「Agent 和用户都可以对某张卡退出跟踪」。
- **写入身份**：`actor` 取连接的 `principal`（M6a 第 6 节），外加 `session`。消息里自报的一律不认。

## 4. 页面一侧

- `src/store/core.ts` 的 `setProject(next)`，在「整份替换」之外多做一件事：
  - 调 `diffProject(prev, next)`，把 `ops` 交给新的 `docsync` 模块（`src/store/docsync.ts`）提交；
  - 本地先落地（乐观更新）。
- **收到别人的 `project.ops`**：
  - 把操作应用到本地 project，生成新对象，走 `set` 而不是 `setProject`，所以不进撤销栈、不回发；
  - 应用前若本地有**未确认**的操作，先把它们撤回、应用远端的、再把本地的重放。这就是乐观更新的标准做法；因为路径按 id 寻址，重放几乎总能成功，重放失败的那条丢弃并提示。
- **`.proc` 保存**：只在所有本地操作都拿到 `ok` 之后才写（语义「页面只在拿到文档服务对最新操作的确认之后才写」）；没确认完就等，超时提示。
- **本地项目**（没有共享）：页面连本机编辑器里挂的文档服务（`/docservice`，`local` 空间）。数据流和共享项目完全一样，只是没有别人。这样本地和共享走同一条路，不留两套。
- **离线**：连不上文档服务时，操作照常本地落地并进待发队列（第 6 节）。

## 5. Agent 一侧（D1、D4）

- **写工具的执行位置**从页面移到 Agent 服务端（编辑器 vite 进程里的 `vite-plugin-ai.ts`）：
  - 用 vite 的 `ssrLoadModule` 载入 `src/mcp/handlers/*` 和 store，在服务端起一份**项目副本**。副本随文档服务的 `project.ops` 保持最新，每个 Agent 对话读同一份副本。
  - 写工具在副本上执行 handler，`diffProject` 算出操作。以 Agent 对话的身份、带 `expectRev`（这个对话最后一次读到的版本）提交。
  - 被拒（`stale`）时，工具回错，附上 `since` 的摘要（谁、改了哪些实体），Agent 重读后再改。
- **只读页面独有状态的工具**留在页面，照旧经 SSE：选区、播放头交互、面板 UI、`web_handoff` 一类（`cloud-task.md` D1 的判据）。`mcp-tools.mjs` 逐条标 `side`。
- **D4**：`MIRRORED_TOOLS`（`get_layout` 等）搬到 Agent 服务端执行，读副本，不经页面。
- **读后写一致**：Agent 服务端的副本以 `project.op.ok` 的 `rev` 为准，读工具回包里带 `rev`，写工具用它作 `expectRev`。
- **Agent 对话的身份**：Agent 服务端作为一条 `agent` 角色的连接接入文档服务（M6a 第 5 节），每个对话一个对话号。本机 `local` 空间下由本机信任；共享项目下，凭页面签发的连接票据（`kind: 'conn'`, `role: 'agent'`, `c: 对话号`）进入。

## 6. 离线〔按语义〕

- 断线期间的操作按顺序进待发队列，记下断线时最后知道的版本 `offlineRev`。
- 重连后，第一条带 `expectRev: offlineRev` 提交：
  - 被接受：其余的依次提交（不带期望版本）；
  - 被拒（`stale`）：说明离线期间别人改过，整批停下，由用户决定「重放」（去掉期望版本依次提交）还是「丢弃」（本地回到服务端版本）。

## 7. D2：工具调用事件

- 新模块 `events`（类型前缀 `events.`），频道是项目频道。Agent 服务端每个工具调用发两条：
  - 创建：工具名、图标、目标片段、参数摘要；
  - 完成：状态、摘要、耗时。
- 完整参数同时写进内容库 `event-detail`，页面展开时再拉。
- 文字回复整条完成时推。页面 AI 栏按事件 id 更新对应记录，列表虚拟化。

## 8. 用户感知到的撤销 / 重做（Gemini 出稿，主会话核对后并入）

技术框架（主会话定，Gemini 在这个框架内写用户看到的行为）：
- **撤销栈按写入身份分开**：每个页面会话一个栈，每个 Agent 对话一个栈。用户按撤销，只撤自己这个页面会话做过的；Agent 的改动由 Agent 自己的撤销工具撤，或者用户在 AI 栏里对某一条进度条目点「撤销这一步」。
- **撤销就是提交 `inverse`**：带 `undoOf`，是一次新的写入，版本号照常加一，别人照常收到。
- **撤销前查冲突**：`inverse` 涉及的实体，若在这一步之后被**别的写入身份**改过：
  - 这些实体不撤，其余的照撤；
  - 告诉用户哪几处因为别人改过而没撤，谁改的。
  - 理由：语义「最后写的赢」，撤销也是一次写入，不能悄悄盖掉别人后来的改动。
- **重做**：同理，重做的是撤销的 `inverse`；中间有新的本地操作时，重做栈清空。
- **栈上限**：100 步，与现在相同；「一步」= 一次提交，拖动松手、数字框回车各算一步（数字框的连续输入合并成一步，300 ms 内的算同一步）。

**用户侧行为**（Gemini 稿 `gemini-c65-undo.md`，97 行，主会话核对后采纳；完整文案表以稿件为准，实现时附进报告）：

- 快捷键：Ctrl+Z 撤销，Ctrl+Shift+Z 与 Ctrl+Y 重做；栈空时按钮变灰；焦点在输入框里时交给输入框。
- 悬停提示写明「只撤你自己在这个页面做的」。按下后画面直接变，不弹「已撤销」。
- **部分没撤**：提示条列出没撤的几处，标明是谁改的（Agent 的某个对话、别的成员、你在另一个页面）。超过 3 处时折叠；点实体名跳过去并选中；约 8 秒后消失，带关闭按钮。
- **全部没撤**：「没撤成。这几处后来都被改过了，保留了现在的样子」，并附同样的列表。
- **AI 栏「撤销这步」**：只在改过项目的进度条目上出现，不需要二次确认，不是最新的一步也能点；成功后按钮变灰，显示「已撤销」。
- **别人撤销**：不弹提示，画面直接变。只有触发覆盖通知时，被覆盖的一方看到提示，并告诉他本地备份在哪。
- **离线重连、第一条被拒**：弹对话框，给「重放」「丢弃」两个选项，并说明各自的后果。

Gemini 列出的待裁定项，主会话裁定如下：

| 问题 | 裁定 | 理由 |
|---|---|---|
| 一步全部没撤成，还留在撤销栈里吗 | 不留，出栈，也不进重做栈 | 它涉及的实体都已归别人后来的版本，留着下次按还是撤不成，只会让用户反复看到同一条提示 |
| AI 栏的「撤销这步」算谁的写入 | 算用户这个页面会话的写入（`undoOf` 指向 Agent 那次提交），进用户自己的撤销栈 | 动手的是用户；进用户的栈，用户按 Ctrl+Z 就能把 Agent 的改动恢复回来，符合直觉 |
| 本地备份怎么找回 | 「项目」菜单加「本地备份…」：按时间和实体列出，点「恢复」就把那个实体以一次新写入写回去 | 语义只要求先备份、没规定入口；恢复也是写入，照样通知别人，不破坏「最后写的赢」 |
| 别人的改动要不要短暂高亮 | 要：时间轴上被改的片段描边 1.5 s | 多人同时在线时，只看画面跳变很难发现变了哪里；高亮不打断操作 |
| 离线对话框关掉后从哪里再打开 | 顶栏显示「同步已暂停」状态，点它重新打开 | 关掉等于「暂不决定」，必须有个地方能回来做决定 |
| 点「丢弃」前要不要先备份那批本地修改 | 要，存进本地备份 | 与「被覆盖方先备份」同一个精神：用户的东西不能无痕消失 |

另外采纳 Gemini 的两处取舍：按撤销不弹提示，AI 栏撤销不需要二次确认。理由是撤销本身就能再撤回来，不需要多一步确认。

## 10. 内容库写入区分会话

## 13. 第一批集成时的裁定（2026-09-26）

主会话在集成 `c65-docservice`、`c65-kernel`、`c65-tests` 时裁定，`claude/c65-integ` 按此落实。精确的操作语义以 `c65-ops-spec.md` 为准，该页已与本节一致。本节与第 2、3 节原文不一致处，以本节为准。

**操作语义**（两端已对齐，差分模糊对照 0 不一致）

- `remove` / `move` 的目标不存在 = 空操作，照常落地：两人同时删同一片段是常见竞态，后到的那批不该整批被拒、连带丢掉同批的其它修改。
- `set` / `insert` 的父级不存在（含路径上找不到的 `@id`）= `bad-path`，整批拒：往已被删掉的东西里写，落地了也没人看得见；`set` 途中缺的**对象键**照第 2 节连同父级对象一起建，走不通的只是数组里找不到的 `@id`、途经标量等建不出来的情形。
- `insert` / `move` 的 `index` 超过长度 = 放到末尾：越界不是错误，别人并发删了几个元素后，插到末尾最接近本意。
- `move` 的 `index` 指挪完之后的位置（先拿出来再插）：与数组的最终样子直接对应，页面算差异、服务端应用都按这一种理解，不会差一位。
- 根替换「变了哪些实体」由服务端按新旧值的实际差别统计（在实体之上 `set` 一个容器同理）：页面只知道路径，按 `*` 算会把 10 分钟内写过的所有人都标成被覆盖；页面自己的撤销冲突判定仍按路径算，偏保守。

**实体粒度**

- 项目顶层的每个字段各算一个实体（`/meta/name`、`/meta/fps`……，不再合成一个 `/meta`；顶层非标量字段同样按顶层键，如 `/style/color` → `/meta/style`）：别人改了 fps 不该让我撤不回自己改的 name。页面（`diffProject` 的 `entityOfPath`）与服务端（`json-ops` 的 `entityOf` / `entitiesOf`，覆盖通知、`since.entities`、`project.follow`）一起改。

**兼容**

- `project.state` 同时带新字段 `rev` 与旧字段 `projectRev`：C6.3 的旧客户端与预渲染发布流程还在读 `projectRev`；旧测试 `docservice-project.test.mjs` 的 P1～P7 一条不改、全过。

**页面一侧**

- 离线期间每次编辑各算一条提交，不合并：第 6 节「按顺序」落地，别人看到的是与在线时相同的一串提交，撤销栈的一步也仍对应一次提交。
- 撤销时一处都没撤成就不产生提交：没有改动的提交只会让版本号空涨、让别人收到一条空广播。

**接受 `c65-docservice` 的新增**

- `project.upload` 分片上传与 `project.ops` 的 `resync: true`：单次提交 ≤ 256 KiB 与「打开旧 `.proc` 用根替换」同时成立，大项目只能分片进来；这种提交的广播太大，改为让别人重新 `project.open`。
- `forbidden` = 渲染节点的连接（`role: 'render'`）提交或发事件：渲染节点只读项目，管理身份本来就进不了空间。
- `project.overwritten` 带 `writer`（被覆盖的那次写入的身份）：Agent 服务端一条连接上跑多个对话，要靠它把通知分给对应的对话。
- `by` 两边都指对方（覆盖方 `ok.overwrote[].by` 是被覆盖的人，被覆盖方 `project.overwritten.by` 是覆盖它的人）：每一方要知道的都是「和谁撞了」。

**接受 `c65-kernel` 的越界**

- `c65-kernel` 改了 `src/store/actions/coreActions.ts`（`undo` / `redo` / `loadProject` 装了同步挂钩时交给 docsync，新增 `canUndo` / `canRedo`）：两种模式对 actions 的接口要一致，`undo` / `redo` 就在这个文件里，不改做不到；没装挂钩时行为不变（G0-R 导出像素与 main 0 差异）。

## 14. 第二批集成时的裁定（2026-09-26）

主会话在集成 `c65-agent`、`c65-editor`、`c65-tests2` 时裁定，`claude/c65-integ2` 按此落实（报告 `AGENT-c65-integ2.md`）。每条是「裁定：理由」。本节与前文不一致处，以本节为准；与 auth 有关的同步写进 `auth-contract.md` 第 15 节。

**接受 `c65-agent`**

- 每个 Agent 对话一条 `agent` 连接（第 5 节原文「一条 agent 角色的连接」、第 13 节「一条连接上跑多个对话」都改按此理解）：写入身份只取连接的 principal，对话号在握手时定死，一条连接上跑多个对话会把所有对话记成同一个对话号。第一条对话连接兼做副本的订阅。
- 对话号由 Agent 服务端按对话 id 首次出现的顺序在本进程内发（1、2、3……），`session` 记 `agent:<对话 id>`：票据与握手要正整数，页面的对话 id 是字符串；编辑器重启后号码重发，同一对话靠 `session` 认。
- 页面经 `POST /api/agent/bind { projectId, mode, url? }` 告诉 Agent 服务端项目与文档服务（`mode`：本机项目 `local`，共享项目 `ticket`，票据由页面经 SSE 的 `agent.ticket` 签），换项目时重新 bind；没 bind 时写工具照旧经页面：Agent 服务端不知道页面在编辑哪个项目、连的是哪个文档服务，设计稿没写这一步。
- 发布方（预渲染 `plan`）在项目有真身时，`project.announce` 只作查询（不发号、不改状态、不上传快照），以真身的 `rev` 发布；页面推来的与真身不同就不交给队列：拿真身 `rev` 最轻，`project.open` 要传整份项目。
- handler 抛错时整次不提交：服务端执行时把跑到一半的修改留下没有意义，也不该提交出去（页面上的老行为会留下抛错之前的 store 修改，这里不沿用）。
- 期望版本取「这个对话最后读到的版本」，写成功后更新为这次写入后的 `rev`；页面在对话读后改了任何地方，对话的下一次写入都回 `stale`：语义「和当前版本不符就拒绝」，不按实体放行。

**D1 判据：5 个既读页面状态又写项目的工具**

- `set_project_meta`、`switch_cut`、`add_cut`、`remove_cut`、`attach_clip_motion` 改为写入在 Agent 服务端以 agent 身份执行（`side: "agent"`）：留在页面执行的话，写入身份是页面，带不了期望版本，违反 D1「写工具不再经页面执行」。
- 所需的页面状态向页面要一次，经现有 SSE 页面通道取只读值（内部工具 `__page_state`，Agent 看不到）：切剪辑三个要页面播放头（存回被停放的那条剪辑），`attach_clip_motion` 要页面内存里 `track_points` 跑出来的那段素材的轨迹；`set_project_meta` 不读页面状态，不要。页面通道不通时播放头退回服务端记着的页面播放头，轨迹没有替代、直接回错：只读值才能这样要，一次调用只问一次，不把页面拉进写入。
- 这几个工具原来顺手做的页面状态的「写」（切剪辑后换播放头、停播、清选区、清总时长手动值；截断总时长后记手动值），改由页面看到远端改动时自己推出来（`src/store/remotePageState.ts`）：激活剪辑变了 → 播放头取切之前那一版里目标剪辑停放的值；总时长变了 → 手动值按 `manualDurationFor(新总时长, 内容末尾)` 推；选区里被删的片段摘掉。理由：页面状态只该由页面自己写；同一条规则也让本机两页、成员之间互相跟上，不再被时间轴按内容末尾把别人截断的总时长改回去。
- Agent 侧单次写入超过 256 KiB 改走 `project.upload`：把这次改动换成「根替换 = 跑完的整份项目」分片上传、提交里只引用它，逆操作仍用差异算的那份：与页面一侧同一个做法；原来直接回错，一次工具调用改出大差异（长文本、大参数）时 Agent 无路可走。

**页面真接线**

- 页面挂上 DocSync 后调 `/api/agent/bind`（本机 `local`，共享 `ticket`）；SSE 的 `agent.ticket` 由页面在自己的共享连接上签 `auth.ticket { kind: 'conn', role: 'agent', conversation }` 交回；留在页面的工具回包带这次调用期间本页面发出的提交 `opIds`：c65-agent 给了接口、c65-editor 没接，不接的话 Agent 写工具在真实页面里不生效。
- 完成事件带 `opId`、`callId`、`inverse`、`rev`、`actor`；`callId` 是模型那一侧这次工具调用的 id（Claude Code 在 MCP `tools/call` 的 `_meta["claudecode/toolUseId"]` 里带，API 直连用 tool_use id），创建事件也带：AI 栏按它把事件对上聊天记录里的那次工具调用；codex、agy 那两路拿不到，只能在操作记录里撤。
- AI 栏按事件 id 更新记录：新增「Agent 操作记录」（`AgentEventLog.tsx`），创建、完成两条按 `eventId` 合成一条，只存摘要；列表行高固定、虚拟化（只渲染可见的十几行）。聊天记录本身沿用 `.ai-row` 的 `content-visibility` 与逐条 memo（已实测过 1200 次工具调用下每片段 13 ms），不另做窗口化：不论调用来自本页面的聊天、命令行、别的页面还是别人的 Agent，都得在 AI 栏里看得到、撤得了；聊天列表的渲染代价此前已解决。
- 「撤销这一步」出现在操作记录与聊天操作卡上（写进了项目的那一条），不二次确认，撤成后变灰「已撤销」。

**接受 `c65-editor` 的增补与偏差**

- `shared.mjs` 的三项增补：只读操作 `list-bans`（带证明，回禁入表，限定进入另带名单用户名、不带盐与 K）、`set-list` 条目 `{ username, keep: true }`（沿用此人现有口令）、`set-password` 成功后给本空间其余连接发 `shared.notice { event: 'password-changed' }`；以及 `set-creator-password`（带旧口令的证明，不加代数、不作废已发票据、在线连接不断，两种进入方式都能用）：都是界面（禁入列表、改名单、密码被改气泡、改创建者密码）逼出来的最小扩展，写进 `auth-contract.md` 第 15 节。
- 稿件没写、`c65-editor` 补的文案原样接受（`AGENT-c65-editor.md` 第 3 节第 1 条）：放本机时要重启编辑器的提示与「复制命令」按钮；保存等确认超时的提示；顶栏「离线」小标记（悬停「连不上文档服务：修改照常，先攒在本机，恢复后按顺序提交」）；提示条里逆操作落不下去的一项写「(已不存在，没法退回)」；「改创建者密码」菜单项、弹窗标题与成功气泡；「本地备份…」对话框的说明、「(还没有本地备份)」「恢复不了:…」、菜单小字「被覆盖、离线丢弃的修改」；托管地址格式不对的提示「托管地址不对：要以 http:// 或 https:// 开头。」；有一步修改被文档服务拒绝 / 离线重放时丢弃的气泡：都是稿件没覆盖到的情形，文案风格与稿件一致。
- 对稿件的偏差原样接受（同报告第 3 节第 2～10 条）：
  - 「我是创建者」只在本机记过创建者名时预填并置灰，否则用户名框可编辑：查找接口只回 `{ projectId, name, mode }`，页面不知道创建者叫什么；
  - 登录时「已被踢」提示只在本机记过「在这个项目以这个用户名被踢过」时给，否则给「用户名或密码不对」：握手失败按契约只回 401、不说原因；
  - 「尝试太多次」只在取挑战回 429 时判断得出，回环来源不计限速：同上；
  - 「等 X 处」的 X 取总数：中文「等 N 处」的习惯；
  - 片段的称呼用时间轴上片段的标题并带开始时间（`片段「模糊浮现 @2.0s」`）：同一张卡出现多次时才分得开；
  - Agent 的称呼写 `Agent「第 2 个对话」`（别人的 Agent 写成员列表同款「张三 · Agent · 第 2 个对话」）：页面从写入身份里只拿得到对话号，拿不到对话标题；
  - 本机两页之间的覆盖通知显示「你在另一个页面」：本机 `local` 空间里所有页面都是 `userId: 'local'`，靠 `session` 区分；
  - 创建者在自己本机上的局域网项目也凭创建者证明经回环进入，不用本机声明：本机声明的用户名固定是 `local`，成员列表里会显示成「local」。
- 放本机时的一键重启（编辑器以 `PROMPTCUT_LAN_HOST=1` 重启）留给 C10 / 桌面壳，记为遗留：桌面壳眼下没有重启编辑器的接口。

**测试方 `c65-tests2` 的歧义**（按主会话先前的裁定）

- `opId`、`inverse` 在完成事件里（事件模块透传），完成时补写一次 `event-detail`：创建时还没有提交。
- 写成功后，这个对话的期望版本 = 这次写入后的新 `rev`：写成功也算一次读到。
- 读工具也发创建、完成两条事件：D2「每个工具调用两条」。
- AI 栏撤销的冲突 = 这一步之后被**不同于原写入身份**的任何写入（含本页面自己后来的、含还没确认的）改过的实体都不撤；原写入者（那个 Agent 对话）自己后来又改的不算：撤的是那个对话的一步，挡住它的只能是别人。
- 改创建者密码不作废已发票据（不加代数）：只有改项目口令、名单才加代数；创建者密码只管创建者特权，每次特权操作都要当场证明。

- **Agent 写入与总时长**（2026-09-26 收尾时裁定）：Agent 的写入若改了片段而使内容超出总时长，总时长按 `src/kernel/duration.ts` 的规则在服务端算出，随同一批 ops、同一个 rev 提交；页面收到后不再补写。理由：页面补写会让这个 Agent 对话下一次写入因版本不符被拒一次；同批提交也让撤销这一步时总时长一起撤回。

# 第 75 轮 · 第 7 份：第 5 步：A1 的素材上云与按需拉取、A3b、A5、A6
## 1. 结论
有条件能动工（需补全文档服务与素材云端的相关接口定义，并解开步骤间的依赖倒置与数据结构矛盾）。

## 2. 阻塞项

**素材的上传状态标记存在自相矛盾**
- L103「project.media[i] 加 uploaded: boolean」
- 证据：与之冲突的另一处在 L103「project.media[i].tiers = { small?, original }（值是哈希...）」及 L103「localHashes 改由文档云端项目里 media[i].tiers 的 uploaded 标记决定」。如果是两档异步上传，单个 boolean 无法区分小分辨率版和原片哪个上传完毕；且若 tiers 的值是字符串哈希，则无法在它上面挂 uploaded 标记。
- 建议改法：删除 `project.media[i] 加 uploaded: boolean`，并将 `tiers` 结构改为对象：「`project.media[i].tiers = { small?: { hash: string, uploaded: boolean }, original: { hash: string, uploaded: boolean } }`」，后续逻辑均按此读取。

**素材上传端点自相矛盾且断点续传缺少查询接口**
- L103「排队上传素材云端（PUT media/<hash>，断点续传」
- 证据：同一段 L103 后面又写「上传分片：固定 8 MB 一片 PUT media/<hash>/<n>，服务端记已收分片」。这既没有说明何时用整件端点何时用分片端点，也没有给客户端定义断网恢复时查询「服务端已收到了哪些分片」的接口，导致无法实现「只补缺的分片」。
- 建议改法：明确要求全部走分片（或约定阈值），并新增 `GET media/<hash>/chunks` 返回已收分片序号列表的接口。

**内容库快照清单与源码同步缺少接口端点定义**
- L106「清单（共享键 → 本地帧 → 块哈希）写文档云端的内容库」
- 证据：与之冲突的另一处在 L66，L66 仅说明了文档云端提供 WebSocket，并未定义读写快照清单以及 L110「卡片源码同步」所需的具体 HTTP 端点或 WS 消息形状。第 5 步作为云端对接的客户端将无接口可调。
- 建议改法：在 L106 明确写入云端的接口，例如：「通过 HTTP `PUT/GET /api/content/manifest/<key>`（或对应的 WS 消息）」；并在 L110 补充对应的卡片源码同步端点。

**不上云的块在共享清单里缺少表示法 / 接口定义不全**
- L106「只有共享档；data:image 占比超过一半的块不上云。」
- 证据：任务书没写不上云的块要不要进清单。如果在云端清单里写了它的哈希却不上传该块，下载端将无法区分「块还没产（需等待）」和「块故意不上云（需降级为本地预渲染）」。
- 建议改法：在 L106 明确不上云的块在云端清单中的表示法。改为：「data:image 占比超过一半的块不上云，写入云端共享清单时需带上『不上云』的特殊标记供其他端降级」。

**playbackUrl 签名不足以产出浏览器模式所需的绝对地址**
- L103「新增 playbackUrl(media, localHashes) ... 返回 /@media/<那一档的哈希>」
- 证据：L103 同时要求「在线浏览器模式 ... 地址直接是素材云端的」。但 `playbackUrl` 只有 `media` 和 `localHashes` 两个入参，返回值写死了相对路径，在没有素材云端 base URL 上下文的情况下，无法产出在线浏览器模式所需的绝对地址。
- 建议改法：修改签名与逻辑，改为：「新增 `playbackUrl(media, localHashes, cloudBaseUrl?)`，在线浏览器模式下拼接 `cloudBaseUrl` 返回绝对地址，否则返回 `/@media/<那一档的哈希>`。」

**A3b 的下载落盘逻辑绕过了 index.json 的更新**
- L106「下载：打开项目时... 本地 controls-html/<key>/ 缺的块从素材云端按哈希拉、落盘后 C3 把它算作就绪」
- 证据：与 L105「每个 <共享键>/ 目录一份 index.json... fillCardControls 每批写完更新它」冲突。A3b 的下载逻辑未提及更新 `index.json`，若不更新，本地 C3 或后续读取时会因清单没记录而读不到刚下载的帧。
- 建议改法：在 L106 下载落盘后加上对清单的更新。改为：「...落盘后同步更新该目录的 index.json，C3 才把它算作就绪」。

**第 5 步的本地模式依赖了第 6 步才做的本机文档服务（步骤成环等待）**
- L110「本地模式下由本机文档服务在 edit_card / create_card 落盘时自增」
- 证据：第 5 步（L19）要求完成 A6，但 A6 的本地模式依赖本机文档服务来自增 cardRev。而本机文档服务要到第 6 步（L20）才落地，导致第 5 步的本地模式分支处于成环等待，无法在当前步骤自洽并测试。
- 建议改法：将 A6 本地模式依赖本机文档服务的逻辑后移至第 6 步，或在第 5 步仅要求实现并测试云端模式部分。

**.procp 离线包与两档素材的设计脱节**
- L71「.procp：zip，首条目 project.proc，其余 media/<hash>.<ext>。」
- 证据：L103 引入了「同一素材两档（小分辨率档和原片）」，各档有独立的哈希。但 L103 再次定义 .procp 时仅提到了 `media/<hash>.<原扩展名>`。如果不打包小分辨率档，另一台机器离线导入时将缺失小档，与两档设计脱节。
- 建议改法：在 L103 明确 `.procp` 需包含两档。改为：「.procp：... 其余打包 `media[i].tiers` 中引用的所有哈希及文件（含小分辨率档）。」

**原片档仅做流复制违背了 H264 流式传输的硬约束**
- L103「原片后传，没有 faststart 的先 -c copy -movflags +faststart 重封装再传」
- 证据：违背了 pinned 架构 1「素材云端（H264流式传输，先传800*600小分辨率版本/完成以后传原素材版本」的硬约束。如果原素材不是 H.264 编码，仅做 `-c copy` 上传，素材云端分发的将不是 H.264 流。
- 建议改法：在 L103 明确原片非 H.264 时的强制转码行为；或修改 pinned 目标（见第 5 节）以放宽该约束。

## 3. 非阻塞项

**预取队列轮询请求存在 URL 超长风险**
- L103「页面每 2 秒问一次 GET /api/media/local?hashes=」
- 证据：大型项目可能包含大量素材，将全量 64 位哈希拼接到 GET 请求参数中，极易触发服务器端 414 URI Too Long 限制。
- 建议改法：改为：「页面每 2 秒请求一次 `POST /api/media/local`（Body 为 hashes 数组）...」。

**A5 与 A3b 对不上云的判定依据不同**
- L109「A5 不上传缓存的卡。canvasHeavy 卡和图卡（H）只同步代码，本地重放」
- 证据：与 L106「data:image 占比超过一半的块不上云。」的判定依据不同。A5 看卡片类型，A3b 看快照内容比例，两者可能对同一张卡（例如生成了过半 data:image 的非 canvasHeavy 卡）产生不同判断逻辑，容易造成实现侧漏判。
- 建议改法：在 L109 中明确补充：「（注：按 L106，data:image 占比过半的快照块也同样只在本地重放，不上云）」。

## 1. 结论（这一步照着写能不能直接动工：能 / 有条件能 / 不能；条件逐条列）
**不能**直接动工。要先解掉下面 8 条阻塞（逐条 = 一个动工条件）：

1. K6 降级写回 `costs` 的报文形状与已落地的 `mergeCosts` / `validRecord` / `CardCostRecord` 三处冲突（阻塞 1）；
2. K1 探针记录字段在「事件 → 父页 → `/api/data/costs`」这条链上凑不齐，且 `mode` 字段已落地类型里没有（阻塞 2）；
3. `catchUpMs` 在 L180 与 L182 被定义了两次且互不兼容，K2 拿它做判定会系统性高估（阻塞 3）；
4. K1 显式写 `pinnedHeavy: false` 与已落地代码里「人工钉死」的语义冲突（阻塞 4）；
5. K4「一拍不足 1/fps 就等到整拍」只给了 `__pcRealRaf` 一条机制，等不满一拍（阻塞 5）；
6. `ProbeGate` 拿不到「`back` 就绪」这个信号——`Preview.tsx:81` 的 `stageReady` 是组件内部 state（阻塞 6）；
7. K5 第一路只改了三支传 `t` 的表达式，漏了图卡那一支，与 E7 的口径不一致（阻塞 7，manager 补）；
8. 探针把 `back` 换成缩水项目时绕过了 `stageBridge` 的基线，之后 D4 的 `syncProject(back, …)` 会静默不发（阻塞 8，manager 补）。

## 2. 阻塞项

### 1. K6 降级更新记录违背完整性校验且丢失已有数据
- **L199 摘要**：要求父页把 `{ frameMs: null, catchUpMs: null, capped: true, demoted: true }` 写回 `costs`，并称「只覆盖这四项，`vtOk` / `seekOk` 等保留」。
- **证据**：`server/costs-store.mjs:72-93` 的 `mergeCosts` 使用 `next = { ...record }`，这意味着如果不传完整对象，旧的 `vtOk` / `seekOk` 等字段会被**直接丢弃**。同时，`validRecord` (`:44-49`) 要求记录必须包含 `identityKey` 和 `device`，而 K6 的 `{ type: 'demote', clipId }` 并没有提供这些信息。此外，`CardCostRecord` (`cardCostKey.d.mts:8-12`) 定义 `frameMs` 和 `catchUpMs` 为 `number`，传 `null` 将报 TS 类型错误。
- **改法**：父页收到 `demote` 时，必须通过 `clipId` 查出完整的旧记录，在此基础上合成带有 `identityKey` 和 `device` 的全量记录，并将 `frameMs` / `catchUpMs` 置为合法数字或修改 TS 接口定义，最后才通过全量 PUT 提交到接口。

### 2. K1 探针事件漏传关键字段与 `mode` 定义缺失
- **L186 摘要**：要求写回 `{ identityKey, fps, frameMs, stepMs, catchUpMs, capped?, kind, vtOk, seekOk, seekMs, measuredAt, device, mode: 'dev' | 'build', demoted: false, pinnedHeavy: false }`，并要求父页把探针结果「转发到 `/api/data/costs`」。
- **证据**：`StageEvent` 里的 `{ type: "probe" }`（`stageRpc.ts:128`）**不包含** `device`、`measuredAt`、`mode`、`demoted`、`pinnedHeavy`。此外，`CardCostRecord` 类型定义中**根本不存在** `mode` 字段。
- **改法**：父页不能只做「转发」。`{ type: 'probe' }` 收到后由父页补齐 `device`（它本来就按 L186 的口径算 `device`）、`measuredAt`，并显式附加 `demoted: false`，再整条 PUT。`mode: 'dev' | 'build'` **不能删**——L18 明写「3b 步之后在 `vite preview` 的构建产物上重跑、记录带 `mode: 'build'` 才算数」，正确改法是给 `src/render/cardCostKey.d.mts` 的 `CardCostRecord` 补 `mode: 'dev' | 'build'` 字段，并在 L186 里写明这一项由父页按当前运行模式填、舞台不报。

### 3. `catchUpMs` 包含冻结时间的自相矛盾
- **L180 摘要**：`catchUpMs = 从第 0 帧冲到最后一帧的总帧数 × 不含冻结的单帧 stepMs`。
- **L182 摘要**：`catchUpMs = 实测总时间`（而 L182 的测量过程是“每帧推 + 冻结本控件 HTML”）。
- **证据**：如果在第一趟测试中每帧都冻结 HTML，`实测总时间` 将大幅包含 HTML 冻结耗时（比如每帧多 5ms），而 L180 明确要求“不含冻结”。这将导致 K2 (`L190`) 里的公式 `catchUpMs / (CATCHUP_STEPS_PER_BEAT × stepMs) ≤ MAX_CATCHUP_BEATS` 被严重高估，把轻卡误判为重卡。
- **改法**：L182 里的 `catchUpMs` 必须通过 `总时间 - (单帧冻结耗时 × 帧数)` 来修正，或者直接统一改为 L180 的乘法预估公式。

### 4. K1 探针覆盖人工钉死标志 (`pinnedHeavy`)
- **L186 摘要**：“探针写回时显式带 demoted: false / pinnedHeavy: false”。
- **证据**：`costs-store.mjs:18` 规定 `pinnedHeavy` 是“人工钉死”；如果探针显式回传 `pinnedHeavy: false`，下次打开项目时任何触发探针的操作都会无意中洗掉用户的永久钉死设置。
- **改法**：K1 写回时只显式带 `demoted: false`，**禁止带** `pinnedHeavy: false`。K6 `L199` 判定单调性时应改为“见到 `demoted` 或 `pinnedHeavy` 均当做 `capped`”，降级时仅写入 `demoted: true`。

### 5. K4 节拍器帧率对齐错误 (30fps 项目跑在 60Hz 屏幕上)
- **L194 摘要**：“封顶项目 fps (一拍不足 1/fps 就等到整拍)... 用 `window.__pcRealRaf` 等真实一帧”。
- **证据**：`requestAnimationFrame` 回调的间隔是屏幕物理刷新率。对于 60Hz 屏幕，一次 `__pcRealRaf` 只等待 16.6ms。如果项目是 30fps，一帧需要 33.3ms。单次 `__pcRealRaf` 结束后时间不足一拍，会导致舞台跑得比预期的 30fps 快得多，或者产生逻辑死锁。
- **改法**：使用 `while (now - last < 1000/fps)` 配合多次 `__pcRealRaf`，或者使用真实的 `setTimeout` 兜底。

### 6. `ProbeGate` 获取 `back` 舞台的时序断层
- **L180 摘要**：`ProbeGate.tsx` 遮罩需要等 `back` 就绪后发 `setRole('back', { job: 'probe' })`。
- **证据**：`ProbeGate` 是与 `Preview` 同级渲染的，而 `src/editor/stageBridge.ts` 导出的 `backStage()` 并不会派发任何 “ready” 事件。`ProbeGate` 无法在不违背 React 反模式的情况下主动侦听 `back` iframe 的加载完成事件。
- **改法**：在 `stageBridge.ts` 中增加对 `StageReady` 事件的订阅派发机制，或者将探针队列驱动逻辑下放到 `Preview` 内部。

### 7. K5 第一路只改三支传 `t` 的表达式，漏了图卡那一支（manager 补）
- **L196 原句**：「`Stage.tsx:169` / `:175` / `:177` 三支传 `t` 的表达式对 `settling` 里的片段改读 `settling.get(clip.id) / 1000`」
- **证据**：`src/kernel/Stage.tsx` 里传 `t` 给组件的一共是**四支**——`:169` `<PartTree … t={Math.max(0, t - clip.start)} …>`、`:172-173` `<GraphCard … t={Math.max(0, cardT - clip.start)} …>`、`:175` `<DirectCard … t={Math.max(0, cardT - clip.start)} …>`、`:177` `<C … t={Math.max(0, cardT - clip.start)} …>`。同一件事在 E7 的 **L171** 里是写全了的：「…`Stage.tsx:169`（组合卡，`t - clip.start`）/ `:175` / `:177`…（…；H3 插的图卡那一支同样冻）」。K5 这一路没有这句。
- **后果**：图卡（H，按 L179「同样按实测分派」，可以是 `vtOk` 的重卡）进 `.pc-settling` 之后，它的 `t` 仍读全局，子树虚拟时间推不动它；而 `.pc-settling` 又把子树 `visibility: hidden` 掉，快照平面摘掉那一刻画面直接跳变。照 L196 逐字实现必然做错。
- **改法**：把 L196 那句改成「`Stage.tsx:169` / `:173`（图卡）/ `:175` / `:177` 四支传 `t` 的表达式对 `settling` 里的片段改读 `settling.get(clip.id) / 1000`」，并照 L171 的写法补一句「H3 插的图卡那一支同样改」。

### 8. 探针换缩水项目绕过 `stageBridge` 基线，`back` 会卡在缩水项目上（manager 补）
- **L185 原句**：「探针先用 `setProject(full, { reset: true })` 把后台舞台的项目换成只含该片段的缩水项目…**探针期间 `back` 的项目由探针独占**：父页的常规 `setProject`（`Preview.tsx:367` 那处广播）只发 `front`」
- **证据**：`src/editor/stageBridge.ts:65-84` 的 `syncProject` 按 iframe 记「上次推过的项目」基线，`:70` `if (slot.pushed === project) return;`、`:79` `slot.pushed = project;`。探针直接对 RPC 客户端发 `setProject(缩水)`，不经 `syncProject`，所以 `slots.back.pushed` 仍指着上一次推过去的整份项目对象。D4 的页面侧测量走的就是 `syncProject(backRole(), …)`（`src/editor/right/index.tsx:94`），探针结束后它拿同一个项目对象再调一次会在 `:70` 直接短路、一个字节都不发，`back` 就一直停在只有一个片段的缩水项目上——测出的 `rectsWithBounds` 少掉其余全部卡片，且不报错。这正是 L185 自己警告过的「测出的数被污染且不报错」，只是方向相反。
- **改法**：在 L185 里补一句「探针每次换缩水项目、以及探针结束恢复整份项目时，都要把 `stageBridge` 里 `back` 的基线作废（`setStageClient('back', 同一个 client)` 不行，它只在客户端换了才清；需要给 `stageBridge.ts` 加一个 `invalidatePushed(role)` 导出，探针前后各调一次），否则 D4 的 `syncProject(backRole(), …)` 会在 `stageBridge.ts:70` 短路」。

### 3. K2 的贪心与验收算例：已核，无问题（manager 复核）
- 按 L190 的停止条件 `Σ w(已入轻管线的卡, P) + 重卡数 × DEAD_MS > B` 独立重算了 L200 的四个算例：10 张 direct 卡（1/1/2/2/3/5/8/13/21/34 ms，fps 30，B = 23.3）前 7 张 Σw = 22、剩 3 张重卡 × 0.3 = 0.9、合计 22.9 ≤ 23.3，加第 8 张 Σw = 35 必超 —— 对；6 秒 / `stepMs` 1 ms 的 Motion 卡 `catchUpMs` = 180 ms、180 /(4 × 1) = 45 拍 ≤ `MAX_CATCHUP_BEATS` = 2 × 30 = 60，`w` = 5 ms —— 对；同卡改 10 秒 = 300 ms、300 / 4 = 75 > 60 判重 —— 对；同位置 5 张 `w` = 5 ms 的 (b) 档卡，4 张 Σw = 20 + 1 × 0.3 = 20.3 ≤ 23.3、第 5 张 25 > 23.3 —— 对。「每拍多推 4 步、2 秒内追完」与 `MAX_CATCHUP_BEATS = 2 × fps` 自洽（追帧时播放头也走 1 帧，净增 4 步/拍）。
- 唯一的前提是阻塞 3：这些算例都靠「本用例取冻结成本 0 以便对数」才成立，`catchUpMs` 的口径不统一时真实项目上算不出同一张表。

### 4. K4 播放到头的收尾与 E0 的规定不一致（manager 补）
- **L194 原句**：「父页收到调 `actions.pause()` + `actions.seek(duration)`（`Preview.tsx:145-149` 的逻辑搬到这里…）」
- **冲突处 L158 原句**：「`{ type: 'ended', sec }`（K4 播放到头：舞台停在最后一拍、不再 post；父页收到后走和按暂停一样的收尾——`pause()` 拿 `stoppedAt`、`setPlaying(false)`、`setTime(stoppedAt, { settle: true })` 进 K5，最后一帧的重卡从 `suppressed` 追到精确活渲，pinned 架构 9）」
- **后果**：照 K4 逐字写，`ended` 之后只动 store，不发 `setPlaying(false)` / `setTime(stoppedAt, { settle: true })`，最后一帧的重卡永远留在 `suppressed`（子树被藏、`t` 冻住），播完停在那里就是一层透明或一张旧流帧，违背 pinned 架构 9「暂停时使用活渲染」。另外 E0 说舞台「停在最后一拍、不再 post」，此时父页再发 `pause()` 拿 `stoppedAt` 是对一个已经停了的循环发的，K4 的 `pause()` 定义（「本拍走完、post 完这一拍的 `frame` 后停」）没有覆盖这种情形，回不回包、回什么没写。
- **改法**：把 L194「父页收到调 `actions.pause()` + `actions.seek(duration)`」改成「父页收到后按 E0 的收尾做：`actions.pause()` + `actions.seek(duration)` 写 store，同时发 `setPlaying(false)`、发 `pause()` 拿 `stoppedAt`（舞台已停时直接回最后一拍的 `sec`，不等新拍）、再 `setTime(stoppedAt, { settle: true })` 进 K5」，并在 E0 的 `pause()` 定义里补「循环已停时立即回 `{ ok: true, stoppedAt: 最后一拍的 sec }`」。

### 5. K4 的 `mediaStalled` 通道：`setPlaying(false)` 与循环查 `paused` 语义打架，且没有携带拍长的信号（manager 补）
- **L194 原句**：「父页维护 `mediaStalled` 状态，`MediaLayers` 的 `playing` prop 改成 `playing && !mediaStalled`（`Preview.tsx:597`），舞台侧经 `setPlaying(false)` 同步」；同段前文「可见舞台自己循环（每拍开头和 post `frame` 之前查 `paused` / 角色，E0）」
- **证据**：`src/render/stageRpc.ts:116` `setPlaying(on: boolean): Promise<{ ok: true }>;` 与 `:111` `play(fromSec: number)` / `:112` `pause(opts?: { atSec?: number })` 是三个独立方法，任务书没写 `setPlaying(false)` 与循环查的那个 `paused` 是不是同一位。若是同一位，卡一拍就把 K4 的节拍循环整个停掉、再也不会自己恢复（`mediaStalled` 置回 false 时没有任何人重发 `play`）；若不是同一位，舞台里就有两个「在不在播」的状态，E7 传给 `VideoTrack` 的 `playing` prop 该读哪个也没写。
- **另**：七种 `StageEvent`（`stageRpc.ts:123-130`）里没有任何一条带拍长，`{ type: 'frame', sec }` 只有时刻。父页要判「这一拍超过 40 ms」只能自己量两条 `frame` 的到达间隔（含 postMessage 延迟），任务书没写这一点，也没写首拍怎么判。
- **改法**：在 L194 里写死「`setPlaying(on)` 只管素材层（`VideoTrack` / 音频），**不碰** K4 循环的 `paused`；循环只由 `play` / `pause` / `setRole('back')` 起停」，并补一句「父页用 `__pcRealNow` 量相邻两条 `frame` 的到达间隔判 40 ms，首拍以 `play()` 返回时刻为起点」。

## 2. 阻塞项
1. `/api/cards/layout` 参数与 Agent 环境版本轴脱节
   - 行号与原句：L142 `body { session, localRev, t, clipIds }`
   - 证据：L142 规定传入 `session` 和 `localRev`，但依据 L73，它们专属于浏览器页面的镜像插件概念。根据 L139 和 L125，Agent 服务端作为客户端只维护 `projectRev`；且 L372 说明了 `agent` 模式预渲染进程直接接收整份项目。Agent 侧根本无法提供 `session` 和 `localRev` 供该接口使用，造成接口参数要求与调用方环境成环死锁。
   - 建议改法：将 L142 的 body 修改为 `{ projectRev, t, clipIds }`，并在预渲染侧或 Agent 端对齐项目版本。
2. 项目 JSON 层面的操作覆盖备份与通知机制缺失
   - 行号与原句：L123 `复用 edit_card 的备份机制`；L124 `每张卡记最近 10 个 cardRev`；L125 `写工具带期望版本、expectedVersion = projectRev`
   - 证据：B4 (L125) 中明确了项目操作级别（如 `add_clip`）会受 `projectRev` 管控并在覆盖时拒绝，但 B2 和 B3 关于备份与通知的全部内容均只定义了基于「卡」和 `cardRev` 的机制。导致当项目 JSON 修改被覆盖或拒绝时，系统没有任何对应的备份或通知下发策略。
   - 建议改法：在 L123 补充项目 JSON 被覆盖时的备份存盘路径；在 L124 补充项目操作冲突时的通知对象列表及内容格式。
3. D2 操作级事件的推送方定义矛盾
   - 行号与原句：L69 `向页面推操作级事件`；L120 `D2 的操作级事件都从这条连接推下来`；L66 `操作级事件（D2）`
   - 证据：L120 明确规定统一由文档服务的 WebSocket 下发 D2 事件，L66 同样将此划为文档服务职责。但 L69 却将“向页面推操作级事件”指派给了 Agent 服务端，造成架构数据流推向来源互相矛盾。
   - 建议改法：修改 L69，删除 "向页面推操作级事件"（由 Agent 服务端推给文档服务，再由文档服务统一下发给页面）。
4. 缺少按事件 ID 拉取工具完整参数的接口定义
   - 行号与原句：L140 `完整参数展开时按事件 id 拉。`
   - 证据：在 L140 及 B 节上下文中，仅提出按 ID 拉取数据的要求，但完全未给出具体接口定义（缺失 HTTP 端点或 WebSocket 消息标识、请求体及返回体形状）。
   - 建议改法：在 L140 补充拉取接口："（接口：GET `/api/events/:id` 或通过 WebSocket 发送 `get_event_detail` 消息，返回完整 JSON）。"
5. `message_ignore` 缺少接口与参数规范
   - 行号与原句：L124 `退出跟踪：message_ignore(cardId)`
   - 证据：未在全文定义 `message_ignore` 的接口形态。若为 Agent 工具，未在 `MIRRORED_TOOLS` 等列表声明；若为 WebSocket 消息，也未给出协议端点。
   - 建议改法：在 L124 明确说明："（Agent 可调用新增写工具 `message_ignore({ cardId })`，或人类客户端通过对应 WebSocket 消息触发）。"

## 3. 非阻塞项
1. B3 通知内容缺少已约定的备份路径字段
   - 行号与原句：L124 `相对那版的 diff 摘要`
   - 证据：L123 明确规定 "通知里附路径"，但 L124 罗列接收方收到的具体字段时并未包含备份路径。
   - 建议改法：在 L124 的通知内容里补充："、备份文件路径"。
2. B2 中「云端版本」的用词与本地模式架构矛盾
   - 行号与原句：L123 `换成云端版本前`
   - 证据：依据 pinned 架构 2 及 L307 总验收，系统有完全断网的本地模式；此时的冲突版本来源于本机文档服务，并不存在“云端版本”。
   - 建议改法：将 L123 中的 "云端版本" 改为 "服务端最新版本"。
3. 熔断机制中被锁方的写权限覆盖描述不一致
   - 行号与原句：L127 `被锁方 edit_card 收拒绝并附最后 6 次改动`
   - 证据：该条前半句说是锁“写权限”（理应涵盖所有写入该卡的工具），后半句举例却只点名 `edit_card` 收拒绝，范围遗漏产生歧义。
   - 建议改法：将 L127 修改为 "被锁方对该卡的所有写操作（如 edit_card、set_position 等）均收拒绝并附最后 6 次改动"。
4. `MIRRORED_TOOLS` 缺乏明确定义
   - 行号与原句：L142 `进 MIRRORED_TOOLS`
   - 证据：全文并未给出 `MIRRORED_TOOLS` 的清单或语义定义，将 `get_layout` 这个纯读取工具列入具有镜像写暗示的列表中易引起混淆。
   - 建议改法：在 L142 补充简短定义："（该表指代需交由 Agent 服务端拦截处理的工具列表）"。
5. 留在页面的工具缺乏明确清单
   - 行号与原句：L139 `只有必须在页面里做的工具留在页面。`
   - 证据：并未提供具体清单或判别示例，会导致服务端拆分开发时的边界模糊。
   - 建议改法：在 L139 附上示例说明："（如强依赖本地 UI 环境的工具）"。
6. 锁状态的崩溃恢复持久化未写明
   - 行号与原句：L66 `崩溃恢复用`
   - 证据：L66 点出操作日志用于崩溃恢复，但未说明 L127 中产生的锁状态是否会随操作记录一并持久化到该 ndjson 日志中，抑或仅存内存。
   - 建议改法：在 L66 明确写出："锁状态变更也记入操作日志持久化"。
7. 总验收 B 里的版本轴指代不明
   - 行号与原句：L322 `A 写 v5、B 写 v6、C 写 v7... 收到 v7 通知`
   - 证据：此处仅以 v5、v6 称呼，未严谨说明其对应的是 `projectRev` 还是 `cardRev`，凭 B3 只能模糊推理为 `cardRev`。
   - 建议改法：将 L322 修改为 "A 写 cardRev v5..."。
8. `/api/cards/layout` 的模式归属矛盾且被误标为新端点
   - 行号与原句：L76 `以上是 user 模式`；L142 `新端点 / user 模式回 503`
   - 证据：L76 将其归于 `user` 模式，L142 却说 `user 模式回 503`；另外 L376 称 `user` 模式不建 `agent` lane，而 L16 却说此端点借 `agent` lane 且已落地。L142 将其称为 "新端点" 与 L16 的已落地相矛盾。虽然描述互相打架，但端点主体已被确认。
   - 建议改法：修改 L76 将该接口移至 `agent`/`full` 模式；删除 L142 的 "新端点" 三字。

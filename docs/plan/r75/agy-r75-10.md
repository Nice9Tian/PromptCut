# 第 75 轮 · 第 10 份：第 9 + 10 步：F1 / F3 / F4、目标 L（在线浏览器模式）

## 1. 结论
不能直接动工；需补充本地内容库的回收策略、修改模式切换导致的历史覆盖缺陷，以及纠正浏览器模式下离线落盘和 canvas 重卡活渲与硬约束之间的矛盾。

## 2. 阻塞项
### 浏览器模式下离线素材导入与交换缺失本地存储
- **行号与原句**：L206 `素材：离线导入只落本地内容库，恢复后补传；` 以及 `离线交换只靠 .procp。`
- **证据**：与 L272 `在线浏览器模式...只有页面...素材直接打素材云端` 冲突。另据 L71 `.procp...导入 = 解包进本地内容库`。在线浏览器模式没有本地文件系统，无法进行离线落盘和解包操作。
- **建议改法**：在 L206 末尾补充 `（明确在线浏览器模式不支持离线素材导入与 .procp 交换，相关菜单置灰或抛错）`。

### 本地内容库缺失 GC 回收口径
- **行号与原句**：L204 `GC 只扫 this.root 直接子项，跳过 controls、controls-html...其余 hex 目录按 mtime 保留 7 天`
- **证据**：L204 只规定了直接子项下的 hex 目录和五个共享目录的回收，没说真正的素材存储处（本地内容库）由谁回收、按什么策略。根据组件表 L70 现状列 `out/media` 按文件名（目标形状是「按哈希存素材字节」），云端模式下它是素材云端的本地缓存兼上传队列，缓存必须要有明确的回收与淘汰口径。
- **建议改法**：在 L204 末尾补一句本地内容库（如 `out/media` 或直接存哈希的文件）的具体回收与 LRU 淘汰规则。

### 模式切换中 projectRev 强制清零可能覆盖云端已有项目
- **行号与原句**：L208 `本地 → 云端：项目整份推到文档云端（projectRev 从 0 起）后立刻标成云端模式；`
- **证据**：与 L208 后文的 `云端 → 本地：... projectRev 续用` 形成自相矛盾。若云端项目拉到本地后再推回云端，强制清零将破坏云端已有的版本历史。
- **建议改法**：将 L208 改为 `本地 → 云端：若首次上云则 projectRev 从 0 起，若已关联云端项目则用 expectedVersion 检测冲突再推整份；`。

### 浏览器模式下 canvas 重卡未走快照，导致卡顿违背不做清单与硬约束
- **行号与原句**：L277 `只有 DOM 重卡按拍换 HTML 快照（canvas 卡在在线浏览器模式下不按拍换快照...它是活渲的）`
- **证据**：违背不做清单 L400 `该位置判重的卡在播放或拖动中活跑`（被列在不做清单代表禁止该行为）；且与 L195 `每张当前位置判重的卡在可见舞台里处于三种状态之一` 冲突（L195 的三态是「播放中 = `suppressed`」「拖动中或 settle 未完成 = `snapshots`」「settled = 活渲」——活渲只属于暂停 settled 态，播放与拖动中判重卡不得活渲；**此括号由 manager 更正**，agy 原文把三态写成「suppressed、snapshots、透明」有误）。旁证：pinned 渲染 10 提及了 `canvas 已栅格成带实体框的 img` 作为快照形式，canvas 的快照形态是存在的。
- **建议改法**：将 L277 改为 `重卡按拍换 HTML 快照（包含 DOM 重卡与 rasterized 的 canvas 重卡图像，SWAP_MS 预算均算），装不下的重卡透明；`，删除例外说明。

## 3. 非阻塞项
### L 的验收未包含 L365/L366 要求的断言
- **行号与原句**：L279 `验收：纯浏览器（没有本机进程）打开一个含 3 张重 Motion 卡的云端项目...`
- **证据**：不做清单中 L365 与 L366 明确要求「L 的验收加一条断言这个提示 / 这个报错」，但 L279 的验收条目中遗漏了这两项断言，导致验收条件不全。
- **建议改法**：在 L279 末尾补上对相应菜单提示及报错的断言。

### 浏览器模式快照键含斜杠可能带来的定界歧义
- **行号与原句**：L275 `snapshots（key = <kind>/<key>/<localFrame>，值 = deflate 后的 HTML）`
- **证据**：L266 写明 `kind` 为 `local` 时 `key` 自带一个斜杠（`<entry.key>/<共享键>`）。按 L275 拼接后会产生三个斜杠，引发与框架截断解析 `localFrame` 时的定界歧义。
- **建议改法**：建议在 L275 中明确对 key 进行 URL 编码，或采用数组等复合键结构以规避斜杠分割问题。

### 云端快照下载后未显式触发就绪订阅
- **行号与原句**：L276 `缺的块从素材云端拉...写进 L2、ranges 立即就绪`
- **证据**：L275 规定 `subscribeReady 由 L1 的写入直接触发`，未覆盖 L3 (L276) 下载落盘导致数据就绪的情况，会导致可见舞台未能及时得到素材更新通知。
- **建议改法**：在 L275 的 `subscribeReady` 触发条件中加入 `L3 下载落盘`。

### 实测换帧成本替换标量预算的维度不匹配
- **行号与原句**：L277 `每拍换帧的实测成本代替 K2 的 DEAD_MS 进预算`
- **证据**：L188 中 `DEAD_MS` 为全局固定标量（0.3），而在 K2 传参时 (`opts.deadMs`) 也只接收单个标量，且 L186 的 `costs` 记录中并没有用于记录单卡换帧成本的字段。每张卡独立的实测替换标量预算在类型及接口上均不成立。
- **建议改法**：修改 L277 和 `planPipelines`，以明确是否取多卡的保守峰值作为新的 `deadMs` 整体传入，或扩展成本表结构。

### StreamSource 接口缺失签名定义
- **行号与原句**：L278 `照 J3 的思路把取流抽成 StreamSource 接口`
- **证据**：J3 (L266) 中只详尽给出了 `SnapshotSource` 的接口签名定义，整个任务书中并未给出 `StreamSource` 的具体类型或方法签名。
- **建议改法**：在 L278 中补全 `StreamSource` 的确切 TS 接口声明。

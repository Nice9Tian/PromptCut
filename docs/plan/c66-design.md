## 1. 目标

1. **两档**：导入视频时，导入方本机生成素材小尺寸（800×600 以内的 H.264）；素材原尺寸保持原编码，缺 faststart 的只做重封装。两档都经素材服务入库。
2. **上传队列**：逐个素材上传，同一素材先小后大，两档都 `complete` 才轮到下一个；在后台、低优先级进行，不挡编辑。
3. **拉取与换档**：另一端打开项目，先拉素材小尺寸显示，素材原尺寸到了再换素材原尺寸。换档时画面不跳、播放位置不变。素材原尺寸是浏览器放不了的编码时，预览一直用素材小尺寸。
4. **导出只用素材原尺寸**：素材原尺寸还没到时提示「等待上传方」，不拿素材小尺寸代替。
5. **卡片源码同步**：用户卡、改过的卡的源码经内容库（`card-source`）同步，另一端打开项目时自动装上，版本号是 `cardRev`。

## 2. 两档的生成〔按 A1 原文〕

- **素材小尺寸**：等比缩到 800×600 以内，H.264，`-preset veryfast -crf 26`，帧率跟素材原尺寸、上限 60，AAC 64k，`-movflags +faststart`。
- **素材原尺寸**：不转码；没有 faststart 的做一次 `-c copy -movflags +faststart` 重封装。重封装的结果算作新的素材原尺寸，按它的哈希入库〔裁：重封装只挪 moov 的位置，编码不变，导出像素不受影响〕。
- **在哪生成**：导入方本机的编辑器进程，用 `findFfmpeg`。素材服务从不转码。在线浏览器模式导入的素材只有素材原尺寸一档（C10）。
- **只对视频做**：图片、音频不生成素材小尺寸。
- **项目里的记录**：`project.media[i].tiers = { small?: <哈希>, original: <哈希> }`。同步状态（传没传完）不进项目，只问素材服务的 `chunks`。

## 3. 上传队列

- 编辑器进程里一个持久队列 `upload-queue.json`，放在本机数据目录，重启后续传。
  - 顺序：逐个素材，先素材小尺寸、再素材原尺寸；
  - 每一档按分片上传，断了只补缺的分片；
  - 两档都 `complete` 才出队。
- 连本地素材服务时，入库就是本地写入，队列是空操作，但素材小尺寸照样生成。
- 共享项目连的是远端素材服务（托管端或局域网主机），上传要带素材票据（M6a）。
- 优先级低：不占用户交互的帧请求；和预渲染产物的推送队列（C6.4 的 A5）共用一个带宽闸，素材排在产物后面〔裁：别人能早点看到预渲染结果，比早点拿到素材原尺寸更要紧；素材小尺寸本来就先走〕。

## 4. 拉取、预取与换档

- **按需拉取**：本地素材服务的读路由在本地内容库里找不到时，向当前连接的远端素材服务流式拉取，边落盘边按 Range 服务。都找不到才回 404。
- **预取队列**：打开项目后，按片段在时间轴上的先后，把引用到的哈希先小后大地拉进本地内容库。
- **页面换档**：
  - 页面上每个视频层先挂素材小尺寸（有的话）。
  - 每 2 秒问一次当前素材服务的 `GET media/<素材原尺寸哈希>/chunks`，`complete` 翻真之后，下一次轮询里换素材原尺寸。
  - 换档用双缓冲：在后台 `<video>` 上挂素材原尺寸，seek 到当前时刻、等 `seeked` 与首帧之后再对调，所以画面不跳、`currentTime` 不变。
- **可播性**：按 A1 原文，本机先 `canPlayType`、再试放首帧。结论按哈希存设备本地缓存（`src/render/playability.ts`），不进项目。判为放不了的素材原尺寸，这台设备上预览永远停在素材小尺寸。
- **导出**：只用素材原尺寸。素材原尺寸在当前素材服务上不 `complete`，导出前拦下，提示「等待上传方」，列出缺的素材。

## 5. 卡片源码同步（A6）

- **写**：
  - 卡片文件每次保存（`edit_card`、`create_card`、安装）后，编辑器进程把源码 `content.put({ kind: 'card-source', key: <仓库相对路径>, body })` 写进当前项目空间的内容库，拿到新的 `cardRev`；
  - 本机记下「这个文件上次同步到的 `cardRev` 与内容哈希」。
- **读**：
  - 加入共享项目时，经 `content.list('card-source')` 列出源码；
  - 本机没有这个文件，或者本机文件没改过而服务上的 `cardRev` 更新了，就拉下来装上（走现有的 `/api/cards/install` 路径，装进改动层，不碰仓库里的原卡）；
  - 本机改过、服务上也改过，就是「最后写的赢」：本机先备份自己那份，再装服务上的，并给出覆盖提示（语义「冲突」）。
  - 服务上的新版覆盖的是本机写过的那一版时，同样先备份再装、给提示（第 9 节第 4 条）。
- **订阅**：`content.watch('card-source')`，别人改了卡就按上面的规则当场同步。卡换了代码，按现有规则重测、重排预渲染。现有代码里「卡片代码变了、项目没变」不触发重测，所以卡片代码变了（同步装上或本机改卡）要由页面显式触发这张卡的重测，随后照现有规则重排预渲染（第 9 节第 5 条）。
- **本机项目**（`local` 空间）：同步那一半是空操作，但 `cardRev` 照常自增，版本轴照有。
- **范围**：只同步用户卡和改过的内置卡（改动层里有的）；未改的内置卡两端都有，不同步〔裁〕。

## 8. 查资料的结论（codex，`gpt-6-sol` / `high`；原文在 scratchpad 的 `research-c66.md`）

| 题 | 结论 | 怎么用 |
|---|---|---|
| 素材小尺寸命令 | 保留 VFR 时间戳，只丢间隔不足 1/60 s 的帧（`select` 滤镜）；`scale` 不放大、保持比例、限 800×600、偶数尺寸；`-map 0:a:0?` 容忍无音轨；`-autorotate` 让旋转落进像素；HDR（BT.2020/PQ）走 `zscale` + `tonemap` 分支 | **采纳**，照原文命令实现；HDR 分支只对有正确标签的源启用，其余照 SDR 走〔裁〕 |
| faststart 判定 | ffprobe 没有现成字段；按 ISO BMFF 顶层 box 逐个跳读、比较首个 `moov` 与 `mdat` 的位置；MKV、AVI 不需要；重封装失败就保留源文件 | **采纳** |
| 可播性 | 按实际容器选 MIME；codecs 串拿不全就交给试放；`canPlayType` 回空直接判不支持，否则等 `loadeddata` 加帧回调确认；本地 5 s、远端 10 s 超时，超时记「未知、稍后重试」；缓存键加浏览器主版本 | **采纳** |
| 无缝换档 | 后台静音加载素材原尺寸，播放中再校正一次时间，比较帧回调的 `mediaTime`，容差一帧，一次合成里对调；不用 `fastSeek`；音频先留在素材小尺寸、对齐后再切，或用 20～50 ms 交叉淡变；限制同时预热的层数 | **采纳**；T5 的验收口径按此改 |
| 测试素材 | ProRes MOV 与晚置 moov 的 MP4 的生成命令 | **采纳**，测试时现场生成 |

## 9. 集成裁定（2026-09-27，主会话）

四个子分支的报告（`AGENT-c66-tiers`、`AGENT-c66-fetch`、`AGENT-c66-cards`、`AGENT-c66-tests`）提出的歧义与偏差，集成分支 `claude/c66-integ` 按下面落实。标〔裁〕的是主会话自行定的，理由写在同一条里。

**要集成方补做的**：

1. **页面把共享项目的素材服务交给上传队列**〔裁〕：页面进入共享项目时，把远端素材服务基址和一张 `rw` 素材票据经 `POST /api/media/upload-queue/target { base, ticket }` 交给编辑器进程，票据剩 1/3 有效期时续上（与主执行计划 12.2 节「素材票据」一致），离开共享项目时 `POST { base: null }`。理由：编辑器进程没有自己的项目凭证，页面手里有连接、能签票据，是最直接的来源（`AGENT-c66-tiers` 第 5 节第 3 条）。没有页面时不传（同节第 4 条），以后需要再接。
2. **打开项目时补转素材小尺寸**〔裁〕：桌面版打开项目时，对缺 `tiers.small`、本地有素材原尺寸的视频，交给两档管理器在后台补转，好了补写 `tiers.small`；页面不在时下次打开再补。`.procp` 还原的素材也由这条补上小尺寸，还原本身仍不重封装（哈希不变）。理由：页面在小尺寸好之前关掉时，项目里不会有 `tiers.small`（同报告第 5 节第 2 条、第 4 节第 5 条），而语义说小尺寸可再生。
3. **服务端导出拦截**〔裁〕：预渲染进程的 `/api/export`（`handleExportStart`）开头按当前素材服务核对被片段引用的素材原尺寸，缺就回 409 `awaiting-uploader` 并列出缺的素材；页面上的两处拦截保留。理由：Agent 或脚本直接打 `/api/export` 时也要拦（`AGENT-c66-fetch` 第 4 节第 2 条）。
4. **被覆盖时也先备份**：第 5 节「读」已补一句。服务上的新版覆盖的是本机写过的那一版时，同样先备份再装、给提示（`c66-cards` 的 T8-7、`AGENT-c66-tests` 歧义 1）。
5. **卡片代码变了显式触发重测**：第 5 节「订阅」已补一句（`AGENT-c66-cards` 第 5 节；codex 攻坚按此修 `b-no-remeasure`）。
6. **`c66-kit.mjs` 对账**：按实际模块名改 K1～K5，用例本身尽量不动；改了用例的，逐条写进集成报告。
7. 跑 G0 与 G0-R。

**认可子分支的做法**〔裁〕（理由各在对应报告里，这里只列结论）：

- `c66-tiers`（报告第 4 节）：
  - 丢帧判据加 0.2 ms 容差；
  - HDR 分支给 `zscale` 显式输入参数，本机 ffmpeg 没有 `zscale` / `tonemap` 时 PQ 源不生成小尺寸；第 2、8 节的小尺寸命令按这两条理解；
  - 重封装在导入请求里同步做，小尺寸在后台转；重封装前那份只删这次导入刚写进库的；
  - 只有 `?tiers=1` 的导入才做两档；
  - 目标是本机素材服务时，上传队列暂停、不丢；严格按序；跨进程带宽闸读 `push-queue.json`；
  - `upload-queue.json` 与 `tiers.json` 放在本地内容库所在的 `out/` 下；
  - 转码并发 1，低于正常优先级。
- `c66-fetch`（报告第 3 节）：
  - MOV 的 `canPlayType` 按 `video/mp4` 问，放不了的 ProRes 由试放判出；
  - 「还没问过 → 有小尺寸给小尺寸」；
  - 预取先全部小尺寸、再全部原尺寸；
  - 播放中音频先留在上一档，停下再换；
  - 「等待上传方」加角标；页面导出拦截两处；
  - 载入别的项目时清掉当前远程素材服务；
  - 可播性探测的离屏 `<video>` 挂进文档。
- `c66-tests`（报告「歧义与更正建议」）：
  - 超时回 `undefined` 或 `null`，不落「放不了」，下次调用重试；
  - 「远端」按绝对 http(s) 地址判；
  - 导出拦截只看被片段引用、带哈希的素材（没有哈希的老素材只可能在本机，不拦）；
  - 音频不重封装、没有小尺寸。

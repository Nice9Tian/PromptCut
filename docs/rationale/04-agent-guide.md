# Agent 指南：为什么这样定

对应 `docs/semantics/04-agent-guide.md` 和 `docs/semantics/agent/`。这里只写理由和取舍，不是规范。

## 为什么是闭环

目的只有一个：用户和 Agent 的协作必须形成闭环。对齐保证做的是用户要的东西；验证保证做完了、而且没把项目弄坏；汇报和用户决定保证结果由用户确认。少了任何一环，都会出现 Agent 自己宣布完成、用户事后才发现不对的情况。

## 为什么 `/goal` 达成不等于任务结束

`/goal` 的完成与否由另一个小模型判定，它只读对话、不自己运行命令。它能确认条件在对话里被证明了，不能代替用户决定是否合并。所以验证的证据必须出现在对话里，而 `/goal` 达成之后，汇报和用户决定照常进行。

## 为什么改动在专用 worktree 里做

- 验证没通过时，改动能原样保留给用户，不污染主工作区。
- 多个会话同时改一个仓库时互不覆盖。

划线的标准是「这次改动会不会让基线变红」。纯文档改动不会，而且常常是和用户逐句确认着改的，放在主工作区更顺手。

## 为什么验证失败也要保留改动

回滚还是返工是用户的决定，不是 Agent 的。曾经有一个子 Agent 被额度打断，留下十几处没提交、没报告的改动，没法验收。所以失败时改动要提交在分支上，换会话、断电都不丢，再由用户决定怎么办。

## 为什么只有 main 要授权

用户要对 main 上的每一行负责；其它分支是 Agent 的工作区，限制它们只会拖慢工作，不会增加安全。

## 为什么基线始终全绿，而必跑项按改动范围定

main 上任何时候都可能被拿去构建和发版，红着的基线会让后面每一次验证都说不清是谁弄红的。导出类脚本每跑一次要几分钟，每次改动都全跑不现实，所以按改动范围决定哪几项必跑，类型检查和全量测试每次都跑。

## 为什么已确定的语义优先，但要告诉用户

文档指导代码，代码和已确定的语义冲突时，改代码才能让两者收敛。但冲突本身可能说明语义写得不对，所以要告诉用户冲突在哪、改了什么，由用户判断是改代码还是改语义。

## 为什么规则只写在一个地方

整理之前，给 coding agent 的规则散在记忆笔记、交接文档、早期契约、计划分册里，已经互相矛盾：子 Agent 的政策有三套，验证端口一处写 5197、一处写 5203，「先读旧目标清单」的规则在目标清单被取代后仍然留着。规则只写一份，改一处就全变。

## 为什么本机信息单独放、不入库

端口习惯、磁盘情况、本机工具的怪癖、账号和密钥的位置，只对这一台机器成立，对别的机器上的 Agent 是错的，密钥位置也不该进仓库。仓库里的端口号和桌面版的默认安装路径是所有机器都一样的，所以它们算通用信息，写进仓库。

## 为什么用不用子 Agent 不写进规则

这取决于任务的大小、额度和用户当时的意愿，由用户按任务指定。规则里只写「用了之后怎么做」，那部分是固定的。

## 为什么新增依赖和安装要先问

装东西会改变用户的环境，有时要下载几百兆、有时会碰到需要付费的服务，而且不容易干净地撤回。

## 为什么验证分册要精简

第一版把规则、测法、排障经验混在一份里，规则被淹没，而且不少条目是在给工具缺陷打补丁。现在规则留在分册里；测法挨着代码放，做成脚本后只留一条命令；排障写成按症状查的表；工具缺陷开任务修掉，修好就从表里删，不把缺陷永久写进规范。

## 为什么入口文件只写指针

仓库里只要有 CLAUDE.md，Claude Code 就只读它、不读 AGENTS.md。所以 AGENTS.md 作为所有工具共用的唯一入口，CLAUDE.md 只引入它，规则本身都在 04，入口里不重复。

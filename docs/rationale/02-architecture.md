# 架构：为什么是这个形状

对应 `docs/semantics/02-architecture.md`。这里只写理由和取舍，不是规范。

## 从产品目的推出的三条硬要求

1. **人和 Agent 改同一份项目。** 核心目的是用语言指挥 Agent，同时保留手动操作。两边各改一份，看到的结果就不一样。所以项目只能有一个修改入口，这就是文档服务。
2. **Agent 必须能看到结果。** 剪辑是看着画面做判断的活。所以渲染要能被 Agent 按时刻查询，这就是查询渲染，和给人看的成片渲染是两个角色。
3. **给人看的画面不能卡。** 手动操作那一半要即时反馈。所以成片渲染默认放用户设备，不放云端。

## 多人协作只增加一条

修改入口不能长在某一个用户的设备上，要放在各方都能到达的地方。所以文档服务在云端，即使一期只有单人使用。

## 为什么按角色而不按机器列

用户给的信息都是「某个角色默认在哪、将来可以搬到哪」：渲染可搬到渲染服务器，Agent 可搬到项目方服务器，无渲染设备就是渲染不在本机。按机器列表就要为每种组合单独写一类客户端；按角色列，扩展点全部变成「换位置」。

## 为什么文档服务和素材存储分开

一个是有排序、版本、通知的服务，一个是只存字节的仓库，负载形态和一致性要求完全不同。合在一起写会让「云存储」这个词同时指两种东西。

## 为什么把 Agent 的提供方和计费放在一起

用户用本地模型或自己的计费服务，项目方无关；只有用项目方的 Agent 服务才计费。这条规则只取决于「谁提供 Agent」，和 Agent 跑在哪无关，所以写在 Agent 角色里，不单独成节。

## 已定但未展开的

- 协作等级维持现有计划：最后写的赢加通知，不做 CRDT / OT。
- 「文档服务也许做成微应用」是用户的初步想法，未定，所以规范里没写部署形态。

## 1. 结论

**不能直接动工。** 4 处阻塞项、8 处非阻塞项（3.7 是 5 条走查合格记录，不计为问题）。要开工，任务书需先补齐下面四条：

1. **G3 的滤镜链要约束宽度为偶数**（2.1）：`format=yuv420p` 要求宽高都是偶数，现在的 `pad=iw:ih+8` 只保证了高，实体框宽为奇数时 ffmpeg 直接崩。
2. **G3 要交代透明像素的 RGB 怎么处理**（2.2）：`format=rgb24` 只丢 alpha 不清理透明区的 RGB，4:2:0 下采样会把它渗到不透明边缘。
3. **G3 / G4 要写死单卡流怎么隔离非本卡像素**（2.3）：`captureFrame` 是整页截图、没有 clip 矩形，而 G4 规定 `frameWindow = null`（全员挂载）、不做清单 L383 又禁止 `bakeStream` 传 `clipIds`，三条凑起来现在无路可走。
4. **G1 要给组流平面定命中测试与实体框的规矩**（2.4）：`[data-pc-group-plane]` 不在任何 `[data-pc-clip]` 里，`solid.ts` 的 `hitTest` 会略过它、`:197` 的平面排除名单也没有它。

另：G0-a 三项探针（L213）本来就是第 4 步的准入条件、b5c65dc 时「未跑」（L151），不计入上述阻塞项，但同样是开工前置。

## 2. 阻塞项

### 2.1 ffmpeg format=yuv420p 导致奇数宽报错
- **任务书行**：L223
- **原句摘录**：`[rgb][mask]vstack=inputs=2,scale=out_range=pc:out_color_matrix=bt709,format=yuv420p"`
- **证据**：`iw` (原画面宽) 可能是奇数。`format=yuv420p` 严格要求宽度和高度均为偶数。当前滤镜 `pad=iw:ih+8:0:0:black` 和 `vstack` 仅保证了高度 `2(H+8)` 恒为偶数，未约束宽度。若片段实体框宽为奇数，ffmpeg 管道将报错崩溃。
- **建议改法**：将 L221 和 L222 改为 `pad='ceil(iw/2)*2':ih+8:0:0:black[rgb]` 或通过 scale 强制宽为偶数。

### 2.2 RGB24 丢弃 alpha 导致边缘颜色污染
- **任务书行**：L221
- **原句摘录**：`[c]format=rgb24,pad=iw:ih+8:0:0:black[rgb];`
- **证据**：PNG 透明像素可能含有 RGB 垃圾值。`format=rgb24` 仅丢弃 alpha，但在后续 H.264 的 YUV4:2:0 色度下采样压缩中，透明区的垃圾色彩会渗入邻近的不透明像素边缘造成杂色。
- **建议改法**：在分离出 `[c]` 后做黑色预乘（或对带有垃圾背景的 RGB 清零），确保 alpha 为 0 处的 RGB 值为纯黑。

### 2.3 轨道流未隔离非本卡像素
- **任务书行**：L215、L230、L217
- **原句摘录**：L215「每张卡单独一条」、L230「`bakeStream` 一律 `frameWindow = null`（`__pcSetFrameWindow(null, …)`）」、L217「输入是经 `captureFrame` 取得的 PNG」
- **证据**：查看 `scripts/capture-frame.mjs:18` 和 `export-frames.mjs:525-527`，截帧动作是针对整页截图，没有 clip 剪裁矩阵。若 `bakeStream` 传 `null`，挂载交由 `FrameScene` 处理（全员挂载），则同一画面里和该卡实体框重叠的别的卡会被一起截进这条单卡流里，规格通篇没写单卡像素怎么隔离。L383 又禁止 `bakeStream` 传 `clipIds`。
- **建议改法**：G3 需补一句：截流时怎么把非本卡像素排除——例如给 `captureFrame` 传 `clip` 矩形只截实体框、并额外规定同框内其它卡如何处理；或在预渲染页上按流临时隐藏非本卡子树。

### 2.4 hitTest 点击穿透组流平面
- **任务书行**：L215
- **原句摘录**：「它的 `<canvas>` 不挂在任何一张卡的包裹层里」
- **证据**（manager 更正行号）：`src/render/solid.ts:165` = `    const wrap = el.closest("[data-pc-clip]");`；`:167` = `    if (!clipId) continue;`。组流平面是卡包裹层的兄弟、不在任何 `[data-pc-clip]` 里，`hitTest` 取不到 `clipId` 就 `continue` 略过它；而 `:197` 的平面排除名单 `if (el.hasAttribute("data-pc-proxy-plane") || el.hasAttribute("data-pc-snapshot-plane") || el.hasAttribute("data-pc-stream-plane")) {` 也没有 `data-pc-group-plane`，`bounds` / `rects` 同样没有为它定规矩。结果是点击穿透、错误选中背后图层。
- **建议改法**：L215 中补充：在创建 `[data-pc-group-plane]` 时添加 `pointer-events: none` 样式使点击天然穿透。

## 3. 非阻塞项

### 3.1 附加编码器参数缺失 `-c:v`
- **任务书行**：L229
- **原句摘录**：「编码器参数：`libx264 -preset veryfast -crf 16`」
- **证据**：公共命令（L218-L228）无输出视频编码器声明。L229 只是简写，直接拼会引发语法错误。
- **建议改法**：前置补充 `-c:v`，写成 `-c:v libx264 -preset veryfast -crf 16` 等。

### 3.2 硬件编码器对 GOP 指令的兼容性缺失
- **任务书行**：L224
- **原句摘录**：`-g 15 -keyint_min 15 -sc_threshold 0 -bf 0`
- **证据**：`h264_nvenc` 等可能不支持通用的 `-sc_threshold 0`，为了保证 G2 首帧 IDR 可能需要 `-forced-idr 1` 等专属参数。目前的公共命令行并不能简单拼接到所有编码器。
- **建议改法**：补充「针对不同编码器自动转换或补充严格 GOP 与 IDR 参数，如 NVENC 加 `-no-scenecut 1 -forced-idr 1`」。

### 3.3 输出颜色矩阵缺少原型实测背书
- **任务书行**：L223
- **原句摘录**：`out_color_matrix=bt709`
- **证据**：`docs/async-track-playback.md:55-71` 的原型实测命令中，并未引入 `out_color_matrix=bt709` 以及 `-colorspace` 等容器标注。新加的 bt709 套件虽逻辑不互斥，但未经实测背书。
- **建议改法**：标明该处属理论推导添加，开发时需核验播放色差。

### 3.4 fMP4 分片剥离位置未定义
- **任务书行**：L216
- **原句摘录**：「每个分段一个独立 fMP4 片段文件（`moof + mdat`，首帧 IDR，`mfra` 剥掉）；流目录一个 `init.mp4`。」
- **证据**：ffmpeg `-f mp4 -movflags ...` 会把 `ftyp`+`moov` 及 `moof+mdat` 打包为一个连贯流，任务书未定义由谁、在哪里剥离 `init.mp4` 和 `mfra`。
- **建议改法**：补充「由 Node 端读取 ffmpeg 管道后按 MP4 Box 结构执行内存剥离」。

### 3.5 streamPool 没有说明获取接口
- **任务书行**：L230
- **原句摘录**：「`streamPool` 的会话不经 `acquireUser`」
- **证据**：`server/frame-pipeline.mjs:195` 现有的是通用 `acquire(lane, project)`。G4 没写 `frame-stream.mjs` 该调哪个 API 拿会话、`streamPool` 和现有 `lanes` / `acquire` 是什么关系。
- **建议改法**：补充「在 FramePipeline 中明确 `streamPool` 该如何通过专有参数换取裸会话」。

### 3.6 frameWindow 及 installFrameMedia 隐式描述不准
- **任务书行**：L230
- **原句摘录**：「`staticSkip` 和 `frameWindow` 只在外层循环用」、「`installFrameMedia` 在 `openBakery` 里一个页面装一次」
- **证据**：`scripts/export-frames.mjs:627` 中 `warmUp` 用到了 `frameWindow`，非外层循环；`src/ExportView.tsx:27` 证明 `installFrameMedia` 是在前端页面加载时自执行安装，并不是 Node 端的 `openBakery` 里调用的。
- **建议改法**：修改为「`frameWindow` 藏在传入的闭包中被内部使用」、「`installFrameMedia` 由导出页面自身挂载加载」。

### 3.7 G3/G4/G5 走查正常项明细
- **L219 选项位置**：`-reinit_filter 0 -f image2pipe -c:v png -framerate <fps>` 位置都在 `-i pipe:0` 之前，核过、没问题。
- **L221 填充版式**：下边 8 行填充经 vstack 生成 `[RGB H][pad 8][alpha H][pad 8]`，与 docs 里的 `alphaTop=(H+8)/(2H+16)` 对得上，核过、没问题。
- **L226 稀疏分段 timescale**：timescale 设置等于 fps，而 G2 中使用连续馈送重复帧替代丢帧跨度，不改变媒体时间基，自洽，核过、没问题。
- **L230 createStepper 签名**：参数足够覆盖闭包所用外层变量（含 `page`/`beginFrame`/`waitNet` 从 bakery 取，其余靠参），核过、没问题。
- **L230 planStreamSegments**：字段及量纲与现有 `planPlaybackBatch` 对得上，`stride` 位于公式分母以等比缩小渲染消耗，正确。核过、没问题。

### 3.8 VideoFrame 预算与 80 MB 验收对不拢（manager 补做）

- **任务书行**：L231、L234
- **原句摘录**：L231「解码后保留的帧总数全局预算 24 帧，按流优先级分配、每流保底 3 帧」；L234「N 条流同时播 30 fps 不掉帧、解码帧总内存 ≤ 80 MB」
- **证据**：解码出来的 `VideoFrame` 是**上下拼合后的编码画面**，不是还原后的卡片画面——`docs/async-track-playback.md:52` = `[RGB  H 行][填充 8 行][alpha H 行][填充 8 行]   编码高度 = 2 × (H + 8)`，与 L221 / L222 的 `pad=iw:ih+8:0:0:black` 一致。取验收自己举的 1080p（W=1920、H=1080）：编码画面 1920 × 2176，NV12 按 1.5 字节/像素 ≈ 6.27 MB 一帧，24 帧 ≈ 150 MB，是 L234 所写 80 MB 的近两倍。（按未拼合的 1920×1080 算才是 3.11 MB × 24 ≈ 74.6 MB，那是把编码高度当成了 H。）
- **非阻塞的理由**：L234 开头写明「验收（数字以 G0-b 实测为准）」，G0-b(4)(6) 本来就要重定解码器预算。
- **建议改法**：在 L231「全局预算 24 帧」后加一句口径——预算按**编码画面**字节算而不是按帧数，或对 1080p 档把帧数下调到约 12；同时把 L234 的「解码帧总内存 ≤ 80 MB」改成按 `2 × (H + 8)` 重算的数，并写明分辨率前提。

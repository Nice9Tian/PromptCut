# 第 75 轮 · 第 9 份：第 7b + 8 步：目标 I（Agent 的只查询预渲染进程）、D3 的预渲染部分
## 1. 结论（能 / 有条件能 / 不能直接动工；条件逐条列）
不能直接动工；有阻塞项需要先修复。

## 2. 阻塞项

**2.1. 接口缺失：第 8 步未定义实体矩形如何附在 see_frames 响应中**
*   **任务书行号与原句摘录**：L141 `第 8 步：预渲染进程给 Agent 渲 see_frames 图时附实体矩形。`
*   **证据**：任务书要求附实体矩形，但 L141 导出的 `window.__pcSolid = { isSolid, bounds, rects, hitTest, stageOrigin, canvasBox, canvasPaintedBox }` 面根本没给带 bounds 的那个查询（`rectsWithBounds`）。第 8 步缺乏读取几何信息的接口定义，也未定义结果如何随 `FrameResult` 返回以及如何给到大模型。
*   **建议改法**：在 L141 的第 8 步后补充：“`__pcSolid` 面要么补一个带 bounds 的查询、要么写明用现有的 `rects()`，并写明 `FrameResult` 加什么字段、`see_frames` 回包怎么带格式。”

**2.2. 成环/死锁：AI 菜单插队队列在 background 链空闲时将永远挂起**
*   **任务书行号与原句摘录**：L254 `FramePipeline 给 background 链加一个插队队列... 检查插队队列，有插队项时 this.background 那条链主动把 background bakery 交出去... 插队项复用交出来的这个 bakery、不走 acquire('background')`
*   **证据**：L248 写明 `acquire 的调用点在 readFramesCore 里（frame-pipeline.mjs:464，flush 间接调它）`。`ensureGif` 通过 `renderFrames` -> `readFramesCore` 发起，其底层会无条件等 `acquire('background')`。如果当前预渲染队列空着，没有任务去“主动把 bakery 交出去”，该插队项由于绕过正常的 `acquire` 将在死锁中永远挂起。
*   **建议改法**：废弃由 `background` 链主动交出并跳过 `acquire` 的设计。在 L254 (b2) 中改为：“给 `acquire('background')` 加一个高优先级插队队列标志（如 `isJump` 参数）。`ensureGif` 传入 `isJump: true`。`release` 释放时优先出列高优先级请求；`fillCardControls` 在批边界主动调用一次 `release` 并重新 `acquire`，以此让出资源。”

**2.3. 违背硬约束：AI 菜单预览被错误路由至 agent 角色，抢占专用 Chrome**
*   **任务书行号与原句摘录**：L254 `Agent 的路一律 'agent': ... :253 的 /api/ai/visual` 以及同段 `(b2) AI 菜单的操作预览可以插在预渲染前面... ensureGif 在 user / full 模式传 lane: 'background'`
*   **证据**：L254(c) 将 `/api/ai/visual` 整条路由分发给 `'agent'` 角色，而操作预览（`GET /api/ai/visual/gif/<key>.gif`）正归属此路由。在 `PROMPTCUT_PRERENDER_SPLIT=1` 时，请求将发至 `agent` 进程。但 L248 规定该进程“只建 `agent` 一条 lane（…`acquire('background', …)` 直接抛 `cancelled`）”。这导致操作预览要么崩溃（请求被 cancel），要么被迫走 `agent` lane 跑在专用 Chrome 上——直接违背了 **pinned 架构 5** 的「也不占用 Agent 的专用 Chrome」和 L254(b2) 自己说的「它不用 Agent 的专用 Chrome」。
*   **建议改法**：在 L254 (c) 的路由口径处增加例外说明：“`/api/ai/visual` 里的 GIF 那条子路（AI 菜单操作预览）在 `user`/`full` 模式下必须走 `'user'` 角色”。

**2.4. 接口不一致：Agent 请求必须携带 session 和 localRev 以通过镜像鉴权**
*   **任务书行号与原句摘录**：L250 `Agent 服务端每拿到新的 projectRev 就把整份项目 POST 到自己 agent 进程的镜像插件... agent 模式每次查询按现在的方式在 agent lane 里重挂载 + 补跑`
*   **证据**：根据 L113，所有帧请求必须带 `{ session, localRev, lane, ...extra }`。Agent 服务端通过推送确认了 `session: agentId` 和 `localRev: projectRev`，但 L254 描述的 MCP 工具发起查询时并未明确注入这两个鉴权参数。缺失它们将导致请求被预渲染侧的 `ensureMirror` 拒绝（409）。
*   **建议改法**：在 L254 (c) 中补充明确参数注入逻辑：“Agent 服务端的 `see_frames` 和 `inspect_card_dom` 等工具在经 `proxyToPrerender` 转发前，必须在请求体中显式注入 `session: Agent身份id` 和当前记录的 `localRev: projectRev`。”

## 3. 非阻塞项

**3.1. 接口缺失：`/api/cards/dom` 借用 bakery 缺少空闲计时器的重置触发机制**
*   **任务书行号与原句摘录**：L248 `把 domChain 换成 pipeline.laneChains.get('agent') 那条链，/api/cards/dom 的活以「先等链、再 acquire、干活、把自己接回链尾」的方式挂进去`
*   **证据**：L248 给 `agent` lane 加了 10 分钟空闲计时器，但 `release('agent') 今天对 agent 直接早退`，同时 `/api/cards/dom` 那条路又不许调 `bakery.close()`。接口设计漏掉了谁来负责重置和启动这个计时器。
*   **建议改法**：在 L248 补充明确生命周期接口：“`/api/cards/dom` 干活完毕后必须调用 `pipeline.release('agent')`，且要求 `release('agent')` 的内部实现需负责重置并启动这 10 分钟的空闲计时器。”

**3.2. 自相矛盾：Agent 专用 Chrome 闲置时拒绝分担主线预渲染任务**
*   **任务书行号与原句摘录**：L254 `这个 Chrome 只接锚帧和 wanted 单帧，等待上界 = 一帧；不接 background 的 4 帧批、不接 streamPool 的分段`
*   **证据**：这与同在 L254 段落内的另一句 `Agent 没活时预渲染也用得上全部 Chrome。` 产生段内自相矛盾。既然排除了 `background` 和 `streamPool` 这两项产生大量画面的主线任务，当待办里只剩 4 帧批和流分段时，该 Chrome 只能空转，无法兑现“用得上全部”的本段声明。
*   **建议改法**：将 L254 中的限制句修改为：“这个 Chrome 空闲时也接 `background` 的 4 帧批和 `streamPool` 的分段，等待上界为该批次/分段时长。”

**3.3. 验收不全：I0 的跨平台验收标准未全面覆盖 pinned 平台要求**
*   **任务书行号与原句摘录**：L247 `同一项目在 Windows 和 Ubuntu 22.04 上跑 agent 模式的 see_frames... 两平台各自的像素基线通过` 与 L80 `Agent 端（Agent 服务端 + 预渲染进程的 agent / full 模式，pinned 平台末句）面向 Windows、Linux、Ubuntu`
*   **证据**：pinned 平台明确要求覆盖 `full` 模式，并广泛面向 Linux 及其子版 Ubuntu。I0 的实际接口探测逻辑（`process.getuid` / `--no-sandbox`）虽全，但其验收部分却“只跑 `agent` 模式、只跑 Windows 和 Ubuntu 22.04”，造成测试缺口。
*   **建议改法**：在 L247 的验收部分补充：“并补充在 Linux 和 Ubuntu 上跑 `full` 模式（涵盖本地协同及 fallback）的验收用例。”

# R9 GL 图集探针报告

## 做了什么

- 新增 `scripts/probes/gl-atlas-probe.mjs` 和 `scripts/probes/gl-atlas-harness.html`。探针只监听 5240、5241，自己启动并关闭 Chrome 和静态服务。
- 图集为 1600×720，含 20 个 320×180 区域。Worker OffscreenCanvas WebGL2 属性为 `{ alpha: true, antialias: false, premultipliedAlpha: true }`。用 `renderbufferStorageMultisample` 建 RGBA8 FBO，samples = min(4, MAX_SAMPLES)，逐区域填色、`blitFramebuffer` 到默认帧缓冲，再裁出 20 个 `ImageBitmap` 并 transfer。
- `perDocument`：跨源 iframe 自己持有 Worker。`shared`：父页持有 Worker，通过 `MessageChannel` 转交端口。两路均另测 `transferToImageBitmap()` 整图一次 transfer、主线程按区域 `drawImage` 到 20 张 2D canvas 的退路。
- 每个方法先预热 3 拍，记录 60 拍；首拍逐卡校验中心像素与位图尺寸。主线程时间是收到 `done` 后到 20 次 `transferFromImageBitmap` 或 `drawImage` 结束；往返时间是发 `beat` 到贴图结束。Worker `bitmapMs` 是裁图或整图获取调用耗时，`drawMs` 是绘制与 blit 调用耗时。未用 `gl.finish()` 强制 GPU 完成。

## 结果与 M3 判定

Chrome/152.0.7977.75（复测启动 PID 39920，结束后关闭）；ANGLE / NVIDIA GeForce RTX 3080 / Direct3D11；实际 samples = 4。父页 `http://localhost:5240`，子页 `http://127.0.0.1:5241`。两路均跨源，CDP 可见 OOPIF target；每种方法 20/20 卡像素正确。表中耗时单位 ms，顺序是 p50 / p90 / 最大值；占比按 60 fps 的 16.7 ms 预算计算。

| 路线 | 方法 | 主线程 p50 / p90 / max | beat→present p50 / p90 / max | Worker 位图 p50 / p90 / max | 主线程最大占比 | 往返最大占比 |
|---|---|---:|---:|---:|---:|---:|
| perDocument | crops | 0 / 0.1 / 0.2 | 1.4 / 1.7 / 29.8 | 0.3 / 0.3 / 0.4 | 1.2% | 178.4% |
| perDocument | fallback | 0 / 0.1 / 0.1 | 1.2 / 2.4 / 2.9 | 0 / 0 / 0.1 | 0.6% | 17.4% |
| shared | crops | 0 / 0.1 / 0.2 | 3 / 3.2 / 4.6 | 0.3 / 0.3 / 0.4 | 1.2% | 27.5% |
| shared | fallback | 0 / 0.1 / 0.1 | 1.5 / 2.9 / 3.8 | 0 / 0 / 0.1 | 0.6% | 22.8% |

M3 没写数值门槛。以 16.7 ms 为一拍预算，**两条路线的链路和主线程成本达到 M3 探针要求**：主线程 p90 ≤0.1 ms（≤0.6% 预算），最大 ≤0.2 ms（≤1.2%）。本机没有因主线程成本而需要启用整图退路；退路亦通过像素检查。

**不能保证每拍端到端都在 16.7 ms 内。** 60 拍复测中，`perDocument` 裁图第 2 个测量拍往返 29.8 ms（178.4% 预算），其中 Worker 绘制与 blit 调用段为 29.4 ms。此前 30 拍运行，`perDocument` 裁图最大 32.1 ms，`shared` 裁图最大 82.1 ms，主线程最大均为 0.1 ms。这些尖峰不在主线程贴图段；探针没有定位 GPU 或驱动等待的根因。若“每拍端到端 ≤16.7 ms”是硬门槛，裁图路线尚未达标。
